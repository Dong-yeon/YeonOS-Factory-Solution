## 0. 요약

### 0.1 한 줄 결론

현장이 MES 를 안 쓰는 이유는 기능 부족보다 **① 입력이 일보다 비싸다(손·장갑·시간) ② 예외(분할·재작업·특채·단절)를 시스템이 못 받아 종이·엑셀로 돌아간다 ③ 입력한 데이터가 작업자에게 아무것도 돌려주지 않는다 ④ 관리할 사람이 없다**의 네 가지다. 시장 제품들은 이를 **"사람이 치는 값을 줄이고(설비·스캔), 남은 입력은 큰 터치·모국어·오프라인으로 받고, 입력의 대가로 화면이 무언가를 돌려준다"** 방향으로 풀고 있고, 생성형 AI 는 그 위에 얹는 보조(문서→작업 안내, 번역, 질의)다.

SmartHappy 는 1인 개발이라 Tulip 식 노코드 플랫폼을 만들 수 없다. 대신 **P0 에서 싸게 잡을 수 있는 것 — "활용을 재는 키"와 "입력 최소화 규칙" — 을 먼저 잡고**, POP 표준 컴포넌트를 P2 첫 POP 화면 전에 만들어 모든 현장 화면이 같은 손맛을 갖게 하는 것이 가장 효율적이다 [추정].

**모듈을 넓히면**(2.11): 네 원인은 QMS·WMS·CMS·SRM·PMS 에서도 그대로 나오지만 **"누가 입력하고, 그 사람이 시스템을 안 쓸 때 무엇으로 돌아가는가"**가 모듈마다 다르다 — QMS 는 종이 체크시트 몰아 쓰기·부적합 미보고, WMS 는 스캔 생략·감독자 우회, CMS 는 고장 코드 없이 작업 종료, SRM 은 **우리 직원이 아닌 협력사**가 포털 대신 이메일·엑셀, PMS 는 금요일 몰아 쓰는 M/D. 특히 SmartHappy 고객은 그 자신이 완성차·1차사 포털(VAATZ·SCEMS 등)에 입력하는 **협력사**이므로 SRM 은 "로그인 없는 협력사 응답"과 "고객사가 OEM 에 낼 자료를 다시 치지 않게"를 같이 설계해야 한다 [추정].

**공통 패턴** [추정]:
1. **사람이 치는 값을 줄인다** — 설비가 아는 것(가동/정지·카운트)은 설비가, 사람은 맥락("왜")만.
2. **현장 화면은 별도 제품처럼** — 사무용 메뉴·그리드와 다른 단말 UI(Opcenter 는 아예 새 터미널로 다시 만듦).

### 2.2 입력 최소화 (바코드·QR·RFID·설비 자동수집)

- 키보드 입력 오류 ≈ 300자당 1 (미 국방부 LOGMARS, 바코드 1,266,444건 중 4건 오류), Bell Labs 0.42~0.48%, 바코드는 수백만 분의 1 수준 — 수치는 오래된 2차 인용이지만 방향은 일관 [검색 U1]. 2025 JAMIA Open: 수기 3,023건 중 100건 오류 vs 자동 전송 4,768건 중 1건 [검색 U1].
- MachineMetrics 모델이 가장 실용적: **정지 감지는 100% 자동, 사유는 규칙으로 자동 분류(공구·품목 교체), 나머지만 작업자가 태블릿에서 선택, 현장에서 안 넣으면 감독자가 사후 분류** [검색 P4][P5]. → 설비 연동이 없는 고객에게도 "자동 감지 + 사유만 사람" 구조를 POP 비가동 화면 기본으로 [추정].
- InSource: **사유 그룹·사유가 너무 많고 기록 임계가 낮으면** 작업자 부담 ↑, 데이터 신뢰 ↓ [원문 R5] → 사유 코드는 1단계 6~8개 + "기타(사진/음성 메모)" 정도로 시작 [추정].
- SmartHappy 연결: 라벨·인쇄큐(P4), LOT 바코드, Collector(P6). **스캔 한 번으로 품목·LOT·작업지시·로케이션이 정해지는 "스캔 키 규칙"**(바코드 내용 → 대상 판별 → 화면 자동 채움)을 P1 기준정보에서 정해야 P2 POP 이 짧아진다 [추정].

### 2.3 POP·모바일·터치 UI

- 터치 타깃: ISA-101 자체에는 mm 기준이 없다. 실무 관행(ISO/TS 9241-411 해석을 내세운 벤더 표) **맨손 12mm / 얇은 장갑 15mm / 작업 장갑 19mm / 안전 관련 25mm, 간격 3~5mm**. Rockwell ISA-101 스타일 가이드: 버튼 최소 40×40px, 절대 최소 30×30px [검색 U6]. 7인치 패널에 버튼 10개면 10~11mm 로 장갑 사용 불가 [검색 U6].
- Plex Mobile: 소음 현장이므로 **시각·진동·소리 알림**, 역할별 메뉴, IAM 로그인 [검색 P3].
- Opcenter X 2607: 공정 완료 시 **다음 공정 자동 열기** — 한 번이라도 탭을 줄이는 방향 [검색 M4].

### 2.4 오프라인

- 창고의 금속 랙·콘크리트·냉동실은 Wi-Fi 음영. 실패 양상: 서버는 받았는데 단말은 타임아웃 → 작업자가 다시 스캔 → **중복 입고** [검색 U8].
- 일반 PWA 패턴: IndexedDB 대기열 + 지수 백오프 재시도 + 대기 건수 배너. 단, **Safari 는 스크립트 저장소 7일 상한**(iOS 단말 주의) [검색 U8].
- MachineMetrics: 태블릿이 끊겨도 기계 데이터는 엣지 장치로 계속, 작업자 입력만 지연 [검색 P5].
- SmartHappy [추정]: 00 P4 PDA 의 write-ahead 대기열을 **POP 에도 같은 라이브러리로**. 재고·실적 수량은 "총량"이 아니라 **증감 이벤트**로 보내 오프라인 충돌 시 덮어쓰기 손실을 막는다(원장 규약과 일치). 오프라인 중 서버 판정이 필요한 검증(LOT 상태·자격 게이트)은 "보류 확정"으로 표시하고 동기화 후 실패 건은 작업자가 아니라 **반장 "내 할 일"**로 보낸다.

### 2.5 다국어 (외국인 근로자)

- 고용허가제(E-9) 체류 28.7만 명(2026-07, 역대 최대) 중 **제조업 80.0%**(22.98만 명) [검색 L2]. 외국인 취업자 110만 명 중 광·제조업 44.9%(2025 이민자 고용조사) [검색 L2]. 뿌리산업 종사자 중 외국인 9.6%(2022), 주물 현장은 "생산직 90% 이상 외국인" 증언 [검색 L2].
- MES 화면 베트남어화 실무 기록(국내 MES 업체의 공개 GitHub 이슈): **문법이 맞아도 그 공장에서 쓰는 말인지는 개발팀이 판정 못 함 → 용어집 한 파일을 현지 담당자가 검수**, 같은 용어를 번역자마다 다르게 옮기는 문제 [검색 L3].
- 건설사들은 현장 문장 500+개 사전 번역(현대건설), 현장 용어 반영 AI 번역(롯데건설), 16개 언어 실시간(대우건설) — 공장 MES 화면 자체의 공개 사례는 드물다 [검색 L3].
- SmartHappy [추정]: i18n 키는 이미 P0 4단계 결정(ko/en). **POP·PDA 메시지 키에 `vi` 를 P2 와 함께**(나머지 언어는 고객 요청 시), 03 의 **용어 사전**(전역 + 회사별 동의어)을 번역 용어집으로 겸용, 화면 문구는 **짧은 명령형 + 아이콘 + 숫자**로 번역 의존을 줄인다. 작업지시·작업표준서 번역은 03 2.4 대로 P5(원문 병기, 승인 후 배포).

### 2.6 음성·카메라 입력

- 음성 피킹 벤더 주장: 생산성 10~35%↑, 오류 최대 90%↓. 통제된 현장 실험(De Vries 등 2016, IJPR, 101명): 음성 4.4% vs RF 단말 5.6% 오류, **유의차 없음** [검색 U9]. 범용 STT 는 조용한 방 WER 6% → 창고 30%+, 산업 현장 현실 목표 16~24% [검색 U9]. 03 2.4: 공장 소음 한국어 STT 실측 자료 없음.
- 카메라: Tulip 의 종이 traveler OCR, 03 2.6 문서 OCR(P5), 라벨 판독(03 2.12).
- SmartHappy [추정]: 음성은 **숫자·짧은 명령 + 화면 확인 후 확정**(03 결정 유지), 자유 발화 입력은 하지 않는다. 카메라는 ① 바코드(스캐너 없을 때) ② 불량 **사진 첨부**(사유 기타·MRB 증거, P0 첨부 재사용) 를 먼저 — 판정용 비전은 03 대로 외부 결과 수신.

### 2.7 노코드/로우코드·화면 개인화

- Tulip 은 노코드 앱이 제품 그 자체이고, 2026 에는 **AI 가 앱 초안을 만들고 엔지니어가 검토**하는 방향(Authoring Agent)과 **코드 모드**(엔지니어가 IDE·코딩 에이전트로 앱 작성)를 함께 낸다 [검색 M1][M2]. Opcenter 는 Mendix(로우코드)로 작업자 터미널을 다시 만들었다 [검색 M4]. 업계 칼럼: 로우코드 MES 의 병목은 코드가 아니라 **현장 프로세스 정의** [검색 R4].
- SmartHappy [추정]: 1인 개발로 노코드 빌더는 만들지 않는다. 고객 차이는 **정책 축(00 3장)**, 화면 차이는 **컬럼 상태 저장(09 #9)·역할별 홈·필드 표시/필수 정책**까지만. "고객이 만드는 화면"이 필요해지면 **정의된 조회 도구(03 코파일럿 1안)를 쓰는 리포트 화면** 수준에서 검토.

### 2.11 모듈별 — QMS·WMS·CMS·SRM·PMS

> 근거 수준 주의: 모듈별 자료는 MES 보다 더 **벤더 글 위주**다. 독립 연구는 CMMS 작업지시 품질 사례(X5), 전자조달 협력사 수용 연구(X1), 타임시트 저항 연구(X6), 대구 원·하청 실태(X3) 정도이고 나머지 수치는 방향만 참고한다.

#### 2.11.2 QMS

- 종이 체크시트의 구조적 한계: 수행 여부를 검증할 수 없고, 사본으로 보이는 동일 기록, 사무실 재입력의 이중 작업과 지연 [검색 X4]. 측정기(디지털 캘리퍼·토크렌치·CMM) 직접 연동이 수기 오류를 없애는 가장 확실한 방법으로 반복 언급되고, 구매 가이드는 "데모 때 작업자에게 직접 과제를 시켜 보라", "작업자가 모국어 태블릿으로 쓸 수 있나", "Wi-Fi 없이 되나"를 묻는다 [검색 X4].
- **부적합 미보고는 화면보다 문화 문제**: 비난·불이익 우려, 보고해도 바뀌지 않는다는 인식, 번거로운 절차. 품질 문화가 강한 조직은 초기에 **부적합 보고가 오히려 늘고**, 보고 급감은 개선이 아니라 경고 신호 [검색 X4]. 건설 ETO 연구(IJPR 2025)도 손실 책임을 피하려 공식 보고를 꺼림을 보고 [검색 X4].
- SmartHappy [추정]:
  - 자주검사·공정검사는 `hb.pop` 의 `numPad` + 측정기 입력(키보드 웨지·시리얼은 P6 Collector) — 값마다 `entry_method`.
  - 검사 기록은 **검사 시점**에만 저장 가능(일괄 사후 입력은 사유와 함께 별도 경로) — IATF 기록 신뢰와 3.2 사후 입력률이 같은 지표.
  - 부적합 등록은 "누가 잘못했나" 필드 없이 **현상·사진·LOT** 만으로 30초 안에. 원인·책임은 MRB·시정조치 단계에서. 부적합 건수 KPI 는 "많을수록 나쁨"으로만 쓰지 않는다(급감 경보 포함).
  - 출하 성적서는 검사 데이터에서 생성(Top #15) — 품질 담당이 엑셀 성적서를 다시 치지 않는 것이 QMS 채택의 가장 큰 보상.

#### 2.11.3 WMS

- 작업자는 기술 자체보다 **마찰**을 거부한다: 장갑 낀 손으로 3번 탭, "감독자를 찾으세요"로 끝나는 예외, 원래 화이트보드보다 느린 흐름은 몇 주 안에 우회된다. Zebra 조사에서 창고 작업자 86% 는 기술·단말이 인력 유치·유지에 도움된다고 답함 [검색 X8].
- 품목·로케이션 데이터가 틀리면 신뢰가 무너지고 우회가 시작된다. **감독자가 마감 시간에 맞추려 불일치를 통과시키면 시스템은 허구를 기록**한다. 훼손 라벨 → 수기 입력 → 오류율 복귀 [검색 X8].
- 권고: 매월 현장을 돌며 화이트보드·종이·엑셀을 **세고**, 각각을 징계가 아닌 재설계 대상으로. 실제 단말·실제 작업자 계정으로 시험, "문서화 안 된 우회 없이 내일 물량을 처리할 수 있나"를 가동 조건으로 [검색 X8].
- SmartHappy [추정]: P4 PDA 설계(00)의 스캔 잠금 루프에 **override = 사유 코드 + 권한 + 접속 로그 `action=OVERRIDE`** 를 추가하고 override 비율을 KPI 로. 라벨 재발행은 PDA 에서 바로(인쇄큐). 가동 전 기초 재고 실사·병행 기간은 도입 방법론(Top #12)에.

#### 2.11.4 CMS (설비관리)

- 독립 사례 연구: CMMS 작업지시 386건 중 **고장 기술이 원인 분석에 충분한 것은 202건(52%)** — 신고(작업자)와 완료 보고(보전 기사) 양쪽의 빈약한 기술이 데이터 활용의 주 장애 [검색 X5].
- 벤더 글들의 공통 지적(수치는 미검증): 작업 종료 시 문제·원인·조치 코드 미선택, 며칠 뒤 기억으로 입력, 특정 설비 대신 일반 위치로 등록, **동기화 안 된 종료를 한 번 겪은 기사는 몇 주 안에 모바일 입력을 포기**, 데스크톱 8단계 입력은 현장에서 안 일어남. 대응으로 "종료 시점에만 필수 드롭다운"을 권함 [검색 X5].
- SmartHappy [추정]: 설비 QR(물리 자산 P1)을 스캔하면 그 설비의 고장 신고 화면이 바로 열리게. 비가동 구간은 설비 상태 원장(P2)에서 자동 생성하고 사람은 사유·조치만(MachineMetrics 모델, 2.2). Top #13 "닫을 때 필수". 예방점검은 체크리스트 + 사진, 기한 지나면 반장 "내 할 일".

#### 2.11.5 SRM — 입력자가 우리 고객의 직원이 아니다

- **포털 피로**: 협력사는 고객사 10~20곳 이상의 서로 다른 포털·로그인을 감당해야 하므로 "또 하나의 행정 부담"으로 본다. 등록만 하고 응답은 이메일로 돌아가면 포털이 불완전해져 **가시성이 있다는 착각**을 만든다. 실패 1순위는 기술이 아니라 "만들면 오겠지" [검색 X2]. Hackett 벤치마크(벤더 2차 인용): 협력사 등록을 이메일·엑셀·ERP 로 하는 기업 50%, 포털 도입 기업의 43% 가 기대 이하 [검색 X2]. 전자조달 협력사 수용 연구(구문헌): 통합·유지 비용 51.0%, 법적 지원 부족 49.5%, 상호운용성 부족 45.8% [검색 X1].
- 대안 패턴: ① 협력사 이메일 회신을 구매사 쪽에서 해석해 PO 에 붙이기 ② **1회용 매직 링크**(계정·비밀번호 없음, 모바일, 진행 저장) ③ 협력사 규모별 채널(큰 곳은 EDI·API·일괄, 작은 곳은 이메일 기반). 주의: "확인했어요" 같은 비공식 회신은 합의 내용이 모호하므로 **라인별 수량·단가·납기를 구조화해서 받고 변경은 구매 검토** [검색 X2].
- **국내 맥락**: 완성차·1차사는 VAATZ·TPOS 같은 포털에서 2차사 정보 변경을 기한 내 전산 입력하게 하고, 점검에서 성적서 허위 작성·LOT 대장 허위 작성이 지적된다 [검색 X3]. 대구 원·하청 실태(2023): 2차 협력업체는 **품질**을 가장 큰 경영 부담으로, 납품 애로 "과도한 품질 요구" 2차사 40.8% [검색 X3]. 08 조사처럼 ESG·탄소 데이터 요구도 2차사로 내려오는 중.
- **SmartHappy 고객은 양쪽에 서 있다** [추정]: ① 위로는 OEM·1차사 포털에 입력하는 협력사 → SmartHappy 가 그 자료(출하 성적서·LOT 추적·ESG 항목)를 **이미 가진 데이터에서 만들어 주면** 고객의 채택 동기가 된다(Top #15). ② 아래로는 자기 2·3차 협력사에게 SRM 을 쓰게 해야 함 → 더 작은 회사라 로그인형 포털은 실패 확률이 높다 → **링크형 응답 + 구매 담당 대리 입력 허용(대리 입력으로 표시)**.
- 보안·멀티테넌트 함의 [추정, 원래 세션·05 결정 필요]: 협력사는 회사(`comp_cd`) 밖의 **외부 주체**다. 링크 토큰은 (발행 회사, 대상 문서, 협력사, 허용 동작, 만료, 1회/다회)로 범위를 제한하고, 토큰으로 들어온 요청도 **발행 회사의 회사 범위로 `TenantContext` 를 열어** RLS 를 그대로 태운다. 토큰은 해시로 저장, 접속 로그 `client_type` 에 `EXT`(신설) 구분. 협력사가 여러 고객사와 거래해도 고객사 간 데이터는 링크 단위로 완전히 분리된다(협력사 통합 계정을 만들지 않는 이유이기도 함).

#### 2.11.6 PMS (프로젝트관리)

- 상용차 제조사 웹 타임시트(약 150명): 출시 두 분기 안에 사용자 감소, 원인은 **낯섦에 대한 두려움과 불편 인식** — 인식(교육)과 효익 체감의 상관은 약함 [검색 X6].
- 주 단위 회상 기록은 같은 날 일지보다 약 10% 과대(미 연방 통계 인용), 짧고 부수적인 작업일수록 누락. 금요일 몰아 쓰기는 익숙한 코드로 몰리고 조정·협의 업무가 사라진다. 가장 효과적인 것은 **PM 이 배정한 작업·예산 시간을 미리 채워 두고 매일 확인만** 하게 하는 방식, 분류는 3~5개, 준수(제출)와 정확도(올바른 코드)를 따로 측정 [검색 X7]. PC 활동 자동 추적은 정확하지만 "AutoCAD 6.2시간"처럼 쓸모없는 기록이 되기 쉽고 감시로 느껴진다 [검색 X7].
- SmartHappy [추정]: PMS 사용자는 사무직이므로 POP 컴포넌트가 아니라 **"내 할 일" 홈 + 미리 채운 일일 공수 확인 카드**. 이슈는 품목·금형·LOT·설비 같은 업무 객체에 붙여 등록해 MES·QMS 화면에서도 보이게(메신저 이슈를 끌어오는 동기). M/D 는 프로젝트 원가·견적 근거로 **본인이 다시 보게 되는 화면**(내 프로젝트 공수 추이)을 함께.

## 3. 측정 — 활용률·입력 지연·데이터 품질

### 3.1 채택 지표 (SaaS 제품 분석 지표를 MES 에 맞게)

일반 제품 분석의 정의: 기능 채택률 = 기능 사용자 ÷ 전체 활성 사용자, 폭(breadth: 대상 사용자 중 쓴 비율 / 사용자당 기능 수 / 계정 중 활성 비율 — **정의가 셋이라 보고 시 명시**), 깊이(depth: 사용자당 상호작용 수), 고착도(DAU/MAU), 채택 소요 시간 [검색 U11]. MES 에서는 "로그인 수"보다 **업무가 시스템을 통과했는가**가 중요하다 [추정].

| 지표 | 정의 (월·주 단위) | 원천 | 현재 |
|---|---|---|---|
| 계정 활성률 | 기간 중 1회 이상 접속한 사용자 ÷ 사용 중 계정 | `sys_access_log`(LOGIN) | ✅ 가능 |
| 화면 활성률 | 화면별 사용자 수·건수, **한 번도 안 쓰인 메뉴** 목록 | `sys_access_log`(prog_cd, PAGE_VIEW/ACTION) | ✅ |
| 단말 유형 비중 | WEB/POP/PDA 별 ACTION 비중 — 현장 입력이 POP·PDA 로 들어오는가 | `client_type` | ✅ |
| 고착도 | 현장 역할 사용자의 일 활성 ÷ 월 활성 (근무일 기준) | 접속 로그 + 근무조(P2) | 🟡 근무일 기준 필요 |
| **업무 통과율** | 작업지시 중 POP 실적이 있는 비율, 입고 예정 중 스캔 입고 비율, 검사 대상 LOT 중 검사 기록 비율 | 업무 테이블 | 🔴 P2~P4 |
| 확산 | 파일럿 라인 → 전 라인 활성 라인 수 | 실적 원장 × 작업장 | 🔴 P2 |
| 모듈별 업무 통과율 | QMS 검사 계획 대비 기록률 · WMS 스캔 준수율(스캔 ÷ 재고 이동) · CMS 예방점검 기한 준수율·고장 기술 충분률 · SRM 협력사 응답률·PO 확인 지연 · PMS 일 단위 제출률 | 각 모듈 테이블 | 🔴 P3~P5 (2.11.1) |
| 대리·우회 비율 | `entered_by` ≠ 행위자 비율, override 비율 | 원장·접속 로그 | 🔴 대리 입력 컬럼 규약 필요(D12) |

### 3.2 데이터 품질 KPI (입력 지연·사후 입력·수기 비율)

GMP 데이터 무결성은 "수행 시점에 기록(contemporaneous)"을 요구하고, FDA 경고장 빈출 지적 중 하나가 "수행 시점에 기록하지 않음"(21 CFR 211.100(b)) [검색 U12]. 자동차 부품(IATF)도 추적성 기록의 신뢰가 같은 문제다 [추정]. 일반 데이터 품질 지표의 적시성(지연 = 기록 시각 − 사건 시각)·완전성(필수 필드 채움률) 정의를 원장에 그대로 적용한다 [검색 U12].

| KPI | 정의 | 원천 | 비고 |
|---|---|---|---|
| **입력 지연** | `recorded_at − occurred_at` 의 중앙값·P95 (공정·조·단말별) | 원장 공통 규약 | **이미 규약에 있음** — 계산만 하면 됨 |
| **사후 입력률** | 지연 > 정책값(예: 같은 조 안 / 60분) 또는 `occurred_at` 이 이미 마감된 조·기간에 속하는 비율 | 원장 + 근무조·기간 마감 | 조 끝 일괄 입력 = "형식적 입력"의 신호 |
| **정정률** | 역분개 행 ÷ 원 행 (마감 후 정정 별도) | 원장 역분개 | 높으면 입력 UI·검증 문제 |
| **수기 비율** | `entry_method=KEY` ÷ 전체 (AUTO·SCAN 대비) | **`entry_method` 신설 필요** (Top #2) | 낮아질수록 좋음 — 고객에게 보여 줄 "스마트화" 지표 |
| 사유 미입력률 | 사유 없는 비가동·불량 ÷ 전체 | CMS 상태 원장·불량 | MachineMetrics 식 사후 분류 비율도 |
| 수기 vs 설비 불일치 | 수기 수량과 설비 카운트 차이 > 허용치 비율 | Collector(P6) | 연동 고객만 |
| 필수 필드 채움률 | 선택 필드 중 품질상 필요한 필드(LOT·사유 메모) 채움 | 업무 테이블 | 화면별 |

### 4.1 현장 화면 원칙 (01 6장에 추가 제안)

1. **서버가 아는 값은 묻지 않는다** — 회사·공장·작업자·일시·작업장은 로그인·단말·스캔에서. (클라이언트가 보낸 작성자·회사값 불신 원칙(09 7장)과 같은 방향)

6. **끊겨도 잃지 않는다** — 대기열, 멱등, 증감 이벤트, 대기 건수 표시.
7. **모국어·아이콘·숫자** — 문장 대신 명령형 짧은 문구.
8. **측정 가능하게** — 모든 현장 입력은 `client_type`·`terminal_cd`·`entry_method`·`occurred_at/recorded_at` 를 남긴다.

### 4.3 화면 설계 체크리스트 — 사용성·현장 절 (skill `checklists.md` §2 추가 제안)

- [ ] 이 화면의 **주 사용자 역할·단말(WEB/POP/PDA)·장갑 여부**를 적었다.
- [ ] 사용자가 **직접 치는 필드** 목록과 각각 "왜 서버·스캔·기본값으로 못 채우는지"를 적었다.
- [ ] **예외 흐름**(분할·병합·재작업·특채·긴급·취소·통신 단절·중복 스캔) 각각의 처리 위치를 적었다.
- [ ] 확정 후 **사용자에게 돌려주는 정보**가 있다.
- [ ] 오류 메시지가 "무엇이 잘못됐고 **무엇을 하면 되는지**"를 말한다(i18n 키, 코드 노출 금지).
- [ ] `help_key` 를 화면·주요 필드에 달았다. 빈 상태 안내 문구가 있다.
- [ ] POP/PDA: 터치 타깃 ≥ 정책값, 문자 입력 없음(메모 제외), 오프라인 대기열 사용, 확정 1회.
- [ ] 측정 키(`client_type`·`terminal_cd`·`entry_method`·`occurred_at`)가 남는다.
- [ ] 필수값은 **확정·종료할 때만** 강제한다(입력 도중 막지 않음). 원인 코드는 6~8개 + 기타.
- [ ] 우회(override)·대리 입력 경로가 있으면 사유·권한·로그와 "대리" 표시가 남는다.
- [ ] 외부 사용자(협력사)가 쓰는 화면이면 로그인 없이 링크로 열리고, 모바일 한 화면에서 끝난다.
- [ ] 이상 사용 테스트에 **연타·중복 스캔·스캔 도중 작업자 전환·오프라인 중 확정 후 복구·언어 전환 후 확정**을 넣었다(dev-playbook `playbook/testing/abuse-testing.md` 와 함께).
