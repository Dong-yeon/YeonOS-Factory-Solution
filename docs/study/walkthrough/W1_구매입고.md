## 1. 현업 말로 — 공장에서 실제로 일어나는 일

1. 구매 담당이 협력사에 **발주**를 낸다(품목·수량·납기). 협력사는 "받았다·이만큼 언제 보내겠다"고 **회신**한다.
2. 협력사가 물건을 싣기 전에 **사전 납품 통지(ASN)** 를 보낸다 — "이 트럭에 발주 몇 번 행, 공급사 LOT ○○ 를 몇 개".
3. 물건이 도착하면 창고에서 **납품서 바코드(ASN:번호)를 찍고** 입고한다. 우리 쪽 **내부 LOT** 이 생기고 라벨이 붙는다.
4. 받은 양은 **재고**가 되고(보통 수입검사 대기 상태), 발주 쪽에는 "얼마 받았다"가 쌓인다.
5. 월말에 구매팀은 협력사를 **평가**한다 — 납기를 지켰나(OTD).
6. 생산계획(APS)은 "아직 안 들어온 발주"를 **입고 예정**으로 보고 자재 부족을 판단한다.
7. 잘못 받았으면 **취소(역분개)** 한다. 고치거나 지우지 않는다.

## 2. 시스템 지도 — 누가 무엇의 주인인가

```
 SRM(구매)                         WMS(창고)                          다른 모듈
 ─────────                         ─────────                          ─────────
 발주·회신 (srm_po)                                                   APS ← PoSupplyQuery(열린 발주)
 ASN (srm_asn)   ── AsnQuery ──▶  입고 화면(ASN 고르기·스캔)
 입고 이력 (srm_po_receipt) ◀─ PoReceiptGate ── 구매 입고 RCV_PO ──▶ MES LotService.receive(내부 LOT)
 평가 OTD_RATE                      재고 원장 inv_trx / 재고 칸 inv_stock
```

| 질문 | 답 | 왜 그렇게 나눴나 |
|---|---|---|
| "얼마 받았나"의 **원본**은? | **WMS 재고 원장**(`inv_trx` 의 RCV_PO 행) | 물건이 실제로 움직인 기록이 진실. SRM 의 받은 수량은 **투영**(원장에서 파생) |
| 발주 수량·초과 허용·상태 판단은? | **SRM**(게이트 안) | 발주 규칙은 구매가 안다. WMS 가 SRM 표를 직접 고치면 규칙이 두 군데 생긴다 |
| LOT 번호는 누가 만드나? | **MES**(`LotService.receive`) | 계보(어떤 원자재 LOT 이 어떤 제품에 들어갔나)의 주인이 MES |
| 모듈끼리 어떻게 말하나? | **계약 인터페이스**(`*.link`) | 남의 표·서비스를 직접 부르면 모듈 경계가 무너진다(모듈러 모놀리스) |

볼 곳: `src/main/java/io/smarthappy/module/srm/link/PoReceiptGate.java`, `.../srm/link/AsnQuery.java`, `.../srm/link/PoSupplyQuery.java:43`

## 3. 한 건이 지나가는 순서 (한 트랜잭션)

`MaterialReceiptService.receive` (`.../wms/inv/MaterialReceiptService.java:195`) 가 아래를 **한 트랜잭션**으로 한다.

| # | 단계 | 무엇을 | 왜 |
|---|---|---|---|
| ① | 요청 id 선점 | `sys_inbox`(WMS_RCV_MAT)에 요청 id 기록. 이미 있으면 처음 결과를 돌려준다 | 스캐너 연타·네트워크 재전송에도 **입고가 두 번 생기지 않게**(멱등) |
| ② | SRM 게이트 | `PoReceiptGate.receiveAt(발주행, 수량, "RCV_PO:요청id", 처리자, 발생시각, ASN행)` (`:249`) | 발주 규칙(상태·초과 허용률·단위 환산)은 SRM 이 판단. 실패하면 **전체 롤백** |
| ②-a | 게이트 안: 잠금 | 발주 머리 → 발주 행 → (ASN 행) 순으로 잠금 | 같은 발주를 두 창고가 동시에 받아도 초과 판단이 정확하게 |
| ②-b | 게이트 안: 판정 | 열린 수량·초과율(`SRM_RECV_OVER_PCT`)·상태(발행·회신·부분입고만) (`SrmPoReceiptGate.java:148`) | 너무 많이 받으면 409. ERP 원천 발주는 409 |
| ②-c | 게이트 안: 기록 | 입고 이력 1행(`srm_po_receipt`), 발주 행 받은 수량·머리 상태 갱신 (`:190`) | 날짜가 있는 이력이 있어야 **납기 준수율**을 계산할 수 있다 |
| ③ | 내부 LOT 생성 | MES `LotService.receive` → RECEIVED LOT (`.../production/LotService.java:170`) | 우리 공장 추적 단위. 공급사 LOT 은 속성 |
| ④ | 재고 원장 | `inv_trx` 에 RCV_PO(+) 1행 — 기본 단위 수량 + 발주 단위 수량(`po_qty`) | 원장은 **기본 단위만**(혼합 단위 합산 사고 방지). 대사용으로 발주 단위도 함께 |
| ⑤ | 라벨 | 인쇄 대기열(아웃박스) | 프린터가 꺼져 있어도 입고는 끝나야 한다 — 인쇄는 나중에 |

**잠금 순서**: 발주 머리 → 발주 행 → (ASN) → LOT → 기간 → 재고 칸. 모든 경로가 이 순서를 지켜야 교착이 없다(스터디 S1).

## 4. 핵심 결정과 버린 안

| 결정 | 버린 안 | 이유 |
|---|---|---|
| 받은 수량의 원본 = **WMS 원장**, SRM 은 투영 | SRM 이 원본, WMS 가 따라감 | 실물이 움직인 기록이 기준. 투영이 어긋나면 **대사**(`countRcvPoMismatch`)로 찾는다 |
| SRM 표는 **게이트(계약)로만** 바꾼다 | WMS 가 `srm_po_line` 을 직접 UPDATE | 규칙이 두 곳에 생기고, 한쪽만 고쳐지는 사고 |
| 입고 이력 합계 = 받은 수량을 **커밋 때** 검사(지연 제약 트리거) | 앱에서만 맞춘다 | 직접 SQL·버그로 어긋나면 DB 가 커밋을 거부 (`V128__srm_po_receipt_log.sql:66`) |
| 취소는 **역분개 행**(−) | 원 행 수정·삭제 | 감사 추적: 누가 언제 무엇을 되돌렸는지가 남는다 |
| 역분개는 **원래 입고 발생일**로 SRM 에 알린다 | "오늘"로 알린다 | 어제 입고를 오늘 취소할 때 "오늘 순입고보다 많이 되돌림" 409 → 실제로 났던 결함(#199 리뷰) |
| 입고·역분개 계약은 **이름을 나눔**(`receiveAt` / `reverseAt`) | 인자 개수 같은 오버로드 | null 로 부르면 어느 쪽인지 모호 → 호출 실수 |
| ASN 은 **조회 계약만**(`AsnQuery`), 입고 경로는 하나 | ASN 전용 입고 경로 | 입고 규칙·잠금이 두 벌이 된다. ASN 은 "칸 채우기 도우미" |
| ASN 한도는 **등록 때만**, 입고 때는 발주 초과율로만 | ASN 남은 양 초과 입고 거부 | 실물 수량이 기준. 협력사 ASN 이 틀릴 수 있다 |
| 같은 공급사 LOT 이 또 오면 **새 내부 LOT**(결정 #43) | 기존 LOT 에 더하기 | 만든 양 고정·원장 대사·계보 단순. 리콜은 공급사 LOT 으로 전부 조회 |
| APS 입고 예정은 **WMS 구매 입고가 생긴 뒤** 켬(A30) | 처음부터 켬 | 입고가 발주에 안 붙던 시절엔 받은 양이 재고와 발주 양쪽에 남아 **이중 계산** |

## 5. 잘못되면 생기는 일 (리스크와 방어)

| 리스크 | 증상 | 방어 |
|---|---|---|
| 스캐너 두 번 | LOT·재고 두 배 | ① 요청 id 선점(`sys_inbox`) |
| 두 창고 동시 입고 | 발주 초과 | ②-a 발주 머리·행 잠금 |
| 다른 회사 데이터 | A사가 B사 발주에 입고 | RLS(회사별 행 격리) + 트리거의 "같은 회사" 검사 |
| 단위 혼동 | 박스로 발주, 개로 재고 | 게이트가 기본 단위로 환산, 자릿수 넘으면 거부(반올림 안 함) |
| 어제 입고 오늘 취소 | 409 오판 | 원래 발생일 전달(4장) |
| 투영 어긋남 | SRM 받은 수량 ≠ 원장 | 대사 `rcv_po_mismatch` + 커밋 때 합계 검사 |
| 교착 | 500 오류 | 잠금 순서 고정(3장) |
