## 결함 목록 (심각도 순)

### #1 작성 중 머리의 모품목 변경이 순환 검사를 우회 — 중간

- 재현: FG1←SA1 확정. RM2 작성 중 BOM 에 행 FG1(정상). 앱 계정 회사 범위에서 `update mst_bom set item_id = <SA1> where bom_id = <RM2 작성 중>` → 1행 갱신 성공, SA1←FG1←SA1 순환.
- 원인: `V015__bom_structure.sql:134` `hb_guard_bom` — 불변 검사(160행)는 RELEASED·OBSOLETE 에만 걸리고, DRAFT 의 `item_id`·`alt_no` 변경은 허용. 순환 검사는 행 트리거(`:262`, 행 INSERT·자품목 변경 때)에만 있다. 서비스는 머리 모품목을 바꾸지 않으므로(`BomService.update` 주석) 화면으로는 재현 안 됨 — 직접 SQL·향후 코드(ERP 동기화 등) 경로. V015 머리 주석은 "DB 트리거가 직접 SQL 까지 막는다" 고 적혀 있다.
- 제안: 새 마이그레이션(V0xx)에서 `hb_guard_bom` 에 `TG_OP = 'UPDATE' AND (NEW.item_id <> OLD.item_id OR NEW.alt_no <> OLD.alt_no)` → `ck_mst_bom_key_immutable` 거부 추가(상태 무관). 순환 재검사보다 단순하고 서비스 규칙("모품목·대체 번호는 바꾸지 않는다")과 같다.
- 테스트: `BomAbuseTest.결함1_작성중_머리_모품목을_직접SQL로_바꾸면_순환이_생긴다` (@Disabled 해제 후 통과해야 함)

### #2 대체 그룹 우선순위 중복·1 없음이 확정됨 — 중간

- 재현: 그룹 G1 에 우선순위 1·1(50+50) → 확정 200. 그룹 G2 에 2·3(30+70) → 확정 200.
- 원인: `BomService.release` (`BomService.java:295-314`) 는 그룹별 비율 합 100 만 본다. docs/18 §4 "우선순위 1 이 기본 소요, 나머지는 대체 허용 목록" 이 3b 전개·P2 투입 검증의 기준인데 기본 소요가 0개 또는 2개가 될 수 있다.
- 제안: 확정 검사에 그룹별 "우선순위 중복 없음 + 1 이 정확히 하나" 추가(행 오류 `altPriority` `ALT_PRIORITY`, 메시지 키 ko/en). 행 저장 때 막을지는 선택 — 저장 중간 상태를 허용하려면 확정 검사만으로 충분.
- 테스트: `결함2_대체그룹_우선순위_중복이면_확정_거부`

### #3 기본 단위 변경 후 환산 수정이 to_unit 을 고치지 않음 — 중간

- 재현: RM1(KG) 에 ROLL=850 KG. 품목 기본 단위 KG→G. ROLL 환산 배율만 850000 으로 수정 → 200. 목록 `toUnit` 은 여전히 KG, ROLL 행이 있는 BOM 확정은 계속 `NO_CONV`. 사용자는 "고쳤는데 왜 안 되지" 상태. (삭제+재추가는 되살리면서 `to_unit` 을 새 기본 단위로 바꿔 정상.)
- 원인: `BomMapper.xml:202` `updateConv` 가 `to_unit` 을 갱신하지 않음. `findConvs` 는 `to_unit ≠ 품목 기본 단위` 인 옛 기준 행도 그대로 보여 줌. 근본은 `ItemService`(`ItemService.java:213,264`) 가 BOM 행·환산이 있는 품목의 기본 단위 변경을 막지 않는 것 — 확정본 행 "1 KG" 의 뜻이 품목 단위 변경으로 사라짐(3b 전개 때 환산 불가).
- 제안: (a) `updateConv` 에 `to_unit = (select unit_cd from mst_item where item_id = #{itemId})` 추가, `findConvs` 에 `to_unit = 품목 기본 단위 여부`(stale) 표시. (b) 설계 결정: BOM 행·환산에 쓰인 품목의 기본 단위 변경을 `IN_USE` 로 막을지(docs/18 에 기록 후).
- 테스트: `결함3_기본단위_변경후_환산_수정이_to_unit_을_고치지_않는다`

### #8 화면에서 자품목을 바꿔도 단위가 그대로 — 낮음~중간

- 재현(1366): 작성 중 BOM 에서 행 자품목 `TIP-M6-1.2`(EA) → `WIRE-ER70S-1.2`(KG) 로 고침 → 단위 선택 EA 유지 → 행 저장 성공(단위 EA 는 사용 가능 코드) → 확정에서야 `NO_CONV`. 새 품목에 EA 환산이 있으면 오류 없이 다른 양이 된다.
- 원인: `static/js/views/master/bom-mgt.js:180` `lookupItem` 이 `if (!l.unitCd)` 일 때만 단위를 채움 — 한 번 채운 뒤엔 품목이 바뀌어도 안 바뀜.
- 제안: 자품목이 바뀌면 `l.unitCd` 가 비었거나 **이전 품목의 기본 단위와 같을 때** 새 기본 단위로 바꾸고(사용자가 일부러 고른 단위는 유지), 바뀌었음을 행 옆에 표시. 서버 쪽 보조: 행 저장 때 단위가 자품목 기본 단위도 아니고 환산도 없으면 경고성 행 오류(확정 검사와 같은 `NO_CONV`)를 미리 줄지 검토.
