## 결함 목록 (심각도 순)

### #6 역전개 `top` 계산이 O(행²) — 높음

- 재현: D0 ← D1×2 ← … ← D13 (같은 자품목 두 행씩, 13단). D13 역전개 = 16,382행(정책 상한 20,000 안쪽) → 30초 뒤 500 `DB_ERROR`(57014). 4,094행은 2.6초(정전개 0.7초). 화면도 같은 500.
- 원인: `BomMapper.xml:326` `not exists (select 1 from up u2 where u2.child_id = u.parent_id) as top`. 재귀 CTE 는 통계가 없어 행 수 추정이 11 이라 해시 반조인이 아니라 **행마다 CTE 전체를 훑는 SubPlan** 이 된다. top 을 뺀 같은 SQL 은 16,382행 0.5초(EXPLAIN ANALYZE).
- 제안: `left join (select distinct child_id from up) used on used.child_id = u.parent_id` → `used.child_id is null as top`(해시 조인) 또는 `BomTreeService.whereUsed` 에서 `child_id` 집합을 만들어 Java 로 표시. 실측 테스트(`-Dhb.perf`)에 상한 근처 역전개를 추가.
- 테스트: `BomTreeAbuseTest.결함6_상한_안쪽_역전개는_몇_초_안에_끝나야_한다`

### #1 상한을 넘는 구조도 전체 경로를 계산 — 높음

- 재현: 같은 구조(D0 ← D1×2 …)를 17단으로 → D0 전개 400 `BOM_TOO_MANY_ROWS` 까지 3.7~4.9초(131,070 경로), 19단 20.4초, 같은 구조 역전개는 30초 시간 초과 500. 22단이면 838만 경로.
- 원인: `BomMapper.xml:242-289`(`explode`)·`:300-332`(`whereUsed`) 가 `order by t.ord limit #{rowLimit}` — 정렬 때문에 재귀 결과 전체가 만들어진 뒤 자른다. `BomTreeService.java:113,201` 의 `maxRows + 1` 은 결과 크기만 줄인다. 같은 자품목을 한 BOM 에 여러 행으로 쓰는 것은 허용(`uq_mst_bom_line_no` 만 유일, 비교 키도 공정별 여러 행 전제)이고 다이아몬드 공유도 흔해 2^n 구조는 저장 권한만으로 만들 수 있다. 문장 시간 제한 30초가 상한이지만 그동안 커넥션을 붙잡는다.
- 제안: 재귀를 정렬 전에 끊는다 — `capped as (select * from tree limit #{rowLimit})` 를 두고 바깥에서 `order by` (PostgreSQL 은 바깥 LIMIT 만큼만 재귀 작업 테이블을 당긴다. 너비 우선이라 잘린 결과는 위쪽 레벨부터 → 초과 판정은 그대로). 역전개도 같게. 회귀 테스트는 `결함1_…`(22단, 5초 안 400).
- 테스트: `BomTreeAbuseTest.결함1_경로_폭주_구조는_상한에서_바로_끊겨야_한다`

### #7 전개 화면이 행을 한꺼번에 그림 — 중간

- 재현(1366, 헤드리스 Chromium): 전개 QD0 16,382행 → 응답 후 그리기까지 13.5초, "1레벨만" 0.9초, 이어서 "모두 펼치기" 14.9초 — 그동안 화면 입력 불가. 4,094행 3.9초 / 1.4초.

### #3 일괄 대체 미리보기가 미래 확정본을 보지 않음 — 중간

- 재현: P1 A0 [−30, +5)·A1 [+5, ∞) 확정, 둘 다 X 사용. X → Y, 기준일 +2 → 미리보기 P1 NEW_REV(원본 A0) → 실행 → A2(+2 시작, Y) 생성 → BOM 관리에서 확정 409 `BOM_PERIOD_OVERLAP`(A1 이 +5 에 시작). 확정할 수 있었다 해도 +5 부터 A1 이 X 를 다시 쓴다.
- 원인: `BomChangeService.preview`(`BomChangeService.java:262` 부근)는 모품목마다 "작성 중 또는 기준일 유효 확정본" 하나만 본다. 기준일 뒤에 시작하는 확정본은 판정에 없다(`bomsUsing` 결과에는 있음).
- 제안: 기준일 뒤에 시작하는 확정본(대체 번호 같음)이 있으면 SKIP `FUTURE_REV`(이유 문구: "○일 시작 확정본이 있어 새 리비전을 확정할 수 없습니다 — 그 리비전을 먼저 정리") 또는 그 미래 리비전에도 새 리비전을 만드는 2단계 반영. 단순한 쪽은 SKIP.
- 테스트: `BomChangeAbuseTest.결함3_기준일_뒤_확정본이_있으면_미리보기가_건너뛰거나_경고해야_한다`

### #5 공정 사용 중지 뒤 라우팅 새 리비전 불가 — 중간

- 재현: PRESS 단계가 있는 확정 라우팅 → 공정 관리에서 PRESS 사용 중지(허용, 확정본은 그대로) → 새 리비전 → 400 `INVALID_VALUE` + `procCd INACTIVE`(rowKey 없음), 라우팅 수 그대로. 화면은 상단 "입력값이 올바르지 않습니다."만(어느 단계인지 없음). 폐기 라우팅의 작업장을 사용 중지해도 같은 400 `WORK_CENTER`(O11).
- 원인: `RoutingService.newRevision`(`RoutingService.java:553`) 의 `copySteps` 가 INSERT 라 `hb_guard_routing_step`(`V022__routing.sql:216-220`) 의 "새 참조는 사용 중 공정만" 에 걸린다. 서비스는 이 오류를 칸 오류로만 바꾼다(`:558`). 단종 공정을 다른 공정으로 바꾸는 개정이 정확히 이 경로인데 막힌다 — 신규 라우팅에 단계·조건을 처음부터 다시 입력하는 수밖에 없다. BOM 은 같은 상황(사용 중지 자품목)에서 새 리비전을 만들고 확정 검사가 행 단위로 알려 준다.
- 제안: 복사는 "기존 참조 유지" 로 본다 — 새 리비전 트랜잭션에서만 트리거 검사를 건너뛰게(예: `set_config('app.copy_rev', …, true)` 를 트리거가 확인, 또는 INSERT 대신 같은 값 복사임을 트리거가 원본 step 으로 확인) 하고, 확정 검사(`release`)가 그 단계에 `procCd INACTIVE`·`nodeId WORK_CENTER` 를 행 키와 함께 낸다. 트리거를 바꾸려면 새 V 파일(V022 수정 금지).
- 테스트: `RoutingAbuseTest.결함5_공정_사용중지_뒤에도_새리비전은_만들어지고_확정검사가_그_단계를_알려야_한다`

### #4 BOM 비교가 기준 수량을 무시 — 낮음~중간

- 재현: A0(기준 1, SA 2) ↔ A1(기준 10, SA 2) → `same 1`, 행 SAME. 실제 1개당 소요 2 → 0.2. 반대로 A1 을 기준 10·SA 20 으로 하면(소요 같음) CHANGED(qty).
- 원인: `BomChangeService.diff`(`BomChangeService.java:110`) 가 `qty` 를 그대로 비교, 머리 기준 수량은 `CompareHead.baseQty` 로 응답에만 있고 `bom-mgt.js:461` `showCompare` 는 표시하지 않는다. 설계 변경 검토(ECN)에서 "바뀐 게 없음" 으로 읽힌다.
- 제안: 비교는 `qty / base_qty`(고정 수량 행은 qty 그대로)로 판정하고 표에 두 쪽 수량과 기준 수량을 함께, 요약 줄에 "기준 수량 1 → 10" 표시.
- 테스트: `BomChangeAbuseTest.결함4_비교는_기준수량으로_나눈_소요로_판정해야_한다`

### #2 전개 필요량 소수 자릿수 누적 — 낮음

- 재현: 기준 1·수량 1 사슬 10단 → 10단 행 `reqQty` 가 `1.000…0`(402글자). 기준 3 이면 의미 있는 숫자 뒤에 0 이 수백 자리.
- 원인: `BomMapper.xml:254-255,268-269` — numeric 나눗셈(유효 20자리)과 곱셈이 레벨마다 scale 을 더한다. 화면은 소수 3자리로 보여 문제를 숨기지만 JSON(20,000행이면 수 MB 추가)·엑셀·#1 의 계산 비용이 커진다.
- 제안: 레벨마다 `round(…, 10)`(또는 `numeric(38, 12)` 캐스트) 로 자릿수를 묶고, 응답은 `round(t.req_qty, 6)`. 검산 테스트(`BomExplodeTest`)는 `isEqualByComparingTo` 라 그대로 통과.
- 테스트: `BomTreeAbuseTest.결함2_필요량은_정해진_자릿수로_반올림되어야_한다`
