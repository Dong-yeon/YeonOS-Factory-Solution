## 1. 일반 계획으로 바뀌는 과정 [실측·코드]

- MyBatis `#{page.size}`·`#{page.offset}` 은 바인드 값이다. 그래서 같은 조건·정렬 조합이면 SQL 글자가 같고, 연결 하나에서 같은 문장으로 쌓인다.
- 드라이버(pgjdbc 42.7.13) 기본 `prepareThreshold = 5` — **5번째 실행부터** 이름 있는 서버 준비 문장이 된다.
- 서버(PG16 `plan_cache_mode = auto`)는 그 문장에 custom 계획을 5번 세운 뒤 일반 계획 비용과 견준다. 일반 계획이 싸 보이면 그 뒤로 일반 계획을 쓴다.
- 일반 계획은 limit·offset 값을 모르고 **"10% 를 읽는다"** 고 가정한다.
- 실측에서 12번 호출 끝 `pg_prepared_statements` 는 `일반 3 · custom 5` 였다. **10번째 호출부터 일반 계획**이다(1~4번은 이름 없는 문장).
- 캐시는 **연결마다** 따로다. 풀 10개(`DB_POOL_SIZE` 기본)면 연결마다 따로 바뀐다. 조건·정렬 조합이 다르면 다른 문장이다.
- **[코드·추정]** LOT 엑셀은 grid 와 **같은 문장**(`findLotPage`, `PageQuery.sortOnly` = limit 2147483647)을 쓴다. 엑셀 실행이 custom 계획 평균 비용을 크게 끌어올려 일반 계획이 상대적으로 싸 보이게 한다 — 일반 계획 쪽으로 기울이는 요인.

"1쪽 10번 → 깊은 쪽 3번", "깊은 쪽 10번 → 1쪽 3번"(다른 쪽의 이력으로 고른 일반 계획을 이어 쓰는 경우)도 같은 범위였다.

일반 계획 모양(`EXPLAIN (GENERIC_PLAN)`): H1·H2 는 `Limit → Sort → 스캔`(색인 순서 안 씀), M4 는 `Parallel Seq Scan`(`sys_outbox` 에 `created_at` 색인 없음), 접속 로그만 `Index Scan Backward`(정렬 `desc` 에 `nulls last` 없음).

## 3. 플랫폼 공통안 득실

| 안 | 어디서 | 득 | 실 |
|---|---|---|---|
| (가) 목록별 `customPlan()`(WMS 지금) | 서비스에서 조회 직전 `set_config('plan_cache_mode','force_custom_plan', true)` | 문제 있는 목록만 · 효과 확인됨(WMS 3초 → 0.13초) | 목록마다 기억해야 한다. 매퍼 메서드가 모듈마다 생긴다 |
| (나) 플랫폼 헬퍼 — **PageQuery 깊은 쪽만** | 예: MyBatis 인터셉터가 파라미터의 `PageQuery.offset ≥ N` 을 보고 같은 연결에 위 `set_config`(트랜잭션 한정) | 한 곳. 1쪽은 계획 재사용 그대로 | 실측 피해는 **1쪽**(알람)에서 났다 — 깊은 쪽만으론 그 경우를 못 막는다. 인터셉터는 보이지 않는 동작이다. 트랜잭션 밖이면 효과 없음(DB 접근은 항상 트랜잭션 안 — 규칙상 문제없음) |
| (다) 전역 `force_custom_plan` | ⓐ 역할 설정 `ALTER ROLE happyboot_app SET plan_cache_mode = …`(init 스크립트에 timezone·statement_timeout 선례) ⓑ `TenantAwareTransactionManager` 가 이미 부르는 `set_config` 한 문장에 칸 하나(왕복 추가 없음) ⓒ URL `options=-c plan_cache_mode=…` | 모든 목록이 한 번에 · 연결 풀 영향 없음(연결마다 같은 설정) | **모든 문장이 매번 계획**: 짧은 문장 +40%(기본키 0.12 → 0.17ms). | (라) 드라이버 `prepareThreshold=0` | JDBC URL | 서버 준비 문장을 안 쓴다 → 항상 custom. 덤: DDL 뒤 "cached plan must not change result type" 이 없고, PgBouncer transaction 모드와도 맞는다 | 파싱까지 매번 — 짧은 문장 약 2배(+0.1ms/회). 문장별로 고를 수 없다 |
| (마) limit·offset 을 글자로 | 매퍼 `${}` | — | **금지**(`./gradlew check` 가 막는다). 제외 |

## 4. 제안 (상위 판단)

1. **정렬 `nulls last` 정리를 먼저 한다(N-1).**
   - 큰 목록(LOT·알람·점검 회차·설비 상태 검토·카운트·SRM 통지)의 정렬 키가 **NOT NULL 이면 `nulls last` 를 붙이지 않는다**. 빈 값이 있는 키(`cleared_at`·`due_date` 등)에만 둔다.
   - 지연 조인과 같이 하면 1쪽은 ms 단위, 깊은 쪽은 색인 항목만 건너뛴다.
   - `asc` 는 기본 색인 순서(NULLS LAST)와 같아 문제없다. **`desc nulls last` 만** 걸린다.
   - 가드 후보: 원장 표 offset 문장에서 NOT NULL 열에 `desc nulls last` 를 막는다.
2. **일반 계획은 목록별 유지(가).**
   - 이번 실측에서 일반 계획 피해는 "색인 순서를 못 써서 큰 정렬을 병렬로 하는 계획"에서만 났다. 1번을 정리하면 일반·custom 이 같은 계획이 된다.
   - 1번 뒤에도 남는 목록(WMS 처럼 실측으로 확인된 것)만 `customPlan()`.
   - 플랫폼에 둔다면 (가)를 공통 메서드 하나로 묶는 정도. (나) 인터셉터는 실측 근거가 약하다.
3. **전역 강제((다)·(라))는 보류.** 짧은 문장 비용 +40~100% 에 비해 이득이 실측에서 남지 않았다.
4. WMS 실측(0.13 → 3초)이 여기서 그대로 재현되지 않은 이유는 **[추정]** 데이터 분포·색인 선택(10% 가정에서 다른 색인을 고름)이다. WMS 는 실측 근거가 있으니 지금 방식을 유지한다.
