## 1. QC-1 — 같은 NCR 을 두 클레임에 동시에 [재현] · [코드]

**[코드]** 트리거 `hb_guard_srm_claim_ncr` 는 "다른 살아 있는 클레임에 같은 NCR 이 있나" 를 `EXISTS` 로 볼 뿐 잠그지 않는다. 그래서 커밋 전 다른 트랜잭션의 행은 보이지 않는다.

`ClaimService` 의 두 경로:
- **만들기**: 채번(`numbers.next(SrmNumbers.CLAIM)`)의 채번 행 잠금이 회사 안 만들기를 줄 세운다 [추정 — 시험 안 함]. 그래서 동시 만들기끼리는 우연히 막힌다.
- **고치기**(작성 중 클레임의 NCR 바꾸기): `lockClaim` 이 **자기 클레임 행만** 잠근다. 서로 다른 두 클레임을 고치는 요청 사이에는 공통 잠금이 없다.

**[재현]** `결함QC1_같은_NCR_을_두_클레임에_동시에_넣으면_하나는_거부`
1. 작성 중 클레임 둘(K1·K2)을 만든다.
2. 트랜잭션 A 가 K1 에 NCR 921 을 넣고, 커밋 전에 멈춘다(넣은 것을 확인).
3. 트랜잭션 B 가 K2 에 같은 NCR 을 넣는다 → 통과·커밋.
4. A 를 커밋한다 → **살아 있는 클레임 2건**.

순차로 넣으면 `uq_srm_claim_ncr_live` 로 거부된다(대조 시험 통과).

**영향.** 한 NCR 로 협력사에 클레임이 두 번 나간다(시정조치·비용 청구 중복). 반품 상세의 연결 목록에도 둘이 보인다.

**제안.** 트리거나 서비스에서 NCR 단위로 잠근 뒤 검사한다. 예:
- `pg_advisory_xact_lock(hashtext('srm_claim_ncr:' || ncr_id))`
- 또는 회사·NCR 단위 잠금 행
- 부분 유일 색인은 부모 상태(취소)를 봐야 해서 못 쓴다고 트리거 주석에 적혀 있다. 다른 방법은 `srm_claim_ncr` 에 살아 있는지 표시 칸(클레임 취소 때 같이 바꿈)을 두고 부분 유일 색인을 거는 것이다.

## 2. 같은 NCR 에 여러 건 · 취소가 섞일 때 [재현]

| 해 본 것 | 결과 |
|---|---|
| 클레임(NCR 901·902) + 반품 901-1·901-2·902-1(취소)·902-1(새로)·903-1 | 클레임 상세 = [901-1, 901-2, 902-1(새로)], 세 반품 상세 = 그 클레임 하나, 903-1 = 없음 |
| 취소된 반품(902-1) 상세 | 클레임이 보인다 — 반품 쪽 거름은 클레임 상태만 본다(관찰) |
| 클레임 취소 → 같은 NCR 새 클레임 | 반품 상세: 취소 직후 0건 → 새 클레임 1건. 취소된 클레임 상세에는 반품이 그대로(관찰) |
| 살아 있는 클레임이 있는 NCR 을 세 번째 클레임에 | `uq_srm_claim_ncr_live` 거부, 살아 있는 클레임 1 |

**정책 확인(관찰).** 취소된 쪽 상세에서 상대가 보이는 것은 "그때 무엇이 걸려 있었나" 를 보는 데 쓸모가 있다. 다만 화면에 취소 표시가 없으면 헷갈릴 수 있다. 의도라면 그대로 둔다.

## 3. 협력사 경계 [코드]

- **서비스 검사:** 클레임 근거 NCR 과 반품 근거 NCR 은 서비스가 계약 `SupplierQualityQuery.ncr` 로 "그 NCR 의 공급사 = 그 협력사" 를 확인한다(`SRM_RTN_NCR_SUPPLIER`). LOT 의 공급사는 바꿀 수 없다(`lot_master` 트리거).
- **연결 질의:** NCR id 만 맞추고 `cust_id` 를 같이 보지 않는다.
- **판단:** 지금은 다른 협력사 반품이 끼는 API 경로가 없다. 다만 스냅샷 값이라 DB FK 는 없다. 직접 SQL·이관 데이터가 어긋나면 다른 협력사 행이 연결 목록에 보인다. 방어 조건 `and r.cust_id = (클레임의 cust_id)`(반대쪽도 같게)를 넣으면 비용이 거의 없다 — 제안.
- **잘림:** 연결 목록은 `limit 200` 에서 말없이 자른다. 한 NCR·클레임에 200건은 비현실적이라 그대로 둬도 된다.
