## 1. POP PIN 확인 선점 (#533)

**[코드]** 흐름은 다음과 같다. 바깥 트랜잭션은 없다.
1. 조회.
2. **선점**: 조건부 UPDATE 한 문장. `pin_locked_until` 이 없거나 지났을 때만 실패 수 +1(만료 뒤면 1). 5번째가 잠금 시각을 건다.
3. 연결 없이 bcrypt 비교.
4. 맞으면 `pinOk` — `pin_fail_cnt = 0, pin_locked_until = null`.

| 해 본 것 | 결과 | 근거 |
|---|---|---|
| 잠금이 끝나는 바로 그 시각(시계 고정)에 단말 8대 동시 틀림 | PIN_WRONG 4 · PIN_LOCKED 4, 실패 수 5, 다시 잠김 — 만료 경계에서 횟수가 늘지 않음 | [재현] |
| 맞는 PIN 의 비교를 멈춘 사이(선점 실패 수 1) 틀린 시도 3번 → 실패 수 4 → 맞는 PIN 기록 | 실패 수 **0** — 3번이 사라지고 틀린 시도 4번이 다시 PIN_WRONG(예산 가득) — **O-1** | [재현] PasswordEncoder 스파이로 맞는 PIN 비교만 멈춤 |
| 같은 사이에 틀린 시도 4번(선점 5번째 = 잠금) | 맞는 PIN 기록이 **잠금을 푼다** — O-1 같은 뿌리 | [재현] |
| A사로 B사: 같은 배지 글자를 두 회사가 씀 / B사에만 있는 배지 | A사 단말은 A사 작업자만(배지 해시에 회사 코드) — B사 PIN 은 A사 작업자의 틀림, B사 실패 수 0 / BADGE_UNKNOWN | [재현] |
| 같은 작업자 동시 틀림 5번째 잠금·작은 풀 연결 바닥 없음·잠긴 동안 해시 비교 | 모듈 시험(PopPinPoolTest)이 덮음 | — |

O-1 수정 안: `pinOk` 를 "자기 선점분 되돌리기"(`pin_fail_cnt = greatest(pin_fail_cnt − 1, 0)`, 잠금 시각은 그대로)로 바꾼다. 다만 "맞으면 잠금 해제" 를 기대하는 화면 문구·시험이 있으면 정책을 같이 정한다.

## 2. QMS SPC 투영 (#536, V186)

**[코드]** `qms_spc_event_state` 는 처리 기록 INSERT 트리거가 상태를 **마지막 처리 종류**로 바꾼다. 다시 계산 함수는 우선순위(VOID > CLOSE > 그 밖)로 정한다. 둘이 갈라지려면 종결·무효 **뒤에** 처리가 들어가야 한다.
- V157 가드(`hb_guard_qms_spc_event_act`)가 이벤트 단위 advisory 잠금 뒤 종결·무효가 있으면 55000 으로 거부한다.
- 그래서 서비스의 상태 확인이 잠금 없는 읽기여도 DB 에서 순서가 지켜진다.

## 3. SRM ASN 덜 받은 행 수 (#534, V185)

- **[코드]** `hb_srm_asn_open_refresh` 는 `srm_asn` 행 FOR UPDATE 뒤 다시 센다. plpgsql 다음 문장이 새 스냅숏이라 먼저 커밋된 입고가 보인다 — 읽기-쓰기 경합이 막힌다.
- 칸 직접 수정은 `pg_trigger_depth() < 2` 로 거부한다.
- **교착(여러 ASN 을 한 트랜잭션에)**: **경로 없음** [코드]
  - `SrmPoReceiptGate.receiveAt(poLineId, …, asnLineId)` 는 호출마다 발주 행 하나·ASN 행 하나다.
  - WMS 입고(`MaterialReceiptService`)는 요청 하나에 원장 행 하나다.
  - 잠금 순서는 발주 머리 → 행 → ASN(`lockAsn`)이고, 트리거의 FOR UPDATE 는 같은 행을 다시 잡을 뿐이다.
- 무작위 흐름(만들기·줄 고치기·확정·입고·되돌림) 뒤 칸 = 이력 재계산, 같은 ASN 다른 줄 동시 입고(잠금 대기 관찰), 직접 쓰기 거부·줄 고치기 재계산, A사로 B사·grid 정렬은 모듈 시험(`AsnOpenLineCntTest`)이 모두 덮는다. 그래서 **QA 시험은 더하지 않았다**.

## 4. WMS B-1·B-2 (#538)

- **B-1**: `QualityLinkQaTest` 의 관찰 기대가 WMS 에서 뒤집혀(스위치 끈 뒤 NCR 폐기 종결 → 재고 반영) 통과한다 — **해결 확인**.
- **B-2 [코드]**: 판정된 LOT 에 생산 입고가 더 들어오면 `QcReceiptRule` 이 그 LOT 의 살아 있는 최신 판정을 본다. NG 면 BLOCKED(이어받음), OK 면 QC(재검사)다. NG 를 무효로 하면 `releaseInherited` 가 판정 뒤 BLOCKED 입고 순합만큼 QC 로 되돌린다.
- **B-2 동시 [재현]**: NG LOT 에 추가 입고(+4)가 판정을 읽어 BLOCKED 로 게시한 채 커밋을 미루는 동안 그 NG 를 무효로 하고 반영했다.
  - 무효 반영이 입고 트랜잭션의 잠금을 **기다렸다가**(잠금 대기 1) 입고 커밋 뒤 이어받은 몫까지 QC 로 되돌렸다(QC 14, BLOCKED 0).
  - 입고가 판정을 읽은 뒤 무효가 끼어들어 추가분이 BLOCKED 로 남는 틈은 없다.
