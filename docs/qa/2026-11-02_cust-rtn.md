## 3. 결함 상세

### CR-a 다른 원장의 요청 id 로 반품 — 재고 없는 반품 (고칠 것, 중)

- [재현] 출하 확정(SHIP 원장)이 쓴 `client_req_id` 를 그대로 반품 요청 id 로 → **200**. [관찰] 반품 RECEIVED 1 · 클레임 NCR 1 · LOT `hold_yn = Y` · `inv_trx` 출처 CUST_RTN **0행** · QC 칸 BLOCKED **0**.
- [코드] `CustRtnService.receive` → `inventory.post(List.of(row), req)` → `InventoryService.postAs`: 같은 `client_req_id` 행이 있으면 **아무것도 넣지 않고** `PostResult(done, replay=true)`. receive 는 replay 를 보지 않는다. 반품 쪽 확인(`findByReq`)은 `wms_cust_rtn` 안만 본다.
- 파급: 받을 수 있는 양이 줄고(반품 합에 들어감), NCR 처분 때 `WMS_QUALITY_SHORT` 또는 같은 LOT 의 **다른 BLOCKED 재고를 소비**(CR-c 와 겹침). 반품 취소는 `liveTrxOf` 가 비어 역분개 없이 CANCELLED — 취소하면 정합은 돌아온다.
- 경로: 화면은 요청 id 를 새로 만들고 입력이 바뀌면 버린다(`cust-rtn.js` input/change) — **API·연동·단말 재사용 경로**. 이상 사용 원칙상 서버가 막아야 함.
- 고칠 방향: `postChecked`(PQ-1 — 다른 출처 원장 행이 쓰던 id 면 409) 를 쓰거나, `PostResult.replay()` 가 true 면 `DUPLICATE_REQUEST` 를 던져 반품·NCR 까지 롤백.

### CR-b QMS 화면이 클레임 NCR 을 취소 — 막다른 반품 (고칠 것, 중 + 방식 질의)

- [재현] 반품(QC 칸 2) → QMS `POST /api/qms/ncrs/{id}/cancel`(qms-ncr DELETE) → **200**. [관찰] NCR CANCELLED · LOT 보류 해제(N) · 반품 RECEIVED · QC BLOCKED 2 · 반품 취소 → **409 `QMS_NCR_STATE`**.
- [코드] `NcrService.cancel` 은 OPEN 만 보고 `src_type` 을 보지 않는다. 반품 취소(R-6)는 `cancelForClaim` 이 OPEN 이 아니면 409.
- 결과: 반품 기록은 영영 RECEIVED, BLOCKED 재고는 처분 경로가 없다(NCR 이 없으니 `onNcrClosed` 도 없음). 풀려면 사람이 상태 이동 — 반품 기록과 재고가 어긋난다. docs/59·docs/29_P3 38장에 이 경로 언급 없음.
- 질의(방식): (가) QMS 화면 취소가 `src_type` 있는 NCR 을 거부("반품 화면에서 취소") / (나) QMS 취소가 WMS 반품을 연쇄 취소. QA 는 (가)를 권함 — R-6(취소 = 반품 화면, NCR 과 함께)과 같은 방향, 모듈 경계도 지금 방향(WMS → QMS) 그대로.

### CR-c 클레임 NCR 처분이 다른 반품의 물건을 처리 (고칠 것, 중 + 설계 질의)

- [재현] 같은 LOT 반품 1(QC 칸 2) · 반품 2(A 칸 2, node_id A < QC). 반품 1 의 NCR 을 SCRAP 2 로 종결 → [관찰] **QC BLOCKED 2 그대로, A BLOCKED 0** — 판정 전인 반품 2 의 물건이 폐기됐다.
- [코드] `QualityStockPosting.onNcrClosed` 는 LOT 의 BLOCKED 칸을 `QualityStockMapper.cellsOf`(`order by s.node_id`) 순으로 소비. NCR 에는 칸이 없다(B3 설계는 LOT 단위).
- 위험: 반대 조합(반품 1 불량 → SCRAP, 반품 2 양품 → USE_AS_IS)이면 **불량품이 가용**으로, 양품이 폐기로 — 품질 유출. 같은 LOT 의 검사 NG BLOCKED 재고(B3)가 더 작은 node_id 칸에 있어도 같은 일(추정, 같은 코드 경로).
- 질의: 클레임 NCR(`src_type = WMS_CUST_RTN`)은 그 반품의 RCV_RTN 원장 칸을 먼저 쓰고 모자라면 기존 규칙 — 로 할지, LOT 단위 처분을 유지하고 "같은 LOT 열린 클레임 둘" 을 막을지.

### CR-e 수불 원장 화면의 출하 SHIP 역분개 (고칠 것, 중~높음 — #749 이전부터)

- [재현] 출하 3 → 반품 2 → 수불 원장 화면 `POST /api/wms/trx/{SHIP 행}/reverse` → **200**. [관찰] 출하 SHIPPED · 피킹 SHIPPED · 영업 `shipped_qty` 3 · 순 출하(SHIP 원장) **0** · STAGING 재고 3 복귀 · 살아 있는 반품 2.
- [코드] `InventoryService.reverseAll` 의 사람 화면 차단 = 출처 `QMS_INSP`·`QMS_NCR`(SOURCE_ONLY)·`CUST_RTN` 만. `SHIP_PICK` 없음. 출하 취소(`ShipService.undo`)는 영업 게이트 음수·피킹 상태·반품 확인을 함께 하는데 원장 화면은 원장만.
- 반품과 무관하게 출하·영업·원장 셋이 어긋난다(같은 물건을 다시 피킹·출하 가능 → 영업 출하 수량 이중). 피킹 이동 짝(MOVE_OUT/IN, 출처도 SHIP_PICK)도 같은 경로로 되돌릴 수 있을 것(추정, 미실행).
- 고칠 방향: `SHIP_PICK` 출처를 사람 화면 역분개에서 막음(출하 취소·피킹 취소 화면으로만) — RTN_SUP 이 게이트를 같이 되돌리는 것처럼.

### CR-d 같은 요청 id·다른 칸/사유 (정책 질의 → 결정 2026-11-02: 칸·사유까지 비교, 다르면 409)
