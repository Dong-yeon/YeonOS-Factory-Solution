# 64. 설비관리(CMS) 부족 기능 분석 — ISO 55000 · ISO 14224 · SAP PM 기준

> 작성 2026-11-02 · CMS 하위 세션(`claude/cms-work`) · 상태: **분석·제안(사용자 결정 대기)** — 코드 변경 없음(같은 PR 의 데모 시더 `CmsDemoFlow` 는 docs/51 C3 일부)
> 계기: 상위 세션 지시 "CMS 화면을 실제로 띄워 보고 부족한 기능을 공개 레퍼런스(ISO 55000·ISO 14224·SAP PM 등) 근거로 정리(분석만)"
> 관련: docs/33(CMS 설계·결정 D1~), docs/47 7장(CMS 반입 후보 1~5·Y6~Y9), docs/51(C1~C4 차트·대시보드·데모 데이터), docs/52(비교 2)

## 1. 결론 먼저

- YeonOS CMS 는 **"작업지시·예방점검·KPI 계산"의 골격은 시장 일반 CMMS 와 같은 수준**이다(docs/52 32행 판정과 같음).
  - 있는 것: 고장 신고(사무·POP)·보전 작업지시(BM/CM/PM, 현상·원인·조치 코드, 정지 시각, 공수, 첨부)·예방점검(달력·사용량 주기, 점검표, CHECK/WO 방식, 달력 화면)·예비품 연결과 사용(WMS 출고 연동 스위치)·상태 원장 기반 KPI(OEE·MTBF·MTTR·PM 준수율)·비가동 사유 검토·알람·설비 이력 카드·위험성평가·설비 보안 대장.
- 비어 있는 것은 크게 세 갈래다.
  1. **보이는 분석이 없다** — 고장 코드를 모으지만 **원인·현상·설비별 고장 파레토와 반복 고장**을 보여 주는 화면이 없다. KPI 는 표·엑셀만이다(docs/51 C1~C2 가 차트를 맡음). 2026-11-02 로컬 화면 실측에서 **KPI 가 전 설비 "수집 없음"** — 데이터도 비어 있었다(같은 PR 의 시더가 채운다).
  2. **고장 기록이 ISO 14224 의 구분보다 거칠다** — 현상·원인·조치 3종 + 원인 상위 분류뿐. 고장 모드·메커니즘·탐지 방법·영향(정지/성능 저하/잠재)·고장 부위(유지보수 가능 항목)가 없다.
  3. **계획·자산 관점(ISO 55001)이 얇다** — 작업 계획(예상 공수·자재 예약·백로그), 측정점 기반 상태 보전, 자산 수명주기(취득가·내용연수·갱신 계획), 위험 기반 중요도 평가가 없다.
- 추천 우선순위(8장 질의 — 사용자 결정 대기):
  1. **G1 고장 분석 화면 + G2 수리 시간 분해** — 마이그레이션 없이 지금 원장으로 된다. C1 `hb.chart` 병합 뒤 C2 대시보드의 한 판(탭)으로.
  2. **G3 ISO 14224 고장 기록 칸** — 면접에서 "고장 데이터를 표준 분류로 쌓았다"를 말할 근거. G1 의 축을 늘린다.
  3. G5 측정점·상태 보전, G6 작업 계획·백로그 — 중간 크기.
  4. G4·G7·G8·G9 — 보류 또는 다른 제안과 합침.
- 이번 분석 중 **결함·정책 질의 4건**(6장): 예비품 사용 이력의 날짜가 "기록 시각"이라 사후 입력이 오늘로 잡힘, PM 작업지시 완료 시 점검 실행 수행 시각이 "지금"(작업지시 완료 시각과 다름) 등.

## 2. 조사 방법

- **화면**: 로컬 8090(다른 세션이 띄운 `claude/ui-local-fixes` 앱, 보기만) — `cms-kpi`·`cms-mwo`·`cms-breakdown`·`cms-equip-card`·`cms-pm-plan`·`cms-chk-run`·`cms-spare`·`cms-state-review`·`cms-equip-profile` 를 열어 조회 조건·열·빈 상태를 확인(2026-11-02 17시경, DEMO 회사).
- **코드**: `module/cms/*Service`·`mapper/cms/*.xml`·V041·V042·V051·V073·V093 을 읽음. 근거는 파일·메서드로 적고, 코드로 확인 못 한 것은 "(추정)".
- **공개 자료**: 9장. 표준 원문은 유료라 ISO·CEN 공식 목록 페이지와 공개 요약·발췌로 범위만 확인했다 — 표준 조항 번호를 인용할 때는 "(요약)" 표시.
- 고객사 자료는 쓰지 않았다(A사~L사 언급 없음).

## 5. 후보 (G1~G10)

규모는 1인 기준 대략(설계·시험·화면 포함). "마이그레이션" = 새 V 파일 필요 여부.

### G1. 고장 분석 화면 — **상**, 2일(C1 뒤), 마이그레이션 없음

- 무엇: 기간·공장·설비 클래스 조건으로 **원인 파레토**(막대 + 누적 %), 현상·설비별 전환, 원인 상위 분류(`CMS_FAIL_CAT`) 묶음, 설비별 고장 수·정지 분·MTBF·MTTR, **반복 고장**(같은 설비 × 같은 원인이 N일 안에 2번 이상 — N 은 정책) 표시. 막대 → 그 작업지시 목록 드릴다운(같은 필터, docs/51 C4 짝 규칙).
- 근거: 3장 #3. 고장 코드를 필수로 받으면서 집계해 보여 주지 않으면 코드 입력의 의미가 없다(ISO 14224 의 목적이 "모은 데이터로 분석"). 51 C3 "고장 잦은 설비 → Pareto 1위 → 작업지시" 시연 줄의 빈 고리.
- 원천: `cms_mwo`(BM, DONE·CLOSED, 정지 시각) + `cms_fail_code`. 기간 기준은 **정지 시작(없으면 신고 시각) — 공장 시간대**. MTBF·MTTR 은 KPI(상태 원장)와 원천이 다르므로 이름을 "작업지시 기준"으로 구분하거나 KPI 값을 그대로 옆에 둔다(6장 F3 결정에 따름).
- 시험: A사로 B사 0건, 파레토 합 = 기간 BM 수, 취소 제외, 공장 시간대 자정 경계, 드릴다운 건수 = 막대 값.
- 사용자 결정: 독립 화면(`cms-fail-analysis`) vs C2 대시보드의 탭 → **권고: C2 탭**(화면 수를 늘리지 않음).

### G2. 수리 시간 분해(MTTR 분해) — **상**, 1일, 마이그레이션 없음

- 무엇: 고장 작업지시마다 **대기(신고 → 착수)**·**수리(착수 → 완료)**·**설비 정지(정지 시작 → 끝)**·**공수 합**을 계산해 설비·담당별 평균. KPI 화면 MTTR 옆에 "평균 반응 시간"(MTTA).
- 근거: 4장 #4. 정지 시간을 지연과 실 수리로 나누는 것은 EN 13306·ISO 14224 의 시간 구분(요약). 지금 칸(`reported_at`·`started_at`·`finished_at`·`down_*`·`cms_mwo_labor`)이 이미 있다.
- 주의: 정지 없이 신고된 것(down_yn = N)은 정지 칸 빈칸. 착수 전 취소는 제외.
- 사용자 결정: 반응 시간 목표(예: 중요도 A 30분)를 정책으로 둘지 → 권고: 처음엔 값만 보이고 목표는 보류.

### G3. ISO 14224 고장 기록 칸 — **중상**, 2~3일, 마이그레이션 있음

- 무엇: 고장 코드 유형에 **메커니즘(MECHANISM)**·**탐지 방법(DETECT: 점검 중·운전 중 이상·알람·고장 후 발견·예방 작업 중)** 추가, 작업지시에 `mechanism_id`·`detect_id`·**영향**(`STOP` 정지 / `DEGRADED` 성능 저하 / `INCIPIENT` 잠재) 칸. 현상 = ISO 14224 의 고장 모드로 문서상 매핑(화면 이름은 "현상(고장 모드)").
- 근거: 4장 #2 [I1][I2] — 모드·메커니즘·원인을 섞는 것이 CMMS 데이터 품질의 대표 오류라는 공개 해설 [V1]. 탐지 방법은 "점검으로 찾은 고장 비율" 같은 예방 보전 효과 지표의 재료.
- 마이그레이션: `cms_fail_code` 유형 CHECK 확장 + `cms_mwo` 칸 3개(NULL 허용 — 기존 행 유지) + 전역 코드 `CMS_FAIL_IMPACT`. 완료 필수 여부는 정책으로(기본 선택).
- 사용자 결정: (a) 칸 추가 vs (b) 지금 3종 유지 + 문서 매핑만 → **권고 (a), 선택 입력**. 알람 → 고장 신고 경로는 탐지 방법을 `ALARM` 으로 자동.

### G4. 고장 부위(유지보수 가능 항목) — 중, 2일, 마이그레이션 있음

- 무엇: 설비 클래스별 **부위 코드**(예: 프레스 = 유압·슬라이드·메인 모터·클러치·안전 장치) 를 고장 코드 유형 `PART` 로, 작업지시에 부위 칸. 예비품 연결에 부위를 선택적으로.
- 근거: 4장 #1·#2 — ISO 14224 8단계, SAP 부위(B) 카탈로그 [S2]. "어느 부위가 자주 고장 나나" 가 G1 의 두 번째 축.
- 사용자 결정: 코드 목록(가볍다) vs 설비 구성 트리(설비 BOM, 무겁다) → **권고: 코드 목록**. 트리는 보류.

### G5. 측정점·상태 기반 보전 — 중, 3~4일, 마이그레이션 있음

- 무엇: 설비 **측정점**(진동 mm/s·베어링 온도·유압) 정의 + **측정값 원장**(occurred_at·recorded_at·정정은 역분개) + 한계·경향(최근 N개 기울기) 경보 → 고장 신고/작업지시 제안. 입력 길: 점검 실행 NUM 결과를 측정점에 연결(같은 값이 두 곳에 남지 않게 원장 하나), 수집 이벤트 PARAM 을 지시 공정이 없을 때 측정점으로.
- 근거: 4장 #6 — SAP 측정점·측정 문서 [S4][S5], ISO 17359 [I4]. 지금 PARAM 은 진행 지시 공정이 없으면 거부된다(`EquipEventService.param`).
- 범위 주의: MES 6단계 원장(`prd_param_actual`)과 경계 — **남의 표 변경 없이** CMS 새 표로. 수집 쪽 분기는 MES 세션과 합의 필요.
- 사용자 결정: 카운터 표 확장 vs 새 표 → 권고: 새 표(카운터는 누적 사용량, 측정은 순간값 — 의미가 다름).

### G6. 작업 계획·백로그 — 중, 2~3일, 마이그레이션 있음

- 무엇: 작업지시에 **계획일·예상 공수**, 사용 예비품 줄에 **계획/실사용 구분**(예약), 열린 작업지시의 예상 공수 합 ÷ 주간 보전 가용 공수 = **백로그(주)**, 계획 작업 비율(PM+CM 공수 ÷ 전체), 일정 준수.
- 근거: 4장 #7 — SAP 작업지시 [S6], EN 15341·SMRP 지표 [E2][M1].
- 겹침: 47 CMS-5(보전 비용·외주) 와 같이 설계(외주 공수 Y6 해소 포함).
- 사용자 결정: 보전 가용 공수의 원천(근무조 × 보전 인원 vs 정책 상수) → 권고: 정책 상수로 시작.

### G7. 자산 등록부·갱신 계획 — 중하, 2일, 마이그레이션 있음

- 무엇: 설비 자산 칸(취득일·취득가·내용연수·잔존 가치·갱신 예정 연도) + 연도별 갱신 계획 표 + 누적 보전 비용(G6·47 CMS-5) 대비 "고치기 vs 바꾸기" 참고 표.
- 근거: 4장 #8 — ISO 55001:2024 6.2.1 SAMP·자산 관리 계획·수명주기(요약) [I3].
- 범위 주의: 회계 감가상각은 ERP 소관 — **값은 참고용, 회계 원장 아님**을 화면·문서에 명시.
- 사용자 결정: 할지 말지 → 권고: 보류(포트폴리오 이야기로는 좋지만 현장 사용 빈도 낮음). 한다면 G6 뒤.

### G8. 위험 기반 중요도 평가 — 하~중, 1~2일, 마이그레이션 있음

- 무엇: 안전·품질·납기 영향·대체 설비 유무·고장 빈도(G1) 점수 → A/B/C 제안 + 근거 저장. 사람이 최종 확정(지금 칸 그대로).
- 근거: 4장 #9 — ISO 55001 위험 기반 의사결정(요약) [I3]. `RiskMatrix`(위험성평가) 계산을 재사용할 수 있는지 확인 필요.
- 사용자 결정: 점수 항목·가중치 → 정의 없으면 임의 설계하지 않음(질의).

### G9. 작업 안전 조치(LOTO) 확인 — 중, 1~2일, 마이그레이션 있음

- 무엇: 중요도·작업 유형에 따라 착수 전 "에너지 차단·표지·잔류 압력 해제 확인" 체크(누가·언제), 완료 시 해제 확인.
- 근거: 4장 #10 [O1].
- **47 CMS-3(가동 중단·재가동 승인)에 합치기를 권함** — 같은 "착수·재가동 전 확인" 흐름.

### G10. 보증(warranty) — 하, 1일, 마이그레이션 있음

- 설비·예비품 보증 만료일, 보증 기간 안 고장 표시. SAP PM 에 있는 기능(요약). **권고: 보류.**
