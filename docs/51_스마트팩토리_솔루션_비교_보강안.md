## 0. 요약

### 0.1 한 줄 결론

**업무 기능의 폭과 데이터 규약은 이미 시장 상위권 수준인데, 그 데이터를 "보여 주는 층"이 비어 있다.**
OEE·MTBF·MTTR 계산(`EquipKpi`)·SPC(X̄-R + WE1~4 + Cp/Cpk/Pp/Ppk, `SpcCalc`)·상태 구간 원장·에너지 검침 원장까지 있는데, 관리자 화면은 **표(hb.grid)와 홈 할 일 카드뿐**이다. 시장 제품(Tulip·Plex·MachineMetrics·Siemens Insights Hub)은 첫 화면이 **OEE 추이·비가동 Pareto·KPI 타일**이다. 따라서 이번 보강의 1순위는 새 업무 기능이 아니라 **차트 공통 부품 + 관리자 대시보드 2~3장 + 그 차트가 비지 않게 할 데모 데이터**다.

### 0.3 면접용 3줄

- 시장 제품은 OEE·Pareto 차트를 기본으로 보여 준다. YeonOS 는 **그 숫자의 정의(ISO 22400)와 분모(미수집·계획 정지 제외)를 차트 옆에 같이 보인다.**
- 차트를 클릭하면 **같은 SQL 조건의 목록**으로 내려간다. hb.grid 의 "화면 = 엑셀 = 같은 SQL" 원칙을 차트까지 넓힌 것이다.
- AI 요약 이전에 **원장의 `entry_method`·`recorded_at` 으로 "믿을 수 있는 숫자인가"부터 보여 준다**(MachineMetrics AI Summary 가 2025-12 에 내놓은 기능을 규칙만으로).

| **A. 자체 `hb.chart`(SVG)** | `spc.js` 의 SVG 코드를 일반화하면 된다. CSP(`style-src 'self'`) 문제가 없고, 색은 디자인 토큰을, 글자는 i18n 을 그대로 쓴다. 인쇄·PDF 에서 벡터로 나온다. `node --test` 로 눈금·Pareto 누적을 단위 테스트할 수 있다. hb.grid 와 같은 논리로 면접에서 설명할 수 있다 | 확대·브러시·애니메이션은 직접 만들어야 한다. 위 5종 + 툴팁 + 표 대체 보기는 **약 800~1,200줄 추정** |
| B. Apache ECharts(Apache-2.0) | 종류·상호작용(확대·범례 토글·내보내기)이 풍부하다. aria 를 지원한다 | 전체 빌드가 약 1MB(부분 빌드를 하면 줄어든다 — **추정**). 기본 툴팁이 inline `style` 속성이 든 HTML 을 만들기 때문에 **CSP `style-src 'self'` 에서 깨질 가능성이 있다(추정, PoC 필요)** — 사용자 formatter·richText 로 우회해야 한다. 토큰 색을 옵션으로 매번 넘겨야 한다 |
| C. uPlot(MIT) / Chart.js(MIT) | 작고 빠르다(시계열에 강함) | Pareto·히스토그램은 직접 조합해야 한다. canvas 라 인쇄 품질과 접근성은 따로 챙겨야 한다 |

**권고: A(자체 `hb.chart`)를 기본으로 한다.** 그 이유:
1. 필요한 종류가 5개로 좁고, 이미 SVG 관리도가 동작하고 있다.
2. hb.grid 를 직접 만든 이유(CSP·라이선스·"같은 SQL" 원칙)가 그대로 적용된다.
3. 차트가 "데이터를 보여 주는 표준 부품"이 되므로 접근성 규칙(색만으로 구분 금지, 표 대체 보기 — WCAG 1.4.1, 12 1.4 표)을 한 곳에서 강제할 수 있다.

**단, 1일 PoC 를 먼저 한다**: ECharts 부분 빌드를 CSP 그대로 띄워 툴팁·범례가 깨지는지 확인한다. 깨지지 않고 확대·브러시가 꼭 필요하다고 판단되면 B 로 바꾼다. 결과는 10 H7 에 기록한다.

### 4.3 `hb.chart` 규칙(안)

- API 모양은 hb.grid 와 맞춘다: `hb.chart.line(el, {series, x, y, bands, marks})`, `.bar`, `.pareto`, `.hist`, `.spark`, `hb.kpiTile(el, {value, unit, period, target, def})`. 타입은 `types/hb.d.ts` 에 넣는다.
- 색: 범주색 = Okabe-Ito 토큰(`--hb-data-1..6`), 상태색은 **상태를 뜻할 때만**(가동/고장 누적 막대 = 40 부록 A.2 의 설비 상태 톤). 목표를 벗어났을 때만 강조색을 쓴다(12 1.5).
- 모든 차트에 **"표로 보기" 토글**을 둔다(같은 데이터, 스크린리더·복사용). `role="img"` + `aria-label` 요약 문장을 단다.
- 빈 데이터는 0 선으로 그리지 않고 **"수집 없음" 문구**를 띄운다(`EquipKpi` D19 "미수집을 0 으로 채우지 않는다"와 같은 원칙).
- 클릭하면 `onPick({key, from, to})` 를 호출하고, 화면이 드릴다운 탭을 연다(C4).
- 날짜 축은 **공장 시간대**를 쓴다(`BizClock`·`hb.fmt.datetime(…, zone)`). UTC 로 그리지 않는다.

## 5. 제안 상세

### C1. `hb.chart` 공통 차트 부품 — 상, 3~4일(PoC 1일 포함)

4장 내용 그대로다. 첫 적용은 SPC 화면이다: `spc.js` 의 그리기 코드를 `hb.chart.line` + bands 로 옮겨서 **회귀 없음**을 확인한다(같은 데이터의 점·한계값 비교 단위 테스트).
**설계 판단**: 공통 부품을 대시보드보다 먼저 만든다. 화면마다 SVG 를 따로 그리면 색·축·빈 데이터 처리가 화면마다 달라진다. 40 에서 이미 "화면마다 상태색이 다른" 문제를 고친 적이 있다.

### C2. 설비·생산 관리자 대시보드 — 상, 3일

- 새 화면 `cms-dashboard`(또는 `mes-dashboard`). sys_prog 를 추가하고 `@ProgAuth` SEARCH 를 건다. 조회 조건은 공장·기간(기본 최근 30일, 공장 시간대)·라인/설비다.
- 배치(위에서 아래로 = 결과 → 원인):
  1. KPI 타일 5개: OEE·가용률·성능·품질·MTTR. 각각 기간 값, 앞 기간 대비, 목표, 스파크라인을 보이고 **정의 버튼**(C4)을 단다.
  2. OEE 추이(일별): OEE 선 + A·P·Q 3선. 표준 사이클이 없는 날은 성능·OEE 를 비우고 이유를 툴팁으로 보인다(D21).
  3. 비가동 Pareto: 사유별 시간. **계획 정지(SDT·NST)와 비계획(UDT)을 색으로 나눈다** — MachineMetrics 의 "unplanned setup 분리"[M1]와 같은 의도다. 미수집(UNKNOWN)은 Pareto 에 넣지 않고 따로 숫자로 보인다.
  4. 설비별 상태 시간 누적 막대(가동·계획 정지·고장·미수집).
  5. 계획 대비 실적(지시 계획 수량 vs 양품) + OTD 자리(47 영업 제안이 구현되면 연결).
- **데이터**: 새 계산을 만들지 않는다. `KpiService.daily`·`EquipKpi.Raw` 를 그대로 쓰고, Pareto 는 상태 구간 원장을 사유별로 합친다(`StateTimelineService` 의 실효 사유 규칙을 공유).
- **갱신**: 처음에는 조회 버튼 + 선택형 60초 자동 갱신으로 한다. SSE·WebSocket 은 넣지 않는다 — 지금 저장소에 그런 기반이 없고, 관리자 대시보드는 분 단위면 충분하다.
- **성능**: 30일 × 설비 수십 대는 원장 직접 집계로 시작한다. 측정해 보고 느리면 일 집계 테이블(일반 테이블 + RLS, `TenantRunner` 배치)을 둔다. 머티리얼라이즈드 뷰는 금지 규칙(01) 그대로다.
- **테스트**: "A사로 B사 설비" 조회 0건, 기간 경계(공장 시간대 자정), 미수집만 있는 설비, 표준 사이클이 없는 실적이 섞인 날의 빈칸, Pareto 합 = 비가동 총합.

### C3. 데모 설비 데이터 생성기 — 상, 1~2일

- 현재 `DemoDataSeeder` 는 MES 관통 흐름 실적 1묶음만 넣는다. 그래서 상태 구간·고장·비가동 사유 이력이 없고, C2 를 띄워도 **차트가 거의 빈다.**
- 30일치 시나리오를 넣는다: 설비 6~8대. 그중 하나는 "고장 잦음", 하나는 "셋업 길어짐", 하나는 "수집 끊김"이다. 교대·휴일 달력을 반영한다. **실제 서비스 경로**(`/ext/v1/equip-events` 와 같은 `EquipEventService`)로 넣어서 원장 규약(`entry_method`)을 지킨다.
- 공개 데모는 매일 04:00 초기화되므로, 시드 기준일을 "오늘 − 30일"로 상대화한다.
- **설계 판단**: 포트폴리오는 "열었을 때 이야기가 보이는 데이터"가 기능만큼 중요하다. 고장 잦은 설비 → Pareto 1위 → 드릴다운 → 보전 작업지시로 이어지는 **한 줄 시연 시나리오**를 데이터로 미리 심어 둔다.

### C4. KPI 정의 카드 + 드릴다운 규칙 — 상, 1일

- KPI 마다 정의를 하나 둔다: 이름, 식, 분자, 분모, 분모에서 뺀 것, 근거(ISO 22400 KPI 이름), 데이터 출처 화면. 저장 위치는 i18n 메시지 + 용어 사전(`master/term-mgt`, docs/21)이고, 별도 테이블은 만들지 않는다.
- 타일·축 제목의 ⓘ 를 누르면 정의가 뜬다. Excel 다운로드 머리에도 같은 정의 문장을 넣는다.
- **드릴다운 규칙**: 차트에서 고른 키·기간을 **기존 목록 화면의 조회 조건**으로 넘긴다(Pareto "금형 교환" → `state-review` 사유·기간 필터, 불량 Pareto → 실적/NCR 목록). 대시보드 전용 상세 SQL 은 만들지 않는다 — "집계와 상세 필터를 짝으로"(CLAUDE.md 수치 규칙)를 구조로 강제하는 셈이다.
- **설계 판단**: 고객마다 "가동률" 정의가 다르다는 문제(02 2.5)는 화면에 정의가 보이지 않을 때 생긴다. 시장 제품은 정의를 문서에 숨긴다. 같은 화면에 보이는 것이 YeonOS 의 차별점이다.

### C5. 품질 대시보드 + SPC 보강 — 중상, 3~4일

- 대시보드(`qms-dashboard`): 불량 유형 Pareto(실적 폐기·재작업 + NCR, 불량 코드 2단의 상위 기준), 불량률(ppm) 추이, NCR·8D 경과일 분포(기한 초과 강조), SPC 요약(기간 내 위반 수 상위 특성 + Cpk < 1.33 특성 목록 → `spc` 화면으로).
- SPC 보강:
  1. **I-MR**: n=1. 검사 실행에서 한 개만 재는 특성이 흔하다.
  2. **p 관리도**: 계수형. 수입·출하 검사 불량률에 쓴다.
  3. **공정능력 히스토그램** + 규격선 + 정규곡선.
  
  모두 `SpcCalc` 순수 함수 + 공개 상수표(E2·D3·D4) + 단위 테스트로 만든다.
- 규칙 수는 지금(WE1~4 선택, 기본 1·2)을 유지한다 — ISPE 권고[R1]와 같은 방향이라는 근거를 29_P3 에 적는다.

### C6. 현장 현황판(TV) 모드 — 중, 2일

- 47 의 "설비 모니터링 카드판"과 합친다. 화면은 설비 카드(상태 톤·현재 지시·오늘 양품/목표·정지 경과 분) + 라인 OEE 타일로 구성하고, 전체 화면·다크·큰 글자(15 `clamp()`)로 띄운다.
- **인증**: 사람 계정 세션을 TV 에 걸어 두지 않는다. POP 와 같은 **단말 활성화(ROLE_TERMINAL) + 읽기 전용 프로그램**을 쓰고, 세션 절대 수명 정책은 단말 쪽 규칙을 따른다(정책 질의 — 8장 Q4).
- 갱신은 30~60초 폴링이고, 끊기면 "마지막 갱신 n분 전"을 크게 띄운다(조용히 옛 숫자를 보여 주지 않는다).

### C7. 데이터 품질·교대 요약(규칙 기반) — 중, 2일

- MachineMetrics AI Summary 는 "수동 수량 정정 1,684건 → 카운터 보정 필요" 같은 데이터 이상을 짚는다[M4]. YeonOS 는 원장에 이미 그 재료가 있다: `entry_method`(수기/스캔/수집), `recorded_at − occurred_at`(입력 지연), 사유 미입력 구간, 미수집 시간, 역분개 정정 수.
- 교대·일 단위로 "주의 목록"을 만든다(예: 설비 X 미수집 3.2h, 라인 Y 실적 62% 수기, 정정 14건). 홈 카드 1장 + 대시보드 패널로 보인다. **AI 라고 부르지 않는다**(03 6.3 표기 원칙).
- 나중에 LLM 을 붙일 때는 이 목록을 **입력으로만** 쓴다. 요약문 생성은 03 의 `LlmPort`·호출 감사 로그와 함께 들어가고, 그것이 28 R7 MCP 와 이어지는 순서다.
- 11 의 "채택 KPI 대시보드 최소형"(D5, `platform/usage`)과 겹치지 않게 한다. usage 는 **사용자 활용도**를, C7 은 **숫자의 신뢰도**를 본다.

### C8. 수집 참조 어댑터 — 중, 3일

- 코어에는 프로토콜을 넣지 않는다(00 "MQTT 브로커를 코어 경로로 안 씀" 유지). 저장소 안에 **별도 실행 샘플**(`tools/collector-sample/`, 배포물 밖)을 두고 OPC UA 노드 구독(Eclipse Milo 등 — 착수 때 라이선스 확인)과 MQTT/Sparkplug B 구독을 `/ext/v1/equip-events` 표준 이벤트로 바꾼다. 연결이 끊기면 로컬 파일 버퍼에 쌓았다가 다시 보낸다(`sys_inbox` 멱등과 맞물림).
- 함께 넣는 것: **OPC UA 시뮬레이터 설정**(공개 데모 서버 또는 로컬 시뮬레이터) — C3 다음 단계의 "살아 있는 데모"다.
- **설계 판단**: 시장은 UNS·Sparkplug 로 모이고 있다[U1]. 하지만 1인 제품에서 브로커 운영은 고객·서드파티 몫이다(28 SAP 브로커 폐기 근거). "표준 이벤트 계약 + 참조 어댑터"까지만 하면 연결 구조를 설명할 수 있다.

### C9. 에너지 원단위 차트 — 중하, 1~2일

- `energy_reading` 원장(V051)을 공장·설비·일별로 합하고, 같은 기간 양품 수로 나눠 **kWh/양품** 추이를 그린다. 설비가 여러 지시를 섞어 돌린 날의 배분 규칙(시간 비례)은 08 에서 정한다 — 정의가 없으면 설비 단위까지만 그린다.
- CBAM 은 현재 철강·알루미늄 등 품목군만 대상이므로 자동차 부품 2·3차사에는 직접 의무가 아니다(**추정**, 08 에서 재확인). 그래서 "탄소 보고"가 아니라 **원가·설비 이상 신호(원단위 급증)** 로 내세운다.

### C10. 단계형 작업표준서 최소형 — 하~중, 3일+

- 47 의 "POP 에서 도면·작업표준서 보기"를 먼저 한다. 그다음 단계로 **표준서 = 단계 목록(문구·사진·확인 체크 여부)**, 개정은 문서 관리(`qms/doc-mgt`)의 배포본만 쓰고, POP 착수 때 **지시에 고정된 개정 번호**로 띄운다. 확인 체크는 실적 원장이 아니라 별도 추가 전용 기록으로 남긴다.
- 시장(Tulip·Plex·Siemens)의 AI 초안·영상·장비 연동은 하지 않는다.
