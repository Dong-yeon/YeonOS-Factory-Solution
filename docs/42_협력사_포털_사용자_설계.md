# 42. 협력사 포털 사용자 — 플랫폼 설계 (2026-10-23, 채택)

> 상태: **채택(2026-10-23 사용자 결정 P1~P5 추천안)** — 9장. 구현은 SRM R4 뒤(결정 docs/29 #49 이후 할 일 ④). 사용자 결정 SRM R3c 를 플랫폼 쪽에서 어떻게 받는지 적는다.
> 근거 문서: docs/31 SRM D4·4.11.3·R3c(포털을 1부에서 미룬 이유), docs/01(인증·회사 범위·RLS), docs/36 Q13(개인 화면), 14장(MFA).

## 1. 결론 먼저 (사용자 결정 R3c)

- 협력사 포털 사용자 = **`sys_user` 의 한 유형**(`user_type = 'SUPPLIER'`) + 소속 협력사 **`cust_id`**. 계정 표를 새로 만들지 않는다.
- **인증·세션·CSRF·잠금·비밀번호 규칙은 회사 사용자와 같다**(로그인 화면·회사코드·5회 잠금·IP 시도 제한·세션 절대 12시간·CSRF 쿠키·비밀번호 정책·관리자 초기화). 다른 것은 **로그인한 뒤 갈 수 있는 곳**과 **볼 수 있는 행**뿐.
- 갈 수 있는 곳: **경계 필터**가 협력사 사용자의 요청을 포털 경로(허용 목록)로만 통과시킨다 — 내부 화면·API 는 모두 막힌다. 거꾸로 회사 사용자는 포털 API 를 쓰지 않는다.
- 볼 수 있는 행: 회사 격리는 지금처럼 **RLS**(같은 회사 안). 협력사 격리(같은 회사의 다른 협력사)는 **포털 서비스가 모든 조회·저장에 로그인의 `cust_id` 를 조건으로 건다** + **가드 시험**으로 빠뜨림을 막는다. **RLS 두 번째 정책은 쓰지 않는다**(4장).

## 2. 표 (P0 플랫폼, 마이그레이션 1개)

| 칸 | 정의 | 규칙 |
|---|---|---|
| `sys_user.user_type` | `varchar(10) NOT NULL DEFAULT 'INTERNAL'` CHECK (`INTERNAL`·`SUPPLIER`) | 기존 행 = INTERNAL. **유형은 만든 뒤 바꾸지 않는다**(트리거로 UPDATE 거부) — 내부 계정을 협력사로 돌리면 남은 권한 그룹·결재선·위임이 협력사에게 넘어간다 |
| `sys_user.cust_id` | `bigint NULL` FK → `mst_cust` | CHECK: SUPPLIER ⇔ cust_id 있음. 같은 회사 거래처만(기존 `hb_check_*_comp` 식 트리거), 구매·겸용(`PURCHASE`·`BOTH`) 거래처만 |

- 협력사 사용자는 **권한 그룹에 넣지 않는다**(`sys_user_auth` 트리거가 SUPPLIER 거부), **결재선·위임 대상이 되지 않는다**(결재 엔진의 결재선 검사에 유형 조건), **알림 받는 사람이 되지 않는다**(`NotificationService.send` 의 사용자 조회에 `user_type = 'INTERNAL'`).
- 감사 행위자 문자열은 그대로 `u{id}:{login}` — 누가 했는지는 `sys_user` 로 안다.

## 3. 갈 수 있는 곳 — 경계 필터

| 항목 | 정한 것 |
|---|---|
| 로그인 결과 | `LoginUser` 에 `userType`·`custId` 를 더한다(세션 직렬화 대상). 성공 뒤 이동: INTERNAL `/main`(지금), SUPPLIER **`/portal`** |
| `PortalBoundaryFilter` | `TenantRequestFilter` 바로 뒤(회사 범위·계정 유효 확인·MFA·비밀번호 변경 강제가 먼저). SUPPLIER 의 요청은 **허용 목록**만: `/portal`·`/portal/**`(화면), `/api/portal/**`, 세션·문구·비밀번호 변경·MFA·로그아웃·`/error`. 그 밖은 API 403 `PORTAL_FORBIDDEN`, 화면 → `/portal`. INTERNAL 이 `/api/portal/**`·`/portal/**` 를 부르면 403 |
| 두 겹 막기 | 필터를 빠져나가도 **`@ProgAuth` 검사(ProgAuthAspect)가 SUPPLIER 를 무조건 거부** — 개인 화면(`self_service_yn = 'Y'`, Q13)도 "로그인한 모든 **회사** 사용자" 로 좁힌다(AuthMapper·HomeMapper·NotificationService 의 self_service 조건 3곳) |
| 포털 API 표시 | 포털 컨트롤러 메서드는 `@ProgAuth` 대신 **`@PortalApi`**(가드 시험이 `/api/portal/**` 의 모든 핸들러에 붙었는지, `@PortalApi` 가 `/api/portal/**` 밖에 없는지 본다). 화면 권한(sys_prog)은 쓰지 않는다 — 포털 메뉴는 코드로 고정 |
| 계정 유효 확인 | 매 요청 `countActive` 에 SUPPLIER 면 **거래처 사용 중**(`mst_cust.use_yn = 'Y'`)까지 — 거래처를 사용 중지하면 이미 로그인한 협력사 세션도 다음 요청에서 끊긴다 |

## 4. 볼 수 있는 행 — 서비스 거름 + 가드 시험 (RLS 두 번째 정책이 아닌 이유)

| 비교 | RLS 두 번째 정책(`cust_id = hb_current_cust()`) | 서비스 거름 + 가드 시험(채택) |
|---|---|---|
| 적용 범위 | 정책은 **표마다**. 협력사가 보는 행은 발주 머리·행·ASN·납품서처럼 여러 표에 걸치고, 행에 `cust_id` 가 없는 표(발주 행)는 조인 정책이 된다 | 포털이 쓰는 질의 몇 개에만 |
| 회사 사용자 영향 | 같은 표를 내부 화면도 쓴다 — 허용(PERMISSIVE) 정책은 OR 로 합쳐져 의미가 없고, 제한(RESTRICTIVE) 정책은 "내부 사용자면 통과" 분기를 모든 표에 넣어야 한다 | 내부 질의는 그대로 |
| 기존 장치 | `TenantCatalogInspector` 의 정책 허용 목록·기동 가드를 표마다 넓혀야 한다(01 RLS 우회 금지 규칙과 부딪힘) | 손대지 않음 |
| 빠뜨림 막기 | DB 가 막는다 | **가드 시험**: 포털 매퍼 XML 의 모든 문장이 `#{custId}` 를 쓰는지(`./gradlew check`), 포털 서비스는 `PortalUser.current().custId()` 로만 값을 얻는지(인자로 받지 않음). + 이상 사용 시험 "A 협력사로 B 협력사"(id 를 바꿔 넣으면 404) |

- 포털 매퍼는 **패키지를 따로**(`module.srm.portal`) — 가드 시험이 경로로 범위를 안다. 내부 SRM 매퍼를 포털이 재사용하지 않는다(거름 없는 질의가 섞임).
- 데이터 접근은 **MyBatis**(SRM 그대로). jOOQ 는 시범 모듈(module.apqp) 한정이라 포털에 쓰지 않는다(docs/43 J6).
- 협력사에게 가는 메일(발주 통지 등)은 지금처럼 아웃박스 — 포털 계정이 생겨도 업무 메일 경로는 `MailService.publish`(docs/36 18.3.1)이고, **알림함·알림 메일(M1)은 협력사 사용자에게 가지 않는다**(2장).
- 회사 격리는 그대로 RLS — 협력사 사용자도 회사 범위는 로그인 회사로 열린다(`TenantRequestFilter`).

## 5. 계정 관리

| 항목 | 정한 것(추천) |
|---|---|
| 누가 만드나 | **회사 관리자**(사용자 관리 화면, `sys-user` SAVE) — 유형 "협력사" 고르면 거래처 고르기(구매·겸용, 사용 중), 권한 그룹 칸 숨김 |
| 협력사가 자기 직원 계정을 만드나 | **안 함**(1차) — 외부 사람이 계정을 늘리는 경로가 생긴다. 필요하면 협력사 대표 계정·상한과 함께 따로 결정 |
| 비밀번호 초기화·잠금 해제 | 회사 사용자와 같은 관리자 기능 |
| MFA | 회사 사용자와 같은 규칙(정책 화면 지정). 관리자 MFA(14장)는 SUPPLIER 에 해당 없음(관리자 그룹이 없다) |
| 엑셀 사용자 올리기(Q26) | 1차는 INTERNAL 만 — 협력사 계정은 화면에서 한 명씩(거래처 확인을 사람이) |

## 7. 구현 순서 (SRM R4 뒤)

1. 마이그레이션(유형·cust_id·트리거 3개: 유형 고정·권한 그룹 거부·거래처 소속) + `LoginUser`·성공 이동 + `PortalBoundaryFilter` + `@PortalApi`·가드 시험 2개 + ProgAuth·개인 화면 3곳에 INTERNAL 조건 + 사용자 관리 화면 유형·거래처 — **시스템관리**
2. 포털 셸(`/portal`, 고정 메뉴·문구) — **시스템관리**
3. 포털 업무 API·화면(발주 회신·ASN 입력·납품서) — **SRM**(이 문서의 규칙: `module.srm.portal`, `@PortalApi`, `custId` 는 `PortalUser.current()`)

## 8. 시험 (정상 + 이상 사용 A~K)

- 협력사 사용자가 내부 화면·API(모든 `@ProgAuth` 경로 표본 + 개인 화면 알림함·결재함·홈) → 403/`/portal` 로. 회사 사용자가 `/api/portal/**` → 403.
- **A 협력사로 B 협력사**: 같은 회사의 다른 협력사 발주 id·ASN id → 404, 목록에 안 보임. **A사 협력사로 B사**: 다른 회사 → RLS 로 404.
- 거래처 사용 중지 → 로그인한 협력사 세션 다음 요청에서 끊김. 유형 바꾸기 UPDATE → 거부(직접 SQL 포함). 협력사 사용자를 권한 그룹·결재선·위임에 → 거부. 알림 대상에서 빠짐.
- 로그인 잠금·IP 제한·CSRF·세션 만료·비밀번호 변경 강제·MFA 가 협력사 사용자에게도 똑같이.
- 가드: 포털 매퍼 문장 `#{custId}` 누락 → `check` 실패(일부러 틀린 예로 가드 자체 시험).

## 13. 구현 기록 — P4 접속 로그 사용자 유형 (2026-10-24, 시스템관리, 마이그레이션 없음)

- 접속 로그 화면(sys-access-log)에 **사용자 유형 열 + 조회 조건**. 로그 행에 칸을 더하지 않고 `sys_user` 를 조인한다 — 유형은 만든 뒤 바뀌지 않으므로(10장 트리거) 지금 값이 곧 기록 때 값이다. 칸을 더했다면 기존 행 채우기·로그 쓰는 곳 전부(AccessLogService) 변경이 필요했다.
- 사용자 없는 행(계정 없는 로그인 실패 등)은 유형 빈칸이고, 유형으로 거르면 빠진다(도움말에 적음).
