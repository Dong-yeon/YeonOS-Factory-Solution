## 1. 결론 먼저

- APS 1단계는 **"지금 지시들을 설비·근무조 용량 안에서 언제 어디서 만들 수 있나"** 를 계산해 **계획 버전**으로 남기고 **간트로 보여 주는 것**까지다. 지시(`prd_wo`·`prd_wo_proc`)는 **바꾸지 않는다**(시뮬레이션).
- 계획 버전 `aps_plan` = 한 번의 계산. **다시 계산하면 새 버전**이고, 결과(`aps_plan_wo`·`aps_plan_op`)는 계산하는 그 트랜잭션에서만 들어가고 그 뒤 바뀌지 않는다(추가만). 버전은 폐기만 된다. → 두 계획을 나란히 비교할 수 있고, "그때 계획" 이 덮어써지지 않는다.
- 스케줄 = **유한 용량 순방향(forward) 목록 스케줄링**: 규칙 하나(우선순위 → 납기 → 계획 시작일 → 지시 번호)로 지시를 줄 세우고, 지시마다 공정 순서대로, 공정마다 **가장 빨리 끝나는 자원**(그 작업장의 사용 중 설비)의 **근무조 시간 안 빈자리**에 넣는다. 공정은 근무 외 시간을 건너뛰어 다음 근무조로 이어진다.
- 화면 `aps-plan`(메뉴 "계획") = 계획 목록·새 계산 폼·요약 + **읽기 전용 간트**(자원 행 × 시간 축, 막대 위치는 JS 가 CSSOM `style.left/width` 로 — 인라인 style 속성 없음, CSP 유지) + 계획 못 한 공정·납기 늦음 목록.
- 계획을 지시 계획일·설비 배정에 **반영**하는 것은 **2단계**: APS 가 지시 표를 직접 쓰지 않고 MES 의 공개 서비스 메서드(일정 변경·설비 배정 — 3단계에 이미 있는 규칙)를 부른다. 지시 표에 시각 칸이 필요해지면 그것은 "남의 표 변경" 으로 MES 세션과 맞춘다(8장 A7).

## 3. 계산 규칙 (1단계)

### 3.1 입력 — 어떤 지시·공정을 계획하나

| 항목 | 규칙 |
|---|---|
| 지시 | 계획 공장의 `PLANNED`·`RELEASED`·`IN_PROGRESS` 지시 중 **계획 시작일 ≤ 계획 기간 마지막 날**(지난 지시·늦은 지시도 포함 — 밀린 일이 먼저 보인다) |
| 공정 | 발행된 지시(`RELEASED`·`IN_PROGRESS`)는 **스냅샷 `prd_wo_proc`**(배정 설비 포함), 계획 지시(`PLANNED`)는 지시가 가리키는 **확정 라우팅 단계 `mst_routing_step`**(확정본은 바뀌지 않는다 — docs/20 트리거). 상태 `DONE` 공정은 뺀다 |
| 잔량 | 공정마다 `계획 수량 − 그 공정의 순 양품`(`prd_result.good_qty` 합 — 역분개 행은 음수라 그대로 더한다), 0 이하이면 뺀다. `RUN`·`PAUSE` 공정은 이미 준비됐으므로 **준비 시간 0** |
| 작업 시간 | `준비(초) = ceil(setup_min × 60)`, `가공(초) = ceil(ceil(잔량 ÷ 사이클당 수량) × 표준 CT)`. 수량이 소수(KG)여도 사이클은 올림 |
| 외주 공정 | 작업장 없음(docs/20) → **무한 용량**, 기간 = 계획 매개변수 `outsrc_lead_hr`(기본 24, 달력 시간 — 근무조와 무관) |
| 범위 상한 | 계획 기간 1~31일, 지시 1,000건·공정 5,000개(넘으면 `APS_TOO_LARGE` — 기간이나 공장을 좁힌다) |

### 3.2 자원 — 공정을 어디서 하나

- 자원 = **설비**. 후보 = 공정 작업장(LINE·CELL) **과 그 아래 노드에 설치된 사용 중 설비**(LINE 공정은 아래 CELL 설비도 — POP 작업장 범위와 같은 규칙).
- 발행된 지시 공정에 **배정 설비**(`prd_wo_proc.equip_id`)가 있으면 그 설비만(사람이 정한 것을 존중).
- 작업장에 설비가 하나도 없으면 **작업장 자체를 자원 1개**로 본다(설비 등록 전인 공장도 계획이 나오게). 간트 행 이름에 "(작업장)" 표시.
- 후보가 여럿이면 **끝나는 시각이 가장 이른 설비**, 같으면 시작이 이른 설비, 그다음 설비 코드 순 — 결과가 실행마다 같다(결정적).

### 3.3 달력 — 언제 일할 수 있나

- 자원의 가용 시간 = 공장의 **사용 중 근무조**(`mst_shift`)를 계획 기간의 **매일** 펼친 것. 공장 시간대 = `sys_plant.time_zone`(없으면 회사 시간대, D5) — `BizClock.zone(plant)` 과 같은 해석.
- 근무조 [시작, 끝) — 끝 ≤ 시작이면 다음 날 끝(자정 넘김). 계획 기간 첫날 **전날** 시작한 야간조의 뒷부분도 포함한다.
- 휴식 `break_min` 은 위치가 정해져 있지 않으므로 **근무조 끝에서 뺀다**(보수적 — 근무조 안에 끝난다고 계획된 일은 실제로도 그 조 안에 끝난다, 8장 A3).
- DST: 현지 시각 → 순간은 `ZonedDateTime.of`(없는 시각은 뒤로 밀림, 겹치는 시각은 앞쪽) — 근무조 길이가 그날 하루만 23·25시간 기준으로 달라진다. 오류로 막지 않는다(달력은 사람이 입력한 시각이 아니므로 `DST_GAP` 를 쓰지 않음).
- 휴일·특근은 1단계에 없다 → 매일 같은 근무조(3단계 공장 달력, 8장 A4). 근무조가 하나도 없는 공장은 계산 거부(`APS_NO_SHIFT`).
- 계획 시작 순간 `sched_from` = max(계획 기간 첫날 00:00(공장 현지), 계산 시각). 과거에 일을 넣지 않는다. 계획 끝 `sched_to` = 마지막 날 다음 날 00:00.

### 3.4 순서 — 무엇을 먼저

규칙 하나 `PRIO_DUE`(8장 A2): **우선순위(1 급 → 9) → 납기(지시 계획 완료일) → 계획 시작일 → 지시 번호**. 지시를 이 순서로 하나씩, 그 지시의 공정을 순번 순서로 넣는다(앞 공정이 끝나야 다음 공정 — 이동·대기 시간 0).

- 지시의 **가장 이른 시작** = max(`sched_from`, 계획 시작일 00:00 현지) — 계획 시작일은 "자재가 준비되는 날" 로 본다.
- 공정 하나는 자원 하나에서 **근무 시간만 소비**하며 이어진다: 근무조 끝에 멈췄다가 다음 근무조에 이어 한다(중간에 다른 공정이 끼어들지 않는다).
- **빈자리 끼워 넣기**: 자원의 이미 잡힌 구간 사이라도 [시작, 끝] 이 다른 구간과 겹치지 않으면 넣는다(우선순위가 낮은 짧은 일이 앞의 빈 시간을 쓴다). 앞에 넣은 일을 밀어내지는 않는다.
- 늦음: 마지막 공정 끝 > 납기일 다음 날 00:00(현지) 이면 지시 `late_yn = Y`.

### 3.5 예외 — 계획 못 한 것

| 코드 | 뜻 | 그 지시의 뒤 공정 |
|---|---|---|
| `NO_CT` | 자체 공정인데 표준 CT 가 없다(확정 라우팅에서는 생기지 않지만 직접 SQL 방어) | `PREV` |
| `NO_NODE` | 자체 공정인데 작업장이 없다 | `PREV` |
| `HORIZON` | 계획 기간 안에 끝나지 않는다 | `PREV` |
| `PREV` | 앞 공정을 계획하지 못했다 | `PREV` |

예외 공정도 결과 행으로 남는다(시각 없음 + 예외 코드) — 화면 "계획 못 한 공정" 표.

## 4. 데이터 모델 (V052)

```text

               트리거: 새 행 = CALCULATED, 계산 칸 불변(상태·폐기 사유·비고·이름만), CALCULATED → DISCARDED 만, 삭제 금지

aps_plan_op    plan_op_id, comp_cd, plan_id, plan_wo_id, wo_id, wo_proc_id(발행 지시만), op_seq, proc_id·proc_cd·proc_nm,
               node_id, equip_id(작업장 자원이면 NULL), res_kind EQUIP/NODE/OUTSRC, qty(잔량), setup_sec, run_sec,
               start_at, end_at, exc_cd                                                               ← 추가만
```

| 규칙 | 내용 |
|---|---|
| 결과는 계산 트랜잭션에서만 | 결과 행 INSERT 트리거가 `계획.status = CALCULATED AND 계획.calculated_at = now()` 를 확인 — 지시 스냅샷(V033 `hb_guard_wo_snapshot`)과 같은 수법. 나중에 직접 SQL 로 결과를 덧붙이지 못한다 |
| 결과 불변 | `hb_forbid_update_delete()` + 앱 UPDATE·DELETE REVOKE. 감사 트리거 대신 행 자체가 계산 결과(`RetentionTest.AUDIT_EXEMPT` 에 근거) |
| 같은 회사 | 결과 행의 지시·설비·작업장·공정이 같은 회사인지 INSERT 트리거가 확인(FK 는 RLS 를 무시한다) |

## 10. 검토 (APS 하위 세션)

- **구현 중 바꾼 것**: 계획 머리에 계산 때 근무 구간 사본(`work_windows`) — 근무조를 나중에 고쳐도 간트 음영이 계산과 맞게. 외주(무한 용량) 행은 겹치는 막대를 줄로 나눠 그린다(브라우저 확인에서 발견). 마이그레이션 이름 가드가 세 자리만 받아 docs/29 임시 번호(`V9850`)와 충돌 → 가드가 `9xxx` 대역도 받게 — 같은 수정이 main 에 먼저 들어와 그것을 쓴다.

- **계획과 지시를 분리한 이유**: 지시 표는 MES 의 것이고 현장(POP)이 실시간으로 쓴다. 계산 결과를 바로 지시에 쓰면 시뮬레이션이 현장을 흔든다. 계획 버전을 따로 두면 "계산 → 사람이 보고 → 반영" 이 되고(AI 원칙 "제안·사람이 확정" 과 같은 모양), 반영 전 비교도 된다.
- **결과 불변의 비용**: 다시 계산할 때마다 행이 쌓인다(지시 1,000·공정 5,000 = 버전당 6천 행). 보존 정리는 3단계로 미뤘다(A9).
- **목록 스케줄링의 한계**: 최적해가 아니다(우선순위가 높은 지시가 먼저 자리를 잡는 탐욕 방식). 대신 결정적이고 설명 가능하다 — "왜 이 지시가 늦었나" 를 앞 지시의 막대로 보여 줄 수 있다. 최적화(제약 프로그래밍)는 이 결과를 출발점으로 쓰는 다음 단계 후보.
- **휴식을 조 끝에서 뺀 것**은 실제 휴식(점심) 위치와 다르다 — 막대가 점심시간을 지나가도 조 안 총 근무 시간은 맞는다. 휴식 위치가 필요하면 근무조에 휴식 구간 표(MES 소관)가 먼저다.

## 11. 2단계 — 반영·계획 비교 (V059)

### 11.1 결론 먼저

- **반영** = 고른 계산 계획(`CALCULATED`) 하나를 한 트랜잭션에서 지시에 옮긴다: 지시 계획 시작일·완료일(A14), 발행 지시 공정의 설비 배정(A16). APS 는 지시 표에 쓰지 않고 **MES 공개 서비스 메서드 `WoService.update`·`WoService.assign` 을 부른다** — 지시 상태별로 고칠 수 있는 칸·rowVer·기준정보 재확인·감사 이력이 MES 한 곳에 남는다(docs/39 10장의 "남의 리비전 확정은 공개 서비스로" 와 같은 원칙). 지시 표 변경(마이그레이션) 없음.
- **낡은 계획은 반영하지 않는다**(A12): 계산 때 읽은 지시·공정 `row_ver` 사본과 지금 값을 비교 + 계산 뒤 생긴 대상 지시 확인. 하나라도 어긋나면 409 `APS_PLAN_STALE` 에 지시 번호별 사유 — "다시 계산하세요".
- **반영 미리보기**(GET)는 실행과 같은 함수로 바뀔 값(지시별 시작·완료일 전후, 설비 전후)과 낡음 목록을 돌려준다. 실행(POST)은 미리보기를 믿지 않고 잠근 뒤 다시 계산한다.
- **비교**: 같은 공장 두 계획을 (지시, 공정 순번)으로 맞대어 시각 이동·자원 변경·계획 됨/빠짐을 보인다(A18). 읽기만.

### 11.2 반영 순서 (한 트랜잭션)

| # | 단계 | 실패 |
|---|---|---|
| 1 | 권한: 컨트롤러 `@ProgAuth(aps-plan, APPROVE)` + 서비스 `PermissionService.require(prd-wo, SAVE)`(A13) | 403 |
| 2 | 계획 행 `FOR UPDATE` → 상태 `CALCULATED`·rowVer | 400 `STATE` / 409 |
| 3 | 계획 끝(`sched_to`)이 지났으면 거부 — 계획 전체가 과거 | 400 `APS_EXPIRED` |
| 4 | 대상 지시 `FOR UPDATE`(번호 순 — 교착 방지) 후 낡음 판정: 지시 row_ver·발행 지시 공정 row_ver·사본 없음(1단계 계획)·새 대상 지시 | 409 `APS_PLAN_STALE`(rowKey = 지시 번호, 사유 `APS_WO_CHANGED`·`APS_PROC_CHANGED`·`APS_NEW_WO`·`APS_OLD_PLAN`) |
| 5 | 지시마다 바뀔 값 계산 — 같으면 건너뜀(row_ver 를 올리지 않는다) | |
| 6 | `WoService.update`(지금 칸 + 새 날짜, 사본 row_ver) → `WoService.assign`(설비 코드, 사본 proc row_ver). MES 검사 오류(예: 계획 지시의 라우팅이 새 시작일에 유효하지 않음 `STALE_REV`)는 **지시 번호를 rowKey 로 붙여** 다시 던진다 | 400/409 — 전부 취소 |
| 7 | 계획 `APPLIED` + `applied_at = now()`·`applied_by`·반영 지시 수·배정 공정 수 | |

- 요청 키(`claimRequestKey("APS_PLAN_APPLY")`) — 연타·재전송은 두 번째가 409 `DUPLICATE_REQUEST`. 같은 계획을 두 사람이 동시에 → 계획 행 잠금 뒤 두 번째는 상태 `STATE`.
- 계획 행 트리거(교체): 새 행 = `CALCULATED`·반영 칸 비움 / `CALCULATED → DISCARDED·APPLIED` 만 / `DISCARDED`·`APPLIED` 는 끝 / 반영 칸은 `APPLIED` 로 바뀌는 그 UPDATE 에서만, `applied_at = now()`.

### 11.3 데이터 변경 (V059 — 모두 APS 표, 남의 표 변경 없음)

| `aps_plan_wo` | `wo_row_ver`(계산 때 지시 row_ver) — 새 행 필수(`NOT VALID` CHECK — 1단계 행은 비어 있고 반영 불가) |
| `aps_plan_op` | `proc_row_ver`(발행 지시 공정이면 그 row_ver, 아니면 비움) — 새 행부터 `(wo_proc_id IS NULL) = (proc_row_ver IS NULL)` |

### 11.5 화면

- 상세 [반영 미리보기] → 아래 "반영 미리보기" 표(지시·시작일·완료일·설비 — 바뀌는 칸만 강조, 낡은 지시는 사유) → [반영](확인 창에 "지시 N건 일정 · 공정 M개 설비 · 완료일 밀림 K건"). 낡으면 [반영] 대신 "다시 계산하세요" 안내.
- [비교]: 같은 공장 다른 계획을 고르면 아래 "계획 비교" 표(구분·지시·공정·A 시작·B 시작·이동·자원 A → B), "바뀐 것만" 토글.
- 반영된 계획은 목록·요약 상태 "반영됨"(반영 시각·사람·건수), 폐기·반영 버튼 없음.

### 11.6 하지 않는 것 (2단계)

- 지시 일부만 고르기(A11), 반영 되돌리기(지시 감사 이력과 이전 계획 재반영으로 대신 — 이전 계획은 낡음 판정에 걸리므로 다시 계산), 지시 공정에 계획 시각 칸(A7 다른 안 — 남의 표 변경).

### 11.7 검토 (APS 하위 세션)

- **MES 메서드를 부르는 비용**: `WoService.update` 는 화면 폼 한 벌(수량·라우팅·BOM·수주 행)을 받으므로 APS 가 지금 값을 다시 채워 넘긴다 — 계획 지시는 라우팅·BOM 을 새 시작일 기준으로 MES 가 다시 확인한다(유효하지 않으면 반영 전체 취소, 지시 번호 표시). 날짜만 받는 좁은 메서드(`WoService.reschedule`)를 MES 에 새로 만드는 안은 MES 코드 변경이라 이번에는 하지 않았다 — 반영이 느리거나 폼 검증이 계속 걸리면 MES 세션과 맞춘다.
- **낡음 기준을 row_ver 로 둔 이유**: POP 착수(진행 중 전이)·설비 배정·일정 변경·완료가 모두 지시나 공정 row_ver 를 올린다. 실적 수량(잔량)만 바뀐 경우는 row_ver 가 그대로라 반영이 된다 — 반영하는 값은 날짜·설비뿐이고, 잔량 차이는 다음 계산이 바로잡는다.
- **늦은 지시를 그대로 반영(A15)**: 지시 완료일이 원래 납기 뒤로 가면 다음 계산에서 그 지시는 "늦음" 으로 보이지 않는다. 늦음의 기준(납기)은 수주 행 납기가 맞지만 1단계 규칙이 지시 완료일을 납기로 쓴다 — 수주 납기를 읽는 규칙은 3단계 규칙 추가(A2 다른 안) 후보.

## 12. 3단계 — 간트 수동 고정·수주 납기 (V064)

### 12.1 결론 먼저

- 계획 결과는 여전히 불변이다 — 사람은 **고정(`aps_pin`)** 을 남기고, **다음 계산**이 고정을 먼저 자리 잡게 한 뒤 나머지를 빈자리에 넣는다(A23). 고정은 지시를 바꾸지 않는다(반영은 2단계 그대로).
- 간트 막대를 다른 시각·다른 후보 자원 행으로 끌어 놓거나 키보드로 옮기면 고정이 저장된다(A24). 이미 고정한 공정은 같은 조작으로 고정을 옮긴다(rowVer).
- 늦음·규칙 순서의 납기를 수주 행 납기로 바꾼다(A21). 반영 미리보기의 지시 상태는 문구로.

### 12.2 데이터 (V064 — 모두 APS 표, 남의 표 변경 없음)

### 12.5 하지 않는 것

- 고정한 순간 다른 막대를 다시 계산해 보여 주기(즉시 재계산) — 고정 뒤 [계산] 으로 새 버전을 만든다(계획은 계산 결과만, A1).
- 고정 일괄 해제·고정 기간 만료, 자원만 고정(시각은 자유).

### 12.6 검토 (APS 하위 세션)

- **고정을 계획 행이 아니라 따로 둔 이유**: 계획은 계산 결과라 불변(A1) — 고정은 "사람이 정한 입력" 이므로 다음 계산의 입력 쪽에 둬야 버전마다 다시 고정하지 않는다.
- **앞 공정과 어긋난 고정을 버리지 않은 이유(A23 PIN_PREV)**: 고정은 대개 현장 사정(설비·사람·자재)을 아는 사람이 넣는다. 계산이 조용히 버리면 사람은 고정이 먹었다고 믿는다 — 그대로 두고 경고로 보이는 편이 "제안·사람이 확정" 원칙에 맞다. 대신 그 지시는 반영 때 그대로 들어가므로 미리보기에서 경고를 보고 판단한다.

## 13. 4단계 — 공장 휴일 달력 반영 (V087, 임시 V9853)

### 13.1 결론 먼저

- MES 가 만든 공장 휴일 달력(docs/25 4.15, `WorkCalendar`, V086)을 계산이 읽는다(A20·A25). 쉬는 날·근무조별 휴무·특근이 근무 구간에 들어가고, 쉬는 날에는 일이 잡히지 않는다(다음 근무일로 건너뜀).
- 휴일 판정 규칙(공장·근무조 > 공장 하루 > 회사 > 주간 정책 > 기본)은 MES 한 곳 — APS 는 결과(날마다 일하는 근무조)만 쓴다.
- 계산 때 쉬는 날을 계획 머리에 사본(`off_days`)으로 남겨 간트 날 머리에 "휴" 표시·사유(A26).
- **기존 결과 불변**: 정책 기본 NONE 이고 예외가 없으면 근무 구간이 1~3단계와 같다 — 같은 입력으로 옛 방식·새 방식 구간이 같은지 시험한다.

### 13.2 근무 구간 만들기

| 단계 | 규칙 |
|---|---|
| 1 | `WorkCalendar.range(공장, 첫날 − 2, 마지막 날)` — 작업일마다 일하는 근무조(작업일 기준) |
| 2 | 근무조마다 실제 시작일 = 작업일 − day_offset. 실제 시작일이 [첫날 − 1, 마지막 날] 인 것만(첫날 전날 시작한 야간조 뒷부분 포함 — 1단계와 같은 범위) |
| 3 | 시작일의 현지 시각 → 순간, 끝 ≤ 시작이면 다음 날 끝, 휴식은 끝에서 뺌, [sched_from, sched_to) 로 자르고 맞닿은 구간 합침(3.3 그대로) |
| 4 | 계획 기간 안 쉬는 날(`workday = false`)을 `off_days` 로 — 특근 근무조가 있는 날은 일하는 날 |

- "근무조 없음"(`APS_NO_SHIFT`)은 그대로 공장의 사용 중 근무조가 하나도 없을 때. 기간 전체가 휴일이면 계산은 되고 모든 공정이 `HORIZON`.
- 달력 읽기는 계산 트랜잭션(반복 읽기) 안 — 지시·공정과 같은 시점.

### 13.3 데이터 (V087 — APS 표만)

| 표 | 변경 |
|---|---|
| `aps_plan` | `off_days jsonb NOT NULL DEFAULT '[]'`(배열 CHECK), 계획 머리 트리거 교체 — `off_days` 도 계산 칸으로 고정 |

### 13.4 화면

- 간트 날 머리: 쉬는 날은 "휴" + 음영(근무 구간이 없으니 이미 근무 외 음영), 머리 칸 title 에 근거·사유.
- 요약에 "쉬는 날 N일".

### 13.5 검토 (APS 하위 세션)

- **day_offset 을 처음 쓰게 됨**: 1~3단계는 근무조를 달력 날짜마다 그대로 펼쳐 day_offset 을 볼 필요가 없었다. 달력은 작업일 기준이라 "작업일 D 의 3조(00~08)" 는 D+1 에 시작한다 — 이걸 놓치면 휴일 다음 날 새벽이 비거나 휴일 새벽에 일이 잡힌다(시험으로 고정).
- 회귀를 "같은 근무 구간" 으로 시험한 이유: 계산 결과 전체를 비교하면 시각(오늘·내일)에 따라 흔들린다. 근무 구간이 같으면 스케줄러는 같은 결과를 낸다(결정적, 1단계 시험).

## 14. 5단계 — 자재 가용 확인·결과 보존 정리 (설계, 결정 대기)

### 15.2 ① CTP 계산 (안)

1. 입력: 공장, 품목, 수량, (선택) 희망 납기, (선택) 우선순위 — 기본은 **맨 뒤**(지금 지시가 다 먼저 가진다). 첫날 = 회사 내일, 기간 = 최대 31일(계획과 같음).

- `ApsService.prepare()` — 계획 계산과 CTP 가 같은 입력(대상 지시·공정·고정·휴일 달력·자재·자원)을 쓰도록 계산 본체에서 떼어 냄(계산 결과 무변경 — 기존 APS 시험 그대로 통과). 가상 지시는 `Virtual(woIn, needs)` 로 받아 입력·자재 소요에 더한다.
- `ApsCtpService.answer()` — `@Transactional(readOnly = true, REPEATABLE_READ)`. 첫날 = 공장 시간대 오늘(지금 시각부터), 기간 기본 14일·최대 31일, 우선순위 없으면 10(지시 1~9 보다 뒤), 외주 리드타임 = 기본 24시간, 입고 예정 포함. 가상 지시 id = −1, 지시 번호 글자 `CTP`.

## 16. 7단계 — MPS 기준생산계획 (docs/62 A1, 결정 AP-1~4 · V232·임시 V9857)

> 상태: **구현(2026-11-03, V232·임시 V9857)** — 사용자 결정 AP-1(첫 범위 A1 MPS → A2 MRP → A3 실행 연결)·AP-2(일 단위, 화면 주 합계 접기)·AP-3(확정 구간 정책 N일, 기본 7일, 안은 사유 필수)·AP-4(계획 주문은 사람이 골라 지시·구매 요청으로)를 따른다. 이 장에서 새로 정할 것(M1~M8)은 **추천안으로 진행**하고 16.8 표에 남긴다(상위 세션에 같은 표를 보냄).
> 근거: 계획 계층·MPS 정의 docs/62 2장, MPS 격자·보충 계산 Odoo MPS(docs/63 [O-MPS]), 확정 구간·확정 SAP planning time fence·firming(docs/63 [SAP-PTF][SAP-FIRM]), 로트 규칙 SAP 로트 절차 EX·FX(docs/63 [SAP-LOT]), "예측과 수주 중 큰 쪽" 소진(APICS 계획 계층 — docs/62 9장 CPIM 자료).

### 16.1 결론 먼저

- **MPS = 공장 × MPS 품목 × 일** 격자. 칸마다 수요(수주 남은 수량 + 소진 뒤 남은 예측) − 공급(가용 재고 + 열린 지시 남은 수량) + 안전재고 → **제안 수량**(로트 규칙) → 사람이 **계획 수량**을 고친다 → **[확정]**.
- MPS 버전(`aps_mps`)은 계산할 때마다 새로(초안 `DRAFT`). 확정(`FIRMED`)은 **공장마다 하나**(= 현행 MPS), 새로 확정하면 이전 확정은 `SUPERSEDED`. 초안은 버릴 수 있다(`DISCARDED`). 결과 비교·"그때 계획" 보존은 1단계 계획 버전(A1)과 같은 이유.
- **확정 구간**(AP-3): 계산일(공장 오늘)부터 N일(정책 `APS_MPS_FENCE_DAYS`, 기본 7) 안 날짜의 계획 수량은 **현행 확정 MPS 값을 그대로** 가져온다(새 제안으로 바꾸지 않는다 — SAP 확정 구간과 같은 뜻). 초안에서 구간 안 수량을 바꾸면 칸마다 **사유 필수**.
- MPS 는 지시·구매 요청을 만들지 않는다(AP-4). 확정 MPS 는 다음 단계 MRP(A2)의 입력이고, 계획 주문 → 지시 변환은 A3.
- 지시·수주·내시·재고 표는 바꾸지 않는다. 수주·내시는 영업 읽기 계약에 메서드를 더해 읽는다(A28·A40 과 같은 방식).

### 16.3 계산 규칙

| 항목 | 규칙 |
|---|---|
| 대상 품목 | `aps_mps_item` 의 그 공장 **사용 중** 행. 품목은 회사에서 **한 공장의 MPS 에만**(M1 — 수주·내시에 공장 칸이 없어 수요를 나눌 기준이 없다). 조달 유형 `MAKE` 만(구매 품목은 MRP 몫) |
| 기간 | 첫날(기본 공장 오늘, 오늘보다 앞 불가) + 일수 7~92(기본 28). 칸 = 날짜(AP-2). 상한 품목 300 |
| 수요 — 수주 | 영업 계약 `OrderLineQuery.openLinesByItems`: OPEN 행, 남은 = 수량 − 출하 수량 > 0. 납기 < 첫날 → **첫날**(밀린 수요 `past_due_qty` 따로 표시), 납기 > 마지막 날 → 뺀다 |
| 수요 — 내시 | 영업 계약 `ForecastQuery.latestLines`: **거래처마다 최신 버전**(rev_no 최대)의 줄 중 예측 기간이 MPS 기간과 겹치는 것. 예측 기간 = [bucket_start, 다음 기간 시작) (DAY 1일·WEEK 7일·MONTH 1개월) |
| 소진(M3) | **거래처 × 품목 × 예측 기간**마다 남는 예측 = max(0, 예측 − 같은 거래처·품목의 그 기간 납기 수주 남은 수량). 즉 기간 수요 = max(예측, 수주) — APICS "큰 쪽" 규칙. 수주는 자기 납기일에, 남는 예측은 **기간 첫날**(MPS 첫날보다 앞이면 MPS 첫날)에 놓는다(M2 — SAP 기간 로트의 기본 소요일과 같은 쪽, 일찍 만들어 보수적). 기간이 첫날 전에 끝난 예측은 뺀다. `firm_yn` 은 7a 에서 같은 규칙 |
| 공급 — 재고 | WMS `StockQuery.available`(가용 정의 하나 — docs/53). **출하 예약은 빼지 않는다**(M7 — 예약은 이미 수주 남은 수량에 들어 있다) |
| 공급 — 지시 | 같은 공장 `PLANNED`·`RELEASED`·`IN_PROGRESS` 지시, 남은 = 계획 수량 − 생산 입고 순수량(`prd_receipt` 합, 역분개 행은 음수 그대로) > 0, 날짜 = 계획 완료일(첫날보다 앞이면 첫날 — 늦은 지시도 공급), 마지막 날 뒤는 뺀다(M6). 다른 공장 지시는 공급 아님. APS 는 1단계부터 지시·실적 표를 매퍼로 읽는다(6장) |
| 예상 재고(PAB) | pab(첫날 전) = 가용 재고, pab(d) = pab(d−1) + 지시 공급(d) + 계획(d) − 수요(d). 화면은 조회 때 계산(저장 안 함 — 계획 수량을 고치면 바로 다시 계산) |
| 제안(M4) | 부족 = 안전재고 − (pab(d−1) + 지시 공급(d) − 수요(d)). 부족 > 0 이면 로트 규칙: `EX` 그대로 / `FX` 로트 수량의 배수로 올림 / `MIN` max(부족, 로트 수량). 단위 자릿수로 올림. 계획(d) 이 정해진 뒤 다음 날을 계산한다(순서대로) |
| 확정 구간(AP-3, M5) | 구간 끝 = 계산일(공장 오늘) + N일(그날 미포함). 구간 안 날짜 d 는 **현행 확정 MPS 의 기간 안이면 그 값**(그 품목·날짜 칸이 없으면 0), 기간 밖이면 제안. 계산이 놓은 값 = 칸 `base_qty`, 구간 칸 `fenced_yn = Y`. 구간 안 칸의 제안은 참고로 남는다 |
| 결정성 | 품목 코드 순·날짜 순. 같은 입력 → 같은 결과(시험 — 계산 본체는 순수 클래스 `MpsCalculator`) |

## 17. 8단계 — 계획 기준정보·부족 → 구매 요청 초안 (docs/63 G1·G2·G9·G10, 결정 AP-6·AP-7·AP-12 · V252·임시 V9850)

> 상태: **구현(2026-11-09, 브랜치 `claude/aps-wave3`, V252·임시 V9850 — 병합 때 재번호)**. 근거 docs/63 4.1·10장(사용자 결정 AP-6~AP-12 추천 채택), 계획 계층 docs/62.
> 로트 크기·반올림 규칙은 SAP 로트 절차(docs/63 [SAP-LOT] — 로트 크기를 정한 뒤 반올림 값으로 올림), 부족 → 요청 초안은 Odoo 보충 보고서 [Order Once]·SAP MD04 의 구매 요청(docs/63 [O-RR][SAP-MD04]).

### 17.1 결론 먼저

- **계획 기준정보 = APS 표 `aps_item_param`(품목 × 공장) 하나**(AP-6): 안전재고, 로트 규칙(그대로 `EX` / 고정 `FX` / 최소 `MIN`) + 로트 수량, **배수**(`lot_mult` — 로트 규칙 뒤 올림), 자체 생산 리드타임(일), 확정 구간(일). 구매 리드타임·MOQ·배수는 SRM `srm_source` 를 **읽기만** 한다(중복 저장 안 함).
- **MPS(7단계)의 안전재고·로트 칸을 이 표로 옮긴다** — `aps_mps_item` 은 "MPS 대상 지정"(공장·품목·비고·사용)만 남기고, MPS 계산은 `aps_item_param` 을 읽는다. 같은 값이 두 표에 있으면 어느 쪽이 맞는지 설명할 수 없다(16.8 M4 가 "G1 의 일부" 로 미뤄 둔 것을 여기서 합침). 기존 값은 V9850 이 회사마다 옮긴다.
- **부족 → 구매 요청 초안**(G2, AP-7): 간트 화면 자재 표에서 부족 줄을 골라 [구매 요청 만들기] → 미리보기(품목별 부족 합 → MOQ·배수 올림, 필요일·발주 필요일) → [만들기] 가 **`PrService.create` 로 `srm_pr` DRAFT 한 건**. 계획 자재 줄 ↔ 요청 줄 연결은 **APS 표 `aps_plan_pr`**(SRM 표 무변경). **자동 생성 없음** — 사람이 고른 줄만(62 AP-4 와 같은 원칙).
- 반제품·외주(`MAKE`·`OUTSRC`) 부족은 요청을 만들지 않고 "지시 필요" 로만 표시한다(MRP 다단은 AP-8 — 다음 차수).
- **G9**: 계획 목록 조회 기본 기간 = 최근 30일. **G10**: 데모 시더 `ApsDemoFlow`(지시 30건·늦음·부족·병목).

|---|---|
| 로트 규칙은 **시스템 고정 값**(EX·FX·MIN, CHECK + 화면 i18n 문구) — 공통코드로 하지 않음 | 계산이 값마다 분기한다(`LotSizing`). 회사가 코드를 늘리면 계산이 모르는 값이 생긴다. 공통코드 전환 세션의 기준("회사가 늘리는 분류 = 공통코드, 코드 분기에 쓰는 값 = 시스템 고정")과 같은 쪽 |

| `pr_line_id` 에 FK 를 걸지 않음 | FK 를 걸면 SRM 의 작성 중 줄 삭제가 실패한다(남의 동작을 바꿈). 대신 "살아 있는 연결" 을 조회 때 판정(17.4) |

### 17.3 로트 크기 계산 (`LotSizing` — 순수 함수, MPS·G2 공용)

`size(need, rule, lotQty, mult, scale)`:

1. need ≤ 0 → 0.
2. `EX` q = need / `FX` q = ⌈need ÷ lotQty⌉ × lotQty / `MIN` q = max(need, lotQty).
3. mult 가 있으면 q = ⌈q ÷ mult⌉ × mult.
4. 단위 자릿수(scale)로 **올림**(모자라게 만들지 않는다).

G2 구매 수량은 `MIN`(lotQty = 주 공급원 `moq`, 없으면 `EX`) + mult = `order_mult` 로 같은 함수를 부른다. 예: 부족 1,234.5 KG, MOQ 2,000, 배수 500 → max = 2,000 → 2,000(500 의 배수) / 부족 2,100 → 2,100 → 2,500.

| 항목 | 규칙 |

| 입력 | 계획 id + 자재 줄 id 목록(1~200). 미리보기와 만들기가 같은 계산 |

| 저장 순서(한 트랜잭션) | 요청 키 `APS_PR_CREATE` → 계획 머리 `FOR UPDATE`(같은 계획 동시 요청 직렬화) → **다음 문장**에서 줄·연결 검사(잠금 문장 안 집계는 옛 스냅샷 — SKILL 2026-10 교훈) → `PrService.create`(자기 검사·채번·요청 키 `SRM_PR_CREATE`) → 요청 줄 읽기(줄 번호 = 넣은 순서) → `aps_plan_pr` 추가 |

| 화면 | 자재 표: 부족·BUY·연결 없는 줄에 고름 칸, 열 "구매 요청"(살아 있는 연결의 요청 번호, 반제품은 "지시 필요"). [구매 요청 만들기] → 대화상자 미리보기 표 → [만들기] → 요청 번호 안내. 목록 기본 기간 최근 30일(G9) |

### 17.8 검토 (APS 하위 세션)

- `aps_mps_item` 칸을 지우는 것은 7단계를 고치는 일이지만 같은 APS 표이고, 남겨 두면 "MPS 품목의 안전재고 vs 계획 기준정보의 안전재고" 가 어긋날 수 있다(조용히 틀림). 옮기기는 회사마다 범위를 열고(V185 수법), 같은 공장·품목에 행이 둘 이상이면(사용 중지 이력) 사용 중 → 최근 수정 순으로 하나만.
- 공급원은 공장 칸이 없다(`srm_source` 는 회사 × 협력사 × 품목) — 공장별 구매 조건이 필요해지면 SRM 쪽 결정.

## 18. 9단계 — 현행 계획·확정 구간(G6) → 일일 작업 배정(G5) (docs/63 결정 AP-10·AP-11 · V260·임시 V9850)

> 상태: **구현(2026-11-10, 브랜치 `claude/aps-wave4`, V260·임시 V9850 — 병합 때 재번호)**. 근거 docs/63 4.1 G5·G6, 10장(AP-10 ⓐ 읽기 계약·순서 어김은 표시만, AP-11 공장 정책 기본 2일 + G1 품목별 값 우선).
> 레퍼런스: 확정 구간 = SAP planning time fence·firming(docs/63 [SAP-PTF][SAP-FIRM]), 일일 배정 = SAP CM25 디스패치·Odoo 작업장 작업 목록(docs/63 [SAP-CRP][O-WC]).

### 18.1 결론 먼저

- **현행 계획** = 공장마다 **마지막으로 반영된 계획**(`APPLIED` 중 `applied_at` 최신) 하나. 따로 칸을 두지 않고 반영 기록에서 정한다 — 반영은 이미 한 트랜잭션·계획 잠금·불변 결과라 "현행" 을 다시 저장하면 두 곳이 어긋날 수 있다. 목록·요약에 "현행" 표시, 보존 정리는 반영 계획 결과를 이미 남긴다(14.4).
- **확정 구간**(AP-11): 구간 끝 = 공장 오늘 + N일(그날 미포함). N = 그 지시 품목의 계획 기준정보 `fence_days`(G1, 사용 중 행) → 없으면 공장 정책 `APS_FENCE_DAYS`(기본 2, 0~60). **지금 지시 계획 시작일이 구간 안이면 반영이 그 지시의 날짜·설비를 바꾸지 않는다** — 미리보기에 "확정 구간 — 그대로" 로 따로 보인다. 바꾸려면 그 지시 공정에 **사유(비고)를 적은 고정**(12장 `aps_pin`)을 두고 다시 계산 → 그 계획의 공정이 사유 있는 고정을 썼으면 구간 안이어도 반영한다.
- 구간 밖 지시가 계획으로 구간 **안으로 당겨지는 것**은 막지 않는다(SAP 도 구간은 이미 있는 주문을 지킨다).
- **일일 작업 배정**(G5, AP-10 ⓐ): APS 읽기 계약 **`ApsDispatchQuery`**(`module.aps.link`) — 현행 계획 결과에서 그날(공장 현지) 시작하는 공정을 **자원별 순서·계획 시각**으로 준다. POP 정렬은 MES 세션이 이 계약을 불러 붙인다(APS 는 POP 매퍼를 고치지 않는다). APS 화면에는 **배정표**(공장·날짜, 자원별 순번·시각·지시·공정·지금 공정 상태, 인쇄)를 둔다.
- **순서 어김은 표시만**(AP-10): 같은 자원에서 앞 순번이 아직 대기인데 뒤 순번이 이미 착수(RUN·PAUSE·DONE)했으면 뒤 행에 "순서 어김". 막지 않는다.

### 18.2 데이터 (V260·임시 V9850 — APS 표·정책만, 남의 표 변경 없음)

| 대상 | 내용 |
|---|---|
| `sys_policy_def` | `APS_FENCE_DAYS`(INT, 기본 2, 0~60) — 공장 값 → 회사 값 → 기본(PolicyService) |
| `aps_plan` | 인덱스 `ix_aps_plan_applied (comp_cd, plant_cd, applied_at DESC) WHERE status = 'APPLIED'` — 현행 계획 찾기 |

칸 추가 없음. 고정 사유는 기존 `aps_pin.remark`.

### 18.3 반영 규칙 추가 (11.2 의 5단계에 끼움)

| 항목 | 규칙 |
|---|---|
| 구간 일수 | 지시 품목 × 공장의 `aps_item_param.fence_days`(사용 중) → 없으면 `APS_FENCE_DAYS`(지시 공장). 0 = 구간 없음 |
| 구간 안 | 지금 지시 `plan_start` < 공장 오늘 + 일수. 진행 중 지시는 시작일이 지났으니 늘 구간 안 |
| 사유 있는 고정 | 이 계획에서 그 지시의 공정 중 하나라도 `pin_id` 가 있고 그 고정의 `remark` 가 공백 아님 → 구간 무시 |
| 결과 | 구간 안 + 사유 고정 없음 + 바뀔 값이 있음 → 바꾸지 않고 미리보기 `fenced` 목록(지시·지금 시작·계획 시작·구간 일수). 반영 지시·공정 수에 안 셈 |
| 낡음 | 구간 판정과 무관 — 낡은 계획은 그대로 거부(11.2) |

### 18.4 `ApsDispatchQuery` (읽기 계약 — 트랜잭션 안, 읽기 전용)

```text
record Slot(long planId, String planNo, int seq, String resKind, Long equipId, String equipCd, Long nodeId, String nodeCd,
            long woId, String woNo, Long woProcId, int opSeq, String procCd, OffsetDateTime startAt, OffsetDateTime endAt)
List<Slot> sequence(String plantCd, LocalDate day)          — 그날 [00:00, 다음날 00:00)(공장 시간대) 시작 공정, 자원(설비 → 작업장 → 외주, 코드 순) × 시작 순, seq = 자원 안 1부터
Map<Long, Slot> slots(String plantCd, Collection<Long> woProcIds) — 현행 계획에서 그 지시 공정들의 자리(POP 목록 정렬용, 최대 500)
NONE — APS 가 없는 설치본은 빈 결과
```

- 현행 계획이 없으면 빈 결과. 다른 회사·공장은 안 나온다(RLS + 공장 조건).
- 계획 공정의 순서·시각은 **계산 때 값**이다(반영이 지시 날짜·설비를 옮기지만 시각 칸은 MES 에 없다 — A7). 반영 뒤 사람이 지시를 바꾸면 다음 계산·반영까지 배정표와 다를 수 있다 → 배정표에 지금 공정 상태·설비를 함께 보여 준다.

### 18.7 검토 (APS 하위 세션)

- 구간 판정을 **지금 지시 시작일** 기준으로 둔 이유: 현장이 이미 준비(자재 불출·작업자 배치)를 시작한 것은 지금 일정이다. 계획 시작일 기준이면 구간 밖으로 밀어내는 변경을 막지 못한다.
- 품목별 구간 값이 공장 정책보다 우선(AP-11)이라 계획 기준정보 화면의 "확정 구간(일)" 이 이제 실제로 쓰인다(17장에서는 저장만).

## 19. 10단계 — MRP 자재소요계획 (docs/62 A2 + docs/63 G3·G7, 결정 AP-1·AP-4·AP-8 · V263·임시 V9850)

> 상태: **설계 → 구현(2026-11-10, 브랜치 `claude/aps-wave5`, V263·임시 V9850 — 병합 때 재번호)**. 근거: docs/62 10장 AP-1(A1 MPS → **A2 MRP** → A3), AP-4(계획 주문은 사람이 골라 지시·구매 요청으로 — **자동 생성 안 함**), docs/63 10장 AP-8(다단 소요 G3 는 MRP 와 함께, 전개 엔진 하나), 4.2 메모(로트 EX·FX·최소·배수, 페깅 = 계획 주문 → 수주 행·내시 줄·상위 지시), G7(재일정 예외 메시지).
> 레퍼런스: 순소요·로트·리드타임 역산·저차 코드(low-level code) = APICS/ASCM CPIM MRP(docs/62 9장), 재고/소요 목록·예외 메시지(10 당김·15 밀기·20 취소) = SAP MD04·예외 모니터(docs/63 [SAP-MD04][SAP-EXC]), 로트 절차 = [SAP-LOT], "기존 공급을 먼저 당겨 쓴다(재일정 가정)" = SAP 재일정 검사·CPIM 의 scheduled receipt 규칙.
> 이 장에서 새로 정하는 것(R1~R10)은 **추천안으로 구현**하고, 사용자가 정해야 할 것(19.9 Q1~Q4)은 **구현하지 않고 질문으로** 남긴다.

### 19.1 결론 먼저

- **MRP 실행** = 공장 하나 × 기간(첫날 = 공장 오늘, 7~92일, 기본 28). 입력은 **현행 확정 MPS**(16장) + 열린 지시의 남은 자재 소요 + 계획 기준정보(17장)의 안전재고. 계산마다 **새 실행 기록**(`aps_mrp`, 추가만 — 1단계 계획 버전과 같은 이유: "그때 무엇을 왜 제안했나" 를 남긴다).
- **전개 엔진 하나**(AP-8): 품목을 **저차 코드(LLC) 순**으로 한 번씩 순소요 → 로트 → 리드타임 역산 → **계획 주문** → 그 계획 주문을 시작일 BOM 으로 전개해 자품목 소요 → 다음 단계. BOM 한 단 전개는 **MES 계약 `WoMaterialQuery.explode`**(지시 발행과 같은 전개 — 유효 리비전·손실률·고정 수량·대체 비율·가상 조립 통과)만 쓴다. 전개 규칙을 APS 에 다시 쓰지 않는다.
- **계획 주문은 제안일 뿐**(AP-4): 지시·구매 요청을 만들지 않는다. 고른 계획 주문 → 지시(`WoService.create`)·구매 요청(`PrService.create`, G2 와 같은 길)은 **A3**(다음 단계).
- **페깅**: 공급 한 줄 ↔ 수요 한 줄 연결(수량)을 저장 → 어느 계획 주문이든 위로 따라가면 **수주 행·내시 줄**(MPS 품목) 또는 **상위 지시**(열린 지시의 남은 소요)에 닿는다.
- **예외 메시지**(G7): 열린 지시·발주가 수요보다 늦으면 **당김**, 너무 이르면 **밀기**, 쓸 곳이 없으면 **취소**·남으면 **줄임**, 계획 주문 시작일이 오늘보다 앞이면 **늦음(리드타임 부족)**. 데이터 문제(리드타임 미정·공급원 없음·전개 실패·단위 환산 없음)도 같은 표에 — 조용히 0 으로 계산하지 않는다.
- 지시·발주·수주·내시·재고·BOM 표는 **읽기만**(계약). 남의 표 변경 없음.

### 19.3 대상 품목과 수요·공급

| 항목 | 규칙 |
|---|---|
| MPS 품목 | 현행 확정 MPS(`aps_mps` FIRMED, 그 공장)의 행 품목. 확정 MPS 가 없으면 MPS 품목 없음(실행 머리 `mps_id` 비움 — 화면 경고) |
| 계획 품목 | MPS 품목 + 그 자품목(전개로 닿는 것 전부) + 열린 지시의 자재 품목 + **그 공장 계획 기준정보 사용 중 행 품목**(안전재고만 있어도 계획 — R1) |
| 독립 수요(R2) | **확정 MPS 계획 수량만**(칸 `plan_qty`, 날짜 = 칸 날짜 = 완성일). MPS 가 이미 수주·내시·재고·지시를 계산했다(16.3). MPS 밖 품목의 수주는 넣지 않는다 — Q1 |
| MPS 품목 처리(R3) | MRP 가 **다시 순소요하지 않는다**: 확정 MPS 칸 하나 = 계획 주문 하나(종류 `MPS`, 수량·날짜 그대로, 시작일 = 날짜 − 자체 생산 리드타임). 바꾸려면 MPS 를 고쳐 다시 확정. 첫날 전 칸의 계획은 넣지 않고 예외 `MPS_PAST`(수량 합). MPS 품목이 다른 품목의 자품목으로 쓰이면 그 소요는 계획하지 않고 예외 `MPS_DEP`(MPS 에 반영 필요) |
| 종속 수요 — 계획 주문 | 계획 주문(MPS·PLAN)마다 `explode(품목, 수량, 시작일)` → 자품목 소요(자품목 기본 단위). 날짜 = 부모 시작일(첫날보다 앞이면 첫날 + 밀림 표시). 종류 `DEP`, 부모 요소를 기억(페깅 위로) |
| 종속 수요 — 열린 지시 | 그 공장 `PLANNED`·`RELEASED`·`IN_PROGRESS` 지시의 남은 소요(`WoMaterialQuery.remaining` — 투입 순수량 뺀 값). 날짜 = 지시 계획 시작일(지난 날짜는 첫날 + 밀림). 종류 `WODEP`, 지시 번호. 전개 안 된 지시는 예외 `NO_BOM` |
| 안전재고(R4) | 계획 기준정보 `safety_qty` > 0 이면 첫날 수요 한 줄(종류 `SAFE`). 같은 날 다른 수요 뒤에 배정(페깅이 실수요부터). MPS 품목은 MPS 가 이미 넣었으니 없음 |
| 공급 — 재고 | WMS `StockQuery.available`(가용 정의 하나 — docs/53), 첫날, 종류 `STOCK`. 출하 예약은 빼지 않는다(16.8 M7 과 같음) |
| 공급 — 지시 | 같은 공장 열린 지시의 남은 수량(계획 수량 − 생산 입고 순수량, 16.3 M6), 날짜 = 계획 완료일(지난 날짜는 첫날), 종류 `WO` |
| 공급 — 발주 | SRM `PoSupplyQuery.open(공장, 품목, 마지막 날)`(ASN 도착 예정 → 회신 약속 → 요구 납기, docs/31 4.8). 날짜 지난 줄은 첫날. 기본 단위로 바꿀 수 없는 줄(`inBaseUnit = false`)은 빼고 예외 `UNIT`. 종류 `PO` |
| 기간 밖 | 마지막 날 뒤의 수요·공급은 넣지 않는다. 계획 주문의 종속 수요는 부모 시작일이라 기간 안 |

### 19.4 순소요·로트·리드타임 (품목 하나, LLC 순)

| 단계 | 규칙 |
|---|---|
| 정렬 | 수요 = 날짜 → 종류(실수요 → `SAFE`) → 요소 번호. 공급 = `STOCK` → 날짜 → 요소 번호 |
| 재일정 가정(R5) | 수요를 날짜 순으로 **기존 공급(재고·지시·발주)부터 앞에서 차감한다 — 공급 날짜가 수요보다 늦어도 당겨 쓴다고 본다**(SAP 재일정 검사·CPIM scheduled receipt 규칙). 그렇게 쓴 늦은 공급은 예외 "당김" 으로 알린다(19.6). 기존 공급을 다 쓴 뒤에만 계획 주문을 만든다 — 1일 늦은 발주 때문에 새 계획 주문이 생기고 그 발주가 "취소" 로 뜨는 잘못된 제안을 막는다 |
| 순소요 | 같은 날짜의 수요 중 기존 공급·앞 계획 주문 남는 양으로 못 덮은 양의 합 = 그날 순소요 |
| 계획 주문(R6) | 순소요 > 0 인 날마다 **한 건**: 수량 = 로트(아래), 완료일(필요일) = 그 날짜, **시작일 = 완료일 − 리드타임(달력 일)**. 로트로 남는 양은 다음 수요가 먼저 쓴다 |
| 로트 — MAKE·OUTSRC | `LotSizing.size(순소요, lot_rule, lot_qty, lot_mult, 단위 자릿수)`(17.3 — EX 그대로 / FX 배수 올림 / MIN 최소 → 배수 → 자릿수 올림). 기준정보 행이 없으면 EX |
| 로트 — BUY(R7) | 위와 같이 기준정보 로트를 먼저, 그다음 **주 공급원**(17.4 와 같은 고르기)의 MOQ·발주 배수: `size(q, MIN, moq, order_mult)`. 예: 순소요 130, 기준정보 EX, MOQ 100·배수 50 → 130 → 150 |
| 리드타임 | MAKE·OUTSRC = 기준정보 `make_lead_days`(비움 → 0일 + 예외 `NO_LEAD`). BUY = 주 공급원 `lead_days`(공급원 없음 → 0일, MOQ·배수 없음 + 예외 `NO_SOURCE`) |
| 늦음 | 시작일 < 공장 오늘 → 계획 주문에 늦음 표시 + 예외 `START_PAST`(시작일은 그대로 — 며칠 모자란지 보이게) |
| 전개 | MAKE·OUTSRC 계획 주문만 전개(BUY 는 안 함). 전개 날짜 = max(시작일, 첫날). 전개 실패(환산·가상 조립 BOM 없음 — `exploded = false`) → 자품목 소요 없음 + 예외 `NO_BOM`. BOM 없음은 소요 없음(원자재처럼 만드는 품목) |
| 저차 코드(R8) | 계산 전에 계획 품목을 첫날 BOM(`explode(품목, 1, 첫날)`)으로 훑어 LLC = 가장 깊은 단계. 계산 중 다른 날짜 BOM 에서 새 자품목이나 더 깊은 단계가 나오면 LLC 를 올리고 **처음부터 다시 계산**(전개 결과는 캐시 — DB 를 다시 읽지 않음). 다시 계산 10번·단계 30 을 넘으면 400 `APS_MRP_BOM_LOOP`(순환 BOM) |
| 상한 | 계획 품목 2,000, 요소 50,000, 계획 주문 10,000 — 넘으면 400 `APS_TOO_LARGE` |
| 결정성 | 품목 = LLC → 품목 코드 순, 같은 입력 → 같은 결과(엔진은 DB·시각 없는 순수 클래스 — 시험이 그대로 부른다) |

### 19.5 페깅 (②)

- 차감할 때마다 **페깅 한 줄**(수요 요소 ↔ 공급 요소, 수량)을 남긴다. 위로 따라가기 = 계획 주문(공급) → 그것이 덮은 수요(`DEP`) → 그 수요의 부모 계획 주문 → … → 독립 수요 / 상위 지시(`WODEP`) / 안전재고(`SAFE`).
- **MPS 품목은 페깅만 한 번 더**(R9): MRP 가 순소요하지 않지만 페깅을 수주·내시 줄까지 잇기 위해, MPS 와 **같은 수요 규칙**(16.3 — 수주 남은 수량은 납기일, 내시는 거래처 × 기간 소진 뒤 남은 양을 기간 첫날)으로 수요 요소 `SO`(수주 행)·`FC`(내시 줄)를 만들고, 공급(재고 → 열린 지시 → MPS 계획 주문)을 같은 차감으로 페깅한다. 남는 수요는 예외 `MPS_SHORT`("MPS 를 다시 계산" — 확정 뒤 수주가 늘었다). 소진 식은 MPS 계산(`MpsCalculator`)의 것을 함께 쓴다(두 곳에 다시 쓰지 않음). MPS 품목의 재고·지시는 이 페깅에만 쓰고 G7 대상이 아니다(MPS 화면 몫).
- 화면: 요소 하나 → 위로 사슬(최대 30단계, 갈라지면 전부 — 한 계획 주문이 여러 수요를 덮는다).

### 19.6 예외 메시지 (③, G7)

| 코드 | 대상 | 판정 | 제안 |
|---|---|---|---|
| `RESCHED_IN` 당김 | 열린 지시·발주 | 페깅된 **실수요**(`SAFE` 아님) 중 가장 이른 날짜 < 공급 날짜 | 제안일 = 그 수요 날짜 |
| `RESCHED_OUT` 밀기 | 열린 지시·발주 | 가장 이른 실수요 날짜 > 공급 날짜 + 허용 일수(정책 `APS_MRP_OUT_DAYS`, 기본 3, 0~60 — R10) | 제안일 = 그 수요 날짜 |
| `CANCEL` 취소 | 열린 지시·발주 | 페깅이 하나도 없음(실수요·안전재고 모두) | 수량 = 남은 수량 |
| `REDUCE` 줄임 | 열린 지시·발주 | 일부만 페깅 | 수량 = 남는 양 |
| `START_PAST` 늦음 | 계획 주문 | 시작일 < 오늘 | 제안일 = 오늘(그때 시작하면 완료 = 오늘 + 리드타임) |
| `NO_LEAD`·`NO_SOURCE`·`NO_BOM`·`UNIT` | 품목·지시·발주 | 19.3·19.4 | 데이터 정비 |
| `MPS_PAST`·`MPS_DEP`·`MPS_SHORT` | MPS 품목 | 19.3·19.5 | MPS 다시 계산·확정 |

- 재고(`STOCK`)는 예외 대상이 아니다. 안전재고만 덮는 공급은 당김·밀기 대상이 아니다(안전재고는 완충 — 날짜가 없다).
- 예외는 **알림만** — 지시·발주 날짜를 바꾸지 않는다(사람이 지시·발주 화면에서).

### 19.10 손 검산 예 (시험 `MrpEngineTest` 와 같은 수)

공장 오늘 = 첫날 D0, 기간 14일. BOM: 완제품 **A**(MPS) = 반제품 **B** 2 + 원자재 **D** 1, **B** = 원자재 **C** 3. A 자체 생산 1일, B 자체 생산 2일·FX 50·재고 10, C 구매(공급원 리드 3일·MOQ 100·배수 50)·안전재고 20·재고 30, D 구매(공급원 없음).

| 품목(LLC) | 계산 | 결과 |
|---|---|---|
| A(0) | 확정 MPS 칸 D5 = 40 → 계획 주문 MPS 40, 완료 D5·시작 D4 | 종속: B 80 @D4, D 40 @D4 |
| B(1) | 수요 80 @D4 − 재고 10 = 70 → FX 50 → 100, 완료 D4·시작 D2 | 종속: C 300 @D2 |
| C(2) | 안전 20 @D0 + 수요 300 @D2. 재고 30 → 안전 20·D2 에 10 → D2 순소요 290 → MIN 100 → 배수 50 → **300**, 완료 D2·시작 D-1 | **늦음** `START_PAST`(제안일 D0), 끝 예상 재고 30(= 안전 20 + 10) |
| D(1) | 40 @D4 → EX 40, 공급원 없음 → 리드 0, 시작 D4, `NO_SOURCE` | |

주: 수요 정렬은 **날짜 먼저**(같은 날이면 실수요 → 안전재고)라 첫날 안전재고가 재고를 먼저 쓴다 — 예상 재고가 안전재고 밑으로 내려가지 않게 하는 식(MPS 16.3 과 같은 뜻).

### 19.11 하지 않는 것 (10단계)

- 계획 주문 → 지시·구매 요청(A3 — 다음 단계), 자동 생성(AP-4), MPS 밖 수주 수요(Q1), 근무일 리드타임(Q2), 밤 자동 실행(Q3).
- 라우팅으로 자체 생산 리드타임 추정(V252 칸 주석의 "다음 차수") — 비우면 0일 + `NO_LEAD` 로 드러낸다.
- 기간 로트(주·월 묶음 TB·WB·MB), 재일정 범위(먼 미래 공급은 당기지 않기), 공급원 여럿 나눠 사기, 공장 간 이동.
- 상세 일정(1~9단계)의 자재 가용 확인 `MaterialPlanner` 는 그대로 1단 — 이미 있는 지시를 유한 용량으로 순서 짓는 쪽이고, 다단 소요는 이 엔진 하나가 맡는다(AP-8).

### 19.12 구현 메모 (APS 하위 세션, 2026-11-10)

- 엔진 `MrpEngine`(순수) — 입력·결과 레코드, `levels`(저차 코드, 순환 30 단계에서 `Loop`), `run`(품목 순회), `lot`(BUY = 기준정보 로트 → MOQ·배수), `pab`. 다른 날짜 BOM 에서 새 자품목·같거나 얕은 단계 연결이 나오면 끝까지 돈 뒤 `Restart`(연결·모르는 품목) → 서비스가 훑기·LLC 를 다시 하고 처음부터(전개 캐시 유지, 10번 넘으면 `APS_MRP_BOM_LOOP`).
- 서비스 `MrpService.Calc` — 확정 MPS 칸(`aps_mps_cell`), 열린 지시(`prd_wo` + `prd_receipt` — MPS 와 같은 읽기), `WoMaterialQuery.remaining`(500건씩)·`explode`, `StockQuery.available`, `PoSupplyQuery.open`, 주 공급원은 G2 의 `ApsPrMapper.findSources`(한 정의 — `cust_id` 칸만 더함), MPS 품목 수요는 `OrderLineQuery`·`ForecastQuery` + `MpsCalculator.residual`(소진 식을 MPS 와 함께 씀).
- 저장 순서: 엔진 → 채번 → 머리(개수 포함) → 품목·요소(부모 번호가 앞이라 자기 참조 FK 가 문장 안에서 맞음)·페깅·예외를 500행씩.
- 요소 번호(`elem_seq`)는 실행 안 번호 — 페깅·부모·예외가 이 번호로 잇는다(삽입 순서가 돌려준 id 순서에 기대지 않는다).
- 화면 선택지(종류 MPS·PLAN)는 시스템 고정 — 공통코드 그룹과 겹치지 않는다(선택지 가드 통과).
