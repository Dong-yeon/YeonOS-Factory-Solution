작성 2026-11-02 (MES 하위 세션). 사용자 요청(상위 병합 세션 경유): "BOM 관리 쪽을 좀 더 개선하고 싶다 — BOM 관리, 전개 조회, 역전개 조회, 일괄 대체 화면".
**1단계 = 분석만, 코드 수정 없음.** 이 문서는 **실측 → docs/18 대비 구현 상태 → 7장 재검토 → 화면별 개선 후보 → 우선순위 → 결정 요청** 순서다. 사용자가 고른 뒤 2단계(구현)를 따로 배정받는다.
표기: [실측] 이 문서의 브라우저·API 측정 · [코드] 저장소 코드 확인(파일:줄) · [원문]/[검색] 레퍼런스(출처 번호는 docs/18 9장, 새 출처는 이 문서 9장) · [추정] 판단.

## 1. 결론 먼저

1. **속도는 문제가 아니다.** 10레벨 × 1,000행 구조(전개 1,100행)에서 전개 API 126ms·화면까지 233ms, 역전개 1,100행 224~263ms, 엑셀 1.3초, 일괄 대체 미리보기 100곳 0.6~0.8초·실행 1.4초 [실측]. docs/18 10장 QA 수정(창 렌더·재귀 상한)이 효과를 냈다.
2. **불편은 "많을 때"와 "이어서 할 때"에 몰려 있다.**
   - 행 200개 BOM 편집 화면이 입력칸 2,800개·세로 10,394px(390 에서 19,994px). [행 저장]이 맨 아래에 있고, [더보기]·[삭제] 한 번에 200행을 다시 그려 포커스를 잃는다 [실측].
   - 일괄 대체로 작성 중 리비전 100개를 만든 뒤 **확정은 BOM 관리에서 한 건씩**(행 고르기 → [확정] → 확인 = 약 300번 누름). 변경 번호·사유도 일괄 대체 화면에서 넣을 수 없다 [실측·코드].
   - 네 화면 사이에 **바로가기가 없다**(전개 행 → 역전개·관리, 대체 결과 → 관리). 공통 링크 경로(`q.*`·셸 `open`)는 이미 있는데 전개·역전개는 링크로 열면 **조건만 채우고 조회하지 않는다** [실측].
3. **바로 고칠 결함 3건**(작음, 결정 불필요):
   - **D1 [새 리비전] 칸을 비우고 [만들기] → 아무 일도 없이 닫힘**(안내문은 "비우면 자동"). 원인은 공통 `hb.dialog.prompt` 가 "비운 값"과 "취소"를 둘 다 `null` 로 돌려주는 것 — 같은 모양이 라우팅 새 리비전·설비 자산 해체 시각·LOT 재작업 수량에도 있다(4곳) [실측·코드].
   - **D2 깊은 레벨에서 자품목 코드와 레벨 숫자가 잘림**(8레벨부터 레벨 칸이 "……", 10레벨은 코드가 "…") — 10레벨 BOM 을 보는 화면에서 정작 깊은 쪽을 못 읽는다 [실측].
   - **D3 엑셀이 화면과 다름**: 역전개 "최상위"가 `false`/`true` 글자로, 레벨이 "`. . 3`" 글자(숫자 정렬·필터 불가) [실측]. (출력 정보 시트에 조건 값이 없는 것은 결함이 아니라 플랫폼의 의도된 설계 — `ExcelExportService.java:84` "조건 키 목록(값 제외)" — 그래서 결정 G8 로 따로 묻는다.)
4. **추천 1순위 = "대량 작업 흐름" 묶음**(일괄 대체 → 결과에서 바로 일괄 확정 + 변경 번호·사유, 네 화면 바로가기, D1~D3). 마이그레이션 없음, 사용자 결정 2건(일괄 확정 범위·권한). 2순위 = 행 편집 개선(찾기·붙여넣기·고정 도구줄·부분 다시 그리기), 3순위 = 전개 표 보강(레벨 숫자 열·경로·유효기간·하위 리비전 상태 표시, 비교 "바뀐 것만").

### 2.3 현장 사용자 관점에서 본 것 (클릭·키보드·빈 상태·오류)

**전개 조회(`mst-bom-tree`)**
- 키보드: 처음 포커스 = 모품목 코드, Enter = 조회. 소문자 입력도 찾는다(`zt-bproot` → `ZT-BPROOT`) [실측]. 좋음.
- 품목을 **코드로만** 찾는다 — 이름으로 찾기·고르기 없음. 없는 코드 → 상단 "입력값이 올바르지 않습니다."(칸 오류는 "대상을 찾을 수 없습니다. 다시 조회해 주세요." — 품목이 없다는 뜻이 바로 안 읽힘) [실측].
- 확정 BOM 이 없는 품목 → "ZT-BW001 의 2026-11-02 기준 유효한 확정 BOM 이 없습니다. 기준일을 바꾸거나 BOM 관리에서 확정해 주세요." — 문구는 좋은데 **BOM 관리로 가는 바로가기가 없다**.
- 기준일 칸은 비어 보이고(`mm/dd/yyyy`) 결과 요약에야 "기준일 2026-11-02" 가 나온다. 비우면 오늘이라는 표시가 칸에 없다.
- **깊은 레벨이 잘린다(D2)**: 레벨 칸이 "`. . . 4`" 처럼 점을 레벨만큼 붙여 8레벨부터 숫자가 안 보이고, 코드 칸은 들여쓰기(레벨당 16px)에 밀려 10레벨이 "…" [실측 — 스크린숏 `tree-multi-1366`].
- 행을 눌러도 아무 일 없음 — 이 자품목의 역전개·BOM 관리로 갈 수 없다. 각 행의 "하위 리비전"은 보이지만 그 리비전의 시작·종료일은 안 보인다.
- 390: 14칸 중 3칸만 보이고 표 안에서 가로 스크롤(페이지 넘침은 없음).
- 링크 `?q.itemCd=ZT-BP1-1` → 칸만 채우고 **조회 안 함** [실측].

**역전개 조회(`mst-bom-where`)**
- 1,100행 263ms, 저레벨 코드 표시. 최상위만·전체 리비전 동작 [실측].
- 쓰는 곳이 0건이면 표에 "자품목 코드를 넣고 조회하세요. 쓰는 곳이 없으면 비어 있습니다." — **조회한 뒤에도 "넣고 조회하세요"** 가 남는다(빈 상태와 결과 0건이 같은 문구).
- "이 결과의 BOM 들을 일괄 대체" 로 이어지는 길이 없다 — SAP·Cetec 방식은 역전개 → 대체가 한 흐름(docs/18 [R1][R2]).

**BOM 관리(`mst-bom`)**
- 행 200개: 행마다 입력 4칸 + 숨은 10칸(더보기) → 2,800칸. 열 머리 없이 칸 이름은 자리표시자뿐(입력하면 사라짐). 행 번호가 "1,440" 처럼 **쉼표로 표시**(숫자 입력 공통 포맷) [실측 — `mgt-more-1366`].
- [행 저장]·[행 추가]가 목록 **맨 아래**(10,394px 아래), 머리 버튼([저장]·[확정])은 맨 위 — 스크롤 중간에서는 어느 쪽도 안 보인다.
- [더보기]·[삭제]가 200행을 통째로 다시 그린다 → 0.3~0.45초 + **포커스가 BODY 로 빠짐**(키보드로 이어서 못 침) [실측·코드 `bom-mgt.js:269·281` → `renderLines()`].
- 자품목 칸에서 Tab → 이름·단위 자동(좋음). 이름으로는 못 찾는다("공통 원자재" → "없는 품목입니다"). Enter 는 아무 일 없음(다음 행 추가 아님).
- 목록 안 찾기 없음 — 200행 중 "ZT-BW150" 을 찾으려면 브라우저 Ctrl+F.
- **엑셀 범위 붙여넣기 없음** — docs/18 10.1 에서 "미완(사용자 확인 대기)"로 남은 그대로 [코드 — `paste`/`clipboard` 없음].
- **D1** [새 리비전] 대화상자: "새 리비전 이름(비우면 자동 …)" 인데 비우고 [만들기] → 닫히기만 하고 요청이 안 나간다. 이름을 넣으면 된다 [실측 — 네트워크에 POST 없음]. 원인 [코드]: `hb.dialog.js:27` 선택 입력이 비면 `{ok: true, value: null}` → `prompt` 가 `null` 반환, `bom-mgt.js:509` `if (rev === null) { return; }`(취소와 구분 못 함). 같은 모양: `routing-mgt.js:566`(라우팅 새 리비전), `asset-mgt.js:86`(해체 시각 — 비우면 지금), `lot-mgt.js:215`(재작업·수리 수량 — 비우면 잔량 전부).
- 비교 대화상자: 같은 품목의 리비전끼리만 고를 수 있다(API 는 두 BOM id 아무거나 받음 — `BomChangeService.compare(leftId, rightId)`). 200행이 모두 "같음"이어도 200줄을 다 보여 준다(바뀐 것만 보기 없음) [실측].
- 390: 머리 폼 → 행 목록이 세로로 길게(약 2만 px). 행마다 [더보기]·[삭제]가 두 줄로 접힘.

**일괄 대체(`mst-bom-replace`)**
- 미리보기 → 반영 방법(새 리비전 A1 생성·작성 중에 반영·건너뜀 5종) 표시가 명확하다. 실행 확인 대화상자도 "확정은 BOM 관리에서 따로" 를 알린다 [실측].
- **실행 뒤가 끊긴다**: 결과는 "100곳 반영: ZT-BP1-10 A1, …(100개)… BOM 관리에서 확정하세요." 한 문장. 링크·목록·[모두 확정] 없음 → BOM 관리에서 상태 "작성 중" 으로 조회해 한 건씩 확정(약 100 × 3번 누름) [실측].
- 변경 번호·사유 칸이 없다 → 새로 생긴 리비전 100개의 변경 번호·사유가 비어 있다(C6). SAP CS20 은 변경 번호가 대체의 유효일·근거를 정한다([N1]).
- 시작일 기본(비움 = 오늘)에서 오늘 확정된 BOM 은 모두 "시작일을 하루 뒤로" 건너뜀 — 안내는 있지만 기본값을 "내일"로 두면 한 번에 된다(확정 시작일은 오늘 이후만 — docs/18 10.1 결정과도 맞음) [추정].
- 실행 후 같은 미리보기가 "건너뜀 — 작성 중 BOM 이 바꿀 자품목을 쓰지 않음"으로 바뀌어 처음 보는 사람은 실패로 읽기 쉽다.

- 1순위는 **실측에서 가장 큰 손실**(일괄 대체 뒤 300번 누름, 조용한 취소 D1, 10레벨이 안 읽히는 D2)을 없애고, 네 화면을 **한 흐름(역전개 → 대체 → 확정 → 전개 확인)** 으로 잇는다. 모두 기존 API·공통(셸 `open`, `q.*` 링크)을 쓰고 마이그레이션이 없다. 일괄 확정은 새 API 1개(건별 기존 `release` 재사용) [추정].
- 2순위는 행이 많은 BOM 의 일상 편집(docs/18 10.1 "복사해 새 리비전 → 바뀐 행만 수정")을 빠르게 한다. 편집 그리드(B8)는 PoC 결론 전이라 행 폼 보강으로 대신한다.
- 3순위는 보기 품질 — 급하지 않지만 작다.

2026-11-02 사용자: **"1순위로 진행, G5 일괄 확정은 추천안대로"**.

| # | 판정 |

구현에서 정해 둔 것:
- **일괄 확정 API** `POST /api/master/boms/release-batch` `{items: [{bomId, rowVer}]}`(1~1,000건, 중복·null 거부) → 건마다 `{bomId, itemCd, rev, ok, code, message}`. `BomReleaseBatchService` 가 건마다 세이브포인트(NESTED — `CloseNotices` 와 같은 방식) 안에서 `BomService.release` 를 부른다. 다른 회사 BOM id 는 RLS 로 `NOT_FOUND`(품목 코드 비노출), 회사 경계 위반 SQL 오류는 삼키지 않는다.
- **결과 표의 rowVer** — 일괄 대체 결과(`ReplaceDone`)에 반영 뒤 머리 버전을 실어, 결과 표에서 바로 확정해도 그 사이 다른 사람이 고친 건은 `CONFLICT` 로 걸러진다.
- **변경 번호·사유**는 새로 만드는 리비전에만 넣는다. 이미 있던 작성 중 BOM 에 반영할 때는 그 머리를 건드리지 않는다(남이 쓰던 작성 중일 수 있다). PLM ECO 의 일괄 대체 호출(`EcoService.replace`)은 예전 4칸 생성자 그대로 — ECO 번호를 변경 번호로 넘기는 것은 PLM 몫 후속.
- **[고른 것 확정] 버튼**은 대체 화면 SAVE 사용자에게 보인다(대체 화면은 BOM 관리의 APPROVE 를 모른다). 판정은 API 403.
- **D1** 공통 `hb.dialog.prompt` — 선택 입력을 비우고 확정하면 `''`, 취소만 `null`(순수 함수 `hb.dialog.submitValue` + node 시험, `types/hb.d.ts` 계약). 저장소 전체 호출 33곳을 확인: 선택 입력은 5곳(BOM·라우팅·**QMS 검사계획** 새 리비전, 자산 해체 시각, LOT 재작업 수량 — 4곳에서 하나 더 찾음)이고 모두 `trim() || null`·`trim()` 으로 `''` 를 받는다(LOT 재작업 빈 수량 = 잔량 전부 — 서버 `OrderService.qty` 가 빈 글자를 null 로). 필수 28곳(사유 입력 래퍼 mesUi·pmsUi·lot-mgt askReason 포함 — `required:false` 로 부르는 곳 없음)은 빈 값이면 대화상자가 닫히지 않으므로 바뀌지 않는다.
- **건별 독립**: 한 요청 = 한 트랜잭션 + 건마다 세이브포인트. 실패 건은 자기 변경(이전 확정본 마감 포함)만 되돌리고 뒤 건은 계속한다(시험: 가운데 건 기간 겹침 → 앞뒤 건 확정, 실패 건의 이전 확정본 그대로). 건마다 별도 트랜잭션(REQUIRES_NEW)이 아닌 이유 — 회사 범위 설정이 트랜잭션 단위라 한 연결·한 범위에서 끝내는 쪽이 단순하고, 결과(성공 건만 반영)는 같다. 순환은 행 저장·대체 때 막혀 확정 검사 대상이 아니다(기존 그대로).
- **D2** 공통 `hb.tree` — 트리 칸 폭에 (가장 깊은 레벨 − 1) × 16px 를 더한다. 레벨은 점 표기 칸 대신 숫자 칸(`lvl`, INT). `lvlMark` 는 응답에 그대로 둔다(예전 호출 호환).
- **D3** 역전개 "최상위"는 LABEL(`bomWhere.top.true/false` = 예/아니오). 공통 YN 은 엑셀에서 "사용/미사용"(사용 여부 칸)이라 boolean 에 맞지 않는다 — 화면 YN(예/아니오)과 엑셀 YN(사용/미사용)이 다른 것은 플랫폼 몫으로 남긴다.
- 전개·역전개에 "경로" 칸(우선순위 3 — 좁은 화면에서는 숨김, 엑셀에는 나옴).
