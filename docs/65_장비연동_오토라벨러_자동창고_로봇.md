## 1. 결론 먼저

- YeonOS 는 **MES/WMS 계층(ISA-95 레벨 3)** 에 머문다. PLC·로봇·자동창고의 실시간 제어는 하지 않고 **"무엇을·언제까지·우선순위"를 지시하고, 결과를 받아 원장에 남긴다.**
- **코드는 하나, 연결 방향만 배포 형태로 바뀐다**(3장). 설치형은 서버가 장비·프린터에 직접 붙을 수 있고, SaaS 는 공장 안 **엣지(게이트웨이)** 가 바깥으로 연결한다. 업무 로직(상태 기계·멱등·원장 반영·대사)은 같다.
- 공통 기반(5장)을 먼저 만든다: 장비 수신 규약(저장 후 200, 업무 키 멱등, 503 금지), 명령 쓰기 4단(의도 → 쓰기 → 다시 읽기 → 결과), 장비 상태 모델(PackML 부분집합), 하트비트·끊김 판정.
- 그 위에 4개 기능을 단계로 얹는다: **라벨 인쇄 보강(6장) → 오토라벨러(7장) → 자동창고 용기(8장) → 로봇 운반 큐(9장)**.
- 실제 장비는 없다 — **가짜 엣지·가짜 라벨러·가짜 WES·VDA 5050 로봇 시뮬레이터**로 정상·끊김·중복·순서 뒤바뀜·늦은 응답을 주입해 시험하고 시연한다(10장).
- 포트폴리오에서 말할 것: 배포 형태와 무관한 연결 추상화, 실측(같은 콜백 297회·메시지 ID 매번 다름)에 근거한 멱등 설계, "송신 성공 ≠ 인쇄 성공", "물리 이동과 장부 반영 분리", 장비 없이 연동을 증명하는 시험.

## 2. 범위·용어

| 용어 | 뜻 |
|---|---|
| 엣지(Edge) | 공장 안에서 장비와 YeonOS 사이를 잇는 별도 프로세스. 프로토콜 변환(OPC UA·Modbus·PLC), 저장 후 전달, 하트비트, 쓰기 허용 목록, 현장 응답 캐시 |
| 오토라벨러 | 자동 인쇄·부착기(Print & Apply). 앞단 스캐너 · 프린터 엔진 · 어플리케이터 · 검증 스캐너 · 리젝트(디버터) |
| WES/WCS | 자동창고 제어 시스템. 랙 위치·로봇 배차·포트(스테이션) 배정·용기 흐름을 맡는다 |
| 용기(컨테이너) | 자동창고가 나르는 보관 단위(토트·빈·트레이). 수출 컨테이너가 아니다(현장 자료의 뜻) |
| Fleet(로봇 관제) | AMR/AGV 무리의 배차·경로·충전·교통을 맡는 시스템. VDA 5050 의 마스터 컨트롤 |
| 연결 방식 | `DIRECT`(서버가 대상에 직접 연결) / `EDGE`(엣지가 바깥으로 연결해 당겨 감) / `AGENT`(라벨 전용 pull 에이전트) |

범위 밖: 안전 기능(비상정지·속도 구역 — ISO 3691-4, 장비 몫), 로봇 경로·교통·데드락, 랙 안 물리 위치, PLC 래더 로직.

## 3. 배포 형태별 차이 (설치형 · SaaS) — 이 문서의 축

YeonOS 원칙은 "SaaS 기준 멀티테넌트 설계 + 설치형 납품"(CLAUDE.md)이다. 장비 연동은 두 형태의 차이가 가장 크게 드러나는 곳이라, **기능마다 두 칸을 함께 설계**한다.

| 영역 | 설치형(공장 안 서버) | SaaS(클라우드 서버) |
|---|---|---|
| 라벨 인쇄 | 서버 → 프린터 TCP 9100 직접(지금 W2) | 서버가 공장 안으로 못 들어감 → **pull 에이전트**(6.2) 또는 프린터 바깥 연결(Zebra Weblink — 범위 밖) |
| PLC·OPC UA | 엣지를 같은 서버에 두거나 생략 가능(같은 LAN) | **엣지 필수**, 바깥으로 HTTPS |
| 자동창고 콜백(WES → WMS) | WES 가 LAN 으로 YeonOS 직접 호출 | WES 는 LAN 주소만 지원하는 경우가 많다 → **엣지가 중계**(LAN 수신 → 바깥 전달) |
| 응답 기한(오토라벨러: 박스가 지나가기 전 수 초) | LAN 이라 여유 | 인터넷 지연·끊김 = 라인 정지 → **엣지가 라벨 데이터를 미리 받아 두고 현장에서 응답**(7.4). 클라우드는 실시간 경로에 넣지 않는다 |
| 인터넷 끊김 | 영향 없음 | 엣지 저장 후 전달 + 현장 계속 운전(오프라인 모드), 복구 뒤 순서대로 반영 |
| 보안 | 사내망이어도 인증·쓰기 허용 목록 | **공장 안쪽으로 들어오는 연결은 열지 않는다**(IEC 62443 존·콘딧). 장치 키는 회사 단위 |
| 설치·업데이트 | 오프라인 설치 묶음(인터넷 없는 공장) | 엣지·에이전트 자동 업데이트(서명 확인) |
| 회사 범위 | 사실상 한 회사(같은 코드·RLS) | 장치 키 → 회사 범위. **A사 엣지가 B사 작업을 못 가져가는지** 시험 필수 |

구현 규칙:
- 장비·프린터·외부 시스템 마스터에 `conn_mode`(DIRECT/EDGE/AGENT)를 둔다. 서비스 코드는 연결 방식을 모른다 — 아웃박스 핸들러(보내기)와 수신 컨트롤러(받기)만 방식별로 갈린다.
- 엣지·에이전트 → 서버 API 는 두 형태 모두 같다(설치형에서도 엣지를 쓰면 같은 API). 그래서 시험은 한 벌.

## 5. 공통 기반

### 5.1 엣지
- 장비 쪽: **OPC UA 기본**(보안 모드 Sign 이상), Modbus TCP·S7·미쓰비시 MC(SLMP)·EtherNet/IP 는 엣지 안 어댑터. 후보 라이브러리 Eclipse Milo(EPL-2.0)·Apache PLC4X(Apache-2.0) — 엣지를 별도 모듈·프로세스로 두면 본 제품과 라이선스 경계가 깔끔하다.
- 서버 쪽: 기존 `/ext/v1/equip-events`(CMS `EquipEventController`·API 키)를 확장한다. MQTT/Sparkplug B 는 선택 확장으로 문서에만 둔다(birth/death·bdSeq 개념은 하트비트에 빌린다).
- 시연용 엣지는 `tools/fake-collector.mjs` 를 키운다(Node, 의존성 없음).

### 5.2 수신 규약(엣지·WES·Fleet·라벨러 → YeonOS)
1. **원문을 먼저 저장하고 바로 200**, 처리는 비동기. 처리 오류는 우리 쪽 격리 큐로(상대에 503 을 주지 않는다 — 현장 WES 는 408·425·429·503·504 를 받으면 5초 간격 **FIFO 순서대로** 다시 보내므로 뒤 메시지가 전부 막힌다. 그 밖의 4xx·5xx 는 "보낸 것"으로 버린다).
2. **멱등 키 = 업무 키**(우리 상관키 + 상태[+ 순번]). 상대 메시지 ID 는 같은 요청이라도 매번 바뀐다(현장 실측: 같은 콜백 297회, 모두 다른 ID). `sys_inbox` 에 수신 경로별 키 규칙을 둔다.
3. **같은 키·다른 내용은 거부 + 경보**(VDA 5050 `SAME_ORDER_UPDATE_ID` 와 같은 원칙). **옛 상태가 늦게 오면 되돌리지 않고 "stale" 로 기록**(VDA 5050 `OUTDATED_ORDER_UPDATE`).
4. **"완료" ≠ "성공"**: FINISHED 와 Errors 가 함께 올 수 있다. 오류 동반 완료는 실패로 본다. 상태 코드를 범위(`>= 5`)로 묶지 않는다.
5. 엣지 순번(`seq`, 장비별 단조 증가)으로 누락·역전을 감지하고, 상태 계산은 `occurred_at` 순. 장비 시계는 믿지 않는다 — `occurred_at`(장비·엣지)과 `recorded_at`(서버)을 함께 저장하고 차이가 기준을 넘으면 경고.
6. 과부하만 429 + `Retry-After`(RFC 6585). 형식 오류는 4xx(엣지가 데드레터로).

### 5.3 명령(쓰기) — 서버는 장비에 직접 쓰지 않는다
`@ProgAuth` 별도 권한(예: EQUIP_CMD) → 아웃박스 → 엣지(쓰기 허용 목록: 논리 태그·값 범위, 인터록 확인) → 장비 쓰기 → **다시 읽어 확인** → 결과 이벤트. 원장에 **의도·쓰기·확인·결과 4단**을 남긴다. Modbus TCP 는 인증이 없으므로(Modbus/TCP Security 는 채택 제한적) 허용 목록이 유일한 통제다. 서버에는 Modbus 주소를 노출하지 않고 논리 태그로 추상화한다. docs/05 의 "쓰기는 별도 활성화 + 감사" 결정을 따른다.

### 5.4 장비 상태 모델
- PackML(ISA-TR88.00.02, OPC 30050) 17개 상태 중 부분집합: Idle · Starting · Execute · Held · Suspended · Stopped · Aborted · Complete. 상위 집계는 OPC UA Machinery(OPC 40001-1) MachineryItemState(NotAvailable/OutOfService/NotExecuting/Executing)에 대응.
- 전이 허용표는 서버가 검증(허용 안 된 전이 = 이상 사용 시험 대상). 정지 사유는 PackTags StopReason 개념.
- 상태 이력은 **CMS 설비 상태 원장**에 둔다(13장 Q3 — 권고). 상태가 바뀔 때만 행을 남겨 양을 줄인다.

### 5.5 하트비트·끊김
- 엣지·장비는 주기적으로 상태를 보낸다(현장 라벨러 5초, WES 헬스 30초, VDA 5050 state 최소 30초). **"안 온 것"을 사건으로 만든다** — `last_seen` + 기준 시간(주기 × N, OPC UA lifetime ≥ keepalive × 3 참고)을 `TenantRunner` 스케줄러가 판정해 알람(CMS `AlarmService`).
- 소모품(용지·리본)은 "없음" 전에 **"부족"(warning) 단계**로 미리 알린다.
- 엣지 기동 때 장비 목록·현재값을 한 번에 보낸다(Sparkplug birth 개념). 끊김 뒤 재연결은 상태 스냅샷으로 수렴.

## 6. 라벨 인쇄 보강

지금 있는 것(W2): ZPL 템플릿 + `{{필드}}`(`^FH` 이스케이프), 아웃박스 → TCP 9100 송신(사설 대역만), 재발행 사유·승인, 유형별 기본 템플릿, 미리보기(ZPL 글자), GS1-128 스캔 파서, 팔레트 SSCC.

### 6.1 인쇄 상태 3단 — "송신 성공 ≠ 인쇄 성공"
`SENT`(소켓 송신) → `PRINTED`(프린터 확인) → `VERIFIED`(검증 스캔 대조, 오토라벨러·PDA). 오류는 `PRINTER_ERROR`(사유 코드). Zebra Link-OS Best Practices: 인쇄 전 상태 확인(일시정지·헤드 열림·용지 없음 — `~HQES`/SGD `zpl.system_status`), 인쇄 뒤 버퍼 포맷 수 0 대기, **`odometer.total_label_count` 전후 비교**(상태 확인보다 정확할 수 있다고 명시). 프린터별 마지막 상태를 화면에 보인다. 벤더 중립 선택지로 SNMP Printer MIB(RFC 3805)를 적어 둔다.

### 6.2 pull 인쇄 에이전트(SaaS·USB·망 분리)
- 공개 레퍼런스(SAP Cloud Print Manager for Pull Integration)와 같은 구조: 공장 PC 의 에이전트가 **서버 API**(DB 아님)에서 작업을 가져가 로컬 드라이버 프린터나 9100 으로 출력하고 결과를 보고한다.
- **DB 직접 접속은 금지** — 현장 PC 마다 DB 계정이 깔려 DB 계정 2개·RLS 원칙과 충돌한다(로컬 레거시 프로젝트의 관행이었으나 공개 근거 없음).
- 인증: 장치 단위 API 키(회사·프린터 범위). 가져가기: `FOR UPDATE SKIP LOCKED` **lease claim**(lease_until·attempt). 결과 보고: job_id 멱등. 대기: 롱폴링(웹소켓은 "깨우기"만, 본문은 pull).
- **lease 만료 = 자동 재인쇄 금지** → `UNKNOWN`(이미 인쇄됐을 수 있다 — SSCC 같은 일련번호 라벨 중복 부착 방지), 사람이 판단. 에이전트 하트비트·오프라인 표시·다른 프린터로 넘기기.
- 프린터 마스터 `conn_mode = AGENT` 로 고른다. 설치형은 DIRECT 그대로.

### 6.3 한글 라벨 — 지금 견본의 결함 후보
`^CI28`(UTF-8)만으로는 한글이 나오지 않는다. **프린터에 CJK TTF 글꼴을 올리고(`~DY`) 별칭을 매핑(`^CW`)** 해야 한다. 지금 W2 견본 템플릿은 `^CI28` + 기본 글꼴 `^A0` 에 품목명을 넣는다 → 실물에서 한글이 빠질 가능성(추정, 실물 확인 필요). 프린터 마스터에 "한글 글꼴 등록 여부"를 기록하고, 템플릿 저장 때 한글 필드 + 글꼴 미지정이면 경고.

### 6.4 미리보기(ZPL → 이미지)와 넘침 검사
- 무료 Labelary API 는 FAQ 에 프라이버시 보장이 **없다**고 적혀 있다 → 운영 데이터 전송 금지. 로컬 렌더러(MIT: Zebrash·BinaryKits.Zpl·zpl-renderer-js — 유지보수 상태 확인 필요) 또는 쓰는 명령 부분집합(`^FO ^A ^FB ^GB ^FR ^BQ ^BC`)만 SVG 로 그리는 자체 렌더러(CSP 준수).
- 글자 폭을 추정해 칸 넘침·`^FB` 줄 초과를 템플릿 저장 때 **경고**. "근사값 — 최종은 실물" 을 화면에 명시. 견본 값 + "긴 값" 케이스를 자동 시험.

### 6.5 템플릿 선택 규칙
물리 규격(크기 ID: 100×70, 100×100 …)과 양식을 분리하고, **거래처 > 품목 > 유형 기본** 순으로 찾는다. 프린터 dpi·용지 크기와 맞는지 검사. `LabelPrintService.request(tplId = null)` 이 규칙을 따른다.

### 6.6 GS1 확장
AI 310n(가변 중량, n = 소수 자리)·15(소비기한) 해석, **한 박스 바코드 두 개 결합**(식별용 + 중량·기한·LOT — 다음 박스 바코드가 섞이면 거부), 스캐너가 FNC1 을 빼거나 바꿔 보내면 경고(가변 AI 가 중간에 오면 깨진다), 출력 `^BX` GS1 DataMatrix(FNC1 은 `^BX` 파라미터, `^FH` 와 섞지 않음). 자동차 납품 라벨(Odette GTL/VDA 4994, AIAG B-10)은 템플릿 후보로만 적는다.

## 7. 오토라벨러(Print & Apply)

### 7.1 흐름
1. 박스 도착 → 앞단 스캐너가 원본 바코드(박스 GTIN·작업 바코드)를 읽는다.
2. 장비(또는 엣지)가 YeonOS 에 라벨 데이터 요청 → YeonOS 는 **데이터와 템플릿·크기 ID** 만 응답(디자인·물리 동작은 장비). SSCC 채번은 YeonOS, **job_id ↔ SSCC ↔ 박스 추적 ID 1:1**.
3. 인쇄 트리거는 **PLC 이산 신호**(Zebra ZE511/521 Start Print, SATO CL4NX PRIN/PREND, Weber Legi-Air Print/Apply·Data Ready) — YeonOS 몫이 아니다. YeonOS 는 "기한 안에 데이터를 넣고 결과를 대조"하는 계약만 맡는다.
4. 부착(tamp/blow/wipe) → 뒷단 **검증 스캐너**가 다시 읽어 결과 보고 → YeonOS 가 **통과/리젝트 판정**(기대 SSCC 와 대조, 필요하면 ISO/IEC 15416 등급).
5. 리젝트 → 디버터 → 재라벨. **같은 물류 단위의 SSCC 는 바꾸지 않는다**(GS1 원칙) — 재인쇄 이력만 남긴다.
6. 마감 순서: 인쇄 확인 → 부착 확인 → ASN(DESADV). 라벨과 ASN 불일치는 고객 입고 거부 사유.
- 이미 라벨이 있는 입고는 "라벨 생략" 플래그로 건너뛴다. 미등록 박스(사전 등록 없음)는 리젝트.

### 7.2 장애 유형
| 유형 | 처리 |
|---|---|
| no-read(앞단) | 데이터 없음 → 라벨 없이 리젝트 |
| WMS 연결 실패 / **응답 기한 초과** | 기한(박스 이동 시간)을 넘긴 응답은 **그 박스에 쓰지 않고 리젝트**("늦게 온 정답 = 오답") |
| 빈 라벨·다른 박스 라벨 | 검증 스캔 불일치 → 리젝트(조용히 틀리는 것을 막는 핵심) |
| 인쇄 실패(용지·리본·헤드) | 장비 오류 API + 하트비트 상태 → 라인 알람, 재인쇄 입력 |
| 미부착·비뚤게 붙음 | 부착 확인 센서·검증 no-read → 리젝트 |
| 리젝트 라인 만재 | 대기·알람·정지 중 정책(`PolicyService`) |

박스 단위 로그(요청·판정)와 장비 단위 로그(상태·오류)를 나눈다. 사유 코드는 공통코드.

### 7.3 위치
WMS 새 `wms/labeler` + `/ext/v1/labeler/*`(CMS `ExtSecurityConfig` API 키 재사용). 값 계산은 기존 `LabelFields`, 멱등은 `sys_inbox`(request_id), 박스 처리 이력은 추가만 하는 원장.

### 7.4 SaaS 에서의 응답 기한
클라우드 왕복을 실시간 경로에 넣지 않는다. 엣지가 **오늘 작업분 라벨 데이터를 미리 받아 두고**(사전 채번 SSCC 묶음) 현장에서 응답한다. 검증 결과·사용한 SSCC 는 저장 후 전달로 올린다. 사전 채번분 중 쓰지 않은 것은 반납(결번 처리 규칙 — 13장 Q5).

## 8. 자동창고 보관 용기(컨테이너)

### 8.1 모델
- **물리 유형**(치수·칸 배치)과 **개별 용기**(ID·바코드·유형·현재 위치·상태: 빈/적재/시스템 안/격리)를 나눈다. 칸(구획) 0~N, 칸 역할(꺼냄·담음), 중첩 용기. 같은 칸에 같은 품목의 다른 LOT 을 섞으면 그 칸은 피킹·실사 대상에서 빠진다(현장 장비 규칙) → 경고.
- 재고 원장: 처음에는 **자동창고 전체를 가상 로케이션 1개**(`wms_loc_attr` 용도 `AUTO_STORE`)로 본다. 용기·칸 차원은 별도 용기 내용 표(사본)로 두고 원장 칸은 늘리지 않는다(13장 Q1 — 권고).
- 스캔 키에 용기 접두어 추가(`ScanKeyResolver`).

### 8.2 입고·출고 요청
- 요청 1건 = 라인 N개(입고는 라인 1 = 용기 1). **요청 → 라인 → 용기 3단 상태**를 각각 저장, 상위 상태는 하위 집계로 계산(직접 쓰지 않음). 라인별 부분 완료, **모든 라인이 끝나야 요청 완료**.
- 용기 정의를 먼저 등록하고 요청한다. 시작 전에는 수정·삭제, **시작 후에는 거절**(WMS 도 "진행 중" 유지), 수정은 전체 덮어쓰기(빠진 칸은 비워짐 — 보낼 때 전체를 보낸다), 지운 요청 ID 는 다시 쓰지 않는다.
- 원장 반영 시점: **입고 = 로봇이 랙에 넣은 시점**(출입구 도착 아님), **출고 = 출구 인계 완료**.
- 송신은 아웃박스(핸들러는 DB 금지 → 외부 요청 ID 를 우리가 만들어 멱등 키로).

### 8.3 컨베이어 경계 교환
용기별 순차: 앞단 스캔 → 교환 요청 → 상대 "진행 중 + 준비됨" 확인 뒤 구동 → 완료 → 다음 용기. 투입 직전 스캔으로 "요청한 그 용기인가" 확인, 미등록·불일치는 리젝트·정지, 포화면 대기. 출구는 반대 방향(WES 가 요청, WMS/컨베이어가 회신). 미리 스캔해 두면 순차 처리로도 처리 속도가 충분하다(현장 회의 결론).

### 8.4 재고 대사와 진실 원천
- 수량·LOT = **WMS 원장**, 랙 안 위치 = WES(13장 Q2 — 권고).
- 평소는 이벤트로, **하루 한 번 전체 용기 정의를 받아 비교**(용기 유무·칸별 품목·수량·LOT). 차이는 **격리(출고 할당에서 제외) + 조정 후보** → 사람 확인 → 조정 전표(역분개 + 새 행). **자동창고 값으로 덮어쓰지 않는다.**
- 스테이션 예외 알림: 수량 조정(파손·빈 용기·부족) → 조정 후보, 격리(못 쓰는 용기·잘못된 품목·형상 불일치) → 보류. "작업자가 조용히 고치지 않는다"(장비 규칙).

### 8.5 오래된 요청·처리량 감시
로봇이 닿지 못하는 용기는 **오류 없이 영원히 NOT_STARTED** 로 남는다(현장 시험) → 기준 시간을 넘긴 요청 경보. 차단된 랙 요청이 접수되고 오류도 오지 않은 사례 → WMS 쪽 사전 검사. 시간당 처리량·사이클 타임·포트 대기율·대사 차이율 KPI(CMS·홈 카드). 우선순위·보관 구역 분리·칸 혼적 금지는 처리량을 깎는다(우선순위를 넣자 병렬이 순차로 바뀐 실측) — 꼭 필요할 때만.

## 9. 로봇 운반 작업 큐(AMR/AGV)

### 9.1 경계
YeonOS 는 로봇과 VDA 5050 을 직접 말하지 않는다. **운반 작업(출발 로케이션·도착 로케이션·화물/용기 ID·우선순위·마감)** 만 Fleet 어댑터에 넘기고, 상태·오류(WARNING/URGENT/CRITICAL/FATAL)·배터리·가동 모드는 요약해서 받는다. WMS 로케이션 ↔ 로봇 지점 대응표(현장 구축자가 설정). 공유 구역·엘리베이터·데드락은 Fleet 몫(VDA 5050 responses의 GRANTED/QUEUED/REVOKED + leaseExpiry, Open-RMF lift adapter) — YeonOS 는 대기 사유로만 표시.

### 9.2 상태 기계
`CREATED` → `SENT` → `ACCEPTED` → (`ASSIGNED`) → `IN_PROGRESS`(집하 완료 = 이동 중, 원장 미반영 — 출발 로케이션에 "이동 중" 예약만) → `ARRIVED` → `COMPLETED`(**하역 확인 + 도착 노드 일치 → 이때만 재고 원장 MOVE**). 그 밖: `FAILED`, `CANCEL_REQ` → `CANCELLED`(상대 확인 뒤 — VDA 5050 cancel 도 RUNNING 을 거쳐 FINISHED), `UNKNOWN`(결과 불명), 용기 속성 `QUARANTINE`.

규칙:
1. 앞으로만 전이, 늦게 온 옛 상태는 stale 기록(5.2-3).
2. **응답을 잃은 생성 요청은 다시 보내지 않고 상관키로 조회**한다. 조회 API 가 없으면(현장 관제 표준판: 명령은 취소만, 완료 이력 없음, 인증 없음) `UNKNOWN` → 사람이 확정.
3. 연결 끊김(VDA 5050 last will `CONNECTION_BROKEN`) → 그 로봇의 진행 작업 `UNKNOWN`, 재연결 뒤 state 스냅샷(orderId·actionStates·loads)으로 수렴.
4. 이동 중 이후 실패·취소 → 용기 위치 불명 → `QUARANTINE`, 원장은 움직이지 않음 → 회수 작업 생성 또는 사람이 위치 확정(조정 전표). **적재 뒤 실패는 사람 확인 전 예약을 풀지 않는다.**
5. 재시도는 **새 작업 행**(원 작업은 FAILED 로 남김 — 역분개 사상). 반영 실패는 운반 없이 반영만 다시.
6. 예약·잠금: 생성 때 도착 로케이션 용량·용기 예약, 확정 때 해제. **용기 하나에 활성 작업 하나**(부분 유니크 인덱스). 가져가기는 `FOR UPDATE SKIP LOCKED`, 큐 일시정지(새 전송만), 큐별 동시 진행 한도, 선행 작업 의존.

### 9.3 장애 시나리오 자동 시험
정상 · 지연 · 응답 유실 · 중복 푸시(완료 푸시가 응답 본문 `err=0` 이 올 때까지 1초마다 재전송되는 현장 관제) · 적재 뒤 실패 — 5종 + A사로 B사 작업.

## 16. E0 설계 — 공통 기반 (2026-11-03, 하위 세션 `claude/equip-e0`)

> 마이그레이션: CMS V233(임시 V9601) + 시스템관리 V234(임시 V9701). 기존 P2 6단계 수신(`/ext/v1/equip-events`, 동기 처리·eventId 멱등)은 **그대로 둔다** — 이미 쓰는 수집기·시험의 계약이라서. E0 는 그 옆에 5.2 규약을 따르는 엣지 경로를 새로 열고, 상태 원장·알람·장치 키는 같은 것을 쓴다.

### 16.1 누가 장비를 대신 말하나 — 연결 방식

| 칸 | 위치 | 뜻 |
|---|---|---|
| `conn_mode` DIRECT/EDGE | 새 1:1 표 `cms_equip_link`(설비 — P1 `mst_equip` 은 고치지 않는 CMS 1:1 표 원칙) | DIRECT = 서버가 LAN 의 장비 어댑터로 **밀어 보냄**(설치형) / EDGE = 공장 안 엣지가 **바깥으로 당겨 감**(SaaS) |
| `terminal_id` | 같은 표 | 그 설비를 대신 말하는 장치(`sys_terminal` 유형 COLLECTOR — API 키 하나). DIRECT 어댑터도 장치로 등록한다 → **받는 길은 두 형태가 같다** |
| `adapter_url` | 같은 표, DIRECT 만 | 서버가 명령을 밀어 보낼 주소. 사설 대역만(라벨 프린터와 같은 검사 `PrinterAddress` — 보낼 때마다 해석·검사) |
| `hb_sec` | 같은 표 | 하트비트 주기(기본 5초 — 현장 라벨러 주기) |
| `write_enabled_yn` | 같은 표 | 명령 쓰기 별도 활성화(docs/05 "쓰기는 별도 활성화 + 감사"), 기본 N |
| `conn_mode` DIRECT/EDGE/AGENT | `mst_ext_system`(P1 — **남의 표 변경**, 기본 DIRECT) | WES·Fleet 같은 외부 시스템(E4·E5)이 쓸 자리. 화면 선택만 더한다 |

서비스 코드는 연결 방식을 모른다. 갈리는 곳은 둘뿐: **명령 보내기**(`EquipCommandTransport` — DIRECT = 아웃박스 토픽 `EQUIP_CMD` → 어댑터로 POST, EDGE = 명령 행을 큐에 두고 엣지가 lease 로 가져감) / **받기**(둘 다 같은 `/ext/v1/edge/*`).

> EDGE 를 아웃박스(`sys_outbox`)로 보내지 않는 이유: 아웃박스 송신기는 트랜잭션·회사 범위 밖에서 상대에게 **밀어** 보내는데, SaaS 서버는 공장 안으로 들어갈 수 없다(3장). 엣지가 당겨 가는 큐는 명령 행 자체가 업무 트랜잭션과 함께 커밋되는 "당기는 아웃박스"다 — E2 pull 인쇄 에이전트(6.2)와 같은 lease 모양.

### 16.2 수신 규약(5.2) 구현 — 원문 저널 + 경로별 키 규칙

```
엣지/어댑터 ──POST /ext/v1/edge/messages──▶ ① 원문 저장(sys_inbound_msg, 한 트랜잭션) ─▶ 200 + 건별 결과(STORED·DUP·CONFLICT·INVALID)
                                               ② 처리기(정기 2초, TenantRunner) ─▶ 경로 처리(InboundRoute 빈) ─▶ DONE / STALE / REJECTED
                                                   예외 = attempts+1 → 다시(뒤로 미룸) → 상한이면 QUARANTINE(격리 큐, 화면에서 다시 넣기)
```

| 규칙 | 구현 |
|---|---|
| 원문 먼저 → 200 | 저장 트랜잭션에는 처리 로직이 없다. 처리 오류는 상대에게 가지 않는다(503 없음) |
| 업무 키 멱등 | 경로마다 `InboundRoute.keyFields()`(상관키 + 상태[+ seq]) — 키 = 경로 + 그 칸 값들의 SHA-256. 상대 메시지 ID 는 키에 넣지 않는다(같은 콜백 297회·ID 매번 다름). 유일 = (회사, 경로, 키) — 충돌 증거 행 제외. 처리 때 `sys_inbox`(소비자 `IN:{경로}`)에도 같은 키로 한 번만 |
| 같은 키·같은 내용 | DUP — 새 행 없이 원래 행 `dup_count`+1(297번 와도 행 1개) |
| 같은 키·다른 내용 | CONFLICT — 원문은 증거로 따로 저장(`conflict_of_id`), 처리하지 않음 + 연동 사건 + 알람 `LINK_CONFLICT`. 내용 = `contentFields()` 의 정규화 값(순서·공백 무관) |
| 늦게 온 옛 상태 | 처리 결과 STALE — 원장을 되돌리지 않고 사건 `STALE` |
| 완료 + 오류 동반 | `InboundOutcome.of(status, errors)` — 오류 배열이 비지 않으면 성공 상태여도 FAILED. 상태 코드를 범위로 묶지 않는다 |
| 순번(seq) | 설비별 단조. 처리 때 마지막 seq 와 비교 → 건너뜀 = 사건 `GAP`(누락 범위), 뒤로 = `REORDER`(이미 지난 것이면 STALE). 같은 처리 묶음 안에서는 seq 순으로 정렬해 처리 |
| 두 시각 | 메시지 `occurredAt`(장비·엣지) + `received_at`(서버). 봉투 `sentAt` 과 서버 시각 차이가 정책 `EDGE_CLOCK_SKEW_SEC` 넘으면 사건 `CLOCK_SKEW`(장치당 10분에 한 번) |
| 과부하 | 그 회사 미처리 원문이 정책 `EDGE_INBOUND_MAX_BACKLOG` 이상이면 **429 + Retry-After**(정책 `EDGE_INBOUND_RETRY_AFTER_SEC`) — 저장 전에 판단, 유일한 재전송 요구 |
| 형식 오류 | 봉투가 깨지면 400(엣지가 데드레터로). 봉투 안 한 건이 깨지면 그 건만 `INVALID:{코드}`(나머지는 저장) |

E1~E5 가 새 수신 경로를 더하는 법: `InboundRoute` 빈 하나(경로 코드 `^[A-Z][A-Z0-9_]{2,29}$`, keyFields, contentFields, orderField(선택), handle). 저널·중복·충돌·격리·429 는 공통이 한다.

### 16.3 E0 수신 경로

| 경로 | 키(상관키 + 상태[+ seq]) | 내용 칸 | 처리 |
|---|---|---|---|
| `EQUIP_STATE` | equipCd + seq | packState·mode·stopReason·occurredAt | PackML 전이 검사(16.5) → CMS 상태 원장(16.6) |
| `CMD_RESULT` | cmdKey + phase(WRITE·READBACK·RESULT) | ok·value·readback·status·errors | 명령 4단 기록·판정(16.4) |

하트비트(`POST /ext/v1/edge/heartbeat`)는 저널을 거치지 않는다(업무 메시지가 아니고 5초마다 온다) — `last_seen` 만 갱신하고, birth 때의 현재값만 `EQUIP_STATE`(snapshot) 로 저널에 넣는다.

### 16.4 명령 쓰기 4단(5.3)

```
화면 POST /api/cms/equip-links/{id}/commands  (@ProgAuth cms-equip-link FN1 + X-Idempotency-Key 필수)
  ├ 서버 1차 검사: 쓰기 활성화(write_enabled_yn) · 논리 태그 허용 목록(cms_equip_tag: 형식·범위·쓸 수 있는 PackML 상태 = 인터록)
  ├ cms_equip_cmd(REQUESTED) + 단계 원장 INTENT  ─ 같은 트랜잭션에 보내기(16.1)
  ├ DIRECT: 아웃박스 EQUIP_CMD → 어댑터 POST {adapter_url}/commands → SENT
  │ EDGE  : 큐 → 엣지 POST /ext/v1/edge/commands/claim (lease) → CLAIMED
  ├ 엣지 2차 검사(엣지 자체 허용 목록·인터록 — 서버 값을 믿지 않음) → 거부 = RESULT REJECTED
  ├ 쓰기 → CMD_RESULT WRITE → WRITTEN
  ├ 다시 읽기 → CMD_RESULT READBACK
  └ CMD_RESULT RESULT(DONE·FAILED·REJECTED + readback + errors) → 서버가 readback = 의도 값인지 **다시 대조** → DONE / FAILED(VERIFY_MISMATCH)
```

- 단계 원장 `cms_equip_cmd_step`: INTENT·SENT·CLAIM·WRITE·READBACK·RESULT·TIMEOUT — 추가만, 순서가 뒤바뀌어 와도 단계는 모두 남고 끝난 명령의 상태는 바뀌지 않는다.
- 서버에는 Modbus 주소가 없다 — 논리 태그(`SPEED_SP`)만. 주소 대응은 엣지 설정.
- 시간 초과(정책 `EQUIP_CMD_TIMEOUT_SEC`): 가져가기 전 = EXPIRED(안 보냄 — 안전), 가져간 뒤·보낸 뒤 결과 없음 = **UNKNOWN**(썼을 수 있다 — 자동 재전송 금지, 사람이 판단). lease 만료도 다시 나눠 주지 않는다.
- 결과 보고는 그 설비를 맡은 장치만 — 다른 장치·다른 회사의 cmdKey 는 REJECTED.

### 16.7 하트비트·끊김(5.5)

- `POST /ext/v1/edge/heartbeat` `{bootId, sentAt, birth, equips:[{equipCd, online, packState?, mode?, seq?, occurredAt?, consumables:[{cd, level: OK|LOW|EMPTY}]}]}` — 그 장치가 맡은 설비만 `last_seen_at` 갱신(남의 설비·다른 회사 설비는 `unknown` 으로 돌려줌).
- **"안 온 것"을 사건으로**: 정기 작업(10초, `TenantRunner` + `JobLock`)이 `last_seen_at + hb_sec × EQUIP_HB_MISS`(기본 3 — OPC UA lifetime ≥ keepalive × 3) 를 넘긴 설비를 끊김으로 판정 → 알람 `LINK_LOST`(CMS `AlarmSink`) + 사건 `LOST` + 원장 UNKNOWN 구간. 판정식은 조회 화면과 같은 하나(`EquipLinkJudge`) — "지금 끊겼나"는 저장하지 않고, 저장하는 것은 알린 시각(`lost_at`, 두 번 알리지 않게)뿐.
- 다시 오면 알람 해제 + 사건 `BACK` + UNKNOWN 구간 닫기 → 같은 하트비트의 현재값(snapshot)으로 수렴.
- 소모품: 수준이 **바뀔 때만** 알람(`CONS_LOW.{cd}` 경고 → `CONS_EMPTY.{cd}`, OK 면 둘 다 해제) — 5초마다 같은 경고를 쌓지 않는다.
- birth: `birth=true` 또는 `bootId` 가 바뀌면 사건 `BIRTH` + 실린 현재값을 snapshot 상태로 저널에.

### 17.2 E1~E5 가 쓸 계약

**① 새 수신 경로 등록** — `InboundRoute` 빈 하나. 저널(원문 먼저 저장)·업무 키 멱등·충돌·격리·429·처리 순서는 공통이 한다.
```java
@Component class WesCallbackRoute implements InboundRoute {
    public String routeCd() { return "WES_CALLBACK"; }                       // ^[A-Z][A-Z0-9_]{2,29}$
    public List<String> keyFields() { return List.of("requestId", "lineNo", "status"); }   // 상관키 + 상태[+ 순번] — 상대 메시지 ID 금지
    public List<String> contentFields() { return List.of("qty", "containerId", "errors"); } // 같은 키·다른 내용 = CONFLICT
    public String partField() { return "requestId"; }                        // 줄 세움 단위(선택)
    public String orderField() { return null; }                              // 순번 칸(선택, 0 이상 정수)
    public InboundResult handle(InboundMessage m) { … }                      // 처리 트랜잭션(MANDATORY), 행위자 = 보낸 장치
}
```
- 결과: `InboundResult.done()/stale(code)/rejected(code)`(남긴 사건은 커밋) 또는 `throw new InboundRoute.Reject(code)`(되돌리고 거부). 그 밖의 예외 = 다시 시도 → 격리.
- "완료 + 오류 = 실패": `InboundOutcome.of(status, errors)` → DONE/FAILED/REJECTED/UNKNOWN.
- 엣지가 보내는 길: `POST /ext/v1/edge/messages {sentAt, messages:[{route:"WES_CALLBACK", …}]}` — 응답 건별 `STORED·DUP·CONFLICT·INVALID:{코드}`, 과부하만 429 + Retry-After. 외부 시스템이 우리 봉투를 못 맞추면 그 모듈 컨트롤러가 받아 `InboundJournal.store(route, sourceId, sourceCd, body, sentAt)` 를 부른다(한 트랜잭션, `noRollbackFor = Invalid`).

**② 명령 API** — 화면 `POST /api/cms/equip-links/{equipId}/commands {tagCd, value, reason}` + `X-Idempotency-Key` 필수, @ProgAuth `cms-equip-link` FN1. 다른 모듈이 서비스로 부를 때는 `EquipCommandService.request(equipId, CmdForm)`(트랜잭션 안). 상태 `REQUESTED → SENT|CLAIMED → WRITTEN → DONE|FAILED|REJECTED`, 시간 초과 `EXPIRED`(안 보냄)/`UNKNOWN`(결과 불명 — 늦은 결과·사람 확정만). 엣지: `POST /ext/v1/edge/commands/claim {max}` → `[{cmdKey, equipCd, tagCd, dataType, value, leaseUntil, expiresAt}]`, DIRECT 어댑터: 서버가 `POST {adapter_url}/commands` 같은 본문 + `X-Idempotency-Key: cmdKey`(어댑터는 cmdKey 로 한 번만 쓴다).

**③ 결과·상태 이벤트 형식**
```json
{"route":"CMD_RESULT","cmdKey":"…","phase":"WRITE","ok":true,"value":"55","occurredAt":"…"}
{"route":"CMD_RESULT","cmdKey":"…","phase":"READBACK","readback":"55","occurredAt":"…"}
{"route":"CMD_RESULT","cmdKey":"…","phase":"RESULT","status":"DONE|FAILED|REJECTED","readback":"55","errors":[],"reason":"INTERLOCK","occurredAt":"…"}
{"route":"EQUIP_STATE","equipCd":"EQ1","seq":42,"packState":"EXECUTE","mode":"PRODUCTION","stopReason":null,"occurredAt":"…"}
```
하트비트: `POST /ext/v1/edge/heartbeat {bootId, sentAt, birth, equips:[{equipCd, online, seq, packState, mode, occurredAt, consumables:[{cd, level: OK|LOW|EMPTY}]}]}`. **seq 는 설비별 단조이고 엣지가 재기동해도 이어진다**(저장 후 전달 큐와 함께 저장 — 가짜 엣지는 상태 파일).

**④ 알람 코드**(CMS `AlarmSink`, 정의는 회사가 `cms-alarm-def` 에): `LINK_LOST`·`LINK_CONFLICT`·`PACKML_TRANSITION`·`CONS_LOW.{소모품}`·`CONS_EMPTY.{소모품}`.

### 18.1 인쇄 상태 3단(6.1) — 상태 = 사건 원장의 마지막 상태

| 상태 | 뜻 | 누가 남기나 |
|---|---|---|
| `QUEUED` | 요청됨(아직 안 보냄) | (사건 없음 = 기본) |
| `CLAIMED` | 에이전트가 가져감(E2) | 에이전트 claim |
| `SENT` | 프린터로 보냄(소켓 송신) | 설치형: 아웃박스 `SENT` 에서 파생 / 에이전트: 결과 보고 |
| `PRINTED` | 프린터가 찍었다고 확인 | 설치형: 상태 확인 작업(odometer 증가) / 에이전트: 결과 보고 / 사람 확정 |
| `VERIFIED` | 검증 스캔이 라벨 값과 같다 | 화면·PDA·오토라벨러(E3) 검증 API |
| `PRINTER_ERROR` | 보냈지만 프린터 오류(용지·리본·헤드 열림 …, 사유 코드) — 끝이 아님(고치면 이어서 찍힌다) | 상태 확인 / 에이전트 |
| `FAILED` | 못 보냄(아웃박스 FAIL·에이전트 실패) | 아웃박스 파생 / 에이전트 |
| `UNKNOWN` | 결과 불명(에이전트 lease 만료 — 찍혔을 수 있다) | 정기 작업 |
| `CANCELLED` | 사람이 "안 찍힘"으로 닫음·다른 프린터로 넘김 | 사람 |

- 표 `wms_print_job_event`(추가만 — 원장 칸: `occurred_at`·`recorded_at`·`entry_method`·`reversal_of_id`(항상 null)) 에 **사건**을 남기고, 지금 상태 = 상태 사건 중 마지막(없으면 아웃박스에서: NEW·SENDING → QUEUED, SENT → SENT, FAIL → FAILED). 작업 행(`wms_print_job`)은 그대로 추가만.
- 전이 허용표는 한 곳(`PrintStates.canMove`) — 서비스·에이전트 결과·사람 확정이 같은 표를 쓴다. 허용 안 된 전이는 사건 `STALE`(늦게 온 옛 결과 — 5.2-3) 로만 남기고 상태는 그대로.

  | 지금 → 다음 | CLAIMED | SENT | PRINTED | VERIFIED | PRINTER_ERROR | FAILED | UNKNOWN | CANCELLED |
  |---|---|---|---|---|---|---|---|---|
  | QUEUED | ✅ | ✅ | ✅ | | ✅ | ✅ | | ✅ |
  | CLAIMED | | ✅ | ✅ | | ✅ | ✅ | ✅ | |
  | SENT | | | ✅ | ✅ | ✅ | | ✅ | |
  | PRINTER_ERROR | | | ✅ | ✅ | | ✅ | ✅ | ✅ |
  | PRINTED | | | | ✅ | | | | |
  | UNKNOWN | | | ✅ | ✅ | | ✅ | | ✅ |
  | VERIFIED·FAILED·CANCELLED | (끝) | | | | | | | |

- 사건만 남는 것(상태 아님): `VERIFY_NG`(검증 스캔 불일치 — 조용히 틀린 라벨), `WARN`(요청 때 경고: 한글 글꼴 없음 등), `STALE`.

**설치형 확인(PRINTED) — odometer 전후 비교**: 송신기는 DB 를 쓸 수 없고(아웃박스 규칙) 아웃박스 `SENT` 는 `last_error` 를 지운다 → 확인은 **따로 도는 상태 확인 작업**(`LabelJobs`, 정책 `WMS_PRINTER_PROBE_SEC` 기본 30초)이 맡는다.
1. 트랜잭션 안에서 확인할 DIRECT 프린터 목록만 읽는다(사용 중·`status_check_yn = Y`·주기 지남 또는 확인 안 된 SENT 작업 있음).
2. 트랜잭션 **밖**에서 TCP: `~HQES`(오류·경고 비트) + SGD `! U1 getvar "odometer.total_label_count"` — 주소는 송신기와 같은 검사(`PrinterAddress.resolveChecked`, 보낼 때마다 해석·사설 대역).
3. 회사 범위 트랜잭션에서 `PrintConfirm.apply`(판정식 한 곳 — 에이전트 하트비트도 같은 함수): 프린터 상태 행을 잠그고 `증가량 = 지금 − 기준`. 확인 안 된 작업(SENT·PRINTER_ERROR, 보낸 순)을 앞에서부터 `장 수 = 부수 × 서식 수(^XA 블록마다 ^PQ, 없으면 1)` 만큼 빼며 PRINTED, 남은 증가량은 버린다(다른 곳에서 찍은 장). 증가량이 첫 작업 장 수보다 작으면 기다린다. 오류 비트가 있으면 확인 안 된 작업에 `PRINTER_ERROR`(사유 = 첫 오류) 한 번.
- 한계(문서·화면 명시): 같은 프린터에 다른 시스템이 동시에 찍으면 증가량이 섞여 **너무 일찍 PRINTED** 가 될 수 있다(Zebra 문서도 "상태 확인보다 정확할 수 있다" 수준). 응답 없는 프린터·벤더(odometer 없음)는 SENT 에 머문다 — 벤더 중립 선택지(SNMP Printer MIB, RFC 3805 `prtMarkerCounterLife`)는 후속.
- `~HQES` 비트(Zebra ZPL 문서): 오류 `1 MEDIA_OUT`·`2 RIBBON_OUT`·`4 HEAD_OPEN`·`8 CUTTER_FAULT`·`10 HEAD_OVER_TEMP`·`20 MOTOR_OVER_TEMP`·`40 BAD_HEAD_ELEMENT`·`80 HEAD_DETECT`, 경고 `1 CALIBRATE`·`2 CLEAN_HEAD`·`4 REPLACE_HEAD`·`8 PAPER_NEAR_END`(부족 = warning 단계 — 5.5). 모르는 비트는 `ERR_x{16진}` 그대로 남긴다.
- 프린터 마지막 상태 `wms_printer_status`(OK·WARN·ERROR·OFFLINE·UNKNOWN, 오류·경고 코드, odometer, 확인 시각, 출처 DIRECT·AGENT) — 라벨 관리 프린터 목록·인쇄 이력에 보인다.

**검증(VERIFIED)**: `POST /api/wms/print-jobs/{id}/verify {scanned}`(wms-print-job PRINT) — 스캔 글자를 작업 값 `barcode`(없으면 bizKey)와 비교(앞뒤 공백·심볼 식별자 `]C1` 등은 걷어 냄). 같으면 VERIFIED, 다르면 `VERIFY_NG` 사건(상태 그대로 — 사람이 다시 붙이거나 재발행). 오토라벨러(E3)가 같은 함수를 부른다.

### 18.2 한글 글꼴(6.3)

- 프린터 칸 `cjk_font_yn`(한글 TTF 를 `~DY` 로 올렸나, 기본 N) + `cjk_font_file`(예 `E:NANUMGOTHIC.TTF`, 형식만).
- 템플릿 검사 경고(저장은 막지 않음 — `ZplLint`): 한글이 들어갈 수 있는 칸(`itemNm·locNm·custNm·spec·path`)의 필드가 기본 글꼴(`^A0`·글꼴 없음)이면 `CJK_FONT_MISSING`, `^CI28` 이 없으면 `CI28_MISSING`, `^Ax` 별칭을 쓰는데 템플릿에 `^CWx` 도 없으면 `CJK_FONT_ALIAS`.
- 요청 때: 프린터 `cjk_font_yn = N` 인데 실제 값에 한글이 있으면 작업에 `WARN NO_CJK_FONT` 사건(인쇄는 한다 — 막으면 지금 쓰는 라인이 선다. 이력 화면에 경고로 보인다).
- 견본 템플릿은 `^CWJ,E:NANUMGOTHIC.TTF` + 한글 칸 `^AJN` 으로 바꾼다(글꼴 파일은 설치 때 프린터에 올린다 — deploy 안내).

### 18.3 미리보기(ZPL → 그림)·넘침(6.4)

- Labelary 등 외부 렌더러는 쓰지 않는다(운영 데이터 전송 금지). **자체 배치 계산 `ZplLayout`**(순수 함수, 쓰는 부분집합 `^PW ^LL ^LH ^FO ^FT ^A ^CF ^FB ^GB ^BY ^BC ^BQ ^BX ^FD ^FS ^FR`) → 요소 목록(TEXT·BOX·BARCODE·QR·MATRIX, 점 단위 좌표·크기)을 미리보기 응답에 싣고, 화면이 **SVG DOM**(`createElementNS`, innerHTML 없음 — CSP 그대로)으로 그린다. "근사값 — 최종은 실물" 문구를 화면에 둔다.
- 글자 폭 추정: 한글·전각 = 글자 높이 h, 그 밖 = 폭 인자 w(없으면 h) × 0.6. 넘침 경고: 라벨 폭(`^PW`, 없으면 템플릿 폭 mm × dpi / 25.4)을 넘으면 `OVERFLOW_X:{칸}`, `^FB` 줄 수 초과면 `FB_LINES:{칸}`, 라벨 높이 밖이면 `OFF_LABEL:{칸}`.
- 저장·미리보기 때 **두 벌**로 계산: 견본 값 + "긴 값"(유형별 칸마다 현실적 최대 길이 — 품목명 한글 40자 등). 저장은 막지 않고 경고만(실물 확인 몫).

### 18.4 템플릿 선택 규칙(6.5)

- 템플릿에 크기 ID `size_cd` = `{폭}x{높이}`(mm, 생성 칸 — 물리 규격과 양식 분리, 같은 크기 템플릿 묶어 보기).
- 새 표 `wms_label_tpl_rule`: (유형, 범위 CUST|ITEM, 거래처 또는 품목) → 템플릿. 사용 중 규칙은 범위마다 하나(부분 유일). 찾는 순서 **거래처 > 품목 > 유형 기본**(`TemplateResolver`, 순수 + 매퍼 한 번).
- `LabelPrintService.request(유형, null, …)` 의 항목에 문맥(거래처 id·품목 id)을 줄 수 있다: `PrintItem(bizKey, values, custId, itemId)` — 기존 2칸 생성자는 그대로(문맥 없음 = 유형 기본, 지금 호출부 영향 없음). 출하 라벨·입고 LOT 라벨 호출부가 문맥을 넘긴다.
- 프린터와 맞는지 검사(요청 때 오류): 템플릿 dpi ≠ 프린터 dpi → `DPI_MISMATCH`(점 좌표가 그대로 커지거나 작아진다), 프린터 용지 폭 `media_width_mm`(선택) < 템플릿 폭 → `MEDIA_TOO_SMALL`.

### 18.5 GS1 확장(6.6)

- 스캔 해석(`ScanKeyResolver`): AI `310n`(순중량 kg, n = 소수 자리, 6자리 숫자) · `15`(소비기한 YYMMDD) 추가 → `Gs1.netWeightKg`·`bestBefore`.
- **두 바코드 결합** `ScanKeyResolver.combine(a, b)`: 한 박스의 식별용 + 속성(중량·기한·LOT) 바코드를 합친다. 둘 다 GS1 이어야 하고 같은 AI 의 값이 다르면 `GS1_MISMATCH`(다음 박스 바코드가 섞임) — 같은 AI·같은 값은 하나로.
- FNC1 경고(`Gs1.warnings`): 스캐너가 GS 를 글자 `<GS>`·`{GS}` 로 바꿔 보내면 GS 로 되돌리고 `FNC1_SUBSTITUTED`, 가변 AI 값 안에 다른 AI 모양(`17`+6자리·`310n`+6자리 등)이 끝에 붙어 보이면 `FNC1_MISSING_SUSPECT`(GS 를 빼먹은 스캐너 — 가변 AI 가 중간에 오면 깨진다).
- 출력 GS1 DataMatrix: 유형 LOT·PALLET·SHIP 에 칸 `gs1`(사람이 읽는 괄호 형식 `(01)…(10)…`) 추가. 템플릿에서 `{{gs1}}` 는 **`^BX` 필드에만**, `^BX` 의 7번째 인자(제어 문자, 예 `_` 아닌 `@`)가 있어야 한다. 렌더는 그 필드에 `^FH` 를 붙이지 않고 `Gs1Encoder` 가 괄호 형식을 검사(지원 AI·길이·검사 숫자 — 스캔 해석과 같은 표)한 뒤 **가변 AI 뒤에만 FNC1(제어 문자 + `1`)** 을 넣는다. GS1 문자 집합(82자) 밖·`^`·`~`·제어 문자 글자는 거부(`VALUE_CHARSET`) — ^FH 없이도 명령 주입이 없다.
- 자동차 납품 라벨(Odette GTL/VDA 4994, AIAG B-10)은 템플릿 후보로만(이번에 만들지 않음).

## 19. E2 설계 — pull 인쇄 에이전트 (2026-11-09, 하위 세션 `claude/equip-e1e2`)

> 마이그레이션: WMS V251·임시 V9301. SaaS 서버는 공장 안 프린터로 연결을 열 수 없다(3장 — 들어오는 연결 금지). 공장 PC 의 에이전트가 **바깥으로** 서버 API 에 붙어 작업을 당겨 가고, 로컬 프린터(9100·드라이버)로 찍은 뒤 결과를 보고한다. 엣지 명령 큐(16.1 "당기는 아웃박스")와 같은 lease 모양.

### 19.1 장치 키 — 시스템관리 쪽

- 에이전트도 **`sys_terminal` 유형 COLLECTOR(Bearer API 키)** 로 등록한다 — 시스템관리 `sys-terminal` 화면에서 등록·키 재발급·폐기(폐기·회사 정지 = 다음 요청부터 401). 새 단말 유형을 만들지 않는다: 키 모양·인증 체인(`ExtSecurityConfig`)·접속 기록·끊김 표시가 이미 있고, 한 PC 가 엣지와 인쇄 에이전트를 함께 해도 키 하나.
- 프린터 마스터 `conn_mode = AGENT` + `agent_terminal_id`(같은 회사 COLLECTOR, 트리거). AGENT 면 장치 필수.
- 장치 키는 회사 범위(키 → 회사) + **장치 범위**(그 장치에 배정된 프린터 작업만). A사 에이전트가 B사 작업을, 같은 회사 다른 에이전트가 남의 프린터 작업을 가져가지 못한다.

### 19.2 큐 — 요청 → 배정 → lease → 결과

```
LabelPrintService.request(…)  ── printer.conn_mode = AGENT ──▶ wms_print_job(conn_mode AGENT, 아웃박스 없음) + wms_print_dispatch(QUEUED)
에이전트 POST /ext/v1/print-agent/claim {max, waitSec}   ── FOR UPDATE SKIP LOCKED, 그 장치 것만 ──▶ CLAIMED(lease_until) + 사건 CLAIMED
          (없으면 waitSec 동안 1초 간격 롱폴링 — 웹소켓 없이, 본문은 pull)
에이전트 → 로컬 프린터(9100) → POST /ext/v1/print-agent/jobs/{jobId}/result {state: SENT|PRINTED|PRINTER_ERROR|FAILED, …}
정기 작업: CLAIMED 인데 lease 만료 ──▶ 사건 UNKNOWN(LEASE_EXPIRED) — **자동 재인쇄 금지**(이미 찍혔을 수 있다: SSCC·LOT 라벨 두 장)
```

| 단계(`wms_print_dispatch.stage`) | 뜻 | 다음 |
|---|---|---|
| QUEUED | 기다림 | claim → CLAIMED · 사람 닫기/다른 프린터로 넘기기 → CLOSED |
| CLAIMED | 에이전트가 가져감(lease) | 결과 SENT → SENT · PRINTED/FAILED → CLOSED · lease 만료 → CLOSED(UNKNOWN) |
| SENT | 프린터로 보냄 — 확인(PRINTED)은 결과 보고 또는 하트비트 odometer(18.1 과 같은 함수) | PRINTED/FAILED → CLOSED |
| CLOSED | 끝 | (늦은 결과는 상태표가 허용하면 반영 — UNKNOWN → PRINTED/FAILED) |

- 인쇄 상태 3단은 E1 과 **같은 사건 원장·같은 전이표**(`PrintStates`). 단계는 큐 관리(누가·언제까지)만 맡는다.
- 결과 보고 멱등: 키 = (작업, 상태). 같은 상태 재전송 = `DUP`(200, 사건 없음), 표가 허용 안 하는 늦은 결과 = `STALE` 사건(200 — 5.2-1 처럼 재전송을 막지 않는다). **보고는 그 작업을 가져간 장치만** — 다른 장치·다른 회사 jobId 는 404.
- 다른 프린터로 넘기기 `POST /api/wms/print-jobs/{id}/move {printerId, reason}`: QUEUED(아직 안 가져감)·UNKNOWN·FAILED·PRINTER_ERROR 작업만. 원 작업은 CANCELLED(사유) + 같은 ZPL 로 새 작업(재발행 경로 — `reprint_of_id`, LOT·파렛트·출하는 APPROVE). CLAIMED·SENT 는 넘기지 않는다(에이전트가 찍는 중일 수 있다).

### 19.3 하트비트·오프라인

- `POST /ext/v1/print-agent/heartbeat {bootId, printers:[{printerCd, online, errors[], warnings[], odometer}]}` — 그 장치 프린터만 반영(남의 프린터 코드는 `unknown` 으로 돌려줌). 프린터 상태는 18.1 `PrintTrackService.apply`(출처 AGENT) — odometer 증가로 SENT 작업 PRINTED, 오류 비트로 PRINTER_ERROR. 응답 `{queued}`(기다리는 작업 수 — 에이전트가 claim 을 바로 하게).
- 오프라인 = 장치 `last_seen_at`(인증 때 갱신) + 정책 `WMS_PRINT_AGENT_OFFLINE_SEC`(120) — 판정은 조회식(저장 안 함), 프린터 목록에 "에이전트 마지막 접속".

## 21. E3 설계 — 오토라벨러 (2026-11-10, 하위 세션 `claude/equip-e3`)

> 마이그레이션: WMS V259·임시 V9300(병합 때 재번호). 7장 흐름을 따른다. 인쇄 트리거·부착은 장비(PLC) 몫이고, YeonOS 는 **"기한 안에 데이터를 넣고 결과를 대조"** 하는 계약만 맡는다.

### 21.1 표

| 표 | 성격 |
|---|---|
| `wms_labeler` | 라벨러 마스터(공장·코드·장치 = sys_terminal COLLECTOR 키·연결 방식 DIRECT/EDGE·템플릿(PALLET 유형 — 물류 단위 SSCC 라벨)·응답 기한 ms) |
| `wms_labeler_box` | 사전 등록 박스(추적 코드 = 앞단 스캐너가 읽는 값, 품목·수량·LOT·참조, **라벨 생략** 표시, SSCC, 상태) — 상태 기계 |
| `wms_labeler_event` | **박스 단위 원장**(추가만): 요청·답(PRINT/SKIP/REJECT)·인쇄·부착·검증 OK/NG·리젝트·SSCC 결번 |
| `wms_labeler_dev_log` | **장비 단위 원장**(추가만): 오류·상태·리젝트 라인 만재 |

박스 상태: `REGISTERED → (PREFETCHED) → REQUESTED → VERIFIED` · `REJECTED`(재라벨 = 다시 REQUESTED, **같은 SSCC**) · `SKIPPED`(이미 라벨 있음). PREFETCHED 를 쓰지 않고 놓으면(결번) REGISTERED 로 돌아가고 SSCC 는 비운다 — 그 번호는 다시 쓰지 않는다(Q5).

### 21.2 판정 — 요청 `POST /ext/v1/labeler/request {requestId, scanned, sentAt?}`

| 경우 | 답 | 사유 코드 |
|---|---|---|
| 앞단 no-read(빈 값) | REJECT(라벨 없이 리젝트) | `NO_READ` |
| 미등록 박스 | REJECT | `UNREGISTERED` |
| 라벨 생략 표시 | SKIP | `LABEL_SKIP` |
| 이미 검증 끝난 박스가 다시 옴 | REJECT | `DUPLICATE` |
| 서버 처리 또는 `sentAt` 부터 기한(`deadline_ms`) 초과 | REJECT — **늦게 온 정답 = 오답**(그 박스에 쓰지 않는다) | `LATE` |
| 정상 · 리젝트 뒤 재라벨 | PRINT + SSCC(처음이면 새로, 재라벨이면 **같은 번호**) + 템플릿 코드·크기 ID + 값 + 렌더된 ZPL | — |

- SSCC 는 출하 팔레트와 **같은 일련번호**(`WMS_SSCC` 채번 규칙, 업체코드 정책 `WMS_GS1_COMPANY_PREFIX`) — 한 회사 SSCC 는 한 줄. 업체코드가 없으면 409(라벨러는 SSCC 없이 못 돈다).
- 멱등: (라벨러, requestId) 의 요청 사건은 하나(부분 유일) — 같은 requestId 다시 = **처음 답 그대로**(답 JSON 을 사건에 저장).
- 결과 `POST /ext/v1/labeler/result {requestId, phase: PRINTED|APPLIED|VERIFY|REJECTED, scanned?, reasonCd?}`: VERIFY 는 검증 스캔(GS1 `(00)`·`]C1 00…`·18자리)을 그 박스 SSCC 와 대조 → `VERIFY_OK`(VERIFIED) / `VERIFY_NG`(REJECTED, `VERIFY_MISMATCH`·`VERIFY_NO_READ` — 빈 라벨·다른 박스 라벨을 잡는 핵심). 장비 리젝트(`NOT_APPLIED`·`PRINT_FAIL` …)는 REJECTED. (requestId, 단계) 한 번 — 다시 = DUP, 이미 뒤 시도가 끝낸 박스면 STALE.
- 사유 코드는 공통코드 `WMS_LABELER_REASON`(시스템 코드 + **회사 확장** — 장비마다 다른 리젝트 사유), 칸에 `hb_check_code_col`. 장비가 모르는 코드를 보내면 `OTHER` + 원래 코드를 설명에(수신을 깨지 않는다).

### 21.3 SaaS — 미리 받기(7.4)

- 라벨러 `conn_mode = EDGE`: 엣지가 `POST /ext/v1/labeler/prefetch {max}` 로 그 공장의 REGISTERED 박스를 **SSCC 를 붙여** 미리 받는다(PREFETCHED). 현장에서는 엣지가 기한 안에 혼자 답하고, 나중에 `request {…, answeredLocally: true, action, sscc}` + `result` 로 올린다(저장 후 전달 — 기한 검사 안 함, 보낸 SSCC 가 미리 받은 번호와 다르면 거부).
- 쓰지 않은 미리 받기: `POST /ext/v1/labeler/release {boxCds}` 또는 정기 작업(정책 `WMS_LABELER_PREFETCH_HOURS`, 기본 24) → 사건 `SSCC_VOID`(결번 기록, 번호 재사용·이월 없음 — Q5).
- 설치형(DIRECT)은 같은 API 를 LAN 에서 바로 부른다(미리 받기 없음).

### 21.4 장비 단위 — `POST /ext/v1/labeler/event {type: ERROR|STATE|REJECT_FULL, code, detail}`

장비 단위 원장에 남기고, 리젝트 라인 만재(`REJECT_FULL`)는 정책 `WMS_LABELER_REJECT_FULL`(WAIT·ALARM·STOP, 기본 STOP)을 답으로 돌려준다 — 장비가 그대로 따른다.

### 21.5 화면·권한

화면 `wms-labeler`(SEARCH·SAVE): 박스 목록(hb.grid, 상태·SSCC·시도 수·마지막 사유) + 상세(박스 사건 원장) + 박스 사전 등록 + 라벨러 마스터. 검증 끝(VERIFIED) 박스 수는 ASN 마감(7.1-6)의 조건 — ASN 연결은 후속.

### 21.6 가짜 라벨러

`tools/fake-labeler.mjs`(Node 18+, 의존성 없음): 박스 흐름(앞단 스캔 → request → 인쇄·부착 → 검증 스캔 → result)과 장애 주입 `--scenario normal|no-read|late|wrong-label|empty-label|print-fail|unregistered|reject-full|dup-request`, `--mode direct|edge`(edge = prefetch → 혼자 답 → 나중에 올림).

## 23. E4 설계 — 자동창고 보관 용기 (2026-11-10, 하위 세션 `claude/equip-e4`)

> 마이그레이션: WMS V261·임시 V9300(병합 때 재번호). 8장·결정 Q1(별도 용기 마스터, 원장은 자동창고 = 가상 로케이션 1개)·Q2(수량·LOT = WMS 원장, 랙 위치 = WES, 차이는 격리 + 사람 확인)를 따른다. 작은 조각으로 나눠 단계마다 커밋한다.

### 23.1 표 (V261·임시 V9300)

| 표 | 성격 |
|---|---|
| `wms_asrs` | 자동창고 마스터 — 공장·코드·**가상 로케이션 노드**(`wms_loc_attr.loc_usage = AUTO_STORE`)·입고 투입구 노드·출고 출구 노드·장치(COLLECTOR 키 — WES 어댑터 또는 엣지)·연결 DIRECT/EDGE·WES 주소(DIRECT, 사설 대역)·처리 기한(분) |
| `wms_ctr_type` | 용기 물리 유형(치수 mm·칸 수) — 마스터 |
| `wms_ctr` | 개별 용기(코드·바코드 = 스캔 키 `CTR:{코드}`·유형·자동창고·상태 EMPTY·LOADED·IN_SYSTEM·QUARANTINE) |
| `wms_ctr_content` | 용기 칸별 내용 **사본**(칸·품목·LOT·수량) — 원장 칸은 늘리지 않는다(Q1). 같은 칸에 같은 품목 다른 LOT = 경고 표시(피킹·실사 대상에서 빠짐 — 장비 규칙) |
| `wms_asrs_req` / `wms_asrs_req_line` | 입·출고 요청 / 라인 — 상위 상태는 하위 집계로 **계산**(직접 쓰지 않음, 8.2) |
| `wms_asrs_event` | 요청·라인·용기 사건 원장(추가만): 보냄·접수·진행·완료·오류·stale·충돌·경계 교환·대사 차이 |
| `wms_asrs_recon` / `wms_asrs_recon_diff` | 대사 회차 / 차이 줄(용기 유무·칸별 품목·수량·LOT) — 차이는 격리 + 조정 후보 |

공통코드: 용기 상태·요청 유형·라인 상태는 분기에 쓰여 시스템 고정(이름만 i18n). 스테이션 예외 사유·대사 차이 종류는 **회사 확장 그룹**(`WMS_ASRS_EXC_REASON` — 파손·빈 용기·부족·잘못된 품목·형상 불일치 등, `hb_check_code_col`).

### 23.2 입고 — 용기 정의 먼저, 원장 반영은 "랙에 넣은 시점"

1. 사람(또는 PDA)이 용기에 담을 내용을 정의: 용기 + 칸별 품목·LOT·수량(입고 투입구 노드의 재고에서 — 재고가 모자라면 409, 원장 그대로).
2. 입고 요청(라인 1 = 용기 1) → 보내기: DIRECT = 아웃박스 `ASRS_REQ` → WES 주소로 POST(외부 요청 id = 우리가 만든 `reqKey` — 송신기는 DB 를 쓰지 않으니 멱등 키를 우리가 정한다) / EDGE = 엣지가 당겨 감(E2 와 같은 당기는 큐 모양).
3. 시작 전에는 수정(전체 덮어쓰기 — 빠진 칸은 비워짐)·취소, **시작 후에는 거절**(WES 가 진행 중이면 WMS 도 진행 중). 지운 요청 id 는 다시 쓰지 않는다.
4. WES 콜백 `STORED`(로봇이 랙에 넣음) 때 **같은 트랜잭션**에서 원장 MOVE(투입구 → 자동창고 가상 로케이션, src `ASRS_IN`, 용기 내용 행 수만큼) + 용기 IN_SYSTEM. 출입구 도착(ARRIVED)은 원장에 반영하지 않는다.

### 23.3 출고 — 라인 = 품목(+LOT)·수량, 용기 고르기는 WES

- 출고 요청 라인 N개 → WES 가 용기를 골라 출구로 → 콜백 `PICKED`(용기·칸·수량) → `HANDED_OVER`(출구 인계 완료) 때 원장 MOVE(자동창고 → 출구 노드, src `ASRS_OUT`) + 용기 내용 사본 차감. 라인별 부분 완료, **모든 라인이 끝나야 요청 완료**.

### 23.4 WES 콜백 — 수신 규약(5.2) 그대로

- 경로 `WES_CALLBACK`(E0 `InboundRoute`): 키 = `reqKey + lineNo + ctrCd + status`(상대 메시지 ID 금지 — 같은 콜백 297회), 내용 = 수량·칸·오류. 받는 길 두 개가 같은 처리: DIRECT WES 는 `POST /ext/v1/wes/callback`(WES 형식을 우리가 저널에 넣음), SaaS 엣지는 `POST /ext/v1/edge/messages {route: WES_CALLBACK}`.
- 같은 키·다른 내용 = CONFLICT(처리 안 함 + 사건), 늦게 온 옛 상태 = STALE(되돌리지 않음), **완료 + 오류 = 실패**(`InboundOutcome`), 상태 코드를 범위로 묶지 않는다.
- WES 가 408·425·429·503·504 를 받으면 FIFO 로 다시 보낸다 → 우리는 저장 후 200, 처리 오류는 격리 큐로(503 금지).

### 23.5 컨베이어 경계 교환(8.3)

`POST /ext/v1/wes/exchange {ctrCd 스캔, direction IN|OUT}` — 투입 직전 스캔이 "요청한 그 용기"인지(입고: 요청 라인의 용기·대기 중) 답한다: `GO` / `REJECT`(미등록·불일치·요청 없음) / `WAIT`(자동창고 포화 — WES 가 알려 준 상태). 판정·사건만 — 컨베이어 구동은 장비 몫.

### 23.6 대사(8.4) — 덮어쓰지 않는다

- 하루 한 번(또는 화면 "지금") WES 전체 용기 정의를 받아(`POST /ext/v1/wes/snapshot` — 큰 본문은 나눠 받음) 우리 사본·원장과 비교: 용기 유무·칸별 품목·LOT·수량.
- 차이 = **격리**(용기 QUARANTINE — 출고 할당 제외) + 조정 후보 줄. 사람이 확인 → 조정 전표(역분개 + 새 행)는 **기존 재고 조정 경로**로(이 단계는 후보까지 — 23.9 Q-E4-1).
- 스테이션 예외 알림(수량 조정·격리)도 같은 차이 줄로(작업자가 조용히 고치지 않는다).

### 23.7 감시(8.5)

- 기준 시간(정책 `WMS_ASRS_STALE_MIN`, 기본 30분) 넘게 NOT_STARTED·IN_PROGRESS 인 요청 = 사건 `STALE_REQ` + 화면 경보(로봇이 닿지 못하는 용기는 오류 없이 영원히 NOT_STARTED — 현장 시험).
- 차단된 랙·격리 용기 요청은 WMS 쪽 사전 검사로 막는다.
- KPI(시간당 처리량·사이클 타임·대사 차이율)는 조회 API 만(CMS·홈 카드 연결은 후속).

### 25.1 출고

- 출고 요청 = 라인 N개(품목 + 선택 LOT + 수량). 만들 때 자동창고 가상 로케이션의 **AVAILABLE 재고 − 격리 용기 내용 − 다른 열린 출고 라인 남은 수량** 이 모자라면 409(원장 그대로). LOT 이 없으면 품목 합으로만 본다(어느 LOT 을 집을지는 WES — Q-E4-3).
- WES 콜백(같은 경로 `WES_CALLBACK`, 키 = reqKey + lineNo + ctrCd + status): 라인 단위 상태(ACCEPTED·IN_PROGRESS·COMPLETED·FAILED·CANCELLED)는 용기 칸에 `-` 를 넣는다(키 칸은 비울 수 없다 — E0 저널 규칙). 용기 단위 상태 = `PICKED`(집음, 원장 없음) → `HANDED_OVER`(출구 인계, qty·slot) 때 **같은 트랜잭션**에서 원장 MOVE(가상 로케이션 → 출구 노드, src `ASRS_OUT`, 품목·LOT·상태별 한 쌍) + 용기 내용 사본 차감 + 라인 반영 수량 증가.
- 인계 수량이 라인 남은 수량보다 많음 = 원장 없음 + 용기 격리 `OVER_PICK`. 용기 사본에 그 품목(지정 LOT)이 모자람 = 원장 없음 + 격리 `SHORT`. 격리 용기에서 인계 = 원장 없음 + 사건(사람이 본다). 모두 "덮어쓰지 않는다"(Q2).
- 반영 수량 = 라인 수량이면 라인 DONE. `COMPLETED` 가 왔는데 덜 집음 = **라인 SHORT**(끝 상태, 사건 SHORT) — 남은 수량은 사람이 새 출고 요청으로(Q-E4-2). 완료 + 오류 = 실패(입고와 같음). 요청 진행은 SHORT 가 있으면 PARTIAL.

### 25.2 긴급 출고 (Q-E4-4)

- 위험(실측, 8장): 우선순위 칸을 넣자 WES 가 병렬로 돌던 출고를 순서대로 처리해 처리량이 떨어졌다. 그래서 **일반 출고는 우선순위 칸을 아예 보내지 않고**(JSON 에 칸 없음), 긴급만 `"priority":"URGENT"`.
- 긴급 표시는 보내기 전(DRAFT) 출고 요청에만, **APPROVE 권한**(조회·저장만 있는 사람은 403), 사유 필수(2자 이상). 사건 `URGENT`(누가·언제·사유) — 표시는 되돌리지 않는다(남용 기록이 지워지지 않게).
- 남용 감시: `GET /api/wms/asrs/urgent-stats?days=N` = 기간 안 출고 요청 수·긴급 수·표시한 사람별 건수(사건 원장에서 셈). 홈 카드·경보 연결은 후속.

### 25.3 대사 + 바로 조정 (Q-E4-1)

- WES 가 전체 용기 정의를 `POST /ext/v1/wes/snapshot {snapKey, partNo, lastPart, containers:[{ctrCd, contents:[{slot,itemCd,lotNo,qty}]}]}` 로 나눠 보낸다. (snapKey, partNo) 가 이미 있으면 DUP(멱등), 마지막 조각을 받으면 그 자리에서 비교. 큰 본문을 E0 저널에 넣지 않는 이유: 비교는 조각이 다 모여야 하고 순서 문제가 없다(조각 표가 원문 보관).
- 비교 = 용기·칸·품목·LOT 별 수량(우리 = IN_SYSTEM·QUARANTINE 용기의 사본). **움직이는 중인 용기**(끝나지 않은 입고 라인, 끝나지 않은 출고 라인에 사건이 있는 용기)는 건너뛰고 건수만 센다(헛 차이 방지). 차이 종류: `QTY`(양쪽 수량 다름 — 한쪽 0 포함) / `UNKNOWN`(WES 만 아는 용기·품목·LOT — 조정 불가, 확인만). 차이가 난 용기 = 격리 `RECON_DIFF`(출고 할당 제외) + 사건.
- 조정 = `POST /api/wms/asrs/recon-diffs/{id}/adjust {reasonCd, remark, rowVer}` — **APPROVE 권한**, 사유 = 재고 조정 사유 공통코드 `WMS_ADJ_REASON` 필수. 원장은 **기존 재고 조정 서비스 `StockService.adjust`(공개 메서드)** 로만(원장 직접 INSERT 금지): ADJ_IN/ADJ_OUT, 가상 로케이션, 차이 = WES − 우리, clientReqId = `ASRS-RECON-{diffId}`(재시도는 처음 결과 — 원장 규칙 PQ-1). 차이 줄은 OPEN → ADJUSTED 한 번만(행 잠금 + rowVer + 끝 상태 되돌림 금지 트리거 + 조정 요청 id 유일) → 같은 차이를 두 번 조정하지 않는다. 누가·언제 = 차이 줄 resolved_by/at + 원장 recorded_by + 사건 ADJUSTED.
- 조정할 때 사본이 대사 때와 달라졌으면(그 사이 출고 등) 409 — 다시 대사. 사본도 WES 값으로 맞춘다. 용기의 열린 차이가 다 닫히면 격리 해제(IN_SYSTEM).
- `dismiss`(APPROVE, 비고 필수) = 우리 쪽이 맞다고 확인 — 원장 그대로, WES 정정은 사람.
- **재고 조정 한도·승인 정책은 아직 결정 대기**(docs/46 11장, docs/29 "WMS 재고 조정 한도·승인"). 그 정책이 생기면 `StockService.adjust` 한 곳에 걸면 이 경로도 같은 정책을 탄다 — 이 화면은 자기 한도를 따로 두지 않는다.

### 25.4 표 (V262·임시 V9301)

`wms_asrs_req.urgent_yn·urgent_reason`(OUT 만), 라인 상태 + `SHORT`, 사건 + `URGENT·SHORT·RECON·RECON_DIFF·ADJUSTED·DISMISSED`, 예외 사유 + `RECON_DIFF·OVER_PICK`, `wms_asrs_recon`(회차)·`wms_asrs_recon_part`(받은 조각 = 원문)·`wms_asrs_recon_diff`(차이 줄, OPEN → ADJUSTED/DISMISSED 끝 상태 고정), 화면 액션 + APPROVE.
