## 2. 구성

```
GitHub (push to main)
  └─ Actions: ./gradlew check → bootJar ─SCP─▶ VM (Ubuntu, Ampere A1)
                                               docker compose
                                               ├─ caddy    :80/:443  자동 HTTPS(Let's Encrypt) → app:8090
                                               ├─ app      prod,demo  (앱 계정만, 힙 512MB)
                                               ├─ migrate  1회 실행    (소유자 계정, 끝나면 종료)
                                               └─ db       postgres:16  (포트 공개 안 함, 내부망만)
```

- **포트 공개**: 22(SSH, 키 인증만)·80·443 만. DB 5432 는 호스트에 열지 않는다(compose 내부망).
- **DB 계정**: `deploy/install/init-roles.sql` 을 그대로 쓴다 — 슈퍼유저 `postgres`(초기화·리셋 전용), 소유자 `yeonos_owner`, 앱 `yeonos_app`. 앱 컨테이너에는 **소유자 자격증명을 주지 않는다**(01 7.1 그대로) → `DatabaseRoleGuard`·`ProdStartupGuard` 통과가 곧 검증.
- **비밀의 위치**: DB 비밀번호 3개·데모 비밀번호는 **VM 의 `/opt/yeonos/.env`(600)** 에만. GitHub Secrets 에는 SSH 접속 정보(호스트·사용자·개인 키·known_hosts)만 둔다 — Actions 가 털려도 DB 비밀번호는 없다.
- **이미지 빌드**: `Dockerfile` 은 빌드 단계 없이 `COPY smarthappy.jar` + JRE 만. VM 에서 `docker compose build` → arm64 로 조립된다. 레지스트리(GHCR) 불필요 → private 저장소 패키지 권한 문제도 없음.

### 2.1 배포 순서 (Actions → VM)

1. `./gradlew check` (Testcontainers — ubuntu 러너에 Docker 있음). 실패하면 배포하지 않는다.
2. `bootJar` → `smarthappy.jar` 로 이름 고정.
3. SCP 로 `/opt/yeonos/releases/{sha}.jar` + compose·Caddyfile 복사, `current.jar` 링크 교체.
4. `docker compose run --rm migrate` (소유자 계정, `--spring.profiles.active=migrate`) — 실패하면 앱은 옛 jar 로 계속 돈다.
5. `docker compose up -d --build app` → `/actuator/health/readiness` 가 UP 될 때까지 대기(최대 120초). 실패하면 이전 jar 로 되돌리고 워크플로 실패.
6. 오래된 jar 는 최근 3개만 남긴다.

> 순서 4→5 사이에 옛 앱이 새 스키마를 보면 `ProdStartupGuard` 의 버전 불일치는 **기동 시**만 검사하므로 이미 떠 있는 옛 앱은 계속 돈다. 데모는 무중단을 요구하지 않으므로 그대로 둔다 [추정].

### 2.2 JVM·자원 상한

| 항목 | 값 | 이유 |
|---|---|---|
| `JAVA_TOOL_OPTIONS` | `-Xmx512m -XX:MaxMetaspaceSize=192m -Xss512k -XX:+UseSerialGC` | Railway 교훈 — 상한 없는 JVM 은 가진 메모리를 다 쓴다 [경험·추정] |
| compose `mem_limit` | app 900m · db 512m · caddy 128m | VM 메모리 안에서 서로 잡아먹지 않게 |
| Hikari 풀 | `DB_POOL_SIZE=5` | 동시 방문자 수가 적다 |
| 스케줄 | 켜 둠(기본) — 아웃박스 5초·집계·다이제스트 매시 | Oracle 은 사용량 과금이 아니라 유지 비용 0. 오히려 약간의 CPU 사용이 유휴 회수 판정을 늦춘다 [추정] |

## 3. 앱 변경 — `demo` 프로필 (E3~E8)

### 3.1 프로필 조합

`--spring.profiles.active=prod,demo`. `application-demo.yml` 은 **prod 위에 얹는 것만** 쓴다.

- prod 가드 8항목(`ProdStartupGuard.java:56-87` [코드]) 전부 그대로 통과해야 한다 → demo 시더는 `happyboot.dev.*`(가드가 막는 값)를 쓰지 않고 **새 키 `happyboot.demo.*`** 를 쓴다.
- `happyboot.dev.login-prefill` 은 쓰지 않는다(가드 위반). 대신 로그인 화면에 "데모 계정 안내" 문구를 demo 프로필에서만 보여 준다(i18n 키 `login.demoNotice`). **2026-10-26 사용자 결정: 손님이 바로 들어오게 회사·아이디·비밀번호를 모두 안내 문구에 쓰고, 회사·아이디 칸을 미리 채운다**(dev.login-prefill 과 별개 — demo 프로필 안내 전용 값).

### 3.2 데모 시더 `DemoAccountSeeder` (`@Profile("demo")`)

`LocalDevSeeder` 와 같은 방식(앱 계정 + `TenantRunner.run`, 멱등) [코드 `LocalDevSeeder.java:25-105`].

| 만드는 것 | 내용 |
|---|---|
| 회사 | `DEMO` "데모 회사", 공장 `P1` |
| 권한그룹 `DEMO_VIEWER` | **허용 목록**: 기준정보 `mst-*` 화면의 모든 액션(P1 화면 포함) + `sys-usage` SEARCH + `sys-my-info` **SEARCH 만**(비밀번호 변경 불가) + **나머지 업무 모듈 전 화면 SEARCH**(`sys-*`·`home-*` 를 뺀 규칙 — 품질·창고·구매·설비·프로젝트·계획·설계변경·APQP, 홈 `home-main` 조회, 2026-10-26 사용자 결정). `sys-support`·홈 카드 관리·앞으로 생길 시스템 관리 화면은 자동으로 빠진다 |

- 회사코드는 `happyboot.dev.comp-cd`(기본 `DEMO`) — `DemoDataSeeder` 와 같은 키. 이 키는 prod 가드 대상이 아니다(가드는 `dev.admin-password`·`dev.login-prefill` 만 막는다).

- `DEMO_PASSWORD` 는 공개되는 값이지만 `.env` 로 받는다 — 코드·yml 에 박지 않아야 바꿀 때 재빌드가 필요 없다.

### 3.3 계정 잠금 공격 (E5)

공개 비밀번호 + 5회 잠금(`application.yml:73-74`, 전역 설정 [코드]) → 아무나 틀린 비밀번호 5번으로 데모를 15분 막을 수 있다.

| 안 | 내용 | 판정 |
|---|---|---|
| A | `application-demo.yml` 에 `happyboot.security.max-login-fail: 1000` — 계정 잠금은 사실상 끄고 **IP 시도 제한**(IP+회사 10분 20회, IP 10분 100회 [코드 `LoginAttemptLimiter`])에 맡김 | **권고** — 코드 변경 없음, 운영 코드 경로에 예외를 만들지 않음 |
| B | 사용자별 "잠금 예외" 컬럼 | 기각 — 스키마 변경 + 운영에도 들어가는 우회 경로 |
| C | 데모 계정 여러 개(demo1~5) | 보류 — 다 막히면 같은 문제, 안내만 복잡 |

A 는 **E6(실제 IP) 이 먼저 고쳐져야** 의미가 있다. 그렇지 않으면 IP 제한이 Caddy IP 하나로 묶여 한 사람이 모두를 막는다.

### 3.4 프록시 뒤 실제 IP·HTTPS (E6) — prod 결함

현재 앱은 `server.forward-headers-strategy` 설정이 없고 IP 를 `request.getRemoteAddr()` 로만 읽는다(`LoginDetails.java:11`, `AccessLogService` l.76, `OpsSecurityConfig` 게이트 [코드]). 리버스 프록시 뒤에서는:

1. 모든 사용자가 프록시 IP → IP 시도 제한이 전원 공유(한 사람이 전원 차단 가능)
2. 접속 로그 IP 가 전부 프록시 IP → 탐지·감사 가치 상실
3. 앱이 요청을 http 로 인식 → HSTS 미발송(`SecurityConfig.java:110-111`), 리다이렉트가 http 로
4. 운영자 콘솔 허용 IP 가 프록시 IP 와 비교됨

**조치(2026-10-20 구현)**: `application.yml`(전 프로필)에 `server.forward-headers-strategy: native` + `server.tomcat.remoteip.internal-proxies: ${TRUSTED_PROXIES:}`.
- 처음 안(Tomcat 기본 신뢰 대역 10/8·172.16/12·192.168/16 을 그대로 씀)은 **기각** — 설치형 고객사는 사용자 PC 자체가 사설 대역이라, 프록시 없이 직접 받는 배포에서 아무 PC 나 `X-Forwarded-For` 로 IP 를 바꿀 수 있다. 그래서 기본은 "아무도 안 믿음"이고 배포마다 프록시 주소를 적는다(데모: compose 내부망 CIDR).
- 확인한 동작 [코드 — Boot 4.1.1·Tomcat 11.0.24 바이트코드]: Boot 는 값을 그대로 `RemoteIpValve.setInternalProxies` 에 넘기고, Tomcat 11 은 빈 문자열이면 신뢰 없음, `/` 가 있으면 CIDR 목록, 아니면 정규식으로 해석한다.
- prod 가드: 신뢰 범위가 공인 주소(TEST-NET·8.8.8.8·2001:db8::)를 받아들이면 기동 중단(`ProdStartupGuard.trustsPublicAddress`, Tomcat 과 같은 규칙으로 해석).
- 테스트(실제 포트, MockMvc 는 밸브를 거치지 않음): `ForwardedHeaderTrustedTest` 4건 · `ForwardedHeaderUntrustedTest` 3건(T3) · `ProdGuardTest` 1건 추가. 고치기 전 Trusted 4건 실패로 결함 재현.

설치형 고객사도 대부분 nginx·IIS 등 프록시 뒤에 둔다 → 이 수정은 demo 전용이 아니라 **01 7장 보안 기본값에 반영**할 항목이다.

### 3.5 운영자 콘솔 (E8)

demo `.env` 에 `OPS_SECRET_KEY` 를 두지 않는다 → `Ops.enabled()` false → `/ops`·`/api/ops/**` 404 [코드 `HappyBootProperties.java:85-87`]. migrate 실행에도 `OPS_BOOTSTRAP_*` 를 주지 않는다.

## 5. 매일 초기화 (E7)

앱 계정은 기준정보 DELETE 권한이 없고(`use_yn='N'`), 원장·감사 로그는 삭제가 막혀 있다 [코드]. 따라서 **DB 를 통째로 다시 만든다**.

`deploy/demo/reset.sh` (VM cron, 매일 04:00 KST):
1. `flock` 으로 배포(`deploy.sh`)와 겹치지 않게 잠근다
2. `docker compose stop app` → app·db 컨테이너 제거 → DB·첨부 볼륨 삭제 → `up -d --wait db`(initdb 가 `init-roles.sql` 로 롤·DB 재생성)
3. `docker compose run --rm migrate` → `up -d app`(시더가 회사·계정·데이터 생성) → readiness 확인(`wait-ready.sh`)
4. 그동안 Caddy 가 502/503 대신 "점검 중" 안내를 보여 준다(`handle_errors`) — 처음 안(`status.json`)은 앱이 꺼져 있으면 읽을 주체가 없어 기각

부수 효과: 감사 로그·다이제스트 체인도 매일 처음부터 — 데모이므로 허용.
