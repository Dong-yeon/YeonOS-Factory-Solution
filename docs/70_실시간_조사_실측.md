## 0. 결론 먼저 (실측 2026-11-10)

1. **지금 구조의 상한은 이 PC 에서 초당 약 540~620 건**이다(장치 10대). 1천·1만 건/초 모두 못 받는다. 이벤트 1건 = **커밋 2번**(실측 커밋/초 ≈ 2 × 받아들인 건/초)이고, DB 대기의 대부분이 **WAL 쓰기·fsync**(`LWLock:WALWrite`·`IO:WALSync`)다 — 스레드도 CPU 도 아니라 **커밋 수**가 막힌다(4.4).
2. 같은 표에 DB 만 두고 잰 상한(pgbench, 10 연결): 지금 모양(이벤트당 커밋 2) **약 1,000 건/초** → **묶음 50건 한 트랜잭션 약 11,000 건/초(11배)** → 묶음 + `sys_inbox` 행 없음 **약 17,200 건/초(17배)**. 즉 **1만 건/초는 W1(요청 하나 = 트랜잭션 하나)만으로 DB 쪽 상한 안에 들어온다**(4.5).
3. 저장량: 행당 약 200바이트(색인 포함). 1천 건/초면 **원장·`sys_inbox` 각각 하루 8,640만 행 ≈ 17GB** — `sys_inbox` 는 지우지 않는 표라 쓰기 속도보다 **이쪽이 먼저 문제**가 된다(W2).
4. **가상 스레드는 차이가 없었다**(수집 API·홈 카드 API 모두 처리량 같음, 오차 안). 상한이 풀 10개와 커밋에 있기 때문 — 켜도 되지만 얻는 것이 없다. 지금은 켜지 않는 것을 권한다(2.3, R1).
5. 같은 장치가 요청을 겹쳐 보내면(동시 4) 처리량은 그대로이고 **지연만 3~4초로** 늘었다 — 장치 seq 행 `FOR UPDATE` 대기(`Lock:transactionid`). 수집기는 **장치당 한 번에 한 요청**이 맞다(4.2).
6. 화면 실시간은 **SSE + "바뀌었다" 신호만**으로 시작했다(홈, 구현·시험 완료, 3장). 데이터는 늘 기존 API 로 → 권한·회사 범위 판단이 한 곳. WebSocket 은 화면에서 서버로도 계속 메시지가 가야 하는 기능이 생길 때 그 기능에만(5장).

## 2. 가상 스레드 (`spring.threads.virtual.enabled`)

### 2.1 켜면 바뀌는 것 (Boot 4.1 기준)

- Tomcat 요청 처리, `@Async`·스케줄러(`SimpleAsyncTaskExecutor`·`SimpleAsyncTaskScheduler`)가 가상 스레드로. 요청 스레드 상한(기본 200)이 사실상 없어진다 → **대기 줄이 Tomcat 앞에서 DB 풀(Hikari) 앞으로 옮겨 간다**.
- 지금 풀은 `maximum-pool-size: ${DB_POOL_SIZE:10}`(`application.yml` hikari). 모든 업무 요청은 DB 트랜잭션 안에서 일한다(01 "DB 접근은 항상 트랜잭션 안") → 가상 스레드를 켜도 **동시에 DB 일을 하는 요청은 10개**. 11번째부터는 Hikari `connectionTimeout`(기본 30초)까지 기다리다 실패한다 — 지금(Tomcat 200 + 풀 10)과 같은 한계, 다른 곳에서.

### 2.2 이 저장소 코드에서 걸리는 것 (확인)

| 항목 | 상태 | 근거 |
|---|---|---|
| `ThreadLocal` | 회사 범위 `TenantContext.CURRENT`, 트랜잭션 관리 `TenantAwareTransactionManager.OPEN`·`AFTER_RELEASE` — 가상 스레드도 스레드별 값을 가진다. 요청 끝에 닫는 구조라 문제 없음 | `platform/tenant/TenantContext.java:21`, `TenantAwareTransactionManager.java:29-30` |
| `synchronized`(가상 스레드를 운반 스레드에 묶는 문제) | Java 24+(JEP 491)에서 `synchronized` 안 대기가 더는 운반 스레드를 묶지 않는다 — Java 25 라 해당 없음. 우리 코드의 `synchronized` 는 8곳(SRM 메일함·그리드 PoC·전자서명 토큰), 모두 메모리 안 짧은 구간 | `grep synchronized` 8건 |
| JDBC 드라이버 | pgjdbc **42.7.14**·HikariCP **7.0.2**(잠금 파일 확인). pgjdbc 는 42.6 부터 내부 잠금을 `ReentrantLock` 으로 바꿨다(추정 — 릴리스 노트 확인 필요). Java 25 라 어느 쪽이든 운반 스레드 묶임은 없다 | `gradle.lockfile` |

| 정기 작업 겹침 | 가상 스레드 스케줄러는 작업마다 새 스레드라 **오래 걸린 고정 주기 작업이 겹쳐 돌 수 있다**(추정 — Spring `SimpleAsyncTaskScheduler` 문서 확인 필요). 우리 정기 작업은 회사마다 `JobLock.tryLock`(advisory lock)이라 겹쳐도 한 곳만 일한다 | SKILL §2 정기 작업 |

### 2.3 실측 — 켬 vs 끔 (2026-11-10)

켜졌는지는 스레드 덤프로 확인했다: 켠 쪽은 Tomcat 작업 스레드(`http-nio-…-exec-N`)가 **0개**, 명령줄 `spring.threads.virtual.enabled=true`.

**① 화면 API 동시 요청** — 한 세션으로 `GET /api/home/cards` 를 동시 C 개씩 15초 계속(닫힌 고리, `tools/api-concurrency.mjs`)

| 동시 | 끔: 요청/초 · p50 · p95 (ms) | 켬: 요청/초 · p50 · p95 (ms) | 오류 |
|---|---|---|---|
| 10 | 28 · 357 · 388 | 26 · 338 · 459 | 0 / 0 |
| 100 | 27 · 3,557 · 3,950 | 29 · 3,435 · 3,556 | 0 / 0 |
| 400 | 28 · 13,869 · 14,865 | 25 · 14,942 · 15,737 | 0 / 0 |

→ 처리량은 **풀 10 ÷ 카드 한 번 약 0.35초 ≈ 28 요청/초**로 같다. 동시가 늘면 지연만 늘어난다 — 끈 쪽은 Tomcat 앞에서, 켠 쪽은 Hikari 앞에서 기다릴 뿐(대기 줄의 위치만 바뀜). 400 동시에서도 Hikari `connectionTimeout`(30초) 안이라 오류 0.

**② 수집 API** — 4.4 표의 `vt-…` 줄: 장치 1대 102 vs 97 건/초, 10대 425~505 vs 473~539 건/초 — **차이 없음**(오차 안, 켠 쪽이 약간 낮은 줄도 있음).

**③ 메모리**: 이번에는 재지 않았다(동시 400 에서도 힙 1GB 안에서 오류 없음까지만 확인).

**권고**: **켜지 않는다(지금)**. 이 앱의 상한은 DB 연결 10개와 커밋 수에 있고, 외부 HTTP 를 요청 스레드에서 기다리는 기능은 이미 아웃박스로 밖에 뺐다(SKILL §2 결재·메시징). 켜서 얻는 것이 없고, 대기 줄이 Tomcat(요청 수 상한·거절이 보이는 곳)에서 Hikari(30초 뒤 실패)로 옮겨 가 과부하 때 증상이 늦게 보인다. 켤 근거가 생기면(외부 호출을 요청 안에서 기다려야 하는 기능) 그때 풀 크기·`connectionTimeout` 을 함께 정한다(R1).
- 덤: 홈 카드 API 가 한 번에 약 **0.35초**(10 동시 기준)로 화면 API 치고 무겁다 — 카드 제공자를 차례로 부르는 구조(docs/37). 홈을 띄워 둔 사용자가 많은 SaaS 라면 5분 폴링 × 사용자 수가 풀을 차지한다 → SSE 신호(3장)로 폴링 간격을 늘리는 쪽이 맞다(추정 — 카드별 시간은 `HomeService` 느린 카드 경고 로그로 나눠 볼 것).

## 3. SSE 시범 — 홈 (구현, 브랜치 `claude/sys-security`)

### 3.1 설계

- **신호만, 데이터는 기존 API 로**: 이벤트 본문은 `event: inbox` / `data: 1` 뿐. 화면은 신호를 받으면 `GET /api/home/cards` 를 다시 부른다 → 권한(`@ProgAuth`·카드별 링크 화면 권한)·회사 범위(RLS) 판단이 **기존 API 한 곳**에 남는다. 신호 경로에 업무 데이터가 없으니 "신호로 다른 회사 데이터가 샌다"는 경로 자체가 없다.
- **구독 키 = (회사, 사용자)** — 로그인 principal 에서만(`CurrentUser`). 프론트가 보낸 회사·사용자 값은 받지 않는다.
- **연결 권한**: `GET /api/home/stream` 은 `@ProgAuth(home-main, SEARCH)` — 홈을 볼 수 없는 사람은 403, 로그인 없으면 401(회사 체인 그대로).
- **수명 5분**(`SseHub.TIMEOUT_MS`): 끝나면 브라우저가 다시 붙고, 그때 `TenantRequestFilter` 가 세션·계정·회사 유효성을, `@ProgAuth` 가 권한을 **다시** 본다 → 사용 중지·권한 회수·세션 끊김이 최대 5분 안에 신호에도 반영. 401·403 이면 `EventSource` 는 다시 붙지 않는다.
- **커밋 뒤에만**: `NotificationService.send` 가 `SseHub.publishAfterCommit` — 업무 트랜잭션이 롤백되면 신호도 없다(시험).
- **상한**: 사용자당 5개(탭 여러 개 — 넘으면 가장 오래된 연결을 닫음), 전체 2,000개(넘으면 429 → 화면은 5분 폴링만으로 동작). 25초마다 주석 줄(하트비트) — 프록시가 조용한 연결을 끊지 않게.
- **폴링은 남긴다**: 5분 주기 읽기는 그대로 — 신호를 못 받는 경우(다른 서버 인스턴스에 붙음·프록시 끊김·상한)의 대비. SSE 는 "더 빨리", 폴링은 "언젠가는".
- **비동기 서블릿**: `SseEmitter` 는 요청 스레드를 잡지 않는다 — 연결 2,000개 = 스레드 2,000개가 아니다(가상 스레드 여부와 무관, 2장).

### 3.4 한계·다음

- **한 인스턴스 안에서만** 전달(메모리). 서버 여러 대(SaaS 확장)면 다른 서버에 붙은 화면은 폴링으로만 갱신된다. 다음 단계 = PostgreSQL `LISTEN/NOTIFY`(채널 하나, 본문 = 회사·사용자·이벤트 이름)로 인스턴스 사이를 잇기 — 새 인프라(Redis) 없이. **NOTIFY 는 커밋 때 보내지므로** 지금의 "커밋 뒤" 의미와 같다. (추정: LISTEN 전용 연결 1개를 풀 밖에 둔다.)
- 세션 비활동 시간(30분): 홈이 보이는 동안은 5분마다 다시 붙으면서 세션을 건드린다 → 홈을 띄워 둔 화면은 비활동으로 끊기지 않는다. **지금 5분 폴링도 똑같다**(새로 생긴 문제 아님). 절대 12시간은 그대로 적용.
- 공개 데모의 Caddy 는 `text/event-stream` 을 모으지 않고 흘린다(추정 — `encode gzip` 이 이벤트 스트림을 압축·버퍼링하는지 데모에서 확인 필요). nginx 앞이면 `X-Accel-Buffering: no` 가 이미 붙어 있다.
- 다음 후보: 셸 알림 배지(지금은 화면 이동 때 읽음), 안돈 화면(새로 만들 때 처음부터 SSE).

## 4. 설비 이벤트 수신 — DB 쓰기 경로와 병목 (코드 분석 + 실측)

### 4.1 요청 하나가 하는 일

`POST /ext/v1/equip-events` (`module/cms/EquipEventController.java:41`) — 묶음 최대 500건(`MAX_EVENTS`). 이벤트마다 **두 번** 서비스를 부른다:

| 순서 | 메서드(트랜잭션) | SQL (COUNT 이벤트 기준) | 근거 |
|---|---|---|---|
| ① | `EquipEventService.trackSeq` — **`@Transactional` 1** | `set_config(app.comp_cd)` → `ensureSeq`(insert … on conflict do nothing) → (있던 행이면) `lockSeq`(**`select … for update`**) → `updateSeq` → 커밋 | `EquipEventService.java:85-103`, `CollectorMapper.xml` ensureSeq·lockSeq·updateSeq |
| ② | `EquipEventService.handle` — **`@Transactional` 2** | `set_config` → `findEquip`(설비·공장·노드 범위) → `InboxService.firstTime`(`sys_inbox` insert on conflict) → `insertCount`(+ 트리거 `hb_guard_equip_count`: 설비·장치가 같은 회사인지 SELECT 2개, FK 4개 확인) → 커밋 | `EquipEventService.java:106-136`, `InboxService.java:40-42`, `V139__mes_equip_count.sql:38-51` |

→ **이벤트 1건 = 커밋 2번 + 문장 약 9개**(트리거 안 SELECT·FK 확인 포함). 묶음 50건 요청 하나 = 커밋 100번. 장치 인증(`PopAuthService.authenticate`)은 요청당 1번(트랜잭션 1 + 1분 간격 `touch`).

### 4.2 직렬화 지점

- **장치 단위**: ①의 `lockSeq` 가 `cms_collector_seq` 의 그 장치 행을 `FOR UPDATE` — 같은 장치의 이벤트는 앞 이벤트의 ①이 커밋될 때까지 기다린다. 한 장치가 보낸 묶음은 컨트롤러가 **순서대로 한 건씩** 돈다(병렬 아님) → 한 장치의 처리량 ≈ 1 / (①+② 커밋 시간). 커밋 하나에 WAL fsync 가 붙으므로(`synchronous_commit=on` 기본) 디스크가 상한을 정한다.
- **설비 단위**(상태 이벤트): `STATE`·`CONN` 은 `lockEquip`(`pg_advisory_xact_lock`) + 열린 구간 `lockOpen` — 같은 설비의 상태 이벤트끼리 줄 선다(정합성 때문에 필요). COUNT·PARAM·METER 는 설비 잠금 없음.
- **장치 사이**: 서로 다른 장치는 병렬. 상한은 풀 10개(2.1) — 장치가 10대를 넘으면 풀 대기.

### 4.6 구현 계획 — W1·W2·W3 (2026-11-16, 브랜치 `claude/collect-batch`)

| # | 바꿀 것 | 지킬 것 |
|---|---|---|
| W1 | 컨트롤러가 이벤트마다 `trackSeq`+`handle`(트랜잭션 2) 부르던 것을 `EquipEventService.ingest(장치, 묶음)` **트랜잭션 하나**로. 처음에 장치 seq 행을 한 번 잡고(`ensureSeq`/`lockSeq`, 같은 장치 묶음끼리 줄 섬), 묶음 안 seq 누락은 메모리에서 이어 보고 GAP 행·`updateSeq` 는 끝에 한 번. COUNT 가 아닌 이벤트(STATE·CONN·PARAM·METER·ALARM)는 건마다 **저장점**(`TransactionTemplate` NESTED = JDBC savepoint) — 거부·DB 오류는 그 건만 되돌림 | 건별 응답(받음·중복·거부 코드) 그대로, 500건 상한 그대로, 거부된 건은 멱등 기록이 없어 다시 보낼 수 있음. seq 는 거부된 건도 "도착"으로 셈(지금과 같음) |
| W3 | COUNT 는 검증(자바)·설비 조회(묶음 안 캐시)만 건마다 하고, 끝에 **멱등 기록 한 문장**(`insert … select unnest(?) on conflict do nothing returning`) → 처음 받은 것만 **원장 한 문장**(`insert into cms_equip_count … select … from unnest(...)`) | 원장 규약(추가만·`occurred_at`·`recorded_at`·`entry_method AUTO`)·트리거 `hb_guard_equip_count`(행마다) 그대로. 한 문장이 예상 밖으로 실패하면 묶음 전체를 되돌리고 **건마다 저장점 방식으로 한 번 더**(조용히 빠지는 건 없음) |
| W2 | 설비 이벤트 멱등 기록을 `sys_inbox`(소비자 EQUIP_EVENT) → **전용 표 `cms_equip_inbox`**(회사·eventId·받은 시각, BRIN)로 옮기고(기존 행도 옮김), 보존 클래스 `EQUIP_INBOX`(기본 7일·최소 3일, 회사 보존 기간·법적 보류는 기존 `sys_retention_policy`·`sys_legal_hold`)로. 정리 = `CmsJobs.equipInboxPurge`(매일, `TenantRunner.forEachActiveComp` + `JobLock`, 회사당 한 번에 5천 행씩 반복). 앱 DELETE 는 이 표에만, **DELETE 트리거가 클래스 최소 기간(3일)보다 새 행·보류 기간 행을 거부** | `sys_inbox` 는 그대로 앱 DELETE 없음. seq 만으로 중복을 가리지 않음(W2 설명). 기간 값은 `PolicyService` 대신 **보존 클래스** — 보존 기간·법적 보류 화면과 최소 기간 규칙이 이미 거기 있다(정책값을 따로 두면 보존 기간이 두 곳) |

- 한계(그대로 둠): 보존 기간보다 오래된 이벤트를 장치가 다시 보내면 **다시 처리된다**(중복 카운트) — 재전송 창 ≤ 보존 기간을 장치 계약에 적는다(R2). 오래된 이벤트를 서버가 거부하는 규칙(STALE)은 데모 시더가 90일 전 상태 이벤트를 넣고 엣지 장기 버퍼도 있어 **정책 질의**로 남김(R5).
- STATE 가 여러 설비에 걸친 묶음은 설비 잠금(`pg_advisory_xact_lock`)을 커밋까지 쥔다 — 같은 설비를 두 장치가 다른 순서로 보내면 교착이 나고 PostgreSQL 이 한 문장을 끊는다(그 건만 ERROR 거부, 다시 보내면 됨). 설비 하나에 장치 하나가 정상 배치(추정)라 그대로.
- 정리 작업이 앱 스케줄인 이유: 로그 정리(`hb_purge_logs`)는 증거라 소유자 전용이지만, 이 표는 증거가 아니라 **중복 판정 키**이고 1천 건/초면 하루 17GB — 운영 도구를 잊으면 디스크가 먼저 찬다. 최소 기간 바닥은 DB 트리거가 지킨다.

## 5. WebSocket 은 언제 쓰나

**기준: 브라우저 → 서버로도 짧은 간격의 메시지가 계속 오가야 할 때만.** 서버 → 화면 한 방향(알림·현황판·진행률)은 SSE, 화면 → 서버는 지금처럼 HTTP 요청.

| 따져 본 것 | SSE | WebSocket |
|---|---|---|
| 방향 | 서버 → 브라우저 | 양방향 |
| 인증·CSRF | 보통 HTTP GET — 세션 쿠키·`TenantRequestFilter`·`@ProgAuth` 그대로, 다시 붙을 때마다 다시 검사 | 연결 때 한 번(핸드셰이크). 그 뒤 메시지마다 회사·권한을 **따로 다시 설계**해야 한다(`@ProgAuth` 가 메시지 단위로 돌지 않음). 핸드셰이크 Origin 검사 별도(CSWSH) |
| 회사 범위(RLS) | 신호만 보내고 데이터는 기존 API — 범위 판단 한 곳 | 메시지로 데이터를 보내기 쉬워져 범위 판단이 두 곳이 된다 |
| 프록시·방화벽 | 그냥 HTTP 응답(Caddy·nginx·IIS 기본 동작) | Upgrade 헤더 통과 설정 필요. 고객 사내 프록시가 막는 경우가 흔하다(추정) |
| 다시 붙기 | 브라우저 내장(`EventSource`, `retry`) | 직접 만든다 |
| CSP | `connect-src 'self'` 그대로 | `connect-src` 에 `wss:` 주소 추가 |
| 서버 자원 | 비동기 서블릿 — 연결당 스레드 없음 | 비슷(연결당 스레드 없음) |

- **양방향이 진짜로 필요한 곳(후보)**: 원격 지원 화면 공유·채팅, 여러 사람이 같은 문서를 동시에 고치는 편집, 장비 조그(jog) 같은 실시간 조작. 지금 YeonOS 기능 중에는 없다.
- **장비 쪽은 다르다**: 엣지·수집기 ↔ 서버는 브라우저가 아니라 장치다. 지금은 HTTPS 푸시 + 명령 당겨 가기(docs/65, 01 7.4 "공장 안으로 인바운드 포트 열지 않음"). 명령 지연을 줄여야 하면 **엣지가 바깥으로 여는** 연결(롱폴링·WebSocket·MQTT)을 검토하되 그건 화면 실시간과 다른 주제다.
- 결론: 화면 실시간은 **SSE + 신호만**으로 시작하고, WebSocket 은 위 양방향 기능이 생길 때 그 기능 하나에만.
