## 2. 주제별 분석

### 2.1 제조 IT 표준 — ISA-95 / IEC 62264, ISA-88, B2MML, MESA-11

#### 표준 요지
- **ISA-95 (IEC 62264)** ✅ — 기업(Level 4: ERP)과 제조운영(Level 3: MES/MOM) 사이의 경계·정보를 정의한다. Part 1(모델·용어, 2025년 개정), Part 2(객체·속성), Part 3(MOM 활동 모델), Part 4·5(운영 객체·트랜잭션), Part 6(메시징), Part 7(별칭 = 시스템 간 ID 매핑). 기술 중립이고 이산·연속·물류 업종에 모두 쓸 수 있다.
- **장비 계층** ☑️ — Enterprise › Site › Area › Work Center(Production Line, Process Cell, Production Unit, Storage Zone) › Work Unit(Work Cell, Unit, Storage Unit).
- **자원 모델** ☑️ — 인원(Personnel Class/Person), 설비(Equipment Class/Equipment), 물리 자산(Physical Asset: 시리얼이 붙은 실물, 교체 가능), 자재(Material Class › Definition › Lot › Sublot). **Class(분류) → Definition(정의) → Instance(실물)** 3단과 "클래스에서 상속받는 속성 + 개별값"이 핵심이다.
- **공정 세그먼트·제품 정의** ☑️ — 공정은 "필요한 인원·설비·자재 능력 + 파라미터"를 가진 재사용 단위(Process Segment). 제품 정의(Product Definition/Segment)가 BOM·라우팅의 ISA-95식 표현이다.
- **운영 객체** ☑️ — 정의(Operations Definition) › 스케줄(Operations Schedule = 작업요청/지시) › 실적(Operations Performance), 그리고 능력(Operations Capability: 가용/약정/불가 능력).
- **Part 3 활동 모델** ☑️ — 운영 영역 4개(생산·품질·보전·재고) × 활동 8개(자원관리, 정의관리, 상세 스케줄링, 디스패칭, 실행관리, 데이터 수집, 추적, 성과분석).
- **ISA-88** ⚠️ — 배치 공정용. 절차 모델(Procedure › Unit Procedure › Operation › Phase)과 레시피 4종(General/Site/Master/Control). 이산 부품에는 "**마스터 레시피 → 실행 시점 사본(Control Recipe)**"과 공정 조건 버전 관리 개념만 유용하다. 열처리·도금·세정 같은 배치성 공정에서 쓸 만하다.
- **B2MML** ☑️ — ISA-95를 XSD로 구현한 MESA 무료 스키마. v7(2020)부터 JSON 스키마도 포함. 내부 모델이 아니라 **경계 포맷**으로 쓰는 게 맞다.
- **MESA-11** ☑️ — 11기능(상세 스케줄링, 디스패칭, 제품 추적·계보, 인력 관리, 품질 관리, 자원 할당·상태, 문서 관리, 성과 분석, 공정 관리, 보전 관리, 데이터 수집). 데이터 모델 기준은 아니고 **기능 누락 점검표**로 쓴다.

#### 현재 설계와의 차이 (ISA-95 활동 × SmartHappy 모듈)

| ISA-95 영역 / MESA 기능 | SmartHappy 모듈 | 상태 | 빠진 개념 |

### 2.2 산업 연계 — OPC UA, MQTT/Sparkplug B, UNS, AAS

#### 표준 요지
- **OPC UA** ✅ — 노드·참조로 된 정보 모델. 업종별 **Companion Specification**을 NodeSet XML로 배포한다. 우리 고객과 관련 높은 것: OPC 40001 Machinery(기계 식별·상태·작업 관리 공통 기반), OPC 40501 Machine Tools(umati, 공작기계), EUROMAP 77/83(사출성형기 ↔ MES). 포장용(PackML, Weihenstephan)은 우선순위 낮음. PubSub over MQTT도 정의되어 있다.
- **Sparkplug B** ☑️ — MQTT 위에 토픽 규칙 `spBv1.0/{group}/{msgType}/{edgeNode}[/{device}]`, 메시지(NBIRTH/DBIRTH 전체 메트릭 선언, NDATA/DDATA 변경분, NCMD/DCMD 명령, NDEATH = MQTT Will로 끊김 감지, STATE = 호스트 상태), Protobuf 페이로드, 시퀀스 번호를 정한다. 3.0이 **ISO/IEC 20237:2023**으로 국제표준화.
- **UNS** ☑️ — 공식 표준이 아닌 **아키텍처 패턴**. 브로커 하나를 허브로, ISA-95 계층(Enterprise/Site/Area/Line/Cell)을 토픽 경로로 써서 모든 데이터 변화를 발행. HiveMQ(브로커 벤더) 자료도 Sparkplug는 토픽 레벨이 적고 Protobuf 고정이라 전사 UNS 백본으로는 경직적이라고 본다. **트랜잭션 무결성·이력 조회(지시·LOT)는 여전히 DB의 몫.**
- **AAS (IEC 63278)** ☑️ — 자산의 디지털 표현. AAS › Submodel › SubmodelElement + `semanticId`(ECLASS/IEC CDD). IDTA 서브모델 템플릿: Digital Nameplate(02006), Technical Data(02003), Time Series(02008) 등. 유럽 고객 대응 시 의미가 있다.

#### 현재 설계와의 차이
- 00: "수집은 별도 Collector, MES는 표준 이벤트 API만 수신" — 방향은 맞으나 **표준 이벤트의 모양**이 정의되지 않았다.
- 설비 **연결 상태**(통신 끊김)와 설비 **가동 상태**(정지)를 구분하지 않으면, 통신 장애가 비가동으로 잡혀 OEE가 틀어진다(Sparkplug NDEATH/stale 개념).
- 설비 태그 ↔ MES 의미(카운트·상태·알람·파라미터) 매핑이 코드에 하드코딩될 위험.

```json
  "seq": 1042                       // 수집기 단위 순번 → 누락 감지
}
```
- `metrics` 구조를 Sparkplug 메트릭(이름·타입·타임스탬프·품질)과 1:1로 맞춘다 → 나중에 브로커를 붙여도 MES 쪽 변경 없음.
- `type=CONN`(연결/끊김)은 `cms_equip_conn_log`로 따로 저장하고 상태 구간 계산에서 "데이터 없음(UNKNOWN)"으로 처리.

**(b) 태그 매핑 설정 (P6)** — `cms_tag_map (comp_cd, equip_cd, protocol: MODBUS/OPCUA/MQTT/SECS, address 또는 nodeId, metric_name, scale, deadband, event_type)`. 수집기는 이 설정을 API로 받아 동작 → 고객별 코드 수정 없음.

**(c) 프로토콜 어댑터 우선순위** — Modbus TCP/PLC 직결(국내 중소 현장 다수) → OPC UA 클라이언트(Machinery 기반 공통 노드 우선) → MQTT(Sparkplug 수신) → EUROMAP 77(사출 고객 생기면). SECS/GEM은 2차 반도체에서 고객이 요구할 때만(3장).

**(d) AAS** — 설비 마스터의 `mst_inst_prop`에 `semantic_id` 컬럼(nullable)만 미리 둔다. 내보내기 어댑터는 유럽 고객 요구 시.

### 2.4 반도체 부품 — SEMI E10/E58/E79/E116/E30, SPC 규칙, 시리얼·LOT

#### 표준 요지
- **SEMI E10** ✅ — 설비 시간을 서로 겹치지 않는 6개 기본 상태로 나눈다: 생산(PRD), 대기(SBY), 엔지니어링(ENG), 계획 정지(SDT), 비계획 정지(UDT, "고장"), 비가동 계획시간(NST). 사용자 정의 하위 상태를 6개에 매핑해 쓴다. MTBF/MCBF 등 신뢰성 지표 포함. 현재판 E10-0422.
- **SEMI E79** ✅ — 설비 생산성·OEE 정의. E10의 상태·시간 지표를 전제로 한다.
- **SEMI E58 (ARAMS)** ✅ — E10 상태를 설비가 자동 보고할 수 있게 상태 모델로 만든 것(E30 GEM 참조). **E116** ✅ — 설비/모듈 단위 성능 추적, 차단 사유 코드.
- **SEMI E30 GEM** ⚠️ — 설비 ↔ 호스트 통신(SECS-II/HSMS: 상태·이벤트·알람·레시피). 팹 장비 대상이다. **반도체 "부품" 공급사(정밀가공·패키지 부품)는 대부분 GEM 장비를 운영하지 않는다.**
- **SPC 런 규칙** ✅ — Western Electric 4규칙(3σ 밖 1점 / 3점 중 2점이 같은 쪽 2σ 밖 / 5점 중 4점이 같은 쪽 1σ 밖 / 8점 연속 같은 쪽). Nelson 8규칙은 여기에 9점 같은 쪽, 6점 연속 증가·감소, 14점 교대, 15점 연속 1σ 이내(층화), 8점 연속 1σ 밖(혼합) 등을 더한다. NIST는 규칙을 더할수록 오경보가 늘어난다고 경고한다.
- **공정능력** ✅ — Cp/Cpk는 군내(단기) σ, Pp/Ppk는 전체 σ. 단측 규격은 단측 지수만. 요구 수준(예: 초기 Ppk ≥ 1.67, 양산 Cpk ≥ 1.33)은 **고객 CSR마다 다르므로 설정값**.
- **반도체 부품 공급사 일반 요구** ⚠️ — CoC/CoA(성적서) LOT 연결, PCN(JEDEC J-STD-046) 고객 통지·승인 기간, 재료 선언(RoHS/REACH/분쟁광물, 최근 PFAS), 청정도(ISO 14644 클린룸 등급·입자 측정), 레이저 마킹 시리얼.

#### 현재 설계와의 차이
- 00은 반도체를 "2차 착수 때 구체화"로 미룸 → 맞다. 하지만 **설비 상태 코드 체계**와 **SPC 데이터 구조**는 자동차 단계에서 만드는 테이블에 그대로 얹히므로 지금 확장 지점을 열어둬야 한다.

### 2.5 KPI·OEE — ISO 22400

#### 표준 요지 ✅/☑️
- ISO 22400-1(개념)·-2(KPI 정의, 2014; **현재 개정 진행 중**)·Amd 1(에너지 KPI)·TR 22400-10(데이터 수집 순서). KPI는 IEC 62264의 Work Unit 기준이며 Level 3에서 계산.
- OEE = **가용률(APT/PBT) × 성능(유효성)** × **품질률(양품/생산량)**. 시간 모델: 계획 가동시간(PBT) › 실제 생산시간(APT) 등. 재작업품은 양품에 넣지 않는다.
- 그 밖에 처리율, 스크랩률, 재작업률, 초회 합격률(FPY), 셋업률, MTBF/MTTR, 재고회전 등 약 30여 개 KPI(목록은 원문 확인 ⚠️).
- 집계는 **"시간·수량을 합산한 뒤 나눈다"** — 설비별 OEE를 평균 내면 틀린다.

#### 현재 설계와의 차이
- KPI 정의가 없다. 고객마다 "가동률" 정의가 다르고(휴식·계획보전 포함 여부), 대시보드 숫자가 고객 엑셀과 안 맞는 문제가 00의 "리포트 불일치" 결함과 같은 유형으로 재발할 수 있다.

#### 구체적 보완안
- 실적 원장(`PRD_RESULT`)에 수량을 **`good_qty`, `scrap_qty`, `rework_qty`(+ `repair_qty`)**로 분리 저장, 재작업 후 양품은 별도 이벤트(`rel_type=REWORK` 계보와 연결)로 기록 — P2.
- 라우팅 단계에 **표준 사이클타임**(`std_ct_sec`, 설비/품목별 override) — P1. 성능 계산의 분모.
- `sys_kpi_def` (전역: kpi_cd, 공식 설명, 단위, 근거 "ISO 22400-2") + `sys_kpi_policy` (회사별: PBT에 휴식 포함 여부, 계획정지 포함 여부, 집계 단위) — P5. **KPI SQL은 뷰/함수 한 곳**(00 절대규칙 2번 적용).
- OEE는 `cms_equip_state_log`(시간) + `PRD_RESULT`(수량) 조인으로 파생. 별도 OEE 테이블은 일 단위 마감 스냅샷만.

### 2.6 아키텍처 — 멀티테넌트 RLS, 원장, 아웃박스

#### 연구·사례 요지
- **AWS (PostgreSQL RLS 멀티테넌트)** ☑️ — 공유 DB에서 개발자가 매 SQL에 테넌트 조건을 넣는 방식만으로는 위험하고, RLS를 안전망으로 쓰라고 권한다. Pool(공유)/Bridge/Silo(전용) 모델을 섞어 쓸 수 있다.
- **RLS 함정** ☑️ — (1) 테이블 소유자는 우회(01에서 `force` + 별도 계정으로 이미 대응), (2) `SECURITY DEFINER` 함수와 일반 뷰는 정의자 권한으로 실행돼 우회 경로가 됨(PG 15+ `security_invoker=true` 뷰 필요), (3) **머티리얼라이즈드 뷰에는 RLS가 안 걸림**, (4) 정책에 쓰는 함수가 leakproof가 아니면 인덱스를 못 탈 수 있음, (5) 세션 변수는 임의 SQL을 실행할 수 있는 클라이언트에게는 보호가 아님.
- **이벤트 소싱/원장** ☑️ — 상태 대신 사건을 쌓고 현재 상태는 투영. 재고는 회계식으로 이동을 from/to 두 행으로 기록하면 "합계 0" 불변식을 검사할 수 있다. 발생 시각과 기록 시각을 나눠야 소급 정정을 설명할 수 있다(Fowler bitemporal).
- **Transactional Outbox / Idempotent Consumer** ✅ — 업무 변경과 같은 트랜잭션에 발행할 메시지를 저장하고, 릴레이가 at-least-once로 발행. 소비자는 메시지 ID로 중복 제거.
- **논문 시사점** ☑️
  - 클라우드 MES(Helo 외 2014; Barenji 2018): SME의 MES–ERP 간극을 클라우드로 메우되, 공장 현장 연결(오프라인·지연)이 핵심 리스크 → 우리 POP/PDA는 **네트워크 단절 시 로컬 큐 + 재전송(멱등키)** 이 필요.
  - 추적성 모델(Jansen-Vullers 외 2003; Kuhn 외 2021): LOT 간 관계를 그래프(gozinto 그래프)로 보는 것이 정석이고, 관계형에서는 **관계 유형 + 수량을 가진 엣지 테이블 + 재귀 질의**로 충분하다. 그래프 DB는 필수 아님.
  - SME MES 도입(MDPI Sustainability 2024; 국내 KCI 연구·KDI 보고서): 실패 요인은 예산보다 **맞춤화 부족·현장 업무 재설계 부담·내부 역량 부족**. 구축 후 활용이 떨어지는 "지속 사용 저조"가 반복 지적됨 → 코드가 아닌 **설정**으로 맞추는 SmartHappy 방향(00 3장)이 연구 결과와 일치. 추가로 **현장 입력 최소화**(바코드·설비 카운트 자동 제안)와 **활용도 지표**가 필요.
  - 디지털 스레드(NIST AMS 100-68, ISO 23247): 제품·LOT·설비·지시 ID가 모든 이벤트에 일관되게 붙어 있는 것이 디지털 스레드의 최소형. 별도 플랫폼이 아니라 **키 규율**의 문제.

### 2.7 국내 — 스마트공장 수준확인, KS X 9001, 지원사업

#### 요지
- **수준 단계** ☑️ — 중기부 4단계(기초 › 중간1 › 중간2 › 고도화). 대한상의 수준확인은 Level 1~5, 1,000점 만점. 중간1(Level 3)은 750점대부터 "수집 정보 분석·제어", 중간2(Level 4) 850점대, 고도화(Level 5) 950점 이상. 기초(Level 1·2) 점수 구간은 원문 확인 필요 ⚠️.
- **단계별 특징** ☑️ — 기초: 기초 ICT로 정보 수집·생산관리(POP 수준, LOT 추적, 생산실적·작업지시). 중간1: 설비 정보 자동 수집, 생산실적·계측정보 자동 집계, 협력사 정보 공유, 실시간 현황 분석. 중간2: 공급사슬·엔지니어링 정보 공유, 제어 자동화 기반 최적화(APS 등).
- **평가 체계** ☑️ — 4영역·10범주·44항목·1,000점(2차 자료). 정보시스템 범주 비중이 가장 크다(2차 자료 220점).
- **KS X 9001 계열** ☑️ — -1 개념·구조(2025 개정), -2 용어, -3 운영관리시스템·진단평가모델, -3-1 제조혁신 역량수준 진단평가모델(2025), -4 중소·중견 전개 가이드. **KS X 9003** 스마트 제조 참조모델 가이드(2024 제정, 2025 개정). 5계층 + 6프로세스(제품개발·생산계획·공정·품질·설비·물류) 프레임 → MES/QMS/WMS/CMS 구성과 정합.
- **사업 운영** ☑️ — 스마트제조혁신추진단 주관. 세부관리기준상 **도입기업은 활용 현황(로그 등) 제출 의무, 공급기업은 무상 유지보수 기간 사후관리 의무**. 국내 연구들이 반복 지적하는 "구축 후 미활용"과 같은 맥락.

#### 현재 설계와의 차이
- 기능 범위는 기초~중간1을 이미 대부분 커버한다(작업지시·POP·실적 원장·LOT 계보·검사·재고·설비 수집). 부족한 건 **증빙**: 활용 현황 리포트, 자동 집계 비율, 수준확인 항목 대비 기능 매핑.

| **작업자 자격** (5장 결정 5) | **수정 채택: P2** | P1이 아니라 POP 착수 게이트와 함께 P2 (자격 마스터 + 공정별 필요 자격 + 게이트) |
| **관리문서 리비전 배포** (5장 결정 5) | **수정 채택: P3** | 첨부(`sys_file`) 위에 문서·리비전·배포 상태. POP에서 최신판만 보이게 |
| 측정값 gauge_id 필수, 교정 NG 역추적 | **채택, P3** | — |
| 처분 enum + 고객 승인·통지 | **채택, P3** | MRB 부분처분과 결합 |
| 변경관리(4M) + 초품/종품 | **채택, P3** | — |
| SPC 최소형 (관리한계 버전·규칙 세트·위반 이벤트) | **채택, P3** | 규칙은 WE1~4 기본, Nelson 확장은 설정. 판정은 저장 시 서버 계산 |
| 오류방지 장치·감사(LPA)·고객 CSR | **P3 후반~P5** | 고객 요구 순서대로 |
| KPI 정의(`sys_kpi_def`/`policy`) | **채택, P5** | OEE·가용률·성능·품질률·FPY·스크랩률·MTBF/MTTR 7개부터 |

| 3장 "반영하지 말 것" 전체 | **동의** | Kafka·브로커 코어화·전 도메인 이벤트 소싱·그래프 DB·SECS/GEM 코어화 모두 제외 |

### 6.4 명칭 (5장 결정 2)

- **PMS = 프로젝트관리**로 유지하고 메뉴·문서에 항상 "프로젝트관리(PMS)"로 표기. 설비보전·가동은 **CMS(설비관리)**. 국내 고객(I사·J사)도 PMS를 프로젝트관리로 써 왔다.

### 6.5 주의

- ⚠️·☑️ 표시 항목(IATF 조항 번호, MSA·Cpk 수치, 정부 평가항목·점수)은 **고객 제출용 문서나 화면 문구에 그대로 쓰지 않는다.** 구현 시점에 원문·고객 CSR로 확인한다.
- 이 검토로 늘어나는 P0 범위는 테이블 6개 + 규칙 테스트 1종 정도. P1~P3은 테이블 수가 늘지만 "나중에 키를 바꾸는 비용"을 없애는 쪽이라 채택을 권한다.
