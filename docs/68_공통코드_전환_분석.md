# 68. 공통코드 전환 분석 — 회사가 늘릴 값은 공통코드로

작성 2026-11-09 · 시스템관리 하위 세션(브랜치 `claude/sys-common-code`, 임시 V9701~V9707) · 근거: 이 저장소 코드·마이그레이션(아래 파일:줄), 자체 시험 `CommonCodeExtTest`

## 1. 결론 먼저

- 선택지 대부분은 **이미 공통코드**다. 공통코드 그룹 166개가 있고(마이그레이션 `INSERT INTO sys_code_grp` 집계), 화면 select 는 거의 다 `data-code`·`hb.codeList` 로 받는다(3.3). 이번에 문제였던 것은 "공통코드인데 **회사가 늘릴 수 없는**(comp_ext_yn = N) 분류 + 표의 `CHECK (x IN (...))` + 서비스 `Set.of(...)`" 이 셋이 겹친 곳이다.
- 그런 분류 중 **분기 로직에 쓰이지 않는 6개 그룹을 (A)로 옮겼다**(5장, 구현 완료): 공지 분류 `NOTICE_CAT`, 공정 분류 `PROC_CAT`, 고객 반품 사유 `WMS_CUST_RTN_REASON`, 유해·위험요인 분류 `CMS_HAZARD_CAT`, 프로젝트 유형 `PMS_PROJ_TYPE`, 문서 유형 `DOC_TYPE`. 회사 코드 그룹은 10 → 16개.
- 공통 기반 두 가지를 더했다. ① 그룹별 **회사 코드 최대 길이** `sys_code_grp.code_max_len` — 업무 칸이 30자보다 좁아도(공정 분류 10자, 유해 분류 5자) 남의 표·함수 변수·jOOQ 를 넓히지 않고 회사 코드를 받는다. ② 범용 트리거 함수 **`hb_check_code_col(그룹, 칸)`** — `hb_code_usable`(V024) 을 쓰는 표마다 손으로 쓰던 트리거 조각을 한 줄 `CREATE TRIGGER` 로.
- 상태값·원장 유형·입력 방법처럼 **코드가 분기를 정하는 값은 (B) 시스템 고정**으로 둔다. 이름은 이미 대부분 공통코드 이름(i18n 키)으로 보인다 — 남은 일은 화면이 코드 그룹을 두고도 목록을 손으로 적은 곳(3.3, 약 40곳) 정리이며 이번 범위 밖(결정 질문 Q3).
- 사용자 답이 필요한 것(자유 입력 사유의 코드화, 측정 단위, 시스템 코드 회사별 숨기기, 화면 하드코딩 정리, 단위 칸 너비 결함)은 6장에 질문으로 남기고 구현하지 않았다.

## 3. 조사 (전수)

### 3.1 마이그레이션 `CHECK (x IN (...))`

V001~V237 에서 `CHECK (칸 IN (…))` 259건(Y/N 칸 제외, ALTER 로 다시 건 것 포함) = 표·칸 244개. 그중 상태(`*status*`) 69개, 원장 입력 방법 `entry_method` 13개, 나머지 유형·분류·출처 144개. 144개를 하나씩 "이 값으로 코드가 갈리는가"로 봤다(Java `equals`·`Set.of`·`case`, SQL `= 'X'`·`IN`, 트리거 분기 grep). 결과는 4장.

### 3.2 Java 상수 목록

서비스 검증의 `static final Set<String> … = Set.of(…)` 가 표 CHECK 를 거의 그대로 되풀이한다(약 60곳 — `NoticeService.CATS`, `ProcService.CATS`, `RiskService.CATS/LEVELS/ROLES`, `CustRtnService.REASONS`, `PmsInputs.PROJ_TYPES/TASK_TYPES`, `DocService.TYPES/TARGET_TYPES`, `ItemService.ITEM_TYPES`, `FailCodeService.CATS`, `ChangeService.M4_TYPES`, `InspPlanService.TYPES`, `LabelFields.TYPES` …). (A) 로 옮긴 그룹은 이 Set 을 지우고 `CodeService.usable`(저장) / `CodeService.isCodeFormat`(조회 조건) 으로 바꿨다. (B) 는 Set 이 분기의 근거라 그대로.

### 3.3 화면 JS·템플릿의 손으로 적은 선택지

화면 select·라디오는 대부분 `data-hb="select" data-code="GRP"` 다. 손으로 적은 목록은 세 종류였다(템플릿·`static/js/views/**` 전수, dev·vendor 제외).

규칙(이번에 정한 것):
- **숨길 수 없는 시스템 코드(`fixed_yn = Y`)** = 서버 분기에 쓰이는 코드: PROC_CAT INSPECT·PACK(APQP 흐름도), DOC_TYPE DRAWING·WI·CP·INSP_STD·PFMEA(PLM 파일 잠금·ECO 대상·검사계획), SPECIAL_CHAR NONE(기본값·CP 분기). 회사 확장이 아닌 그룹은 숨김 자체가 없다(값이 상태 머신 등 시스템 고정).
- **숨김·사용 중지 코드를 가진 옛 행**: `hb.select` 가 첫 항목으로 바꾸지 않고 "(목록에 없음)" 선택지로 남긴다 — 화면을 열었다 저장하면 값이 조용히 지워지던 문제(공통 변경).
- **코드 + 이름 사본 칸(측정 단위)**: `unit_cd` 가 코드, `unit_nm` 은 그 이름 사본 — 작업지시·검사 기준·관리계획 등 이름 글자를 복사해 가는 표는 그대로 둔다. 서버(`CodeService.codeAndName`)가 이름을 채우고(20자 넘으면 `CODE_NAME_LONG`), 코드가 그대로면 다시 보지 않는다(사용 중지 뒤에도 다른 칸 수정). 기존 행은 마이그레이션이 고치지 않는다(확정 라우팅은 가드가 막고 확정본은 이력) — 다음 저장 때 글자가 코드 이름과 같으면 그 코드로, 목록 밖 글자는 그대로.
- **사유 코드 + 메모**: 화면은 코드 필수(`hb.dialog.reasonCode`), 메모 선택 — 메모가 없으면 사유 글자 = 코드 이름(요약 칸이 지금처럼 글자로 보인다). 코드 없이 글자만 보내는 옛 API 호출·자동 근거(QMS·POP 정정·작업지시 취소)는 코드 없이 받는다(미분류) — **정책 질의**: 직접 API 의 코드 없는 수동 보류·건너뛰기를 막을지(지금은 받음).
- **화면 손 선택지 가드(Q3 (다))**: 한 그룹 값과 겹치는 템플릿 손 목록은 회사 확장 그룹이면 `data-code` 로만, 시스템 고정 그룹이면 이름이 그 코드의 `code_nm_key` 일 때만. 조사해 보니 손 목록 대부분이 이미 `#{code.그룹.값}` 이름이라(3.3 ① 의 "이름 두 번"은 4곳뿐) 고친 화면은 채번 초기화 주기·생산 입고 상태 두 곳 + 4M 체크(JS 값 목록 → 코드 목록)다. 시스템 고정 그룹은 회사 코드·숨김이 없으므로 `code` 키 이름이면 `data-code` 와 같은 결과다.
- **Q6 (가) 안내**: 고객 반품 사유(`WMS_CUST_RTN_REASON`)의 회사 코드는 ERP 송신에 코드 그대로 실린다. 회사가 사유 코드를 더할 때는 **ERP 쪽 반품 사유 코드와 같은 값으로** 만든다(다르면 ERP 가 모르는 코드를 받는다). `if_code_map` 에 사유 매핑 유형을 더하는 것은 ERP 연동을 실제로 쓸 때(Q6 (나)).
