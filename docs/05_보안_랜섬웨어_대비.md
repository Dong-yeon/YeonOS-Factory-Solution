## 1. 요약 — 꼭 할 것 Top 10과 반영 시점

**한 줄 결론**: 지금 설계의 **회사 간 격리**(DB 계정 분리·FORCE RLS·기동 가드·카탈로그 검사)는 동급 1인 제품보다 앞서 있다. 반면 **랜섬웨어의 실제 피해 경로인 "관리 권한 탈취 → 백업까지 파괴 → 복구 불가"에 대한 설계는 아직 없다.** 백업·복구 절이 없고, **운영 중인 앱 프로세스가 테이블 소유자 비밀번호를 들고 있다**(Flyway 를 앱 기동 때 실행하기 때문). 이 두 가지가 가장 큰 갭이다.

제조업은 4년 연속 공격을 가장 많이 받은 업종이다(IBM X-Force 2025 전체 사고의 26% [검색] R01). 산업 분야 랜섬웨어 피해의 약 2/3~70%가 제조업이다(Dragos 2025 Q4 [원문] R02). 국내 랜섬웨어 신고의 70.8%가 중소기업이고(2025), 2025년 상반기 피해 기업의 44.4%는 **백업까지 감염**됐다(KISA [검색] R08·R09).

## 3. 랜섬웨어 대비 상세

### 3.1 위협 모델 — 제조 MES 가 당하는 방식

최근 권고·보고서의 공통 흐름 [원문 R03·R02, 검색 R08]:

1. **초기 침투**: MFA 없는 VPN·원격접속 장비 취약점, 탈취·추측된 자격증명(초기접근 브로커), 피싱, 노출 RDP. CISA Akira 권고(AA24-109A, 2025-11 개정)는 표적 업종에 Critical Manufacturing 을 명시한다. 같은 권고에서 **백업 서버 취약점과 백업 DB 자격증명이 직접 공격 대상**이었다 [원문 R03].
2. **권한 상승·확산**: 관리 서버·중앙관리솔루션 장악. KISA 랜섬웨어 대응 가이드라인(2023-08)은 홈페이지 취약점, **중앙관리솔루션 침투**, 관리자 PC 감염을 주 경로로 꼽는다 [검색 R07].
3. **백업 무력화 → 유출(이중 협박) → 암호화**: 2025 상반기 국내 피해의 44.4%, 하반기 23.2%가 백업까지 감염됐다 [검색 R08·R09].
4. **생산 중단**: Jaguar Land Rover(2025-09, 약 5주 생산 중단), Asahi(2025-09, 수주·출하 시스템이 멈춰 수기 주문으로 대체) [검색 R05].

| 제품 웹 로그인 | 인터넷 노출. 자격증명 대입·탈취 → 시도 제한 있음, **MFA 없음** | 사내망. 같은 위험 + 공용 PC |
| 운영자·관리 경로 | **운영자 콘솔·DB·서버 SSH·클라우드 콘솔·GitHub·도메인 계정** = 전 고객 동시 피해 지점 | **원격 유지보수 경로**(우리 → 고객). 우리 PC 가 감염되면 고객 전부가 위험 |
| 앱 취약점(RCE 등) | 앱 프로세스 권한 = 현재는 **소유자 권한**(G1) | 동일 |
| 백업 | 같은 클라우드 계정·같은 자격증명이면 함께 삭제됨 | 같은 서버·같은 NAS·도메인 계정 공유 시 함께 암호화됨 |
| 설비 연동(Collector, P2) | 공장 → SaaS 아웃바운드 | 공장 내부. 인바운드 포트를 열면 OT 경로가 된다 |
| 공급망 | 의존성·CI·빌드 PC | + 설치 패키지 변조 |

### 3.2 백업 원칙 — 3-2-1-1-0 을 SmartHappy 식으로

3-2-1-1-0(사본 3, 매체 2, 오프사이트 1, **불변·오프라인 1, 복구 검증 오류 0**)은 업계 용어다(Veeam). 정부 표준 용어는 아니지만, CISA 가이드의 "오프라인·암호화 백업 + 정기 복구 시험" [검색 R10], KISA 데이터 백업 8대 보안수칙(2025-07: 운영망과 분리된 오프사이트, 3-2-1, 최소 권한·MFA, **연 1회 이상 복구 훈련**, 백업 전 무결성 검증) [검색 R11], NIST IR 8374 Rev.1(CSF 2.0 기반, 2026-06) [원문 R12] 과 같은 내용이다.

**대상**: ① PostgreSQL 클러스터(물리 백업 + WAL) ② 첨부 파일 저장소(`FileStorage`) ③ 설정·비밀값(암호화된 형태) ④ 백업 암호화 키 ⑤ 빌드 산출물·SBOM(재배포용).
**대상이 아닌 것**: `pg_dump` 를 유일한 백업으로 쓰지 않는다. pg_dump 는 PITR 이 안 된다 [원문 R13]. 또 FORCE RLS 상태에서 앱 계정으로 덤프하면 행이 빠지거나 오류가 난다 [추정]. 회사 단위 반출은 **애플리케이션 기능**(회사 데이터 내보내기)으로 따로 만든다.

#### 3.2.1 PostgreSQL — 물리 백업 + WAL 아카이브 + PITR

| 항목 | 권고 | 근거 |
|---|---|---|
| 도구 | **pgBackRest**(Linux). 저장소 여러 개(repo1 로컬·repo2 S3 호환), 클라이언트 측 AES-256 암호화, `verify`, 병렬 복원, 보존 정책 | [원문 R14] |
| 대안(Windows 설치형) | pgBackRest 는 Windows 를 지원하지 않는다 [추정, 확인 필요]. Windows 서버 고객은 `pg_basebackup` + `archive_command`(덮어쓰기 금지) 스크립트를 제품이 제공하거나, **설치형 지원 OS 를 Linux(또는 Docker) 로 한정**한다 → 결정 D5 | [원문 R13·R15] |
| WAL 아카이브 | `archive_mode=on`, `archive_timeout` 60s 정도(RPO 상한), 아카이브 실패를 모니터링. 아카이브 명령은 기존 파일을 덮어쓰지 않아야 하며 **첫 베이스 백업 전에 먼저 시험** | [원문 R13] |
| 주기(제안) | 전체 주 1회 + 차등 일 1회 + WAL 연속. PG17 이후에는 `pg_basebackup --incremental` + `pg_combinebackup` 도 선택지 | [원문 R15], 주기는 [추정] |
| 보존(제안) | 로컬 repo 14일, 오프사이트 불변 repo **35일 이상**(월말 1개는 1년) | [추정] |
| 설정 파일 | `postgresql.conf`·`pg_hba.conf` 는 데이터 디렉터리 백업과 별도로 보관 | [원문 R13] |
| 버전 | PG16 은 보안 마이너(현재 16.15 이상)를 유지하고, **백업·복원 도구도 같은 마이너로** 올린다(pg_dump·pg_basebackup 관련 CVE 가 같은 계열에서 수정됨) | [원문 R16] |

**RPO/RTO 제안값** [추정 — 리허설 실측으로 확정]:

| 배포 | RPO(잃어도 되는 데이터) | RTO(복구 시간) | 비고 |
|---|---|---|---|
| SaaS | 5분 이하(WAL) | 4시간 이하(단일 서버 전체 복원) | 1인 운영이라 야간·주말 대응 시간을 RTO 에 포함해 정직하게 고지 |
| 설치형 기본 | 24시간(일 백업) ~ 15분(WAL 켜면) | 고객 IT 역량에 따라 8~24시간 | 고객과 계약서에 명시 |

#### 3.2.2 불변·오프라인 사본 — "공격자가 관리자 권한을 얻어도 못 지우는 사본"

| 방식 | 내용 | 적합 |
|---|---|---|
| S3 호환 Object Lock **Compliance 모드** | 보존기간 동안 루트 계정도 삭제·단축할 수 없다(Governance 모드는 우회 권한으로 해제 가능하므로 쓰지 않는다). 버전 관리 필수 | SaaS. 국내 클라우드 사업자의 Object Lock 지원 여부는 **미확인** → 결정 D2 [원문 R17] |
| 오프라인 매체(외장 디스크·테이프) 교대 보관 | 주 1회 연결해 복사하고 분리 | 설치형 최소 구성. KISA "콜드 백업" 권고 [검색 R09] |
| 고객 NAS 의 불변 스냅샷(WORM) | NAS 자체 기능 | 설치형 선택 |

**자격증명 분리** [추정, R03·R11·R14 종합]:
- DB 서버가 쓰는 백업 저장소 키는 **쓰기(put)만 가능하고 삭제·보존 변경은 불가**하게 한다. 만료 삭제는 저장소의 수명주기 규칙에 맡긴다.
- 백업 저장소 계정·클라우드 루트 계정은 **운영 계정과 다른 계정·다른 MFA 장치**로 둔다.
- 백업 암호화 키(pgBackRest `repo-cipher-pass`)는 DB 서버와 **다른 곳**(오프라인 봉인 + 비밀값 저장소)에 둔다. 키를 잃으면 백업도 잃는다.
- 백업 서버·NAS 를 도메인 계정·공유 폴더로 운영망에 붙이지 않는다(설치형 가이드).

#### 3.2.3 첨부 파일

- SaaS `S3FileStorage`: 버킷 버전 관리 + Object Lock(보존 35일). 앱 키에는 **객체 삭제 권한을 주지 않는다**. 삭제는 "삭제 표시 + 수명주기 만료"로 처리한다 [추정].
- 설치형 `LocalFileStorage`: DB 백업과 **같은 시점 묶음**으로 복사한다(메타데이터 `sys_file` 과 실제 파일의 시점이 어긋나지 않게). `sys_file.해시`(01 4장)로 복원 후 무결성을 확인한다.

### 3.3 복구 리허설 — "복구 검증 오류 0"

| 무엇 | 어떻게 | 주기 |
|---|---|---|
| 자동 복원 시험 | 최신 백업을 일회용 컨테이너(테스트와 같은 postgres:16 이미지)에 복원 → 앱 jar 를 **앱 계정으로** 기동 → `DatabaseRoleGuard`·`TenantCatalogGuard` 통과 확인 → 회사별 행 수·원장 합계·`sys_file` 해시 표본 비교 → 결과 기록 | SaaS 주 1회, 설치형 월 1회(스크립트 제공) |
| PITR 시험 | "어제 14:00 시점"으로 복원해 그 뒤 데이터가 없는지 확인 | 분기 1회 |
| 전체 재해 훈련 | 새 서버에 OS 부터 → 앱 → DB → 첨부 → DNS 전환까지 실제 시간 측정 → RTO 갱신 | 연 1회(KISA 권고) |
| **회사 단위 복구** | 한 회사만 과거 시점이 필요할 때: 별도 인스턴스에 PITR → 그 회사 `comp_cd` 행만 앱 기능으로 내보내기·가져오기. 물리 PITR 은 클러스터 전체 단위라 공유 DB 에서 한 회사만 되돌릴 수 없다 | 런북에 절차만, 첫 요청 때 실시 |

복원 시험 결과(일시·백업 ID·소요 시간·검증 결과)는 `sys_backup_check`(아래 4.2)에 남기고, 설치형 "백업 건강 상태" 화면의 원천으로 쓴다.

### 3.4 격리·피해 범위 줄이기

1. **DB 권한 층**(4.1): 런타임 앱에는 소유자 권한이 없고, 원장·감사로그·접속로그는 앱 계정에 INSERT/SELECT 만 준다(UPDATE/DELETE REVOKE + 트리거). 랜섬웨어가 앱 권한으로 "원장 덮어쓰기"를 할 수 없게 한다.
2. **대량 변경 제동** [추정]: 화면·API 의 다건 삭제는 상한(예: 1,000건)을 두고, 넘으면 비동기 작업 + 관리자 승인으로 처리한다. "한 요청으로 회사 데이터 전체 삭제" 경로를 없앤다.
3. **삭제 정책**: 마스터는 `use_yn` 비활성 위주로 하고, 물리 삭제는 참조 없는 행만 한다(01 기존 방향).
4. **망 분리**: DB 포트는 앱 서버에서만 접근 가능하게 하고(`pg_hba.conf` `hostssl` + 앱 서버 주소), 관리자 접속은 SSH 터널 또는 별도 관리망으로만 한다.
5. **운영자 PC 위생**(1인 벤더 = 공급망 단일 지점): 개발 PC 와 운영 접속 PC(또는 최소한 다른 OS 계정·브라우저 프로필)를 분리하고, 운영 접속에는 하드웨어 보안키를 쓰고, 운영 자격증명을 개발 PC 에 평문으로 두지 않는다 [추정, R18 62443-4-1 SM 개인키 보호 취지].

### 3.5 탐지 — 랜섬웨어 전조 신호

| 신호 | 출처 | 기준(제안) |
|---|---|---|
| WAL 아카이브 실패·지연, 백업 작업 실패 | `pg_stat_archiver`, 백업 로그 | 1회 실패 즉시 알림 |
| 백업 저장소 삭제 시도·보존 변경 시도 | 클라우드 감사 로그 | 1건이라도 알림 |
| 회사 범위 밖 접근 시도 `TENANT_FORBIDDEN`(403) | 앱 로그 | **1건이라도 알림**(정상 사용에서는 생길 수 없는 SmartHappy 고유 신호) |
| 로그인 실패 급증·여러 계정 동시 실패(패스워드 스프레이) | `LoginAttemptLimiter`·접속 로그 | 5분 기준선 초과 |
| 관리자 로그인 새 IP·업무 외 시간, 권한 부여·계정 생성 | 접속·감사 로그 | 전건 알림(관리자 권한 변경) |
| 대량 조회·엑셀 내보내기·다건 삭제 | 접속 로그 `action=EXCEL/DELETE` | 회사별 기준선 ×N 또는 업무 외 시간 |
| DB: 소유자·슈퍼유저 로그인, DDL, `ALTER TABLE … ROW LEVEL SECURITY` | PG 로그(`log_connections`, `log_statement=ddl`) | 배포 시간 외 1건이라도 알림 |
| 디스크 쓰기 급증·파일 확장자 대량 변경 | OS·NAS | 설치형 가이드에 권고 |

알림 채널은 운영 메일과 분리한다(메일 서버도 피해 범위일 수 있음). 1인 운영이므로 **휴대폰 푸시 1개 채널 + 일일 요약 메일**이 현실적이다 [추정].

### 3.6 대응 플레이북(요약) — 1인 운영 기준

CISA 체크리스트(탐지·격리 → 보고 → 억제·근절 → 오프라인 백업에서 우선순위 복구) [검색 R10]와 NIST SP 800-61 Rev.3(2025-04, CSF 2.0 프로파일형) [검색 R19]를 1인 규모로 줄인 것이다.

| 단계 | 할 일 | 시간 |
|---|---|---|
| 0. 인지 | 시각 기록 = **"알게 된 때"**(신고 기한의 기산점) | T0 |
| 1. 격리 | 앱 유지보수 모드(로그인 차단), DB 를 앱 서버 외 접근 차단, 의심 계정 잠금·세션 전체 무효화, 클라우드·GitHub 토큰 폐기. **백업 저장소 연결 해제**(불변 사본 보호). 감염 서버는 끄지 말고 네트워크만 끊는다(증거 보존) | T0~1h |
| 2. 범위 판단 | 어느 회사·어떤 데이터·개인정보 포함 여부(접속·감사 로그, `comp_cd` 태그 로그) | ~T0+12h |
| 3. 신고 | **정보통신망법: 알게 된 때부터 24시간 내** 과기정통부/KISA 에 신고하고 보완 신고도 24시간 내(2026-10-01 시행 개정으로 법률 의무·과태료 가중) [검색 R20·R21]. **개인정보 유출: 72시간 내** 개인정보보호위원회/KISA 신고와 정보주체 통지(1천 명 이상·민감/고유식별·외부 불법 접근) [검색 R22]. 고객사(위탁자) 통지는 계약 기한에 따름 | ≤T0+24h / 72h |
| 4. 근절 | 침투 경로 차단, **모든 자격증명 재발급**(DB 3계정·백업·클라우드·SSH·서명키 의심 시 서명키까지) | |
| 5. 복구 | 깨끗한 새 서버에 재설치 → 불변 사본에서 **침투 이전 시점**으로 PITR → 카탈로그 검사·복원 검증 → 단계적 재개 | RTO |
| 6. 사후 | 타임라인·원인·조치를 `TESTING.md`·skill decisions 에 기록하고 탐지 규칙을 보강 | 2주 내 |

### 3.7 SaaS vs 설치형 책임 분담(초안)

클라우드 공유 책임 모델의 원칙(데이터·계정·구성은 항상 고객 몫, 인프라 쪽으로 갈수록 사업자 몫) [검색 R23]을 따른다.

| 영역 | SaaS | 설치형 |
|---|---|---|
| 서버·OS·DB 패치 | **우리** | 고객(우리는 지원 버전·패치 권고 제공) |
| 앱 보안 업데이트 | **우리**(배포) | 우리는 **서명된 패키지 제공**, 적용은 고객(원격 지원 가능) |
| 백업 실행·보관 | **우리**(불변 사본 포함) | **고객**. 우리는 스크립트·건강 상태 화면·가이드 제공 |
| 복구 리허설 | **우리** | 고객(우리는 도구 제공·연 1회 유상 점검 옵션) |
| 사용자 계정·권한·MFA 설정 | 고객 관리자(기능은 우리) | 고객 |
| 망 분리·방화벽·원격 접속 | 우리(서버) / 고객(사내 PC·공장) | 고객 |
| 침해 신고 | 우리(정보통신서비스 제공자) + 고객(개인정보처리자) | 고객(우리 협조) |
| 원격 유지보수 계정 | 해당 없음 | **공동**: 고객이 세션을 열고 우리는 개인 계정·MFA·기록을 지킨다 |

이 표를 **계약서 부속·설치 가이드**에 넣어 "백업은 누가 하나"가 사고 후에 다툼이 되지 않게 한다.

**운영 마이그레이션 분리(제안)**:
- prod 에서는 `spring.flyway.enabled=false` 로 두고, 배포 스크립트가 **같은 jar 를 마이그레이션 전용 모드**로 1회 실행한다(소유자 자격증명은 그 프로세스 환경변수로만 전달하고 끝나면 사라짐). 또는 Flyway CLI 를 쓴다.

- local·test 는 지금처럼 기동 시 Flyway 를 실행한다(개발 편의).
- `DatabaseRoleGuard` 에 "앱 계정이 소유자 롤의 멤버가 아닌지(`pg_has_role`)" 검사를 추가할 가치가 있다 — 롤 멤버십으로 소유자 권한을 물려받는 우회를 막는다 [추정].
- docker 로컬 구성은 그대로 두되 01·설치 가이드에 "운영은 소유자 ≠ 슈퍼유저"를 명시한다.

- 원장 6종·`sys_audit_log`·`sys_access_log`·`sys_backup_check`: 앱 계정 `REVOKE UPDATE, DELETE` + 트리거(01 3.1 방향 그대로이고, 감사·접속 로그까지 범위를 넓힌다). 보존 정리 배치는 **파티션 DETACH/DROP 을 소유자 권한의 별도 작업**으로 처리하거나, 앱 계정에 해당 파티션만 허용하는 방식 중 하나를 고른다 → 결정 D6 와 함께.
- 전역 테이블(`sys_prog` 등)은 V005 처럼 앱 계정 쓰기 REVOKE 를 계속한다(좋은 패턴).
- `TRUNCATE` 는 기본 권한에 이미 없음 → 유지. 카탈로그 검사에 "앱 계정이 TRUNCATE·REFERENCES·TRIGGER 권한을 가진 테이블" 검사를 추가할 수 있다.

### 4.2 백업 기능의 제품화 (G3)

```
sys_backup_check   (전역, comp_cd 없음 — 서버 단위)
  check_id, kind: BACKUP/WAL/RESTORE_TEST/PITR_TEST, started_at, finished_at,
  status: OK/FAIL, backup_label, detail jsonb, recorded_at
  → 앱 계정 INSERT/SELECT 만
```

- 전역 테이블이라 회사 관리자에게는 "마지막 성공 백업 시각·마지막 복원 시험일"만 노출한다(설치형에서 의미 있음). SaaS 에서는 운영자 콘솔에만 노출한다.
- 기동 시·매일: 마지막 성공 백업이 기준(설치형 기본 26시간)보다 오래됐으면 관리자 화면 배너 + 로그 WARN 을 띄운다. **기동은 막지 않는다**(가용성 우선, 01 7장 "선택 연동 = 기능 단위" 원칙과 같은 결).
- 기록 주체: 백업 스크립트가 끝날 때 앱 API(`/ext/ops/backup-report`, API 키)로 보고하거나 앱이 pgBackRest `info --output=json` 을 읽는다 [추정 — 구현 때 선택].
- 설치형 초기화 스크립트(P0 9단계)에 백업 설정 템플릿·오프라인 사본 안내·복원 시험 스크립트를 넣는다.

### 4.3 인증·세션·운영자 접근 (G5·G6·G7·G14)

**NIST SP 800-63B-4(최종, 2025-08) 핵심** [원문 R24]:
- 비밀번호만으로 인증하면 **최소 15자**, MFA 의 한 요소로 쓰면 최소 8자. 최대 길이는 최소 64자 허용.
- **문자 조합 규칙 강제 금지, 주기적 변경 강제 금지**(유출 증거가 있을 때만 변경). **유출·흔한 비밀번호 차단 목록 대조 필수**.
- 세션: AAL2 는 전체 24시간·비활동 1시간 이내, AAL3 는 12시간·15분.

**제안 기본값** [추정, 결정 D9]:

| `PWD_POLICY` 키 | 기본 | 비고 |
|---|---|---|
| `min_length` | 12(MFA 미사용 계정)·8(MFA 사용) | NIST 의 15 는 공장 현장 계정에 부담 → 12 로 시작하고 MFA 확대에 맞춰 조정. 고객이 올릴 수 있음 |
| `max_length` | 64(bcrypt 72바이트 제한 유지) | 현재 72바이트 사전 차단 유지 |
| `complexity_rule` | OFF | 고객 요구 시 ON 가능(정책으로 허용, 버그 아님) |
| `expire_days` | 0(끔) | 국내 고객이 "90일 변경"을 요구하면 정책으로 켬 — 기본은 NIST 따름 |
| `blocklist` | 내장 목록(상위 수만 개 흔한 비밀번호 + 회사코드·아이디·회사명 포함 금지) | 외부 API(유출 비밀번호 조회) 호출은 SaaS 만 선택(k-익명 방식) [추정] |
| 세션 | 비활동 30분(현행) + **절대 12시간**(교대 근무 1회) | 절대 수명은 세션 속성에 로그인 시각을 저장하고 `TenantRequestFilter` 에서 검사 |

**MFA (Spring Security 7)** [원문 R25]:
- `@EnableMultiFactorAuthentication` + 요소 권한(`FACTOR_PASSWORD`, `FACTOR_OTT`, `FACTOR_WEBAUTHN` 등). `AuthorizationManagerFactories.multiFactor()` 로 **특정 경로(`/admin/**`, 운영자 콘솔)에만 MFA 요구**, 요소별 `validDuration` 으로 **민감 작업 전 최근 N분 재인증**이 가능하다.
- 순서 제안: ① 운영자 콘솔(P0 9) — TOTP(인증 앱) 또는 패스키 ② 회사 관리자 정책 `MFA_REQUIRED_FOR_ADMIN`(운영 전) ③ 일반 사용자 선택(P1~). TOTP 는 Spring Security 내장 요소가 아니므로 직접 요소를 만들어야 한다 [추정 — 구현 시 확인]. 패스키는 `spring-security-webauthn` + `webAuthn()` 이고, **기본 저장소 테이블에 `comp_cd`·RLS 가 없으므로** 회사별 테이블로 다시 설계해야 한다 [검색 R26].
- CISA 는 피싱 내성 MFA(FIDO/WebAuthn)를 관리자부터 단계 도입하라고 권한다 [검색 R27]. 공장 공용 PC·장갑 착용 환경에서는 일반 작업자 MFA 를 강제하지 않는다(POP 은 별도 저숙련 인증 모델, 01 6장 POP 레이아웃과 함께 P2 에서 정함).

**운영자(Super Admin) 접근 통제** [추정, R28 break-glass 관행]:
- 운영자 콘솔은 별도 경로(예: `/ops/**`)이고, **허용 IP + MFA 필수 + 세션 15분**.
- 운영자의 회사 데이터 열람 = "지원 세션": 고객 관리자가 화면에서 승인(기간·범위) → `sys_support_grant(comp_cd, granted_by, expires_at, scope, reason)` → 기간 동안만 `TenantRunner` 로 그 회사 범위를 연다. 모든 조회는 `sys_audit_log` 에 강제 기록하고, 고객이 볼 수 있다. **SaaS 에서 운영자가 "모든 회사"를 한 번에 보는 경로는 만들지 않는다**(RLS 설계를 운영자도 따른다).
- break-glass 계정 1개: 하드웨어 키, 봉인 보관, 사용 시 즉시 알림, 분기 1회 점검. 1인 운영의 "버스 팩터"(본인 부재 시 고객 데이터 반환 절차)를 문서로 남긴다.

**공장 NAT 대응(G14)**: 고객 공장 공인 IP 를 회사별 "신뢰 IP"로 등록하면 IP 단독 한도를 완화하고 IP+회사 한도만 적용한다(정책 키). 반대로 회사별 **접속 허용 IP 목록**(선택)은 SaaS 의 강력한 저비용 통제다 — 관리자 계정에만 적용하는 옵션도 둔다 [추정].

#### 4.5.1 알려진 취약점 조치 기록 (OSV-Scanner, S-1 2026-11-01)

> 공유 문서라 **패키지·조치 상태·사유만** 적는다(취약점별 악용 방법·세부 내용은 쓰지 않는다 — 각 권고 원문은 OSV·GitHub Advisory 에 있다). OSV 는 CI 에서 **경고**(막지 않음) 그대로 — **사용자 결정 S-2(2026-11-02)**. 다시 볼 시점 = `rimraf` 가 고친 `glob`(14 이상)을 받아 아래 mobile/pda 보류 2건(`glob`·`minimatch`)이 풀릴 때 → 그때 차단(`continue-on-error` 제거)으로 바꿀지 제안한다.
> 분류: **배포물** = 서버 jar(`runtimeClasspath`)·화면 JS·PDA APK 안에 들어감 / **도구** = 빌드·시험·개발 PC 에서만 쓰고 배포물에 들어가지 않음.

| 잠금 파일 | 패키지 | 분류 | 조치 | 상태 |
|---|---|---|---|---|
| `gradle.lockfile` | Tomcat embed(core·el·websocket) 11.0.24 | 배포물 | Spring Boot 4.1.1 → **4.1.2**(Boot 의존성 관리 그대로, 직접 고정 없음) → 11.0.27 | 해결 |
| `gradle.lockfile` | Jackson 3(core·databind) 3.1.5 | 배포물 | 같은 Boot 올림 → 3.1.7 | 해결 |
| `package-lock.json`(화면 JS 도구) | — | 도구 | 검사 0건 | 해당 없음 |
| `mobile/pda/package-lock.json` | `uuid`·`xcode`(Capacitor CLI 경유) | 도구 | Capacitor 8.5.3 → **8.6.0**(cli·core·android 함께 — 한 버전으로 맞추는 것이 Capacitor 규칙) → CLI 가 `xcode` 4 를 써서 빠짐 | 해결 |
| `mobile/pda/package-lock.json` | `glob`·`minimatch`(Capacitor CLI → `rimraf` 6 경유) | **도구**(APK 에 안 들어감 — CLI 가 개발 PC 에서 파일을 지우는 데만 씀) | 고친 버전은 `glob` 14·`minimatch` 11 인데 최신 `rimraf`(6.1.3)가 `glob` ^13 만 받는다 — 강제로 올리면(overrides) `rimraf` 의 선언 범위를 깨므로 하지 않음. **완화**: 배포물 밖, CLI 는 신뢰한 우리 저장소 경로에만 실행 | **보류**(상위 `rimraf`·Capacitor CLI 가 올리면 다음 의존성 갱신 때 반영) |

검사 방법: 이 저장소 CI 의 `osv` 작업(잠금 파일 3개) — 로컬에서는 같은 잠금 파일로 `osv-scanner scan source --offline-vulnerabilities`(오프라인 DB) 또는 `npm audit`. 갱신 절차: Boot 패치·마이너는 Boot 의존성 관리가 고르는 버전을 그대로 쓰고(`ext[...]` 로 개별 고정은 최소), `./gradlew dependencies --write-locks` → `--write-verification-metadata sha256 check` → 차이 검토(아래 주의).

**주의 — 플러그인 표식 POM 체크섬**: `org.springframework.boot.gradle.plugin` 같은 플러그인 표식(marker) POM 은 Gradle Plugin Portal 과 Maven Central(미러)에 **내용이 다른 파일**이 있다. CI 는 Plugin Portal 것을 받는다. 미러를 먼저 보는 환경에서 체크섬을 쓰면 미러 것이 들어가 CI 의 엄격 검증이 깨진다 → 표식 POM 은 Plugin Portal 체크섬을 주 값으로, 미러 것은 `also-trust` 로 둔다(두 파일 모두 공식 저장소에서 직접 받아 비교한 뒤).

### 4.6 감사·보안 로그와 무결성 (G10)

**기록 대상**(OWASP Logging Cheat Sheet [검색 R38] + 안전성 확보조치 기준 [검색 R39]):
인증 성공·실패·잠금·해제, 인가 실패(403), 세션 무효화(`SESSION_REVOKED`), 사용자·권한그룹·권한 변경, 정책 변경, 엑셀 내보내기·인쇄, 개인정보 조회(대상 건수), 운영자 지원 세션, 백업·복원 결과, 설정 변경. **비밀번호·토큰·세션 ID·개인정보 원문은 로그에 남기지 않는다.**

**보관**: 개정 「개인정보의 안전성 확보조치 기준」(2025-10-31 개정): 접속기록 1년, 5만 명 이상 또는 고유식별·민감정보 처리 시 2년. "월 1회 점검" 일괄 의무가 삭제되고 내부관리계획 자율로 바뀌었으며 일부 조항은 1년 유예다(정확한 시행일은 부칙 원문 확인 필요) [검색 R39]. → 보존 클래스(01 4장)에 `ACCESS_LOG` 기본 2년, 고객 정책으로 조정.

**무결성 — 02 결정("행 해시 체인은 요구 시")을 존중하는 가벼운 대안** [추정]:
1. **1단계(P0 6)**: 감사·접속 로그를 앱 계정 INSERT/SELECT 만 가능하게 하고(4.1), **일 단위 다이제스트**를 만든다 — 전날 파티션의 회사별 행을 정렬해 SHA-256 → `sys_log_digest(comp_cd, log_date, row_cnt, digest, prev_digest)` 에 체인으로 기록하고, 다이제스트 파일을 **불변 백업 저장소에 함께 반출**한다. DB 를 통째로 장악한 공격자도 과거 다이제스트는 고치지 못한다(외부 앵커). 비용은 배치 1개다.
2. **2단계(반도체·의료 고객 요구 시)**: 02 안대로 행 단위 `prev_hash/row_hash` + `pg_advisory_xact_lock` 직렬화, 회사별 체인 [검색 R40].
3. PostgreSQL 서버 측 `pgaudit` 은 DB 직접 접속(소유자·DBA) 감사용으로 설치형 가이드에 선택 항목으로 넣는다.

ISMS-P 2.9.4(로그 위·변조 방지 보존)·2.5.6(접근권한 정기 검토) 대응 근거로도 쓴다 [검색 R41]. **접근권한 정기 검토** 기능(분기마다 관리자에게 "권한 보유자 목록 확인" 알림 + 확인 기록)은 ISMS-P 를 준비하는 고객의 실수요라 싸게 넣을 가치가 있다(P0 9 또는 P1).

### 4.8 산업보안 — IEC 62443 과 설비 연동(Collector)

**IEC 62443 위치** [검색 R18·R44]: 벤더에게 직접 해당하는 것은 **4-1(보안 개발 수명주기, 8 practice·47 요구)**과 **4-2(컴포넌트 기술 요구, FR1~7 → CR, SL1~4)**다. 3-3(존·콘듀잇)은 고객 공장 설계 기준이다.
- **지금 할 것**: 인증(ISASecure SDLA/CSA)은 받지 않는다. 다만 보안 절차 문서의 목차를 4-1 의 8 practice(SM·SR·SD·SI·SVV·DM·SUM·SG) 이름으로 만들고, 4-2 FR1~7 대비 자체 매핑표를 둔다(목표 **SL2**: "단순 수단·낮은 동기의 의도적 공격"). 나중에 인증·EU CRA·고객 보안 질의서에 재작업 없이 답할 수 있다.
- 현재 설계는 FR1(식별·인증)·FR2(사용 통제)·FR3 일부(무결성: 원장)·FR6(감사)에 대응하고, FR4(기밀성: 전송·저장 암호화)·FR7(가용성: 백업·DoS)이 이 문서의 보완 대상이다.

**Collector(P2) 연결 원칙** — 01 에 원칙만 지금 넣기를 권고:
1. **아웃바운드 전용**: Collector → 서버 HTTPS push. 서버 → Collector 명령은 Collector 의 폴링으로만 받는다. **공장 안으로 인바운드 포트를 열지 않는다.** 근거: 영국 NCSC 주도·CISA·FBI·BSI 등 공동 「Secure Connectivity Principles for OT」(2026-01) — 가능하면 아웃바운드 전용 단방향 연결 권고 [검색 R45].
2. **OPC UA**: 기본 `SignAndEncrypt` + `Basic256Sha256` 이상, 인증서 신뢰 목록(자동 신뢰 금지), anonymous 금지. `None` 은 명시 설정 + 경고 로그일 때만 [검색 R46].
3. **Modbus/TCP**: 프로토콜에 인증이 없으므로 **읽기 기능코드만 쓰는 모드가 기본**이고, 쓰기는 별도 활성화 + 감사한다. 고객 쪽 방화벽에서 Collector IP 만 허용하도록 가이드한다 [검색 R44].
4. **인증**: `/ext/**` 는 기기별 API 키(회사·기기 바인딩, 폐기 가능) → 장기적으로 mTLS. 멱등은 `sys_inbox`(01 5.8 그대로).
5. Purdue 기준 배치(가이드): 설치형 MES = L3, Collector = L2/L3 경계, SaaS = 인터넷(L4 밖) [검색 R47].

**국내 지원사업 연계** [검색 R48]: 2026 스마트 제조혁신 지원사업 중 부처협업형은 보안 솔루션 도입이 필수이고, R&D 성과확산형은 보안 대책 수립이 필수다. → 고객 제안서용 **「SmartHappy 보안 기능·설치 가이드」(62443 SG 에 해당)** 1부를 운영 전에 만든다. KISA 스마트공장 보안모델 해설서(2023-03)·스마트공장 보안수칙(2025-07 수정)·OT 제로트러스트 안내서(2025-12)를 참고 목록으로 붙인다 [검색 R49].
