# 36. 시스템관리 — 현황 점검과 1단계(사용자·권한그룹·메뉴 관리) 설계

> 작성 2026-10-20 · 시스템관리 하위 세션(`claude/sys-work`, docs/29) · 마이그레이션 V053(임시 V9701)
> 범위: 회사 관리자가 쓰는 시스템관리 화면. 운영자 콘솔(`/ops`)은 대상 밖(이미 9단계에서 끝남)

## 1. 결론 먼저

- 플랫폼(P0)은 사용자·권한그룹·메뉴·공통코드·정책·채번·접속 로그·감사·피드백을 **표와 서비스로는 갖췄지만**, 회사 관리자가 쓰는 화면은 내 정보·활용 현황·지원 세션 허락 3개뿐이다. 권한 부여·사용자 추가·메뉴 정리는 **시드(`LocalDevSeeder`)·운영자 회사 생성·직접 SQL** 로만 된다.
- 조사 중 화면 부족보다 큰 **결함 3건**을 찾았다: ① `pwd_change_req_yn`(다음 로그인 때 비밀번호 변경)이 어디서도 강제되지 않는다 — 운영자가 만든 회사 초기 관리자의 임시 비밀번호가 그대로 계속 쓰인다 ② 회사 생성 뒤 Flyway 로 추가된 새 화면은 **어느 회사의 관리자 그룹에도 부여되지 않는다**(로컬은 시더가 매번 다시 넣어 가려졌다) ③ 관리자 잠금·잠금 해제는 감사 무시 컬럼(`lock_yn`·`locked_until`)만 바꿔 **누가 잠갔는지 남지 않는다**.
- 1단계 = **사용자 관리(`sys-user`)·권한그룹 관리(`sys-auth-group`)·메뉴 관리(`sys-menu`)** + 위 결함 3건 수정. 핵심 규칙은 **"가진 권한보다 큰 권한은 줄 수 없다"(부여 상한)** 와 **"자기 권한은 바꿀 수 없다"**, **"마지막 관리자는 없앨 수 없다"**.

## 4. 1단계 설계

### 4.1 권한 모델 보강

- **관리자 그룹** `sys_auth_group.admin_yn char(1) NOT NULL DEFAULT 'N' CHECK`. 사용 중인 관리자 그룹에 속한 사용자 = 사용 중인 모든 프로그램의 `sys_prog.actions` 전부. 판정은 `AuthMapper` 3개 질의(액션·조회 가능 화면·홈)에 "관리자 그룹 소속이면" 분기를 더한다(행 저장 없음 → D2 해결).
- **부여 상한**(이상 사용 E — 권한 상승 방지). 행위자의 실효 권한 집합 `P(나)`(관리자면 전부) 기준으로:
  1. 그룹 G 의 권한 표를 바꾸거나 그룹 정보를 고치려면 `P(G) ⊆ P(나)` — 나보다 큰 그룹은 손댈 수 없다(늘리기·줄이기 모두). 저장할 새 표도 `⊆ P(나)`.
  2. 관리자 표시(`admin_yn`)를 켜고 끄는 것, 관리자 그룹을 고치는 것은 관리자만.
  3. 사용자 U 를 그룹 G 에 넣거나 빼려면 `P(G) ⊆ P(나)`.
  4. 사용자 U 의 정보 수정·사용 중지·비밀번호 초기화·잠금은 `P(U) ⊆ P(나)` — 나보다 큰 사람의 비밀번호를 초기화하면 그 계정을 가로챌 수 있으므로(초기화 = 권한 상승 경로).
  5. **자기 자신**: 자기 소속 그룹 변경, 자기 사용 중지·잠금·비밀번호 초기화는 거부(`SELF_CHANGE`). 자기 비밀번호는 내 정보에서.
  6. 거부는 403 `GRANT_EXCEEDS` / `SELF_CHANGE` + 접속 로그 `GRANT_DENIED`(WARN) — 정상 화면은 버튼을 숨기므로, 나오면 조작 시도.
- **마지막 관리자 보호**: 사용 중·잠기지 않은 사용자가 속한 사용 중 관리자 그룹이 0이 되는 변경(사용 중지·잠금·소속 제거·그룹 사용 중지·관리자 표시 끄기)은 409 `LAST_ADMIN`. 두 관리자가 서로를 동시에 끄는 경쟁은 **회사 단위 advisory 잠금**(`pg_advisory_xact_lock(hashtext('sys-admin:' || 회사))`)으로 직렬화한 뒤 센다.
- 권한은 지금처럼 요청마다 조회 — 바꾸면 그 사용자의 다음 요청부터 반영(세션 재로그인 불필요).

### 4.2 비밀번호 초기화·변경 강제·세션 끊기

- 관리자는 비밀번호를 **직접 정하지 않는다**. 사용자 추가·초기화 때 서버가 임시 비밀번호(16자, 헷갈리는 글자 뺀 영숫자, `SecureRandom`, 회사 비밀번호 정책 통과할 때까지 다시 만듦)를 만들고 **응답으로 한 번만** 보여 준다. DB 에는 해시만. `pwd_change_req_yn = 'Y'`.
- 초기화는 실패 잠금도 푼다(관리자 수동 잠금은 그대로 — 잠금 해제는 별도 동작). `session_not_before = now()` → 그 사용자의 기존 세션은 다음 요청에서 끊김(D4).
- 변경 강제(D1): `TenantRequestFilter` 가 principal 의 `pwdChangeRequired` 를 보고 허용 경로 밖이면 API 403 `PASSWORD_CHANGE_REQUIRED`, 화면 → `/password-change`. 허용 경로 = `/password-change`, `/api/platform/password-change`, `/api/platform/session`, `/api/platform/messages`, `/logout`, `/error`. 변경 API 는 `@ProgAuthExempt`(대상이 로그인 사용자 자신뿐, 권한그룹이 아직 없는 신규 사용자도 바꿀 수 있어야 함) — 검사는 기존 `MyInfoService.changePassword` 그대로(현재 비밀번호 틀림 = 로그인 실패로 셈). 성공하면 세션 principal 을 갱신한다.

## 7. 검토 (이 세션)

- **부여 상한을 "집합 포함"으로 둔 이유**: "관리자만 권한을 줄 수 있다"(이진)는 단순하지만 공장 현장의 팀장급 위임(자기 화면 범위 안에서 신규 작업자 등록)을 못 한다. 포함 검사는 그룹·사용자 수가 작아(수십) 요청 한 번에 집합 두세 개를 읽으면 끝난다.
- **관리자 표시를 행 대신 플래그로**: 행 방식은 새 화면마다 모든 회사에 행을 넣어야 하는데 마이그레이션은 RLS 표에 회사별로 쓰기 어렵고(소유자도 FORCE RLS), 놓치면 조용히 기능이 안 보인다(D2 가 실제로 그랬다). 대가: 관리자 권한은 "전부" 라 일부만 빼는 관리자는 일반 그룹으로 만든다.
- **세션 끊기를 `session_not_before` 로**: 세션 저장소를 뒤져 지우는 방식은 서버 여러 대·세션 저장소 종류에 따라 다르다. 요청마다 이미 하는 `countActive` 에 조건 하나를 더하면 저장소와 무관하다.
- 폐기한 대안: 권한 변경 승인 결재(4눈 원칙) — 회사 규모상 과함, 감사·접속 로그로 사후 확인. 3단계 로그 화면에서 "권한 변경" 필터로 보완.

### 9.1 부서 마스터 `sys-dept` (docs/35 A10)

- 표 `sys_dept`(회사별 RLS·FORCE·tenant_isolation, 감사·보존 MASTER, 삭제 금지 = 사용 중지): `dept_id`·`parent_id`·`dept_cd`(회사 안 유일, 대문자)·`dept_nm`·`sort_no`·`use_yn`·`row_ver`.
- `sys_user.dept_id`(선택, 한 사람 한 부서). 겸직·결재선 자동화는 하지 않는다(docs/35 결정 표 — 결재 위임과 함께 4단계에서 다시 본다).
- 트리거 `hb_check_dept_tree`: 부모 같은 회사, 순환·10단 금지(회사 advisory 잠금, 하위 높이 포함), 새 부모·다시 사용은 사용 중 부모만, **사용 중 하위가 있으면 사용 중지 거부**. 소속 사용자가 있는 부서의 사용 중지는 허용(사람은 남고, **새 소속만** 막음 — 트리거 `hb_check_user_dept`: 다른 회사·사용 중지 부서로의 변경 거부).
- 다른 모듈이 부서를 고를 수 있게 조회 API `GET /api/platform/depts`(`@ProgAuthExempt` — 공통코드와 같은 참조 데이터). SRM 구매요청의 글자 부서를 바꾸는 것은 SRM 세션 몫(남의 표).

### 9.2 정책 `sys-policy`

- 목록 = 정의(`sys_policy_def`) 전체 + 회사 값·공장 값(공장 범위 정책만) + 기본값·설명(`policy.{KEY}` 문구) — 분류는 키 접두어(PWD·LOGIN·AI·FILE·GRID·BOM·…).
- 저장 = 기존 `PolicyService.set`(형식·허용값·범위 검증 그대로, `row_ver` 동시 편집 확인 추가), **기본값으로** = 회사(공장) 값 행 삭제.
- **보안 정책은 관리자 그룹만**: `PWD_*`·`LOGIN_*`·`MFA_*`·`AI_*`·`FILE_*`·`*SELF_APPROVE*` — 부관리자가 비밀번호 최소 길이를 낮추거나 자기 결재를 켜는 것은 권한 상승과 같은 효과(1단계 부여 상한과 같은 판단). 거부는 `GRANT_EXCEEDS` + `GRANT_DENIED` 로그.

### 9.3 회사 공통코드 `sys-code`

- 그룹 = `comp_ext_yn = 'Y'` 그룹만(UNIT·SPECIAL_CHAR·DOWNTIME_REASON·PAY_TERMS·SUPPLIER_CERT·GAUGE_CLASS·WMS_ADJ_REASON·PLM_CHANGE_REASON …). 시스템 코드는 읽기 전용으로 함께 보인다.
- 회사 코드: 코드(대문자, 추가 뒤 고정 — 업무 행이 글자로 참조)·이름·순서·사용, UNIT 은 `attrs.scale`(0~6) 한 칸만. 삭제 없음(사용 중지 — 기존 행은 그대로, 선택지에서만 빠짐). 시스템 코드와 같은 코드는 기존 트리거가 막는다(`uq_sys_comp_code_system` → 칸 오류).

### 9.4 채번 규칙 `sys-numbering`

- 목록 = 회사 규칙(`nextOrDefault` 가 처음 쓸 때 만든 것 포함) + 지금 기간 마지막 번호 + **다음 번호 미리보기**(번호를 쓰지 않는 계산).
- 저장 = 기존 `NumberingService.saveRule`(패턴 토큰·초기화 주기 정합) + `row_ver`. 규칙 코드는 업무가 부르는 이름이라 추가만(형식 검사), 바꾸지 않는다.
- 패턴·주기를 바꾸면 **이미 낸 번호와 겹칠 수 있다**(예: 접두어 제거, 주기 NONE → MONTH) — 업무 표의 유일 제약이 최종으로 막지만 그 순간 저장이 409 로 실패한다 → 화면이 미리보기와 함께 경고, 저장은 허용(결정 Q8).

### 9.5 회사 정보 `sys-comp`

- 이름·영문명·사업자번호·대표·전화·주소·기본 언어·**시간대**. 상태(`status_cd`)·사용 여부는 운영자만(여기서 안 보냄).
- 시간대 변경은 **관리자 그룹만** + 확인 칸 필수 — 작업일·채번 날짜·일 다이제스트·근무조 판정의 기준이 바뀐다(BizClock). IANA 이름만.

## 12. 3단계 설계 (2026-10-21) — 접속·보안 로그, 변경 감사 모아 보기, 받은 의견함, 내 결재함

### 12.1 원칙

- **회사 관리자는 자기 회사 것만**: 모두 회사별 표(RLS) — 다른 회사 행은 질의에 나타나지 않는다. 운영자 전용 정보(다른 회사·플랫폼 로그 `sys_ops_log`·운영자 콘솔 로그인)는 이 화면들의 대상이 아니다. 운영자가 지원 세션으로 회사 데이터를 바꾼 감사 행(행위자 `ops:{id}`)은 **그 회사의 기록**이므로 보이되, 운영자 신원은 행위자 글자 그대로(이름·IP 없음) — 상세는 기존 지원 세션 화면(`sys-support`, 운영자 동작 로그).
- **감사 모아 보기는 볼 수 있는 화면의 표만**: 감사 행은 그 표의 값 전부(전·후)를 담는다 — 품목 화면 권한이 없는 사람이 감사 화면으로 품목 값을 보면 화면 권한을 우회한다. 그래서 표 → 화면(`AuditViewService.TABLE_PROG`) 대응이 있는 표는 **그 화면 SEARCH** 가 있어야, 대응이 없는 표는 **관리자 그룹만** 본다. "권한 변경" 필터 = `sys_user_auth`·`sys_auth_prog`·`sys_auth_group`·`sys_user`(잠금·사용·초기화 칸) + 접속 로그 `GRANT_DENIED`·`PASSWORD_RESET`·`USER_LOCKED`·`USER_UNLOCKED`.
- 기간은 `hb.dateRange` + 정책 `SEARCH_MAX_RANGE_DAYS`(서버 `DateRanges`), 목록은 `PageQuery`(최신순 고정 + PK), 엑셀 없음(로그 반출은 운영 도구·보존 정책 몫, 개인정보 — IP·아이디).

### 12.3 알림 연결 (2b 이어서)

- `APR_TODO`·`APR_DONE`·하루 요약 결재 줄의 링크 = `sys-approval`(개인 화면이라 받는 사람 권한 확인을 언제나 통과).
- `SECURITY_ALERT`: 접속 로그가 ALERT 로 남으면 그 회사에서 `sys-access-log` 를 볼 수 있는 사용자에게(링크 = 로그 화면, 조건 = 그 이벤트). 같은 이벤트는 **한 시간에 한 번**(중복 키 = 이벤트 + 회사 시각 시) — 공격 중 알림 폭주 방지. 기록과 같은 격리 트랜잭션(REQUIRES_NEW), 실패해도 로그·업무는 그대로.
- `FEEDBACK_DONE`: 의견을 처리 완료로 바꾸면 보낸 사람에게(중복 키 = 의견 id).

### 14.1 4a 관리자 MFA — 결론

- 방식은 운영자 콘솔과 같은 **TOTP**(`Totp`·`SecretBox` 재사용 — 공용 위치 `platform.security.mfa` 로 옮기지 않고 그대로 부른다). 비밀은 AES-GCM 으로 봉인해 저장, 키는 `MFA_SECRET_KEY`(없으면 `OPS_SECRET_KEY`). **복구 코드 10개**는 등록 때 한 번만 보여 주고 DB 에는 SHA-256(사용자 id + 코드) 해시만.
- 강제 대상(Q23): 정책 `MFA_REQUIRED_FOR_ADMIN`(기본값 N → **Y** 로 바꿈) = 사용 중 관리자 그룹 구성원, 정책 `MFA_REQUIRED_PROGS`(기본 `sys-user,sys-auth-group`) = 그 화면에 권한 행이 하나라도 있는 사람. 강제 대상이 아니어도 등록한 사람은 매번 묻는다. 판정은 **로그인 때** — 세션 중 권한이 바뀌면 다음 로그인부터(재로그인 강제는 하지 않음, 7장 "요청마다 권한" 과 다른 이유: 두 번째 요소는 로그인 행위에 묶임).
- 흐름(Q24): 비밀번호 로그인 성공 → 세션 속성 `MFA_STATE`(VERIFY 또는 ENROLL) → `TenantRequestFilter` 가 MFA 화면·API·세션·문구·오류만 연다(API 403 `MFA_REQUIRED`, 화면 → `/mfa`). **MFA 가 비밀번호 변경 강제(D1)보다 먼저** — 관리자가 비밀번호를 초기화해도 두 번째 요소 없이 임시 비밀번호만으로는 아무것도 못 한다. 통과하면 세션 ID 를 바꾼다.
- 실패 제한: 5회 → 15분 잠금(`sys_user_mfa.fail_cnt·locked_until`, 실패 기록은 REQUIRES_NEW), 같은 코드 재사용 거부(`last_step`). 접속 로그 `MFA_OK`·`MFA_FAIL`·`MFA_LOCKED`·`MFA_ENROLLED`·`MFA_RESET`(5회 잠금은 ALERT → 보안 경고 알림).
- 초기화(Q25): 사용자 관리 FN1(비밀번호 초기화와 같은 헬프데스크 권한) — 부여 상한·자기 금지 그대로, 초기화하면 그 사용자 세션 끊김(`session_not_before`) → 다음 로그인 때 다시 등록. **마지막 관리자**(다른 관리자가 없음)는 운영자 콘솔 "MFA 초기화" — 그 회사가 연 지원 세션(`USERS` 범위) 안에서만, 운영자 동작 로그에 남는다.
- 키가 설정되지 않았는데 MFA 가 필요한 로그인 → 등록 화면이 "설정 필요" 를 보여 주고 **열지 않는다**(fail-closed). 기동은 막지 않고 경고 로그(공개 데모·설치형 첫 기동이 막히지 않게 — 운영 런북에 키 설정 추가).

#### 14.4.1 상위 검토 반영 (2026-10-21, #101 보안 검토)

| # | 지적 | 조치 |
|---|---|---|
| 1 | fail-open — Spring Security 는 성공 처리기 전에 인증을 세션에 저장, `onLogin` 판정 중 예외면 대기 표시 없는 세션이 남음 | `onLogin` 이 판정 **전에** VERIFY 를 걸고, 예외면 세션 무효화 후 다시 던진다 |

| 4 | 잠금 해제 직후 1회 실패로 다시 잠김(DoS) | 잠금이 끝난 뒤 첫 시도는 실패 수 1부터 |

배포 안내: 운영·데모 설치본은 **MFA_SECRET_KEY(또는 OPS_SECRET_KEY, Base64 32바이트)를 먼저 넣고** 올린다 — 없으면 prod 는 기동이 멈추고, 그 밖 프로필은 관리자·사용자 관리 권한자의 로그인이 MFA 화면에서 503 으로 막힌다. 4a 이전 local DB 에 남은 등록 행은 AAD 없이 봉인돼 풀리지 않는다 — 관리자 화면 "MFA 초기화" 후 다시 등록.

검토 절(알려진 한계):
- 정책을 켜도 **이미 로그인한 세션**은 다시 로그인할 때까지 MFA 를 요구받지 않는다(세션 절대 12시간이 상한).

### 14.5 4b 사용자 엑셀 올리기 (Q26, 2026-10-21)

- 템플릿 `SYS_USER`(사용자 관리 SAVE): 아이디·이름·메일·부서 코드·언어·권한그룹·사용. **비밀번호 칸 없음** — 새 사용자는 아무도 모르는 무작위 비밀번호 + 다음 로그인 때 변경으로 만들고, 넘겨줄 때 화면 "비밀번호 초기화" 로 임시 비밀번호를 한 번 받는다(결과 파일·작업 행에 비밀번호가 없다).
- 권한그룹은 **새 사용자에게만**(기존 사용자 행에 넣으면 `NEW_ONLY`) — 소속 변경의 규칙(자기 소속·마지막 관리자)이 화면 한 곳에 남게. 줄 수 있는 그룹은 부여 상한 안(`GRANT_EXCEEDS`).

- 별도 표·마이그레이션 없음. 시험 `UserImportTest` 5건, 브라우저: 사용자 관리 → 엑셀 올리기 → ZT 2행(정상 1·오류 1) 미리보기.
- local 개발 회사 시더는 `MFA_REQUIRED_PROGS` 도 `-`(없음)로 — 개발 관리자는 사용자 관리 권한 행이 있어 지정 화면 규칙으로도 MFA 대기에 걸렸다(브라우저 확인에서 발견).

### 14.6 4c 결재 위임·대결 (Q27, 2026-10-21)

- 표 `apr_delegate`(V101): 위임자 → 대리, **기간(회사 날짜, 양끝 포함)**, 문서 유형(비우면 전체), 사유, 회수 시각. 회사별 RLS·감사·보존 SYSTEM, 삭제 없음(회수). 같은 회사·사용 중 사용자 트리거, 자기 자신에게 위임 금지, 같은 위임자의 **사용 중 위임 기간이 겹치면 거부**(전체 ↔ 특정 유형도 겹침 — 트리거가 위임자 행을 잠그고 확인).
- 만드는 사람 = **위임자 본인**(내 결재함 "위임" — 개인 화면). 관리자가 남의 위임을 만드는 화면은 두지 않는다(부재자의 결재권을 관리자가 옮기는 것은 권한 상승 경로 — 필요하면 4단계 뒤 결정).
- 대결: 결재 차례(CURRENT)의 결재자에게 오늘 유효한 위임이 있으면 대리도 승인·반려할 수 있다. **한 단계만**(대리의 대리는 없음), **요청자 본인은 대리라도 자기 요청을 처리 못 함**. 결재선 행에 `acted_by`(실제 처리자), 이력에 `on_behalf_of`(원 결재자) — 상세·결재함에 "대결" 표시. 위임자 권한 상한: 대리는 그 결재의 처리만 받고 화면 권한은 받지 않는다.
- 결재 차례 알림(APR_TODO)은 원 결재자와 함께 **오늘 유효한 대리에게도**, 대리의 결재함 "내 차례" 에도 보인다.
- 결정: D1 만드는 사람 = 본인만, D2 겹침 = 거부(전체 ↔ 유형 포함), D3 한 단계만, D4 위임 시작 전 이미 차례인 결재도 위임 기간 중이면 대리가 처리 가능(차례가 아니라 처리 시점 기준).

### 14.7 4c 구현 결과 (2026-10-21)

- `ApprovalDelegateService`(만들기·목록·후보·회수) + `/api/platform/approvals/delegations*`(sys-approval 개인 화면, 조회 SEARCH·만들기/회수 SAVE). 위임은 **바꾸지 않는다** — 기간·대리·유형은 트리거로 고정(`ck_apr_delegate_fixed`), 회수 뒤에는 행 고정(`ck_apr_delegate_revoked`), 바꾸려면 회수하고 새로.
- 대결 판정은 `ApprovalService` 한 곳의 SQL 조각(`delegated`) — 처리(acting)·내 할 일·결재함(내 차례·지난 결재)·상세 열람·차례 알림이 같은 조건(회수 안 됨, 오늘 회사 날짜가 기간 안, 유형 일치, 요청자 아님)을 쓴다.

- 알림: 위임을 만든 순간 **이미 차례인** 결재는 대리에게 새로 알리지 않는다(결재함 "내 차례" 에는 보인다) — 알림은 차례가 바뀔 때만(중복 키 = 결재·차례). 필요하면 뒤에 "위임 시작 알림" 을 붙인다(미결).

- 발견: 텍스트 블록 줄 끝 공백 제거로 `and """ + 조각` 이 `andexists` 로 붙어 SQL 오류 — 조각 앞뒤에 공백을 둔다.

## 15. 후속 — 운영자 인증 요청당 연결 하나 (2026-10-21, 상위 검토 후속, 마이그레이션 없음)

- 문제: `OpsAuthService` 비밀번호·TOTP·등록 확인이 `@Transactional` 안에서 실패 기록(REQUIRES_NEW)·운영 기록(REQUIRES_NEW)을 불러 요청당 연결 2개 — 운영자 허용 IP 안의 인증 전 경로라 동시 요청으로 연결 풀이 바닥나 앱 전체가 멈출 수 있다(14.4.1 ② 와 같은 모양). 수정 전 코드로 동시 30건 시험 → `Could not open JDBC Connection` 재현.
- 수정: 바깥 트랜잭션을 없애고 짧은 트랜잭션을 차례로 — ① 조회 ② **시도 선점**(조건부 UPDATE 한 문장: 잠금 확인 + 실패 수 증가, 잠겨 있으면 0건) ③ 비밀번호 해시 비교·TOTP 판정은 **연결 없이** ④ 맞으면 기록(비밀번호는 선점분 되돌림, TOTP 는 0 으로) ⑤ 운영 기록. 실패 기록이 선점으로 바뀌어 동시 요청으로 5회를 넘겨 추측하지 못한다(예전은 확인 뒤 증가).
- 지킨 것: 실패 응답 하나(OPS_AUTH_FAILED), 잠겨도 비밀번호 해시 비교를 해 응답 시간으로 잠김을 알리지 않음, 비밀번호·코드 실패 합계(비밀번호가 맞아도 TOTP 까지 마쳐야 0), 잠금 해제 뒤 1부터, 이미 등록된 운영자의 재등록 거부(등록 UPDATE 는 `totp_enabled_yn = 'N'` 행만).
- 남은 같은 모양(우선순위 낮음, 상위 검토 note): `UserAdminService.resetMfa`·`GrantGuard.deny`·`PopAuthService.badge` — 로그인 관리자·활성 단말만 닿는다.

### 15.1 후속 — 접속 로그를 바깥 트랜잭션이 연결을 반납한 뒤 쓰기 (2026-10-24, 상위 결정 B1, 마이그레이션 없음)

- **원인(15장 note 를 조사한 결과)**: 남은 곳이 세 군데가 아니었다. `AccessLogService.record` 가 **항상** `runIsolated`(REQUIRES_NEW)로 쓰므로, `@Transactional` 안에서 접속 로그를 남기는 모든 경로가 요청당 연결 2개를 쥔다. 풀 크기만큼 동시 요청이 각자 연결을 쥔 채 로그를 쓰면 모두 두 번째 연결을 기다리다 연결 대기 시간 초과 → **로그가 사라지고**(기록 실패는 삼킨다) 그동안 앱 전체가 멈춘다.
- **재현(먼저 넣은 시험)**: 풀 4 · 연결 대기 2초 · 동시 4건이 각자 연결을 쥔 채 로그 → 고치기 전 **4건 중 0건 기록**(전부 시간 초과로 사라짐), 고친 뒤 4건 기록·2초 안.
- **고침**: `TenantAwareTransactionManager` 가 스레드가 쥔 물리 트랜잭션(연결) 수를 센다(`doBegin` +1, `doCleanupAfterCompletion` 의 연결 반납 뒤 −1). `afterRelease(work)` 는 0 이면 바로, 아니면 모아 두었다가 **가장 바깥 트랜잭션이 연결을 반납한 직후** 같은 스레드에서 실행한다. `AccessLogService.record` 는 요청 정보(IP·클라이언트 종류)를 그 자리에서 읽고, 쓰기만 `afterRelease` 로 미룬다.
  - REQUIRES_NEW 안쪽이 끝나도 바깥이 연결을 쥐고 있으면 쓰지 않는다(시험).
  - 커밋·롤백·커밋 실패 모두 정리 단계를 지나므로 **거부·롤백 기록도 남는다**(시험으로 고정). 미룬 일 하나가 실패해도 다음 일과 본 요청 결과는 그대로다.
  - **연결 반납(super) 자체가 예외를 던져도** 셈 줄이기·모아 둔 일 실행은 `finally` 에서 한다(상위 검토 #520) — 줄지 않으면 풀 스레드에 셈이 남아 그 스레드의 이후 기록이 영영 미뤄진 채 사라진다(조용히 틀림). 예외가 나도 **실행한다**(반납 실패는 연결 문제지 기록을 버릴 이유가 아니고, 거부 기록을 남기는 규칙과 같다). 예외는 그대로 던진다(시험: 반납 실패 흉내 → 셈 0, 미룬 기록 1건, 다음 기록 바로).
  - 바깥 트랜잭션이 없는 경로(로그인·MFA 확인·전자서명 발급 — 이미 바깥 트랜잭션 없이 설계)는 예전처럼 바로 쓴다.
- **한계**: 바깥 트랜잭션이 끝나고 미룬 기록을 쓰기 전(같은 스레드, 연결 반납 직후의 짧은 틈)에 앱이 죽으면 그 기록은 사라진다. 예전에는 로그가 업무보다 먼저 별도 커밋돼 이 틈이 없었다. 바깥 트랜잭션이 잠금 대기로 오래 걸리면 기록도 그만큼 늦게 남는다(탐지 규칙의 "최근 거부 수" 도 쓴 뒤에 센다).

- **판단: 꼭 남아야 하는 것도 미룬다(즉시 쓰기로 되돌리지 않는다).** 트랜잭션 안의 보안 실패 기록(`GRANT_DENIED`·POP 배지·PIN 실패)이 바로 **반복 요청으로 풀을 바닥낼 수 있는 경로**다 — 그것만 즉시 쓰기로 두면 이번에 막은 고갈이 그 경로에 그대로 남는다. 잃는 틈은 연결 반납 직후 같은 스레드의 짧은 순간이고, 예전 방식도 연결 대기 시간 초과 때는 기록을 조용히 잃었다(재현 시험: 0/4). 로그인 실패·잠금·MFA·전자서명 실패처럼 감사 핵심 기록은 원래 바깥 트랜잭션이 없는 경로라 즉시 쓰기가 그대로다.
- 시험 `AccessLogAfterReleaseTest` 5 — 작은 풀 재현, 롤백돼도 거부 기록, 안쪽 분리 트랜잭션이 끝나도 바깥 반납 전엔 안 씀, 바깥 없으면 바로, 미룬 일 실패가 다음 일·본 요청을 깨지 않음.
- MES 몫(`PopAuthService` 틀린 PIN 횟수 `runIsolated`)은 상위가 넘김 — 배지 접속 로그는 이번 고침으로 풀렸고, PIN 실패 횟수 기록은 같은 모양(시도 선점 한 문장)으로 MES 가 고친다.

### 16.2 설계 — 전자서명

- 플랫폼 `io.smarthappy.platform.esign`: `ESignService.issue`(바깥 트랜잭션 없음 — 조회 트랜잭션 → 연결 없이 비밀번호 비교 → MFA 확인(`MfaService.confirm`, 14.4.1 ②와 같은 순서) → 세션에 토큰), `consume`(MANDATORY — 업무 트랜잭션 안, 토큰 꺼내 지우고 사용자·의미·대상·만료 확인 → 원장 INSERT), `list`(대상의 서명 — 모듈이 상세 API 에 실어 보낸다. 권한은 모듈 화면 권한이 판정하므로 **공통 조회 API 는 두지 않는다**), `hash`(정규 글자 → SHA-256).

### 16.3 MFA 를 모두 잃었을 때 (운영 절차)

1. 관리자 한 명이라도 MFA 를 쓸 수 있으면: 그 관리자가 사용자 관리 "2단계 인증 초기화"(부여 상한·자기 금지) → 잃은 사람은 다음 로그인 때 다시 등록.
2. 앱을 잃은 관리자가 혼자이고 **복구 코드가 남아 있으면**: 복구 코드로 로그인 → 지원 세션 화면에서 **USERS 범위 지원 세션**을 연다 → 운영자 콘솔 "MFA 초기화"(그 지원 세션 안에서만) → 다시 등록. 자기 초기화는 여전히 금지(복구 코드만으로 새 앱을 붙이지 못하게).
3. 복구 코드도 없으면: 회사가 지원 세션을 열 수 없다 → 마지막 수단은 운영자가 **본인 확인(계약 담당자·서면) 후 DB 작업 절차**로 그 관리자의 `sys_user_mfa`·복구 코드 행을 지우는 것(운영 기록 `sys_ops_log` 수기 행 + 회사에 통지). **이 경로는 코드로 만들지 않는다** — 운영자 단독 우회 기능이 생기면 지원 세션 동의 원칙(05 D8)이 깨진다.
4. 예방: 회사 관리자 2명 이상 권장(마지막 관리자 경고 문구), 복구 코드 보관 안내(등록 화면).

### 16.4 SSO 설계 (구현은 고객 요청 때)

- 회사별 IdP 설정 표(회사 = IdP 하나, OIDC 우선 — Authorization Code + PKCE, SAML 은 요청 시), 클라이언트 비밀은 `SecretBox` 봉인.
- 아이디 매핑: IdP 클레임(sub 또는 지정 클레임) ↔ `sys_user.login_id`, **자동 사용자 생성 없음**(권한은 사람이 준다 — 부여 상한).
- 정책 `LOCAL_LOGIN_ENABLED`(기본 Y): N 이면 로컬 비밀번호 로그인 막음 — 단 **회사 관리자 1명은 로컬 비상 로그인 유지**(IdP 장애 대비, MFA 필수).
- MFA: IdP 가 MFA 를 했다는 클레임(`amr`)이 있으면 우리 MFA 생략은 정책으로(기본 생략 안 함).
- 세션 규칙(절대 12시간·회사 범위·`session_not_before`)은 그대로, 로그아웃은 우리 세션만(IdP 단일 로그아웃은 하지 않음).

### 16.7 MFA 스스로 등록 경로 + 모두 잃었을 때 절차 (2026-10-24, 상위 승인 C, 마이그레이션 없음)

16장 "설계와 다르게 한 것 ③"(스스로 등록 API 만 있고 화면 길 없음)과 "남은 일"(MFA 를 모두 잃었을 때)을 닫는다.

- **내 정보 › 2단계 인증 › "2단계 인증 등록"** — MFA 를 쓸 수 있고(서버 키 있음) 아직 등록하지 않았을 때만 보인다. `/mfa?self=1` 을 연다.
- `/mfa` 화면 상태 **SELF**: 로그인 대기(VERIFY·ENROLL)가 없고 `self` 로 열었으며 쓸 수 있고 미등록일 때. 단계는 ENROLL 과 같고(비밀 키 → 첫 코드 → 복구 코드 10개), 끝나면 **돌아갈 곳**(회사 사용자 `/page/sys-my-info`, 협력사 `/portal/me`)으로. 로그아웃 대신 "취소 — 내 정보로". 이미 등록했으면 돌아갈 곳으로 보낸다(바꾸려면 관리자 초기화). `self` 없이 대기도 없으면 예전처럼 셸로.
- SELF 는 세션에 대기 표시를 만들지 않는다 — 화면을 열고 그만둬도 다른 화면이 막히지 않는다. 등록 API(`enroll/start`·`confirm`)는 예전 그대로(VERIFY 대기 중 바꿔치기 금지 포함).
- 모두 잃었을 때 절차는 `deploy/README.md` 5.1 — **절차만**(연락처·내부 이름·비밀 정보 없음): 복구 코드 → 회사 안 다른 관리자 초기화 → 지원 세션(USERS) 안 운영자 초기화 → 허락할 사람이 없으면 두 경로 본인 확인 + DB 소유자 작업으로 대상 1명만 + 운영 대장 기록.
- 시험 `MfaTest` +1(self 없으면 셸로, SELF 화면·돌아갈 곳, 대기 없음 확인, 등록 뒤 다시 열면 돌아감, 다음 로그인부터 확인 요구).

### 17.2 ① hb.grid 전환 — 2묶음 정책 (2026-10-22)

| 화면 | API | 조건 | 정렬 허용 목록(+ 마지막 키) | 기본 순서 |
|---|---|---|---|---|
| 정책 | `GET /api/admin/policies/grid` · `/columns` | 분류(30자)·검색어(키·설명, 50자)·바꾼 것만(Y/N) | 키·분류·설명(+ 키) | 키(목록과 같음) |

- **조건·정렬·쪽을 서버 Java 에서**(다른 grid 는 SQL): 정의는 전역 수십 건이고 설명이 문구 키(지금 언어 글자)라 SQL 로 거르거나 정렬하면 화면 글자와 어긋난다. 정렬 허용 목록·쪽 크기 검증은 같은 `PageQuery.parse`, 설명 정렬은 지금 언어 Collator, 마지막은 키.
- 행 = 표 칸(키·설명·회사 값 글자·공장 값) + 상세가 쓰는 정의 전체(`view`). 회사 값이 없으면 "기본 x"(서버가 지금 언어로), 기본값 그대로인 정책은 흐리게(rowClass).
- 조회 영역이 hb-search 패널로(분류·키·설명·바꾼 것만 + 조회·초기화) — 전에는 입력마다 화면에서 걸렀다. 분류 고르기 칸은 기존 목록 API 로 한 번 채운다.
- 저장·기본값 되돌리기 뒤 같은 정책을 같은 범위(회사·공장)로 다시 고른다(이 쪽 밖이면 폼 닫음).
- 운영 콘솔 회사 목록은 바꾸지 않는다 — 운영자 세션은 회사 세션이 아니라 hb.grid 의 화면 설정 저장(`/api/platform/grid-state`)을 쓸 수 없고, 운영자 몇 명만 보는 짧은 표다. 결재함은 받은함 목록, 부서·메뉴는 트리라 ① 대상 아님. 이로써 시스템관리 ① 은 끝.

## 18. 기능 구현 재개 (2026-10-23, 결정 docs/29 #49)

### 18.1 서명 필수 응답 코드 통일 — 403

정책상 서명이 필요한데 토큰 없이 판정·승인하면 QMS 는 400 `QMS_ESIGN_REQUIRED`, PLM 은 403 `PLM_ESIGN_REQUIRED` 로 달랐다(docs/39 19.3 참고 줄). **403 으로 통일**하고 QMS 를 바꾼다.

| 근거 | 내용 |
|---|---|
| 플랫폼 기존 규칙 | `ESignService.consume` 은 토큰이 **없거나** 만료·다른 대상이면 403 `ESIGN_TOKEN`(구분하지 않음, 16장). QMS 는 "토큰 빈 값 = 400 / 틀린 토큰 = 403" 으로 같은 요청이 토큰 유무로 상태가 갈렸다 |
| 의미 | 요청 형식은 맞고 서버가 이해했으나, 회사 정책이 **본인 재확인(서명) 없이는 이 동작을 허락하지 않는다** — 권한 쪽 거절(403). 400 은 입력 자체가 틀린 경우(서명 대화상자의 비밀번호 틀림 `ESIGN_INVALID`·MFA 코드 없음 `ESIGN_MFA_REQUIRED`)에 남긴다 |
| 영향 | 화면(hb.api)은 401 만 로그인으로 보내고 403·400 은 같은 오류 알림 — 화면 동작 그대로. QMS 화면은 정책 Y 면 서명 대화상자를 먼저 열어 이 응답을 정상 흐름에서 보지 않는다(API 직접 호출·자동화만) |
| 남긴 것 | 오류 코드 이름·문구는 **모듈별 그대로**(`QMS_ESIGN_REQUIRED`·`PLM_ESIGN_REQUIRED`) — 문구가 서명할 곳(PLM 은 "설계 변경 화면에서")을 알려 준다. 공통 코드 하나로 합치면 그 안내가 사라진다 |

- 바뀐 시험: `NcrApiTest`(종결·특채 상신 토큰 없음), `GaugeCalibTest`(교정 등록 토큰 없음) — 400 → 403. PLM 시험은 그대로(이미 403).
- 새 모듈이 서명 필수를 붙일 때: 정책 Y + 토큰 없음 = 403, 코드 `{모듈}_ESIGN_REQUIRED`(문구에 서명할 곳).

### 18.2 결재 엔진 줄 단위 확장점 `ApprovalDocType.beforeAct` (PLM 요청, docs/39 19.3 S2·20.3)

전에는 문서 유형이 끼어들 곳이 상신 전(`beforeSubmit`)과 끝날 때(`onFinished`)뿐이라, 중간 줄(합의·1차 승인)에는 업무 규칙을 걸 수 없었다 — PLM 이 정책 Y 에서 중간 합의 줄의 서명을 강제하지 못한 이유.

| 항목 | 정한 것 |
|---|---|
| 모양 | `default void beforeAct(String bizKey, LineAct act)` — 안 쓰는 문서 유형은 그대로(기본 = 아무것도 안 함) |
| `LineAct` | `aprId·seq·lineType(APPROVE·AGREE)·approve(승인·합의 = true, 반려 = false)·finishes(이 처리로 결재가 끝남 = 마지막 승인 또는 반려)·actorId(누른 사람)·onBehalfOf(위임 대결이면 원 결재자, 아니면 null)·esignToken(결재 처리 요청에 실려 온 전자서명 토큰, 없거나 빈 값이면 null)` |
| 서명 토큰 | 결재 처리 API(`/api/platform/approvals/{id}/approve`·`/reject`)가 선택 인자 `esignToken` 을 받아 그대로 넘긴다 — **엔진은 검증하지 않는다**. 서명을 요구하는 문서 유형이 beforeAct 에서 `ESignService.consume`(의미·대상·내용 해시)로 검증·소비하고, 없음·틀림은 403(18.1 규칙). 요구하지 않는 문서 유형에 온 토큰은 쓰이지 않고 만료된다. 쓰임: QMS 특채 결재자 승인 서명(E-2), PLM 중간 합의 줄 서명(S2) |
| 부르는 때 | 승인·합의·반려에서 **차례·위임 확인 뒤, 줄 상태를 바꾸기 전**, 같은 트랜잭션. 마지막 승인·반려면 이어서 `onFinished` |
| 거부 | `BusinessException` → 그 처리 전체 롤백(줄·이력·다음 차례 알림·업무 상태 그대로). 응답은 그 예외의 오류 코드 |
| 부르지 않는 때 | 회수(요청자, 줄 처리 아님) · 차례가 아닌 사람 · 끝난 결재(확장점 앞에서 409) |
| 왜 이벤트가 아니라 인터페이스 | `onFinished` 와 같은 이유(5.4 주석) — 같은 트랜잭션에서 거부할 수 있어야 하고, 리스너가 없어 조용히 지나가면 안 된다 |
| PLM 쪽 | 확장점만 만든다. ECO 문서 유형에 붙이는 것(정책 Y 면 합의 줄 = REVIEW 서명 확인)은 PLM 세션 몫(docs/39 20.3) |

- 결재함에서 서명: 18.2b(후속 PR).
- 시험(`ApprovalTest` 4건 추가 — 토큰 전달 포함): 줄마다 받는 값(합의 → 승인 마지막, 반려, 회수는 안 부름, 차례 아님·끝난 결재는 확장점까지 안 옴) / 위임 대결이면 actor = 대리·onBehalfOf = 원 결재자 / 확장점이 거부하면 줄·이력·알림·업무 상태 그대로, 합의 줄만 막는 문서 유형에서 회수는 된다.

### 18.2b 결재함에서 서명 — `ApprovalDocType.esignFor` (상위 결정: ② 뒤 작은 PR)

18.2 만으로는 서명을 요구하는 문서를 **공통 결재함**에서 승인하면 토큰이 없어 403 으로 막힌다(조용히 통과하지는 않음). 결재함이 서명 대화상자를 열 수 있게 문서 유형이 안내를 준다.

| 항목 | 정한 것 |
|---|---|
| 모양 | `default ESignSpec esignFor(String bizKey, LineType lineType, boolean approve)` — 지금 차례 줄을 승인(합의 포함)·반려할 때 열 서명 `{meaningCd, targetType, targetId, title}`, 필요 없으면 null(기본) |
| 상세 API | `GET /api/platform/approvals/{id}` 에 `esignApprove`·`esignReject` — 결재 중이고 지금 차례 줄이 있을 때만(끝난 결재·서명 없는 문서 = null) |
| 결재함 화면 | 승인·반려 확인 뒤, 안내가 있으면 **hb.esign** 을 열고 받은 토큰을 처리 요청의 `esignToken` 으로. 서명을 취소하면 처리하지 않는다. 안내가 없으면 지금과 같음 |
| 판정은 여전히 서버 | `esignFor` 는 화면 안내일 뿐 — 검증·소비는 `beforeAct`. 안내와 판정이 어긋나도(안내 null 인데 beforeAct 가 요구) 403 으로 막힌다 |

- 시험(`ApprovalTest` 1건): 합의 줄 = REVIEW·승인 줄 = APPROVE 안내, 반려는 안내 없음, 끝난 결재·서명 없는 문서는 null. 브라우저: 결재함(가짜 목록·상세로 서명 요구 문서를 만들어) 승인 → 확인 → 서명 대화상자, 취소하면 처리 요청 없음, 서명하면 요청에 토큰, 반려는 바로.

### 18.3 메일 알림 — SMTP 송신기 (Q12, 결정 #49)

사내 알림함(11장)에 들어온 알림을 **메일로도** 받는다. 새 이벤트를 만들지 않고 기존 이벤트에 채널을 하나 더 단다.

| # | 정한 것 | 다른 안(안 한 이유) |
|---|---|---|
| M1 | 메일 = **알림함에 새로 들어간 알림만**(알림함 INSERT 가 된 것 — 중복 키·구독·사용 중·화면 권한 규칙을 그대로 지나야 함). 알림함을 끄면 메일도 안 감 | 채널을 따로 판정(알림함 끔 + 메일 켬) — 중복 막기를 메일만 따로 만들어야 하고, 볼 권한 판정(Q15)이 두 벌이 된다 |
| M2 | 이벤트마다 **기본 끔**, 사용자가 켠다(`sys_notify_sub.mail_yn`, 기본 N) | 기본 켬 — 메일 서버를 붙이는 순간 모든 사용자에게 메일이 쏟아진다 |
| M3 | 같은 업무 트랜잭션에서 **아웃박스 MAIL** 발행(업무·알림이 롤백되면 메일도 없다). 제목·본문은 **발행할 때 받는 사람 언어로** 만든다 — 송신기는 DB 를 못 쓴다(01 5.8) | 송신기가 알림 행을 다시 읽음 — 트랜잭션·회사 범위 밖이라 불가 |
| M4 | **글자 메일만**(HTML 없음). 제목 `[YeonOS] {알림 제목}`, 본문 = 제목 + 세부 줄 + 안내 + 열기 주소(`happyboot.mail.base-url` + `/page/{화면}`, 조회 조건은 싣지 않음) | HTML 메일 — 정화·이스케이프 부담, 지금 알림은 한 줄 글자 |
| M5 | 받는 주소 = `sys_user.email`. **좁은 형식 검사**(영문·숫자·`._%+-` @ 도메인, 공백·꺾쇠·쉼표·줄바꿈 없음)를 발행 때와 송신 때 두 번 — 틀리거나 없으면 메일만 건너뛴다(알림함은 들어감) | 넓은 RFC 형식 — 머리 주입(`\r\nBcc:`) 경계가 흐려진다 |
| M6 | 송신 결과: 보냄 / 주소·인증·형식 오류·서버 영구 거절(5xx 받는 주소) = **실패**(다시 보내도 같음) / 연결·일시 오류 = 재시도 / **연결 뒤 시간 초과 = 실패**(서버가 이미 받았을 수 있다 — 같은 메일 두 번이 빠짐보다 나쁨, 01 5.8). 릴레이는 감싼 예외 안의 타임아웃을 못 보므로 송신기가 원인 사슬을 본다 | 모두 재시도 — 중복 메일 |
| M7 | 설정: `happyboot.mail.enabled`(기본 false)·`from`·`base-url` + 스프링 표준 `spring.mail.*`. **켰는데 보내는 주소나 SMTP 서버가 없으면 기동 중단**. 꺼져 있으면 발행하지 않고 구독 화면에 메일 칸도 없다(Q12 의 "보내지 않는데 켜짐으로 보임" 방지) | 회사별 SMTP — 설치형은 한 서버, SaaS 는 발신 하나. 필요해지면 회사 설정으로 |
| M8 | 메일 health 검사는 메일을 켰을 때만(`management.health.mail.enabled`) — 안 쓰는 설치에서 빈 SMTP 주소로 health 가 DOWN 이 되지 않게 | — |

- 표: `sys_notify_sub.mail_yn char(1) NOT NULL DEFAULT 'N' CHECK (Y·N)` — V148·임시 V9709. 구독 저장 API 의 `mailYn` 없음(null) = 지금 값 그대로(예전 화면·알림함만 바꾸는 호출이 메일을 끄지 않게).
- 구독 화면(내 알림 › 알림 설정): 이벤트마다 알림함 스위치 옆 **"메일로도"** 체크 — 메일 설정이 켜졌고 내 메일 주소가 있을 때만 보인다. 알림함을 끄면 메일 체크도 막힌다.
- 아웃박스 본문에 받는 주소·제목·본문이 남는다(아웃박스 보존 규칙을 따름). 송신 오류 기록에는 주소를 넣지 않는다.
- 의존성: `spring-boot-starter-mail`(Jakarta Mail API EPL-2.0, Angus Mail EPL-2.0/GPL-2.0+CE) — 잠금·체크섬 갱신.

**운영 설정**(값은 환경 변수·`.env` 로만, 저장소·문서에 쓰지 않는다): `MAIL_ENABLED`·`MAIL_FROM`·`MAIL_BASE_URL`, `SMTP_HOST`·`SMTP_PORT`(기본 587)·`SMTP_USERNAME`·`SMTP_PASSWORD`·`SMTP_AUTH`(기본 true)·`SMTP_STARTTLS`(기본 true — STARTTLS 필수). 연결 5초·읽기·쓰기 10초 제한.

#### 18.3.1 외부 메일 발행 계약 — `MailService.publish` (2026-10-23, 사용자 결정 · PLM PCN 고객 메일 E3)

사내 알림 메일(M1, 알림함 → 메일)과 **다른 경로**: 업무 모듈이 사람(고객 담당자 등)에게 직접 보내는 메일. 구독·알림함 없이 호출자가 정한 받는 사람에게.

| 항목 | 계약 |
|---|---|
| 부르는 법 | `UUID publish(String bizKey, Recipient(address, name), String subject, String body)` — **업무 트랜잭션 안에서만**(MANDATORY). 아웃박스 MAIL 로 발행 → 업무가 롤백되면 메일도 없다 |
| 메일 꺼짐 | **409 `MAIL_DISABLED`** — 호출자가 "보내지 않았음" 을 안다(조용히 버리지 않음). 화면이 버튼을 보일지는 `MailService.enabled()` |
| 검사(400 `INVALID_VALUE` + 칸 오류) | `bizKey` 영문·숫자·`:_./-` 80자(`FORMAT`) / `to` 좁은 주소 형식(M5, `FORMAT`) / `toName` 100자, 제어·양방향 문자·`" < > , ; \` 금지 / `subject` 필수·200자·제어·양방향 문자 금지 / `body` 필수·2만 자·줄바꿈·탭 말고 제어 문자 금지(`\r\n` → `\n`) |
| 반환 | 아웃박스 메시지 id(`sys_outbox.message_id`) — 호출자가 업무 행에 남겨 추적 |
| 구분 | 아웃박스 업무 키 `EXT:{bizKey}`(사내 알림은 `NOTIFY:{id}`), 본문 `kind = EXTERNAL`(사내 알림 `NOTIFY`). 송신기는 외부 발송을 보낼 때 회사·아웃박스 id·업무 키를 로그에 남긴다(주소·본문은 남기지 않음) |
| 송신 | M4~M6 그대로 — 글자 메일, 표시 이름은 따옴표로 감싸 `"이름" <주소>`(비ASCII 는 UTF-8 인코딩), 실패·재시도 분류 같음 |
| **호출자 책임** | **받는 주소가 그 업무에 맞는 사람인지**(예: 그 고객의 등록된 담당자인지) — 이 API 는 형식만 본다. 사용자가 입력한 임의 주소로 보내지 않게 호출 쪽이 출처를 검증한다. 같은 메일을 두 번 내지 않는 것(재시도·이중 클릭)도 호출자가 업무 상태로 막는다 |


### 18.4 업무 계약 첨부 — `FileService.attachAs` (2026-10-24, 사용자 결정 C25 Q1, 근거 docs/33 11.17)

POP 고장 신고 사진·보전 기록처럼 **업무 계약이 파일을 대신 붙이는** 경로. 화면 첨부(upload)는 대상 화면 SAVE 권한을 보지만, 여기서는 부르는 업무 계약이 대상의 권한·소유를 이미 확인했다.

| 항목 | 정한 것 |
|---|---|
| 시그니처 | `attachAs(targetType, targetId, fileName, declaredSize, InputStream, actor)` → `FileInfo`. content 는 부른 쪽이 닫는다 |
| 트랜잭션 | **MANDATORY** — 업무 트랜잭션 밖이면 거부. 메타 행은 업무 트랜잭션에 같이 들어간다 |
| 권한 | **검사 없음**(부르는 업무 계약 몫). 회사 범위는 지금 트랜잭션의 회사(RLS) — 다른 회사 대상 id 를 넘겨도 행은 지금 회사로 |
| 검사 | upload 와 **같은 코드**(`receive`): 이름 정리 → 확장자(항상 거부 목록 + 회사 허용 목록) → 크기(선언·실제) → 시그니처 → SHA-256. 잠금 규칙(`FileLockRule`)도 같다 |
| actor | 행위자 글자(created_by) — 앞뒤 공백 제거 뒤 1~50자, 제어·양방향·0폭 문자 금지(아니면 400). 로그인 사용자가 없는 단말 경로가 있어 사용자 대신 글자 |
| 실제 파일 | 저장소에 옮긴 뒤 업무 트랜잭션이 **커밋되지 않으면 지운다**(copyAll 과 같은 afterCompletion) |
| 접근 로그 | 거부(FILE_REJECTED)는 바로 따로 커밋(업무가 롤백돼도 남음), 올림(FILE_UPLOAD)은 **커밋 뒤에만** — 둘 다 login_id = actor, detail 에 `attachAs` |
| 좁히는 조건 | `attachAs(…, actor, AttachOptions(onlyExt, maxMb, reuseSameContent))` → `Attached(file, duplicate)`. **넓히지 못한다**: onlyExt = 회사 허용 목록과의 교집합, maxMb = `FILE_MAX_MB` 와 작은 쪽(1 이상), reuseSameContent = 같은 대상의 **사용 중** 파일 중 SHA-256 이 같으면 그 파일(새 행·실제 파일 없음, 대상 단위 advisory 잠금으로 동시 재전송도 한 장). 6인자 = 옵션 없음 |
| 개수 | `countAttached(targetType, targetId, actorPrefix)` — 사용 중 첨부 중 행위자 글자가 접두어로 시작하는 수(POP 사진 한도 = `t` 로 붙인 것). MANDATORY · 권한 검사 없음 · 빈 접두어 거부 · LIKE 와일드카드는 글자 그대로 |

### 18.7 외부 메일 발행 취소 — `MailService.cancel` (2026-10-24, 상위 승인 · 18.6 A6 한계 해소, V182·임시 V9712)

### 18.8 MyBatis 전역 UUID 처리기 (2026-10-24, 상위 결정 · QA #510 제안, 마이그레이션 없음)

## 21. 현장 단말 진입 화면 (2026-11-10, 사용자 요청 "현장단말기도 /pop 말고 메뉴로 들어갈 수 있도록", 브랜치 `claude/sys-pop-menu`, V264·임시 V9713)

- **관찰(기존 동작)**: 단말 활성화(`/api/pop/activate`)는 "다른 단말·작업자로 쓰던 세션을 비운다"며 HTTP 세션을 무효화한다 — 같은 브라우저의 사무 로그인도 끝난다(브라우저 확인). POP 쪽 규칙은 바꾸지 않고 [이 기기 등록] 안내·툴팁에 적었다. 작업자 배지 로그인은 세션 ID 만 바꿔(`changeSessionId`) 사무 로그인은 남는다(추정 — 코드로만 확인).
